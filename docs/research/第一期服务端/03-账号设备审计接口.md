## 0. 给写代码的人：一页清单

1. **任何接口都不要主动回 5xx**。Rust 通路收到 5xx 或连不上时，会改走 hbbs 21116 端口的 TCP 代理（`HttpProxyRequest`），原版 hbbs 不认这条消息，客户端白等最长 36 秒（§1.3）。写库失败这类服务端错误：审计接口回 `200 + {"error":"..."}`（客户端会重试），其他接口回 4xx + `{"error":"..."}`。
2. 所有 JSON 响应用 `Content-Type: application/json; charset=utf-8`（§1.4）。
3. 用户信息里 `name` 必须是非空字符串；登录响应必须带 `user`，否则客户端显示"未登录"，组面板也不拉（§2.2、§2.5）。
4. 列表接口必须带 **int 型 `total`**，缺 `total` 时客户端整段丢弃 `data`（§3.1）。
5. Dart 侧凡是声明成 `String` 的字段，服务端只能给字符串或 null；给数字或对象会抛 TypeError，**整个面板报错**（§2.5、§3.4）。
6. `login-options` 没有第三方登录时回 `[]`，不要学 rustdesk-api 回 `["common-oidc/null"]`（§2.1）。
7. 审计成功回 **200 + 空 body**；按 `nonce` 去重，窗口至少 5 分钟（§5.1）。
8. 审计里的 `session_id` 是随机 **u64**，约一半大于 i64 上限；`conn_id` 是被控端进程内计数器，**被控端重启后会复用**（§5.5）。
9. sysinfo 回纯文本 `SYSINFO_UPDATED`，**一个字节都不能多**（不带引号、不带换行）；heartbeat 和 sysinfo 的状态码客户端不看，只看 body（§4）。
10. axum 的 `Json<T>` 提取器遇到类型不符回 422、缺 Content-Type 回 415，响应体是纯文本，客户端解析会走"未知错误"分支。建议本组接口用 `Bytes` 收 body，自己 `serde_json::from_slice`，失败时回 4xx + `{"error":"..."}`（§1.6）。

### 1.1 api-server 地址推导【读码】

`common.rs` `get_api_server`（1223 行）/ `get_api_server_`（1240 行）/ `get_custom_rendezvous_server`（1206 行）；`ui_interface.rs` `get_api_server`（1051 行）把 `api-server`、`custom-rendezvous-server` 两个选项传进去。

按优先级：
1. `Config::no_register_device()` 为真 → 空串，所有 API 功能关闭。

4. 选项 `custom-rendezvous-server`（为空时依次用 license 的 `host`、编译期 `PROD_RENDEZVOUS_SERVER`）非空：

5. 都没有 → `https://admin.rustdesk.com`。

后处理（`get_api_server`）：
- 去掉一个末尾 `/`。
- 结果以 `https` 开头、以 `:21114` 结尾，且内置选项 `allow-https-21114`（`libs/base/src/config/keys.rs` 145 行）不等于 `Y` → 把 `:21114` 删掉（假定 HTTPS 由 443 反代）。
- 带路径前缀的 api-server（如 `https://h/prefix`）可用：Dart 是字符串拼接，组面板用 `Uri(path: uri0.path)` 保留了路径【读码 `group_model.dart` `_getUsers`】。

`is_public(url)`（1268 行）：host 是 `rustdesk.com` 或 `*.rustdesk.com` 时，heartbeat / sysinfo（`sync.rs` `heartbeat_url` 281 行）和审计（`get_audit_server` 1326 行）一律不发。

改 api-server 时若已登录，客户端先用**旧地址**调一次 `/api/logout`（`common.dart` 3636~3641 行）。

### 1.2 两条 HTTP 通路【读码】

**A. Dart 通路**（登录、currentUser、logout、login-options、users、peers、device-group）
- `utils/http_service.dart` `HttpService.sendRequest`（12 行）：
  - 调用方不传 headers 时默认 `{'Content-Type': 'application/json'}`（18 行）。传了就只发传入的那些。
  - 默认用 Dart `http` 包（1.4.0，`flutter/pubspec.lock`），每次请求 **30 秒超时**（`_requestTimeout`，52 行），无重试。
  - 开了代理，或本地选项 `enable-flutter-http-on-rust` 为真时，改由 Rust `ui_interface.rs` `http_request`（859 行）→ `common.rs` `http_request_sync` 发出（走下面 B 的超时、TLS 重试、TCP 代理回落规则），结果以 `{"status_code","headers","body"}` JSON 回传，Dart 再拼成 `http.Response`（`_parseHttpResponse` 108 行）。
- 认证头：`common.dart` `getHttpHeaders()`（2729 行）只有 `Authorization: Bearer <本地 access_token>`，不含 Content-Type。

**B. Rust 通路**（sysinfo、heartbeat、全部审计、主控端会话备注）
- `common.rs` `post_request`（1635 行）、`post_request_with_status`（1665 行，审计用）→ `post_request_`（1707 行）：
  - header 参数为 `""`，即**不带 Authorization**；`post_request_` 总是加 `Content-Type: application/json`。
  - 每次 12 秒超时；TLS 握手类错误（`e.is_request()`）会依次重试"接受无效证书"、"native-tls"，单次调用最多约 4×12 秒。
  - **4xx 原样返回文本；`post_request` 对任何状态码都返回 `Ok(body 文本)`**，所以 sysinfo / heartbeat 的结果只看 body。

### 1.3 5xx 和连接失败会触发 hbbs TCP 代理回落【读码】

`common.rs` `with_tcp_proxy_fallback`（1579 行）、`post_request_with_status`、`tcp_proxy_request`（1419 行）：
- 条件：HTTP 连接失败或状态码 ≥ 500，且没开 WebSocket，且目标 URL 的 host 等于 api-server 的 host（`should_use_tcp_proxy_for_api_url`）。
- 动作：连 `<custom-rendezvous-server>:21116`，做 KeyExchange，发 `RendezvousMessage.http_proxy_request`（hbb_common 5d52530 `protos/rendezvous.proto` 262、306 行，字段 27/28），等 `HttpProxyResponse`；整体超时 `CONNECT_TIMEOUT + READ_TIMEOUT` = 18 + 18 = 36 秒。
- 原版 hbbs 的 TCP 循环对不认识的消息走 `_ => {}`，继续等下一条（`rustdesk-server@873230e:src/rendezvous_server.rs` `handle_tcp`、`handle_listener_inner` 1184 行），所以客户端会**白等到 36 秒超时**，再返回原来的 HTTP 结果。
- 影响：heartbeat 循环是单线程顺序执行（`sync.rs` `#[tokio::main(flavor = "current_thread")]`），一次 5xx 会让心跳卡住 36 秒以上；审计注释也写明"一次尝试最多 84 秒"（`connection.rs` `post_audit_async` 注释）。
- Dart 默认通路（A 的纯 Dart 分支）没有这个回落。
- 内置选项 `use-raw-tcp-for-api` = `Y` 时所有 API 直接走 TCP 代理（`should_use_raw_tcp_for_api` 1338 行），只有定制客户端会设。

### 1.4 Dart 侧解析的共同规则【读码】

- 多数接口用 `common.dart` `decode_http_response`（4216 行）：`utf8.decode(resp.bodyBytes, allowMalformed: true)`，不看响应的 charset。
- `login-options` 例外，用的是 `resp.body`（`user_model.dart` 252 行），由 Dart `http` 包按响应 Content-Type 的 charset 解码。
- 走 Rust 通路时，Dart 用 `http.Response(String body, …, headers)` 重建响应，`bodyBytes` 是按响应头 charset 把字符串重新编码出来的【读码 `_parseHttpResponse`】。没写 charset 时 `http` 包可能按 latin1 编码，遇到中文会出错或乱码【推测：没读 `http` 1.4.0 源码】。**统一回 `application/json; charset=utf-8` 可以避开这个问题。**
- Dart 强类型：`String x = json['k'] ?? ''` 这种写法，`k` 是数字、布尔或对象时运行期抛 TypeError；`int? x = json['k']` 给字符串或小数同样抛错。抛错后的结果按各接口的 try/catch 位置而定，见各节。

### 1.5 认证与 401【读码】

- token：服务端发的任意不透明字符串，客户端存进本地选项 `access_token`（`login.dart` `handleLoginResponse` 778 行），请求时原样放进 `Authorization: Bearer <token>`。客户端不解析 token，也不管过期。
- 只有 Dart 通路的用户态接口带 Bearer。设备态接口（sysinfo、heartbeat、审计、会话备注）一律不带。
- 401 / 400 的客户端反应：

| 接口 | 状态码 | 客户端反应 |
|---|---|---|
| `POST /api/currentUser` | 401 | `reset(resetOther: true)`：清 `access_token`、`user_info`，清地址簿和组面板缓存（`user_model.dart` 85~88 行、`reset` 138 行） |
| `POST /api/currentUser` | 400 | `reset(resetOther: false)`：只清 `access_token`、`user_info` |
| 组面板三接口 | **最后一个请求**的状态码是 401 | `pull` 末尾 `gFFI.userModel.reset(resetOther: true)`（`group_model.dart` 57 行） |
| `POST /api/login` | 任何非 200 | 只显示错误，不清状态 |
| `POST /api/logout` | 任何 | 忽略，本地照样清（`logOut` 184~188 行） |

- 建议：token 无效、过期、用户被禁用，统一回 **401 + `{"error":"Unauthorized"}`**。

另外【读码】：主控端发起连接时，`PunchHoleRequest.token`（rendezvous.proto 36 行）填的就是本地 `access_token`（`ui_session_interface.rs` `io_loop` 1984 行取值后传给 `Client::start`）。porta-server 的会合模块和 API 在同一进程，可以据此识别"哪个账号发起了连接"。

### 1.6 设备态接口的身份：`id` + `uuid`【读码】

- `uuid` = `base64::encode(hbb_common::get_uuid())`，标准字母表、带 `=` 填充（`common.rs` `encode64` 2100 行；`ui_interface.rs` `get_uuid` 834 行；`sync.rs` 135、238 行；`connection.rs` `post_conn_audit` 1566 行等）。
- 设备向 hbbs 注册时，`RegisterPk.uuid` 是同一个 `hbb_common::get_uuid()` 的原始字节（`rendezvous_mediator.rs` 1262~1266 行），原版 hbbs 把它存在 peer 表的 `uuid` 列（`rustdesk-server@873230e:src/peer.rs` `update_pk`、`src/database.rs` `insert_peer`）。
- 所以 porta-server 可以校验：`base64_decode(body.uuid) == peer表[body.id].uuid`。这只是弱校验（uuid 是机器 ID，不是秘密），但能挡住随手乱填的请求，兼容期内可开。
- 注意例外：主控端的会话备注请求**不带 uuid**（§5.2.4）。

### 1.7 axum 实现注意

- `Json<T>` 提取器：缺 `Content-Type: application/json` 回 415，JSON 语法错回 400，类型不符回 422，响应体都是纯文本【推测：axum 文档行为，未在本仓库读码】。本组接口客户端都会带 `application/json`（§1.2），但纯文本错误体会让 login 走"Unknown Error"、让审计判成不可重试 4xx 而丢弃。建议收 `Bytes` 后自己解析成 `serde_json::Value` 再宽松取字段。
- `GET /api/login-options` 还会收到 Rust 侧的 **HEAD** 请求（TLS 探测，`hbbs_http/http_client.rs` `create_http_client_with_url_` 180 行 `client.head(url)`），只关心能否连上，不看状态码。axum 的 `get()` 路由会自动应答 HEAD【推测：axum 文档行为】。
- Query 参数：`current`、`pageSize` 是数字字符串，`accessible` 是空串，`status` 是 `"1"`。用 `Option<String>` 接最稳。
- 反代：获取客户端真实 IP 要读反代头（现网前面是 nginx）；这条和契约无关，只是提醒。

## 2. 账号接口

### 2.1 `GET /api/login-options`

调用方【读码】：
- Dart `user_model.dart` `queryOidcLoginOptions`（240 行），打开登录框时调（`login.dart` `fetchLoginOptions` 740 行）。
- Rust OIDC 前的 TLS 探测（HEAD，见 §1.7；`account.rs` `ensure_client` 149 行）。

请求：无 body，无认证。Dart 通路下 headers 为 null，所以带了 `Content-Type: application/json`。

客户端解析【读码 `queryOidcLoginOptions`】：
1. 状态码不在 [200, 300) → 抛 `RequestException(status, reasonPhrase)`；登录框显示 Retry 按钮和错误文本，**不显示** `network_error_tip`（`login.dart` `thirdAuthWidget` 868 行 `error is! RequestException`）。
2. `jsonDecode(resp.body)` 必须是 **字符串数组**：逐项 `item as String`，非字符串抛 TypeError；顶层是对象时 for-in 也会抛错。抛错时登录框显示 `network_error_tip` + Retry + 错误文本。账号密码登录不受影响。
3. 有任何一项以 `common-oidc/` 开头 → 把剩下部分 `jsonDecode` 后**直接作为 `List` 返回**；每个元素须是对象，按 `e['name']`、`e['icon']` 生成按钮（`login.dart` 907 行 `ConfigOP(op: e['name'], icon: e['icon'])`）。
4. 否则取所有 `oidc/<name>` 项，生成 `[{name: <name>}]`。
5. 结果为空 → 第三方登录区域隐藏，只剩账号密码。

**Porta 第一期**：回 `200 []`。

坑【读码 `rustdesk-api` `http/controller/api/login.go` `LoginOptions` 103~123 行】：没配任何 OAuth 且关了 web-sso 时，`oidcItems` 是 nil，`json.Marshal` 得到 `null`，返回 `["common-oidc/null"]`。客户端 `jsonDecode("null")` 得到 null，从声明返回 `Future<List<dynamic>>` 的 async 函数里返回 null 会抛 TypeError【推测：Dart 运行期隐式向下转型】，登录框会显示网络错误提示。

### 2.2 `POST /api/login`（只做 `type=account`）

调用方【读码】：`user_model.dart` `login`（193 行），由 `login.dart` `onLogin`（826 行）发起。

请求：
- 头：headers 为 null → `Content-Type: application/json`。**不带 Authorization。**
- body（`hbbs.dart` `LoginRequest.toJson` 155~177 行；值为 null 的键不发）：

| 字段 | 类型 | 账号密码登录时的值 |
|---|---|---|
| `username` | string | 输入框原文（客户端只校验非空） |
| `password` | string | **明文**（客户端只校验非空） |
| `id` | string | 本机 RustDesk ID（`main_get_my_id`） |
| `uuid` | string | 本机 uuid 的 base64（§1.6） |
| `autoLogin` | bool | `true` |
| `type` | string | `"account"` |
| `deviceInfo` | object | `{"os": "windows"\|"linux"\|"macos"\|"android"\|"ios", "type": "client", "name": <主机名>}`（`ui_interface.rs` `get_login_device_info` 1329 行，`os` 是 `std::env::consts::OS`）；Dart 解码失败时为 `{}` |

不会出现的字段：`verificationCode`、`tfaCode`、`secret`（只在第二步出现）。

客户端处理响应【读码 `login`、`getLoginResponseFromAuthBody` 219 行、`handleLoginResponse` 773 行】：
1. 先 `jsonDecode(decode_http_response(resp))` 并赋给 `Map<String, dynamic>`。失败（非 JSON、空 body、顶层不是对象）：
   - 状态码非 200 时弹 toast `HTTP <code>`；
   - 然后抛出，被 `onLogin` 的 `catch (err)` 接住，密码框下显示 `Unknown Error: <异常文本>`。
2. 状态码 ≠ 200 → `RequestException(status, body['error'] ?? '')`，密码框下显示 `translate(error)`。
3. 状态码 = 200 且有 `error` 键（值非 null）→ `RequestException(0, error)`，显示同上。
4. `error` 的值必须是字符串；给对象或数字会在构造 `RequestException(int, String)` 时抛 TypeError，显示 `Unknown Error: …`。
5. 成功判定：`type == "access_token"` 且 `access_token != null`。
   - `access_token`、`type`、`tfa_type`、`secret` 在 Dart 里都是 `String?`，给非字符串抛 TypeError → `Unknown Error`。
   - `user` 非 null 时必须是对象，按 `UserPayload.fromJson` 解析（§2.5），随后 `_parseAndUpdateUser` 设置 `userName` 等并存 `user_info`。
   - `handleLoginResponse` 存 `access_token` 和 `user_info = jsonEncode(resp.user ?? {})`（只含 `name`、`display_name`、`avatar`、`status`，`hbbs.dart` `toJson` 50 行），关闭对话框，返回 true，随后 `UserModel.updateOtherModels()` 拉地址簿和组面板。
   - **`user` 缺失或 `user.name` 为空**：`userName` 保持空，`isLogin` 为假，界面仍显示"登录"按钮，组面板 `pull` 直接 return（`group_model.dart` 41 行）；直到下次启动调 currentUser 才恢复。所以 `user.name` 必填且非空。
6. `type == "access_token"` 但没有 `access_token`：什么都不做，对话框不关，也不显示错误。
7. `type` 为其他值：显示 `Failed, bad response from server`。

错误文本：客户端会 `translate(error)`。例如回 `"Wrong credentials"`，中文界面显示"提供的登录信息错误"（`src/lang/cn.rs` 230 行有这个 key）【读码】。

**Porta 推荐**：
- 成功：`200`
  ```json
  {"type":"access_token","access_token":"<opaque>","user":{ ...UserPayload，见 §2.5... }}
  ```
- 用户名或密码错：`401 {"error":"Wrong credentials"}`（任何 4xx 都行，别用 5xx，§1.3）。
- 用户被禁用：`403 {"error":"<说明>"}`。
- 频率限制：`429 {"error":"<说明>"}`。
- body 解析失败：`400 {"error":"<说明>"}`。
- 可选：参照 rustdesk-api，按 `uuid` 把这台设备归到登录用户名下（§3.4"设备归属"）。

#### 2.2.1 二次验证分支（第一期不做，只记录）【读码】

- 第一步响应 `{"type":"email_check","tfa_type":<null|"email_check"|"tfa_check">,"secret":"<服务端状态>","user":{…}}`。
  - `tfa_type` 为 null 或 `email_check` → 邮件验证码框，显示 `user.email`；为 `tfa_check` → TOTP 框；其他值显示 `Failed, bad tfa type from server`（`login.dart` 790~800 行）。
- 第二步再 `POST /api/login`（`verificationCodeDialog` 1003 行），body：`verificationCode`（输入的码）、`tfaCode`（仅 TOTP 时，同一个码）、`secret`、`username`（`user?.name`）、`id`、`uuid`、`autoLogin`、`type:"email_code"`（**TOTP 也是这个值**）、`deviceInfo`；**不带 password**。
- 第二步成功只认 `type == "access_token"` 且有 `access_token`，只存 `access_token`（`user_info` 由 `getLoginResponseFromAuthBody` 在 `user` 非 null 时写）。
- 常量 `mobile`、`sms_code`、`tfa_code`（`hbbs.dart` 10~20 行）客户端从未发送。

### 2.3 `POST /api/currentUser`

调用方【读码】：`user_model.dart` `refreshCurrentUser`（53 行）。时机：启动时（`main.dart` 143、183 行）、桌面主页收到刷新事件（`desktop_home_page.dart` 786 行）。本地 `access_token` 为空时不发。

请求：
- 头：`Content-Type: application/json`、`Authorization: Bearer <token>`。
- body：`{"id": "<本机 ID>", "uuid": "<base64 uuid>"}`。

客户端处理：
1. 网络异常 → `networkError` = 异常文本。地址簿和组面板标签显示网络错误提示和重试按钮；组面板在 `networkError` 非空时不拉（`group_model.dart` 42 行）。
2. 401 → 全部重置；400 → 只清 token 和 user_info（§1.5）。
3. 其他状态码：一律 `json.decode`。
   - 非 JSON（比如 404 的 HTML 页）→ 异常进 `networkError`，显示网络提示。
   - 有 `error` 键（非 null）→ `networkErrorFromServer = true`，`networkError` = error 文本，不显示"检查网络"提示。
   - 否则 `UserPayload.fromJson(data)`（§2.5），`data` 必须是对象。
4. 成功后更新 `userName`、`displayName`、`avatar`、`isAdmin`，重写 `user_info`；然后 `updateOtherModels()` 拉地址簿和组面板（在 `finally` 里，失败也会拉）。

**Porta 推荐**：200 + UserPayload；token 无效 401（§1.5）。请求 body 可以忽略，也可以用来更新"这个 token 最近在哪台设备上用过"。

### 2.4 `POST /api/logout`

调用方【读码】：`user_model.dart` `logOut`（170 行），用户点注销时调；改 api-server 时用旧地址调。

请求：
- 头：`Authorization: Bearer <token>`、`Content-Type: application/json`。
- body：`{"id": "<本机 ID>", "uuid": "<base64 uuid>"}`。
- **Dart 侧 2 秒超时**（`.timeout(Duration(seconds: 2))`），任何异常和任何响应都忽略，`finally` 里本地 `reset(resetOther: true)`。

**Porta 推荐**：吊销该 token，回 `200 {}`。token 已无效也回 200 或 401，都行。

### 2.5 `UserPayload` 统一定义

服务端在 login、currentUser、users 三处回同一个结构。Dart 和 Rust 两边的严格程度不同：

| 字段 | Dart（`hbbs.dart` `UserPayload.fromJson` 36~48 行） | Rust（`hbbs_http/account.rs` `UserPayload` 79~97 行，只在 OIDC 用） | Porta 建议 |
|---|---|---|---|
| `name` | `String`，`?? ''`；非字符串 TypeError | `String` **必填**，缺失解析失败 | 非空字符串（用户名，全局唯一） |
| `display_name` | `String`，`?? ''` | `Option<String>` | 字符串（可空串） |
| `avatar` | `String`，`?? ''`；以 `/` 开头时客户端拼上 api-server（`ui_interface.rs` `resolve_avatar_url` 254 行） | `Option<String>` | `""` |
| `email` | `String`，`?? ''` | `Option<String>` | 字符串 |
| `note` | `String`，`?? ''` | `Option<String>` | 字符串 |
| `status` | `== 0` → 禁用，`== -1` → 未验证，其他（含缺失）→ 正常；UI 没用到 | `Deserialize_repr` i64，只认 0 / 1 / -1；缺失默认 1；**给 null 或其他整数解析失败** | `1` |
| `is_admin` | `== true`；UI 没用到（全仓无引用） | `bool`，缺失默认 false，**给 null 解析失败** | `true`/`false`，不要给 null |
| `info` | 不读 | **必填对象**（`UserInfo`，字段都有默认值，`{}` 即可）；其中 `email_verification`、`email_alarm_notification` 是 flatten 进来的 bool（给 null 失败），`login_device_whitelist` 每项需 `data`(string)、`info`(DeviceInfo)、`exp`(u64)，`other` 的值必须是字符串 | `{}` |
| `third_auth_type` | 不读 | `Option<String>` | 省略 |
| `verifier` | 仅 Web 版用 | 无 | 省略 |

Rust 侧的 `AuthBody`（`account.rs` 99~108 行）：`access_token`、`type` 必填字符串，`tfa_type`、`secret` 缺失时默认空串、**给 null 失败**，`user` 必填。只影响 OIDC 轮询，但同一套序列化最好全接口通用，日后加 OIDC 不用改。

推荐样例（三处通用）：
```json
{"name":"alice","display_name":"Alice","avatar":"","email":"","note":"","status":1,"is_admin":false,"info":{}}
```

## 3. 组面板（"可访问的设备"）

### 3.1 三个接口的共同行为【读码 `group_model.dart`】

- 触发：`pull`（39 行）。条件：内置选项未禁用组面板、已登录（`userName` 非空）、`networkError` 为空、没在加载中。登录成功后和 currentUser 之后都会拉。
- 顺序：先 `device-group/accessible`，再 `users`，再 `peers`（`_pull` 64 行）。device-group 失败被忽略；users 或 peers 失败则整个面板显示 `pull_group_failed_tip: <错误>`，且**不更新**列表。
- 请求：`GET`，只带 `Authorization: Bearer <token>`，没有 body。
- 分页循环（三个接口相同）：
  ```
  pageSize = 100; total = 0; current = 0
  do { current += 1; 请求 ?current=<current>&pageSize=100[...]
       if (json 有 'total') { if (total == 0) total = json['total'];
                             if (json 有 'data' 且 data 是 List) 逐项解析并按键去重合并 } }
  while (current * pageSize < total)
  ```
  - `total` 用 `var total = 0` 声明成 int，**`json['total']` 必须是 JSON 整数**；给字符串、小数或 null 会抛 TypeError → 当作该接口失败。
  - **没有 `total` 键时 `data` 被整个跳过**，循环结束，接口算成功、列表为空。
  - `total` 只取第一页的值。
  - `data` 不是 List 时跳过；`data` 里某一项不是对象或字段类型不对 → 抛错 → 该接口失败。
- 每页的错误判定顺序：
  1. `_jsonDecodeResp`（284 行）：body 不是 JSON 对象 → 抛出。非 200 时消息为 `HTTP <code>, <body 前 128 字或异常>`，否则为 body 本身或异常文本。
  2. `json` 有 `error` 键 → 抛 `json['error']`（先于状态码检查）。
  3. 状态码 ≠ 200 → 抛 `HTTP <code>`。
- `_tryHandlePullError`（369 行）：错误文本（小写）含 `disabled` 时，清空三个列表。
- 401 处理见 §1.5。成功后把精简结果写进本地缓存（`_saveCache` 297 行）。

### 3.2 `GET /api/device-group/accessible`

- query：`current`、`pageSize`（只有这两个）。
- 响应 `{"total": int, "data": [{"name": string}, ...]}`，按 `name` 去重；只读 `name`（`hbbs.dart` `DeviceGroupPayload` 288 行，非字符串 TypeError）。
- 任何失败都被忽略（注释"old hbbs doesn't support this api"），只是这次请求的状态码会被记进 `_statusCode`，随后被 users / peers 覆盖。
- 设备组用来按 `device_group_name` 过滤 peers（`peers_view.dart` `MyGroupPeerView.filter` 570 行）。
- **Porta 第一期**：不做设备组，回 `200 {"total":0,"data":[]}`（比 404 少一条客户端日志），404 也可以。

### 3.3 `GET /api/users`

- query：`current`、`pageSize=100`、`accessible=`（空串）、`status=1`。语义【推测】：`accessible` 表示"当前用户可见的用户"，`status=1` 表示只要正常状态的用户。
- 响应 `{"total": int, "data": [UserPayload, ...]}`，按 `name` 去重；和当前登录用户 `name` 相同的那项排到最前（`_pull` 81 行）。
- 特殊错误：`error == "Admin required!"` 或含 `ambiguous column name: status` → 显示"请升级 RustDesk Server Pro 到 1.1.10"提示（`_getUsers` 185 行）。Porta 不要用这两个字符串。
- **Porta 推荐**：普通用户只回自己；管理员（或以后的"朋友组"）回可见用户。必须包含当前用户，否则组面板左栏没有"我"。

### 3.4 `GET /api/peers`

- query：`current`、`pageSize=100`、`accessible=`、`status=1`（`status` 的语义【推测】：只要启用状态的设备）。
- 响应 `{"total": int, "data": [PeerPayload, ...]}`，按 `id` 去重。
- 每项字段（`hbbs.dart` `PeerPayload.fromJson` 86~93 行 → `toPeer` 95 行 → `peer_model.dart` `Peer.fromJson` 33~48 行）：

| 字段 | Dart 类型与转换 | 用途 | Porta 取值 |
|---|---|---|---|
| `id` | `String`，`?? ''`；非字符串 TypeError | 设备 ID，去重键 | 设备 ID |
| `info` | 是 `Map<String,dynamic>` 就用，否则当 `{}` | 见下三行 | 对象 |
| `info.username` | 进 `Peer.username`（String）；非字符串 TypeError | 显示被控端系统用户名 | sysinfo 的 `username` |
| `info.os` | 任意类型，`toString()` 后按 `" / "` 切，第一段小写匹配 `windows`/`linux`/`macos`/`android`，否则整串含 `linux` 算 Linux，否则平台为空 | 平台图标 | **原样用 sysinfo 的 `os`**（如 `windows / Windows 11 Pro - 10.0.26100`，§4.1） |
| `info.device_name` | 进 `Peer.hostname`（String），null 变 `''`；非字符串 TypeError | 显示主机名 | sysinfo 的 `hostname` |
| `status` | `int?`；给字符串或小数 TypeError | **客户端不用**（`toPeer` 不传） | `1` 或省略 |
| `user` | `String`，`?? ''` | 客户端不用 | 属主用户名 |
| `user_name` | `String`，`?? ''` → `Peer.loginName` | **按用户过滤的键**：左栏选中用户 X 时只显示 `loginName == X.name` 的设备（`peers_view.dart` 591 行） | 属主的 `name` |
| `device_group_name` | `String?`，`?? ''` | 按设备组过滤 | `""` |
| `note` | `String`，`?? ''`；非字符串 TypeError | 组面板卡片显示备注（`common.dart` `peerTabShowNote`） | 字符串 |

- 在线状态不来自这个接口：组面板的在线点由客户端经 hbbs 的在线查询得到，接口只保留上次的在线标记（`_pull` 93~98 行）【读码】。
- **设备归属**（Porta 要自己定的语义）：原版客户端的 sysinfo 不带属主信息，只有定制客户端的内置选项 `preset-user-name` 会带（§4.1）。rustdesk-api 的做法【读码】：
  - 登录时按请求里的 `uuid` 找到 peer 记录，把它归给登录用户（`service/user.go` `Login` 97~114 行 → `service/peer.go` `UuidBindUserId` 36 行）；
  - 注销时解绑（`Logout` 197~207 行）；
  - sysinfo 新建或更新 peer 时，若无属主，按 uuid 查最近一次登录日志补上（`http/controller/api/peer.go` `SysInfo` 26~59 行）。
  - Porta 可以照搬，也可以只用命令行分配。

## 4. 设备上报（HTTP 层；心跳语义另有人负责）

发送方【读码】：`hbbs_http/sync.rs` `start_hbbs_sync_async`（87 行）。由 `rendezvous_mediator.rs` 281 行启动，也就是向 hbbs 注册的那个进程（Windows 上是服务进程）。每台装了客户端的机器都会发，包括只当控制端用的机器。
- 节拍：每 3 秒 tick 一次（`TIME_CONN`）。
- 选项 `stop-service` = `Y` 时不发。
- 每个 tick 内先按需传 sysinfo，再按需发心跳，两者顺序执行。

### 4.1 `POST /api/sysinfo`

请求：头只有 `Content-Type: application/json`。body（`common.rs` `get_sysinfo` 929 行 + `sync.rs` 133~179 行）：

| 字段 | 类型 | 内容 |
|---|---|---|
| `cpu` | string | `"<型号>, <GHz>GHz, <逻辑核>/<物理核> cores"`；安卓只有 `"<n>/<m> cores"` |
| `memory` | string | `"<总内存GB，两位小数>GB"` |
| `os` | string | `"<distribution_id> / <long_os_version>"`，Windows 再加 `" - <os_version>"` |
| `hostname` | string | 主机名；内置选项 `preset-device-name` 非空时被它覆盖 |
| `username` | string，**可缺** | 当前活动桌面用户；为空或 Windows 下为 `SYSTEM` 时不发；`preset-device-username` 非空时覆盖 |
| `version` | string | 客户端版本串，如 `"1.4.3"` |
| `id` | string | 本机 ID |
| `uuid` | string | base64 uuid（§1.6） |
| `preset-address-book-name` / `-tag` / `-alias` / `-password` / `-note` | string，可缺 | 选项值，非空才发（`keys.rs` 79~83 行） |
| `preset-user-name` / `preset-strategy-name` / `preset-device-group-name` | string，可缺 | **内置**选项，只有定制客户端会带（`keys.rs` 113~115 行） |
| `preset-note` | string，可缺 | 选项值（`keys.rs` 86 行） |

什么时候发【读码 `sync.rs` 108~131 行】：
- 进程启动后第一次。
- api-server 或本机 ID 变了。
- 系统用户名变了。
- 心跳响应里有 `sysinfo` 键。
- 上次失败后满 120 秒。
- 主机名、版本变化**不会**触发；客户端升级会重启进程，所以新版本号会在重启后带上来。

客户端对响应（只看 body 文本，**严格相等，不 trim**）：
- `"SYSINFO_UPDATED"` → 标记已上传，**置 `PRO=true`**。副作用：Windows 上 CM 窗口启动失败时不弹错误；IPC `hide_cm` 生效（见调研 03 §4）。
- `"ID_NOT_FOUND"` → `last_uploaded = None`，**下一个 tick（3 秒后）立刻重传**。服务端如果一直回它，就会每 3 秒来一次。
- 其他任何内容（含 JSON、空 body、4xx 的错误页）或网络错误 → 120 秒后重试。
- `/api/sysinfo_ver` 那个分支只在 `is_public` 为真时走，而 `heartbeat_url()` 对公共服务器已经返回空，是死代码；Porta 不用实现。

**Porta 推荐**：
- 能存下就回 `200`、`Content-Type: text/plain; charset=utf-8`、body 正好 `SYSINFO_UPDATED`。
- 设备还没在会合模块注册（启动时的竞态）：回 `ID_NOT_FOUND` 让它 3 秒后重试，或回别的文本让它 120 秒后重试。后者更稳，前者在设备 ID 配错时会一直每 3 秒打一次。
- 记录 `version`，供 §3.1 的兼容退出统计。原版客户端没有能区分"原版 / Porta"的字段，要 Porta 客户端自己加新字段（服务端对未知字段宽松接收即可）。

### 4.2 `POST /api/heartbeat`（只讲 HTTP 层）

- 节奏：有连接时每 3 秒；无连接时距上次满 15 秒才发（`sync.rs` 232 行）。
- 头只有 `Content-Type: application/json`。
- body（`sync.rs` 236~244 行）：

| 字段 | 类型 | 内容 |
|---|---|---|
| `id` | string | 本机 ID |
| `uuid` | string | base64 uuid |
| `ver` | int(i64) | `get_version_number(VERSION)`：`1.4.3` → `1004030`（每段 ×1000 累加，最后一段再 ×10；`-` 后面的数字加上去；hbb_common 5d52530 `src/lib.rs` 264 行） |
| `conns` | int(i32) 数组，**可缺** | 被控端当前所有连接的 `conn_id`（含未认证的；`connection.rs` raii 注释 6851 行），空时不发 |
| `modified_at` | int(i64) | 本地 `strategy_timestamp`，没有时为 0 |

- 客户端处理响应（`sync.rs` 249~274 行）：
  - body 必须能解析成 JSON 对象（`HashMap<&str, Value>`），否则整个忽略。
  - `sysinfo` 键存在（值任意，含 null）→ 强制重传 sysinfo。
  - `disconnect` 能解析成 `Vec<i32>` → 广播断开这些 conn_id。
  - `modified_at` 能解析成 i64 且和发送值不同 → 存为新的 `strategy_timestamp`。
  - `strategy` 能解析成 `{config_options: {String: String}, extra: {String: String}}` → 应用 `config_options`。**值必须全是字符串**，否则整个 `strategy` 被丢弃。
  - 状态码不看。
- **Porta HTTP 层建议**：
  - 永远回 200 + JSON 对象，最少 `{}`；body 解析失败也回 `{}`，别回 5xx。
  - 收到不认识的 `id` / `uuid` 时回 `{"sysinfo":true}`，让它补传 sysinfo。rustdesk-api 在这种情况下只回 `{}`（`index.go` `Heartbeat` 41~63 行），服务端数据库清空后，客户端要到下次重启才会补传。
  - 在线时间可以用心跳时间戳更新，但 porta-server 本身就是 hbbs，内存里有更准的注册在线状态。

## 5. 审计

URL 由 `common.rs` `get_audit_server(api, custom, typ)`（1326 行）生成：`<api-server>/api/audit/<typ>`；api-server 为空或是公共服务器时为空串，不发。

### 5.1 重试与成功判定（被控端三类审计共用）【读码 `connection.rs` `post_audit_async` 1669 行】

用 `post_request_with_status`，header 为 `""`（不带认证），body 在第一次尝试前序列化一次，**重试时 body 完全相同（nonce 不变）**。

| 响应 | 判定 |
|---|---|
| 2xx 且 body `trim()` 后为空 | **成功** |
| 2xx 且 body 是带非空字符串 `error` 的 JSON | 服务端错误，**重试**（注释：服务端写库失败时会释放这条 nonce，重试才能存进去） |
| 2xx 且其他非空 body | "unexpected response body"，**重试** |
| 5xx、408、429 | 重试（5xx 还会先触发 36 秒的 TCP 代理回落，§1.3） |
| 其他 4xx | **立即丢弃**，记 error 日志 |
| 网络错误 | 重试 |

- 最多 3 次，间隔 10 秒、30 秒；从第一次开始算超过 120 秒就停（`RETRY_DEADLINE`），退避结束后也会再检查一次。
- 注释写明服务端按 nonce 记 5 分钟去重。
- `nonce` 格式：`uuid::Uuid::new_v4().to_string()`，即 36 个字符、小写、带连字符。conn / file / alarm 每条记录一个新 nonce。
- **conn 审计按连接串行**：每个连接有一个 `post_seq_loop`（1326 行），new → 认证成功 → close 依次发，前一条重试完才发下一条。file 和 alarm 各自 `tokio::spawn`，不排队。
- Porta 推荐：
  - 成功回 `200` + 空 body（axum 直接返回 `StatusCode::OK`）。
  - nonce 存成审计表里的 UNIQUE 列，和记录在同一事务写入；冲突说明是重复投递，按成功处理（回 200 空 body）。
  - 写库失败回 `200 {"error":"..."}`（不留 nonce），客户端会重试。
  - body 坏了回 `400 {"error":"..."}`，客户端不重试。

### 5.2 `POST /api/audit/conn`

公共字段由 `post_conn_audit`（1558 行）追加：

| 字段 | 类型 | 内容 |
|---|---|---|
| `id` | string | **被控端**本机 ID |
| `uuid` | string | 被控端 base64 uuid |
| `conn_id` | int(i32) | 被控端进程内连接序号（§5.5） |
| `session_id` | int(**u64**) | `self.lr.session_id`：主控端 LoginRequest 里的会话号；**收到 LoginRequest 之前是 0** |
| `nonce` | string | uuid v4 |
| `conn_audit_ref` | string，可缺 | 只在 new（以及 IP/ID 白名单告警）时、且 hbbs 在 PunchHole / RequestRelay / FetchLocalAddr 里下发了非空 `ControlledContext.conn_audit_ref` 时才带（`conn_audit_ref` 1546 行；rendezvous.proto 69 行）。原版 hbbs 不下发 |

#### 5.2.1 新连接（`action: "new"`）
`on_open`（1505 行）：TCP 或中继连上、通过 IP 白名单后立刻发，**先于认证**。扫描器、密码错的连接也会有这一条。
```json
{"ip":"203.0.113.5","action":"new","conn_audit_ref":"…可缺…","id":"123456789","uuid":"…","conn_id":1234,"session_id":0,"nonce":"…"}
```
- `ip`：`SocketAddr::ip()` 用 serde 序列化成字符串（IPv4 点分或 IPv6 文本）。走中继时是 hbbs 报来的对端地址【推测：`server.rs` `create_relay_connection` 参数名为 `peer_addr`，未深追】。

#### 5.2.2 认证成功（**没有 `action` 键**）
认证通过后（1931~1939 行）：
```json
{"peer":["<主控端ID>","<主控端名字>"],"type":0,"primary_auth":2,"two_factor":1,"id":"…","uuid":"…","conn_id":1234,"session_id":12345678901234567890,"nonce":"…"}
```
- `peer`：二元字符串数组 `[lr.my_id, lr.my_name]`。
- `type`：0 远程桌面、1 文件传输、2 端口转发、3 看摄像头、4 终端。
- `primary_auth`（不为 0 时才有，1~4）：1 点击接受、2 临时密码、3 固定密码、4 切换控制方向（`ConnAuditPrimaryAuth` 310 行）。
- `two_factor`（不为 0 时才有，1~2）：1 TOTP、2 信任设备（`ConnAuditTwoFactor` 326 行）。主认证是"点击"或"切换方向"时，客户端会把 `two_factor` 清零（`normalize_conn_audit_auth_fields`）。

#### 5.2.3 关闭（`action: "close"`）
连接循环退出时（1235 行），认证过没认证过都发：
```json
{"action":"close","id":"…","uuid":"…","conn_id":1234,"session_id":<认证过则为真实值，否则0>,"nonce":"…"}
```

#### 5.2.4 主控端会话备注（另一种请求，同一路径）
- `ui_session_interface.rs` `send_note`（591 行、2108 行）：主控端工具栏 "Note"（`toolbar.dart` 630 行 → `dialog.dart` `showAuditDialog` 1561 行）提交时发。
- 只有本地有 `access_token` 时 URL 才非空（`get_audit_server` 580 行），但**请求本身不带 token**。
- 用普通 `post_request`：不重试，响应忽略。
```json
{"id":"<被控端ID>","session_id":<u64>,"note":"<最多256字>"}
```
- **没有 `uuid`、`conn_id`、`nonce`、`action`**。区分办法：有 `note` 键、没有 `uuid`。关联键是 `(被控端 id, session_id)`。
- 同一会话里远程桌面和文件传输共用一个 session_id（`connection.rs` 6965 行注释），可能匹配多条记录，建议优先更新 `type=0` 的那条，或者全部更新【推测：设计建议】。
- 输入框 `maxLength: 256`（`dialog.dart` `buildNoteTextField`）。

#### 5.2.5 Porta 存储建议【推测：设计建议】
- new：插入一条记录，字段 device_id、uuid、conn_id、ip、conn_audit_ref、nonce、created_at。
- 认证成功：找 `device_id = id AND conn_id = conn_id AND closed_at IS NULL` 的**最近一条**，更新 peer_id、peer_name、type、primary_auth、two_factor、session_id、authed_at；找不到（new 丢了）就新插一条。
- close：同样的查找条件，写 closed_at；找不到就忽略或新插。
- 备注：按 `(device_id, session_id)` 找最近的记录，写 note。

### 5.3 `POST /api/audit/file`

`post_file_audit`（1589 行）：
```json
{"id":"<被控端ID>","uuid":"…","peer_id":"<主控端ID>","conn_id":1234,"type":0,"path":"C:\\x","is_file":false,
 "info":"{\"ip\":\"203.0.113.5\",\"name\":\"<主控端名字>\",\"num\":3,\"files\":[[\"a.txt\",123],[\"b\",45]]}",
 "nonce":"…"}
```
- `type`（`FileAuditType` 6515 行）：0 = RemoteSend，被控端把文件发给主控端（读、下载、剪贴板发出、远程打印）；1 = RemoteReceive，被控端接收文件（写、上传、剪贴板收入）。
- `path`：传输的目录或文件路径；剪贴板文件为 `""`；远程打印为 `"Remote print"`。
- `is_file`：`files` 只有一项且文件名为空串时为 true（此时 `path` 就是那个文件）。
- `info`：**JSON 字符串**（二次编码），对象含 `ip`（string）、`name`（主控端名字）、`num`（文件总数）、`files`（按大小降序取前 10 项，每项 `[name, size]`，size 是 i64）；远程打印时文件名为 `"Remote print"`。
- `conn_id` 是 i32；**没有 `session_id`**。
- 调用点：`connection.rs` 927、3439、3498、3761、5384、5514 行。

### 5.4 `POST /api/audit/alarm`

`post_alarm_audit`（1626 行）：
```json
{"id":"<被控端ID>","uuid":"…","typ":0,"info":"{\"ip\":\"203.0.113.5\"}","conn_id":1234,"nonce":"…","conn_audit_ref":"…可缺…"}
```
- 注意字段名是 **`typ`**（file 和 conn 里叫 `type`）。
- `info` 是 **JSON 字符串**。
- `conn_audit_ref` 只在 typ 0、10 时可能带。

`typ` 枚举（`AlarmAuditType` 6501~6513 行）与 `info` 内容：

| typ | 名称 | 触发 | info 对象 |
|---|---|---|---|
| 0 | IpWhitelist | 来源 IP 不在白名单（`check_whitelist`，1438 行） | `{"ip"}` |
| 1 | ExceedThirtyAttempts | 同一 IP 密码错超过 30 次（4554 行） | `{"ip","id","name"}` |
| 2 | SixAttemptsWithinOneMinute | 一分钟内错超过 6 次（4565 行） | `{"ip","id","name"}` |
| 3/4/5 | 已注释掉的旧值 | 不会出现 | — |
| 6 | ExceedIPv6PrefixAttempts | 同一 IPv6 前缀尝试过多（4472 行） | `{"ip","id","name"}` |
| 7 | TerminalOsLoginBackoff | 终端系统登录退避（4517 行，经 `decision.audit`） | `{"ip","id","name"}` |
| 8 | TerminalOsLoginConcurrency | 终端系统登录并发超限（4284 行） | `{"ip","id","name"}` |
| 9 | SessionScopeViolation | 会话收到越权消息（`post_session_scope_violation_alarm` 1652 行） | `{"id","name","ip","conn_type","message"}`；`conn_type` ∈ `remote`/`file_transfer`/`port_forward`/`view_camera`/`terminal`/`unknown` |
| 10 | IdWhitelist | 主控端 ID 不在白名单（1470 行） | `{"id","ip","name"}` |

上表里的 `id`、`name` 是**主控端**的（`lr.my_id`、`lr.my_name`）。顶层 `id` 是被控端自己。服务端应接收未知的 typ 值（以后会加）。

### 5.5 关联键的坑【读码】

- `session_id`：主控端 `rand::random::<u64>()`，为 0 时改成 1（`client.rs` 2962~2975 行），**约一半大于 i64::MAX**。serde 要按 `u64` 收；SQLite 存成十进制 TEXT，或 `as i64` 位转换存进 INTEGER（查询时同样转换）。rustdesk-api 用 `float64` 接（`http/request/api/audit.go` 16 行），大于 2^53 后丢精度。
- `conn_id`：`server.rs` 136 行起点是 `rand::random::<i32>() % 1000 + 1000`（范围 1~1999），每个新连接加 1（537 行）。**被控端进程重启后重新随机**，所以 `(id, conn_id)` 不是永久唯一的；关联必须加"未关闭、最近"这类条件。heartbeat 的 `conns` 和 `disconnect` 用的也是它。
- new 的 `session_id` 恒为 0，不能拿它关联。

## 6. 与 rustdesk-api 的差异（它的回包 vs 客户端期望）

| 接口 | rustdesk-api 行为【读码】 | 客户端期望 / 后果 |
|---|---|---|
| login-options | 无 OAuth 时回 `["common-oidc/null"]`（`login.go` 103~123 行） | 登录框显示网络错误提示（§2.1） |
| login | 成功 `{"type","access_token","user":{name,email,note,is_admin,status,info:{}}}`；失败 400 `{"error":<本地化文本>}`；参数校验用户名 2~32、密码 4~32（`request/api/user.go` 31~39 行）；不支持二次验证；登录时按 uuid 把设备归给用户 | 能用。`user` 缺 `display_name`、`avatar`（Dart 取默认值） |
| currentUser | 回同一结构（`controller/api/user.go` `Info`）；`is_admin` 是 `*bool`，可能是 null（`response/api/user.go` 25 行） | Dart 能接受 null；Rust OIDC 路径会因 null 解析失败 |
| logout | `200 null`，删 token 并解绑设备 | 客户端忽略响应 |
| 认证失败 | `401 {"error":"Unauthorized"}`，不校验 `Bearer ` 前缀，直接截掉前 7 个字符（`middleware/rustauth.go`） | 符合 |
| users / peers 分页 | 读 query `page`，客户端发的是 `current`，所以永远是第 1 页（`request/api/user.go` 41~53 行，`service/service.go` `Paginate` 55 行） | 超过 100 条时客户端翻页拿到的都是第一页，结果被截断 |
| users | 非管理员且不在共享组 → 只回自己（`group.go` `Users` 30~58 行） | 符合 |
| peers | `status` 恒为 0；`note` 恒为 `""`；`info.os` 来自 sysinfo 原文 | `status` 客户端不用，无影响 |
| device-group | 非管理员 `400 {"error":"Permission denied"}`；管理员 `total` 恒为 0 | 客户端忽略失败；`total=0` 导致只读第一页 |
| sysinfo | 永远回 `SYSINFO_UPDATED`；忽略所有 `preset-*`（`request/api/peer.go` `PeerForm` 只有 8 个基本字段） | 能用 |
| heartbeat | 永远回 `{}`；设备不存在也不要求补传 sysinfo；最多每 30 秒更新一次在线时间 | 策略通道空着 |
| audit/conn | 成功回 `{"code":0,"message":"success","data":""}`（`controller/api/audit.go` 58 行，`response/response.go` `Success`）；不读 nonce；`session_id` 用 float64 | 客户端判"非空 body"→ 再重试 2 次：new 写 3 条；认证成功、close 是更新，重复无害；而且因为按连接串行，后续审计被推迟 40 秒以上 |
| audit/conn 备注 | 没有 `note` 字段；`action` 为空时当作"认证成功"处理，按 `conn_id=0` 找不到记录 → 什么都不做 | 备注静默丢失 |
| audit/file | 同上，非空 body；不读 nonce | 每条写 3 次 |
| audit/alarm | 未实现，gin 回 404 | 4xx 不重试，静默丢弃 |

## 7. 意外与风险（影响实现方案）

1. **5xx 会让客户端白等 36 秒**（§1.3）。所有接口都要避免 5xx。另一个思路：porta-server 和 hbbs 同进程，可以在会合模块里实现 `HttpProxyRequest`，把请求转给进程内的 axum 路由。这样 HTTP 端口不通时 API 仍然可用；原版客户端已经带了这条回落路径。
2. **`session_id` 是 u64、`conn_id` 会复用**（§5.5）：表结构和关联逻辑要按这个设计。
3. **`user.name` 为空或登录响应缺 `user`**：客户端明明存了 token，却显示未登录（§2.2）。
4. **列表的 `total` 缺失或不是整数**：数据被忽略或面板报错（§3.1）。
5. **Dart 强类型**：字符串字段给了数字，整个组面板失败（§3.4）。SQLite 读出来的值要注意类型，比如用户名全是数字时别让它变成 int。
6. **sysinfo 回 `ID_NOT_FOUND` 会让客户端每 3 秒重传**（§4.1）。
7. **设备态接口可做弱校验**：uuid = base64(RegisterPk.uuid)（§1.6）。
8. **主控端在 `PunchHoleRequest.token` 里带了 access_token**（§1.5）：porta-server 可以知道是哪个账号在发起连接。再通过 `ControlledContext.conn_audit_ref` 下发给被控端，new 审计里就会带回这个引用，能把审计记录和账号关联起来。属于可选的增强。
9. **会话备注没有任何身份信息**，只靠随机 u64 的 session_id 做关联（§5.2.4）。
10. **conn 审计按连接串行**：服务端回包稍有不对，后续审计都会被推迟（§5.1）。
11. **响应不带 `charset=utf-8`**：客户端走 Rust 通路时，中文用户名可能乱码或解析异常【推测】（§1.4）。
