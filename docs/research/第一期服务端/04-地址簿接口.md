## 0. 实现清单（照这 12 条做，原版客户端就不会走错分支）

1. **9 个写接口成功时只能回 `HTTP 200` + 空 body**。200 带任何 body（`null`、`{}`、`{"code":0,...}`）都判失败，错误文本是 `"null"` 或 body 原文；`204` 也判失败。【读码 ab_model `_jsonDecodeActionResp` L2002-2026】
2. 失败统一回 `{"error":"<给人看的文本>"}`，状态码非 200（建议 400 / 403 / 404 / 409）。客户端显示 `error` 字段。
3. 4 个读接口（personal、settings、shared/profiles、peers）响应必须是 JSON 对象；`tags/<guid>` 必须是 JSON 数组，空时回 `[]`，不能回 `null`。
4. 分页响应必须带 `total` 键且为 int，否则该页 `data` 整个被忽略。必须按 `pageSize=100` 真分页或一次给全；**不能把每页上限压到 100 以下**（会丢条目）。
5. `/api/ab/personal` 对已登录用户永远回 `200 {"guid":"<非空字符串>"}`。不要回 `null` / `{}` / 404。
6. `/api/ab/settings`、`/api/ab/shared/profiles` 回 200；回 404 = 告诉客户端"不支持共享簿"。
7. shared/profiles 不包含个人簿；同一用户看到的簿 `name` 必须互不相同，且不能是 `My address book`、`Legacy address book`。
8. 类型：字符串字段给 JSON string 或省略；`rule`、`color`、`total`、`max_peer_one_ab` 给 JSON 整数（不能是 `2.0`、不能是 `"2"`）；`tags` 给字符串数组；`same_server` 只能是 bool 或省略。
9. tag 改名、删除时，服务端在同一事务里级联修改本簿所有 peer 的 `tags`。客户端不会逐个 update peer。
10. 权限只能靠服务端校验：只读簿里客户端仍可能调 `DELETE /api/ab/peer/<guid>` 和 `PUT /api/ab/peer/update/<guid>`（多选模式不看权限）。
11. `color` 是 Flutter ARGB 32 位无符号整数，客户端生成的值 alpha 恒为 0xFF，即 ≥ 4278190080，超过 i32。按 i64 存取、原样回传。
12. `401 + {"error":...}` 只用于 token 无效（客户端据此登出、清缓存）；没权限用 403。

## 1. 通用约定

### 1.1 请求形态【读码】
- 12 个接口都带 `Authorization: Bearer <access_token>`（`common.dart` `getHttpHeaders` L2729）和 `Content-Type: application/json`（各函数里设置）。token 为空时头是 `Bearer `。
- 5 个读接口（personal、settings、shared/profiles、peers、tags）：方法 POST，**body 为空**，显式头 `Content-Length: 0`（ab_model `_setEmptyBody` L2029；1.4.5 起才有，提交 7e3f0a60）。
  - axum 里这 5 个 handler **不能**用 `Json<T>` 提取器（空 body 会被拒），只用 `Query` / `Path` / 头。
- 两个 DELETE 接口带 JSON body（数组）。axum 的 `Json` 提取器对 DELETE 同样可用。
- 查询参数名精确为 `current`、`pageSize`（驼峰）、`ab`；值都是十进制字符串；`current` 从 1 开始；`pageSize` 客户端写死 100。
- guid 被直接拼进 URL：`"$api/api/ab/tags/${profile.guid}"` 后 `Uri.parse`（ab_model L1500、L1551 等），`ab=<guid>` 走 `queryParameters`。【建议】guid 只用 `[A-Za-z0-9-]`（UUID 即可）。
- 传输层：默认 Dart `http` 包；开了代理或 `enable-flutter-http-on-rust` 时转给 Rust `http_request_sync`（`utils/http_service.dart` `sendRequest`）。Rust 路径下 HTTP 失败或返回 **5xx** 时，满足条件会改走 hbbs TCP 代理回退（`src/common.rs` `with_tcp_proxy_fallback` L1579-1624），OSS hbbs 没这个能力。【建议】可预期的错误不要用 5xx。

### 1.2 三种响应解析器（决定成败的判据）【读码】

**A. 对象型** `_jsonDecodeRespMap(body, status)`（ab_model L1976-1987）——用于 personal、settings、shared/profiles、peers
- `jsonDecode(body)` 后赋给 `Map<String,dynamic>`。解析失败或不是对象（含 `null`、数组）→ 抛错，文本 = body（body 非空且 <128 字符时）否则异常文本；状态码非 200 时加前缀 `HTTP <code>, `。
- 调用方随后**先**查 `json.containsKey('error')` → 抛 `json['error']`，**再**查 `status != 200` → 抛 `'HTTP <code>'`。所以 `200 + {"error":..}` 也是失败。

**B. 数组型** `_jsonDecodeRespList(body, status)`（L1989-2000）——只用于 tags
- 必须是 JSON 数组，否则抛 body 原文（状态码非 200 时加前缀）。**不会单独读 `error` 字段**，错误体只是被当成"解析失败"原样显示。之后再查 `status != 200`。

**C. 动作型** `_jsonDecodeActionResp(resp)`（L2002-2026）——用于 9 个写接口
```
if (status == 200 && body.isEmpty)  → 成功
else:
  errMsg = jsonDecode(body)['error'].toString()     // 抛异常就吞掉，errMsg 保持 ''
  if errMsg 为空:
     status != 200 → errMsg = "HTTP <code>"
     body 非空     → errMsg 追加 body
     仍为空        → "unknown error"
```
- Dart 里 `null.toString()` 返回 `"null"`：`200 + {}`、`200 + {"code":0,"message":"success"}` → errMsg = `"null"` → 判失败。`200 + null` → `null['error']` 抛 NoSuchMethodError 被吞 → body 非空 → errMsg = `"null"` → 失败。
- 失败时的 UI：changeTagForPeers / changeAlias / changeNote / 设密码 / deletePeers / addTags / renameTag / setTagColor / deleteTag 弹红色 toast 显示 errMsg；addPeers 把 errMsg 当返回值，由「添加 ID」对话框显示在输入框下方或由 `addPeersToAbDialog` toast；syncFromRecent 只写调试日志。
- 动作型**不处理 401**（不会登出），只显示错误文本。

### 1.3 认证失败【读码】
- personal / settings / shared/profiles 出错且 `status == 401` → `gFFI.userModel.reset(resetOther: true)`（清 token、地址簿、组缓存），与 quiet 无关（ab_model `_setListPullError` L220-228）。
- peers / tags 拉取 401 → 只有非 quiet 拉取（会设置 `pullError`）才 reset（`_fetchPeers` finally L1489-1495、`_fetchTags` L1536-1542）。
- 列表错误条显示 `translate(err.toString())`：error 文本若恰好是翻译 key 会被本地化（如 `exceed_max_devices`）；动作型 toast 不翻译。

### 1.4 404 的特殊含义（只对 3 个接口）【读码】
| 接口 | 404 时客户端行为 |
|---|---|
| `POST /api/ab/personal` | 当成旧服务端：继续，`legacyMode = true`，改用 `GET/POST /api/ab`（Porta 不实现 → 地址簿报错）。L271-275 |
| `POST /api/ab/settings` | 静默返回，`_maxPeerOneAb` 保持 0（不限），继续。L239-242 |
| `POST /api/ab/shared/profiles` | 静默返回，只剩个人簿，继续。L320-324 |

其余接口的 404 只是普通失败。【建议】这 3 个接口永远不回 404；guid 不存在等情况在其他接口回 404 / 403 + error 都行。axum 未匹配路由默认 404，正好用于没实现的接口。

### 1.5 客户端版本差异（关系到现网旧安装）【读码：提交 ac124c06，`git tag --contains` 显示含于 1.4.7、1.4.8、1.4.9、1.5.0】
- **1.4.7 起**：personal 出现非 404 的任何错误（包括 `200 + null`、body 不是 JSON 对象）→ 记错误并**停止整个拉取**，不会退回 legacy。
- **1.4.6 及更早**：`_getPersonalAbGuid` 出错只是 guid 为空 → 落入 legacy 模式；shared/profiles 的 404 当普通错误被静默吞掉。
- `docs/research/03` §3.3 说"无 guid（null）也会落入 legacy"：对 `{"guid":null}` / `{}` 成立；对**字面 `null` body** 只在 ≤1.4.6 成立，1.4.7+ 是报错 `null` 并停止。
- 簿级默认共享密码 `info.password` 自 1.4.2 起（提交 5c9b4aba，`git tag --contains` 首个为 1.4.2）。
- `Content-Length: 0` 自 1.4.5 起才带；更早版本经 Rust/reqwest 发空 POST 时可能不带 Content-Length（reqwest#838）。【推测】前置 nginx 一般能接受，未验证。
- 结论：personal 永远回 `200 {"guid":"..."}`，新旧客户端都走新版。

### 1.6 分页循环（shared/profiles、peers 共用）【读码 `_getSharedAbProfiles` L304-350、`_fetchPeers` L1440-1482】
```
pageSize = 100; total = 0; current = 0
do {
  current += 1
  POST ...?current=<current>&pageSize=100[&ab=<guid>]
  （shared/profiles 独有）404 → return false，静默
  解析失败 / 含 error / 非 200 → 抛错，跳出循环（已收集的保留）
  if (json 含键 'total') {
     if (total == 0) total = json['total']        // 赋给 int：null、double、string 都会 TypeError
     if (json 含 'data' && data is List)
        逐条 fromJson，按键去重（peers 按 id，profiles 按 name），后来者覆盖
  }
} while (current * 100 < total)
```
- **没有 `total` 键 → 该页 data 完全不读**，循环结束。
- `total` 只在第一次非 0 时锁定；第 1 页 total=0 → 只拉 1 页（RA 的 shared/profiles 就是这样）。
- `data` 不是数组（含 `null`）→ 该页忽略，不报错。
- 任意一条元素字段类型不对 → TypeError → 整个接口失败（catch 在循环外）。
- 服务端忽略分页、每页都回全量 + 真实 total（RA peers 的做法）也能工作：客户端重复请求 ceil(total/100) 次，靠去重得到正确结果，只是浪费。
- 服务端若每页实际只给 <100 条而 total 真实 → 客户端第 2 页请求 `current=2`，服务端按 offset=50 之类给，**中间条目丢失**。

## 2. 类型严格性（Dart 侧解析）

规则：`json['x'] ?? 默认值` 赋给强类型字段时，值为 null 或缺键 → 用默认值；值的类型不对 → 运行时 TypeError → 所在接口整体失败（被 catch 成错误条）。

### 2.1 Peer（`/api/ab/peers` 的 `data` 元素）【读码 peer_model `Peer.fromJson` L33-48】
| 字段 | Dart 声明 | 解析 | 服务端必须给 |
|---|---|---|---|
| `id` | String | `?? ''` | string，非空 |
| `hash` | String | `?? ''` | string 或省略；个人簿给，共享簿省略 |
| `password` | String | `?? ''` | string 或省略；共享簿给明文，个人簿省略 |
| `username` / `hostname` / `platform` / `alias` | String | `?? ''` | string 或省略 |
| `tags` | List\<dynamic\> | `?? []` | 字符串数组；元素必须是 string（`getCurrentAbTagColor(String)` ab_model L734、`tagContainBy(String)` L949 拿到非 string 会 TypeError，渲染出错） |
| `note` | String | `is String ? v : ''` | 宽松；建议 string |
| `forceAlwaysRelay` | bool | `== 'true'` | 宽松；ab 页不读这个字段（右键菜单读本地 peer 选项），可省略 |
| `rdpPort` / `rdpUsername` / `loginName` / `device_group_name` | String | `?? ''` | string 或省略；ab 页不读（loginName、device_group_name 只在组面板用，`peers_view.dart` L575-591） |
| `same_server` | bool? | 直接赋值 | **只能是 bool 或省略**；int / string → TypeError |
| 其他键 | — | 忽略 | 可以多给 |

- `platform` 取值约定：`Windows`、`Linux`、`Mac OS`、`Android`、`WebDesktop`（`consts.dart` L37-41），决定图标。
- 在线状态不来自 API：客户端经会合服务器查询（`Peers._updateOnlineState`，peer_model L219），服务端不用回 `online`。
- `same_server: true` 的唯一作用：sync-from-recent 不再用本地会话信息覆盖该 peer 的 username/hostname/platform（ab_model L1692-1708）。【建议】第一期省略；以后服务端用 sysinfo 填设备信息时再给 true。

### 2.2 AbProfile（shared/profiles 的 `data` 元素）【读码 hbbs.dart `AbProfile.fromJson` L258-275】
| 字段 | Dart 声明 | 解析 | 要求 |
|---|---|---|---|
| `guid` | String | `?? ''` | string，非空，URL 安全 |
| `name` | String | `?? ''` | string；同一用户可见范围内唯一；不能是保留名 |
| `owner` | String | `?? ''` | string；UI 只在权限图标旁显示 `Owner: <owner>`（address_book L174-177，`owner != null` 恒真，空串也会显示）；RA 填用户名 |
| `note` | String? | `?? ''` | string 或 null / 省略；客户端存了但不显示 |
| `info` | dynamic | 原样 | 任意 JSON；客户端只读 `info is Map && info['password'] is String && 非空` 当簿级默认共享密码（ab_model `getdefaultSharedPassword` L843-863） |
| `rule` | int | `?? 0` | int 1 / 2 / 3；其他值 → 不可写、不显示权限图标 |

- 元素必须是 JSON 对象。

### 2.3 AbTag（`tags/<guid>` 数组元素）【读码 hbbs.dart `AbTag.fromJson` L277-286】
| 字段 | 解析 | 要求 |
|---|---|---|
| `name` | `?? ''` → String | string |
| `color` | `?? ''` → **int** | **必须是 int**。缺键 / null 时默认值写成了 `''`，赋给 int 字段 → TypeError → 整个 tags 接口失败 |

### 2.4 其他
- personal：`_personalAbGuid = json['guid']`（`String?`）。string 非空 → 新版；null / 缺键 → legacy；int → TypeError → 停止。其他键忽略。【读码 L284】
- settings：`_maxPeerOneAb = json['max_peer_one_ab'] ?? 0`（int）。缺键 → 0。【读码 L251】

## 3. 逐接口契约

### 3.1 `POST /api/ab/personal`
- 调用时机：每次"拉列表"——`_pullAb` 在 `!listInitialized || force == listAndCurrent` 时（登录后、刷新用户信息后 `user_model.dart` L165、进入地址簿 tab `peer_tab_page` L60）。每次都重读（注释："avoid upgrading the server without closing the main window"）。【读码 ab_model L146-153】
- 请求：无 query，空 body。
- 成功：`200 {"guid":"<个人簿 guid>"}`。只读 `guid`。
- 失败：见 1.2A、1.4、1.5；401 → 登出。
- 客户端拿到 guid 后自建个人簿 profile：`AbProfile(guid, "My address book", 当前用户名, null, rule=1, info=null)`；personal=true 时 `canWrite()` 恒 true，忽略 rule。【读码 L160-162、L1393-1400】
- 【建议】guid 对同一用户稳定；首次调用时懒建个人簿。

### 3.2 `POST /api/ab/settings`
- 调用时机：非 legacy 且 `_maxPeerOneAb == 0` 时，每次拉列表都调（所以回 0 就每次都调）。返回值被忽略：出错只设列表错误条，**不中止**拉取。【读码 L155-157】
- 请求：空 body。
- 成功：`200 {"max_peer_one_ab": 0}`。
- 语义：`isFull() = max > 0 && peers.length >= max`，**0 = 不限**。只用于客户端添加前检查（`addIdToCurrentAb`、`Ab.addPeers`）。【读码 L1387-1390、L1558】

### 3.3 `POST /api/ab/shared/profiles?current=N&pageSize=100`
- 请求：空 body。
- 成功：`200 {"total": <int>, "data": [AbProfile, ...]}`。
- 客户端合并逻辑【读码 L160-174、L338-345】：
  1. 列表先放客户端自建的个人簿 profile；
  2. 服务端每条按 `name` 合并（同名覆盖）；
  3. `addressbooks`（以 **name 为 key** 的 Map）删掉不在列表里的；已有的 `setSharedProfile`；新的建 `Ab(p, p.guid == personalGuid)`。
- 后果：
  - 两本同名 → 后者覆盖前者，前者在客户端不可见。
  - 共享簿名叫 `My address book` → 替换掉个人簿条目（personal=false），个人簿在客户端消失；Rust 侧 `AbEntry::personal()` 也按名字判断（hbb_common@5d52530 `src/config.rs` L2518-2520），本地缓存里会被当成个人簿读哈希密码。
  - 把个人簿也放进来（同 guid、不同 name）→ 出现两个条目，服务端那条 personal=true 但 key 是服务端的 name，显示和缓存都乱。
- 出错：设列表错误条后继续（只剩已收集到的簿）；401 登出；404 静默。
- 【建议】`data` = 当前用户拥有的共享簿（rule=3，owner=自己）+ 被授权的共享簿（多条授权取最大 rule）；建簿时禁止保留名；名字冲突时在返回里改名（例如 `名字 (owner)`）或建簿时全局唯一；一次返回全部、`total` = 条数。

### 3.4 `POST /api/ab/peers?current=N&pageSize=100&ab=<guid>`
- 调用时机：`Ab.pullAbImpl` 先 `_fetchPeers` 再 `_fetchTags`（L1412-1430）。触发：当前簿首次 / 强制刷新；当前不是个人簿时顺带初始化个人簿（L196-201）；**每次写操作之后**重拉（`pullNonLegacyAfterChange` L790-801；改个人哈希、改共享密码后也重拉 L448、L464）。不是当前、也不是个人的共享簿不会被拉取。
- 请求：空 body。
- 成功：`200 {"total": <int>, "data": [Peer, ...]}`，Peer 字段见 2.1。
- 失败：设 pullError（非 quiet 时显示），`initialized = false`，`peers` 置为已收集的部分（可能为空）。
- 【建议】输出：`id, alias, username, hostname, platform, tags（数组，绝不 null）, note`；个人簿加 `hash`；共享簿加 `password`（解密后的明文，没有就省略或 `""`）。只读用户也要拿到 `password`：客户端连接共享簿设备时用 `peer.password`，为空再用 `info.password`（peer_card `connectInPeerTab` L1541 起）。

### 3.5 `POST /api/ab/tags/<guid>`
- 请求：空 body，无 query（`Uri(scheme, host, path, port)` 不带 query，L1504-1509）。
- 成功：`200 [{"name":"<string>","color":<int>}, ...]`，**顶层是数组**；没有 tag 回 `[]`。客户端按 name 去重。
- 客户端：`tags` = 服务端返回顺序的 name 列表；`tagColors[name] = color`。新版模式下"Sort tags"菜单被隐藏，注释写"It's already sorted after pulling down"（address_book L428-429）→ 【推测】Pro 服务端按名字排序返回。【建议】按 name 排序。
- 失败：同 peers；错误体的 `error` 字段不会被单独提取，显示原文。

### 3.6 `POST /api/ab/peer/add/<guid>`
两个调用来源，body 不同【读码】：

**(a) 「添加 ID」对话框**（address_book `addIdToCurrentAb` L460 → ab_model `addIdToCurrent` L375-395）
```json
{"id":"<String>", "alias":"<String，trim 过，可为空串>", "tags":["<String>",...],
 "password":"<String>",   // 仅共享簿且非空才有
 "note":"<String>"}        // 仅非空才有
```
- 个人簿：`password` 在 `Ab.addPeers` 里被 `removePassword` 删掉（L1561-1565）；不带 `hash`。
- 客户端先用本地 peers 查重，已存在就提示 `ID already exists`，不发请求。

**(b) 「添加到地址簿」**（peer_card `_addToAb` 单个、peer_tab_page `addSelectionToAb` 多选 → dialog `addPeersToAbDialog` L2463）：每个 peer 发一次，body = `Peer.toJson()` 去掉 `password`、`hash`（peer_model `toJson` L50-68）：
```json
{"id":"..","username":"..","hostname":"..","platform":"..","alias":"..","tags":[..],
 "forceAlwaysRelay":"true|false",   // 字符串
 "rdpPort":"..","rdpUsername":"..","loginName":"..","device_group_name":"..",
 "note":"..",                        // 可为空串
 "same_server": true|false|null}
```
来源可以是最近会话、收藏、局域网发现、组面板、另一本地址簿。

**(a)(b) 共同点**
- `tags` 先经 `removeNonExistentTags` 过滤成目标簿**本地已知**的 tag（L406-408、L923-933）。目标簿没拉取过（非当前、非个人）时本地 tags 为空 → `tags` 被清成 `[]`。
- 客户端只跳过目标簿**本地** `peers` 里已有的 id（L1555-1557）。目标簿没拉取过时 peers 为空 → **重复 id 会发到服务端**。
- 逐条发送，遇到第一条失败立即返回 errMsg，后面的不再发（L1569-1572）。
- 发完重拉目标簿（`pullNonLegacyAfterChange(name: name)`）。
- 成功：`200` 空 body。
- 【建议】存 `id, alias, tags, note, username, hostname, platform`；个人簿忽略 `password`、带 `hash` 就存；共享簿存 `password`（加密）、忽略 `hash`；`forceAlwaysRelay / rdpPort / rdpUsername / loginName / device_group_name / same_server` 不存（客户端从不从地址簿读它们）；接受值为 `null` 的键和未知键；不要求 username/hostname/platform 存在（可选：缺失时从 sysinfo 设备表补，RA 就这么做）。
- 【建议】唯一约束 `(book, peer_id)`；重复 add 回 `200` 空 body（见 4.4）。

### 3.7 `PUT /api/ab/peer/update/<guid>`
body 一律是对象，`id` 必带，其余键是**部分更新**（只改出现的键）。全部调用点【读码】：

| 调用 | body | 哪种簿 | 代码 |
|---|---|---|---|
| 改标签（单个，或多选时每个 id 发一次） | `{"id","tags":[String...]}`，可为 `[]` | 可写簿 | ab_model L1581-1604 |
| 改别名 | `{"id","alias"}`，可为 `""` | 可写簿 | L1607-1625 |
| 改备注 | `{"id","note"}`，可为 `""` | 可写簿 | L1628-1646；dialog `editAbPeerNoteDialog` L2105 |
| 个人簿记住密码哈希 | `{"id","hash"}` | 仅个人簿 | L1669-1673。触发：连接成功、且密码不来自地址簿时 Rust 推事件 `sync_peer_hash_password_to_personal_ab`（`src/client.rs` 约 L3710-3722）→ `models/model.dart` L433；仅当该 id 已在个人簿 |
| 忘记密码 | `{"id","hash":""}` | 个人簿 | peer_card `_unrememberPasswordAction` L841 |
| 设置 / 修改共享密码 | `{"id","password":"<明文>"}` | 仅共享簿 | L1676-1679；dialog `setSharedAbPasswordDialog` L2575 |
| 删除共享密码 | `{"id","password":""}` | 共享簿 | dialog L2650（Remove 按钮） |
| 从最近会话同步 | `{"id","username"?,"hostname"?,"platform"?,"hash"?}`，值全是 string，至少一个；`hash` 仅个人簿 | 当前簿且可写 | L1682-1749 |

- 同步细节：桌面主窗口每 3 秒（500ms × 6）检查一次；条件是已登录、列表已初始化、当前簿已初始化且 canWrite、本地选项 `sync-ab-with-recent-sessions` 为 `Y`（L86-95、L582）。只更新簿里已有的 id，**不新增**（注释说明原因）；username / hostname / platform 仅当该 peer `same_server != true`、本地值非空且不同；hash 仅个人簿、本地非空且不同（L1690-1714）。客户端先改本地再发请求，失败不重试。
- `hash` = base64(32 字节加盐密码哈希)，和客户端本地 PeerConfig 里存的同一份（`src/ui_interface.rs` `peer_to_map` L787-803）；连接时直接 base64 解码当密码哈希用（`src/client.rs` `try_get_password_from_personal_ab` L4765-4787，读的是本地缓存里名为 `My address book` 的那本）。服务端当不透明字符串存。
- 多选改标签遇第一次失败就停并 toast。
- 成功：`200` 空 body。
- 【建议】可更新键：`alias, tags, note, username, hostname, platform`；个人簿加 `hash`；共享簿加 `password`（加密）。个人簿收到 `password`、共享簿收到 `hash` → 忽略。其他键忽略。id 不在簿里 → 404 + error。`hash:""` / `password:""` → 清空。

### 3.8 `DELETE /api/ab/peer/<guid>`
- body：JSON 数组 `["id1","id2",...]`。单个删除也是数组；多选一次发全部（ab_model L1752-1771；peer_card L822；peer_tab_page L418）。
- 成功：`200` 空 body。
- 【建议】同一事务删存在的、忽略不存在的，整体回 200。

### 3.9 `POST /api/ab/tag/add/<guid>`
- body：`{"name":"<String>","color":<int>}`，每个 tag 一次请求（L1776-1802）。
- name 来源：`abAddTag` 把输入按 `[\s,;\n]+` 拆分，拒绝 `Untagged`（及其译文）（address_book L680-706）。所以经这里来的名字不含空白、逗号、分号；改名接口则可以带空格。
- color：`str2color2(name, existing).value`，alpha 恒 0xFF（`common.dart` L1416-1446）。
- 客户端**不检查** tag 是否已存在（新版 `Ab.addTags` 无查重，`LegacyAb.addTags` 才查）→ 服务端会收到重名 add。遇第一次失败 toast 并停止后续 tag。
- 【建议】已存在 → `200` 空 body，不改颜色（幂等）。

### 3.10 `PUT /api/ab/tag/rename/<guid>`
- body：`{"old":"<String>","new":"<String>"}`。客户端预检：新名非空、与本地已有 tag 不重名（address_book L823-833；ab_model L1806-1810）。
- 客户端不改任何 peer，只调这个接口，然后重拉；成功后把 `selectedTags` 里的旧名换成新名（ab_model L508-520、L1805-1831）。
- 【建议】old 不存在 → 404 + error；new 已存在 → 409 + error；成功时同一事务把本簿所有 peer 的 `tags` 里的 old 换成 new（并去重）。

### 3.11 `PUT /api/ab/tag/update/<guid>`
- body：`{"name":"<String>","color":<int>}`（`Color.value`），只改颜色（L1834-1855）。
- 【建议】name 不存在 → 404 + error。

### 3.12 `DELETE /api/ab/tag/<guid>`
- body：JSON 数组，客户端恒发单元素 `["<tag>"]`（L1858-1876）。
- 客户端不改 peer，只重拉；新版也不从 `selectedTags` 里移除（`LegacyAb.deleteTag` 才移除）。
- 【建议】删 tag 并从本簿所有 peer 的 `tags` 中移除该名；不存在的名字忽略；`200` 空 body。

## 4. 问题逐条回答

### 4.1 共享簿 profile 字段；个人簿是否出现在 profiles
- `guid` string、`name` string、`owner` string（RA 填用户名 `user.Username`，客户端只显示）、`note` string 或 null（不显示）、`info` 任意 JSON（只读 `info.password`）、`rule` int。详见 2.2。【读码】
- 个人簿**不应**出现在 profiles：客户端自己用 personal 的 guid 构造个人簿条目（ab_model L160-162），profiles 里再出现会产生重复 / 混乱条目（见 3.3）。RA 也不包含（个人簿是 collection 0，不在 collection 表里）。【读码】

### 4.2 客户端怎么判断可写；只读簿里会不会仍调写接口
- `Ab.canWrite()`：个人簿恒 true；共享簿 `rule == 2 || rule == 3`（ab_model L1393-1400）。【读码】
- canWrite 控制的入口：标签栏菜单的 Add ID / Add Tag / Sync with recent sessions / Web 控制台（address_book L423-447）；标签的右键菜单 Rename / Change Color / Delete（L328-340）；peer 右键菜单的 Rename、Forget Password、共享密码、Edit Tag、Edit note、Delete（peer_card L1177-1205）；「添加到地址簿」的目标簿列表 `addressBooksCanWrite()`；后台 sync（ab_model L91、L586）。【读码】
- **漏网的入口**：多选模式的「删除」和「编辑标签」按钮不看 canWrite（peer_tab_page `deleteSelection` L385 只排除组 tab；`editSelectionTags` L478 只看是否在地址簿 tab、tag 是否为空），进入多选（L248）也不看权限。→ 只读簿里用户能触发 `DELETE /api/ab/peer/<guid>` 和 `PUT /api/ab/peer/update/<guid>`（tags）。服务端必须按 rule 拒绝（403 + error，客户端 toast）。【读码】

### 4.3 "完全控制"(3) 比"读写"(2) 多什么
- 客户端：`fullControl()` 有定义（ab_model L1403-1409），全仓库没有任何调用（grep 只有定义处）；`ShareRule` 只用于权限图标和提示文字。→ **客户端对 2 和 3 没有任何行为差别**。【读码】
- RA：删除 peer、删除 tag 要求 3，其余写操作要求 2（ab.go `PeerDel` L642、`TagDel` L306）。【读码】
- Pro 服务端里 3 多出什么：【推测】大概是在 Web 控制台管理簿本身（共享设置等），没有一手来源。
- 【建议】Porta：2 = 簿内 peer / tag 的全部增删改；3 = 再加管理簿本身（改名、成员），第一期簿管理走命令行，所以 12 个接口里 2 和 3 等价。若照搬 RA（删除要 3），rule=2 的用户会看到删除菜单、点了却报错。需要主会话拍板。

### 4.4 同一本里重复 add 同一 id
- 客户端意图是不重复：「添加 ID」先本地查重；`Ab.addPeers` 跳过本地已有的 id。旧版 `LegacyAb.addPeers` 遇到已有 id 走 `_merge`（hash / username / hostname / platform 非空才覆盖，alias 只在旧值为空时填，tags 不动）（ab_model L1100-1124、L1206-1212）。【读码】
- 实际会到达服务端的重复：目标簿没被拉取过（非当前、非个人）时本地 peers 为空；或别的设备刚加过、本地还没刷新。【读码推导】
- 服务端若报错：批量添加在第一条重复处中止，后面的 peer 不再加，并弹错误。【读码 L1569-1572】
- 【建议】唯一约束；重复 add 回 200 空 body，要么不动、要么按 `LegacyAb._merge` 规则合并（推荐不动，最简单）。

### 4.5 tag 改名 / 删除时 peers 的 tags 谁负责改
- 新版客户端只调一次 rename / delete 接口，然后重拉，**不会**逐个 update peer（ab_model L508-534、L1805-1876）。【读码】
- 旧版 `LegacyAb` 在本地做了级联（rename 替换所有 peer 的 tags L1253-1281，delete 从所有 peer 移除 L1292-1305），说明预期语义是级联。【读码】
- 不级联的后果：peer 上留着已不存在的 tag，卡片按名字哈希配色显示，标签栏里没有它，用户无法通过标签菜单清理（只能逐个 Edit Tag）。
- → **服务端负责级联**。

### 4.6 "在 Web 控制台管理"菜单打开的 URL
- 文案 key `ab_web_console_tip`（en：`More on web console`，`src/lang/en.rs` L208；cn：`打开 Web 控制台以执行更多操作`，`src/lang/cn.rs` L578）。
- 显示条件：非 legacy 且 `current.canWrite()`。
- 打开 `await bind.mainGetApiServer()` 的返回值本身——api-server 根地址，不带任何路径，例如 `http://host:21114` 或 `https://rd.example.com`；先 `canLaunchUrlString` 再 `launchUrlString`（address_book L432-441）。【读码】
- → Porta 在 API 端口的 `GET /` 放说明页（架构 §3.6 已定）。

### 4.7 `max_peer_one_ab = 0` 是否表示不限
- 是。`isFull()` 为 `_maxPeerOneAb > 0 && peers.length >= _maxPeerOneAb`（ab_model L1387-1390）。RA 也固定回 0 并注释"0 表示不限制"。【读码】

## 5. 请求序列（新版模式）
进入地址簿 / 登录后：
1. `POST /api/ab/personal` → guid
2. `POST /api/ab/settings`（回 0 时每次都调）
3. `POST /api/ab/shared/profiles?current=1&pageSize=100`（循环到 `current*100 >= total`）
4. 当前簿：`POST /api/ab/peers?current=1&pageSize=100&ab=<g>`（循环）→ `POST /api/ab/tags/<g>`
5. 当前簿不是个人簿、且个人簿未初始化：个人簿再走一遍第 4 步

每次写操作：写接口 → 当前簿（或 add 的目标簿）再走第 4 步。
启动时先读本地缓存（个人簿 + 当前簿）显示（ab_model `loadCache` L641、`_serializeCache` L617-632，缓存只对个人簿存 hash）。

## 7. 意外与风险（影响实现方案的）
1. **写接口成功必须 200 + 空 body**，axum 习惯性回 `Json(...)` 或 204 都会被原版客户端当失败。建议在 API 模块里给地址簿写接口统一一个"空 200"返回类型。
2. **personal 回 `null` 不再回退 legacy**（1.4.7+）：`docs/research/03` §3.3 的"无 guid（null）也会落入 legacy"对新客户端不准确，Porta 不能靠这条做退化。
3. **客户端按簿名做主键**：重名、保留名会让簿在客户端消失甚至顶替个人簿。命令行建簿 / 改名时必须校验，profiles 输出时要保证唯一。
4. **只读簿仍可能收到写请求**（多选模式）：权限校验不能省。
5. **tag 级联必须服务端做**：RA 没做，现网数据里大概率已有孤儿 tag，迁移要清理。
6. **tag/add 重名、peer/add 重复 id 都是常态**（客户端不查重或只查本地缓存），报错会中断批量操作，建议幂等返回成功。
7. **rule 2 和 3 在客户端没区别**：Porta 若沿用 RA"删除要 3"的语义，rule=2 用户会遇到"看得见、点不了"。需要主会话定。
8. **color 超 i32**：SQLite INTEGER 是 i64 没问题，但 Rust 结构体字段别用 i32 / u32 以外的窄类型；用 i64 最省事。
9. **分页不能压小页**：服务端若对 pageSize 设上限（例如 50），客户端会丢条目；要么按 100 分页，要么一次给全。
10. **共享簿明文密码对只读成员可见**：这是客户端连接所需（`connectInPeerTab`），服务端加密只防落盘泄露，挡不住有读权限的成员——和架构 §3.6 的描述一致，只是提醒权限分配时要知道这一点。
