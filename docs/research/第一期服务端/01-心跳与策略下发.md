# 01 · 心跳、sysinfo 与策略下发（字段级契约）

基线：客户端 `rustdesk@bd92623`（Cargo 版本 1.5.1），hbb_common 钉在 `5d52530`（客户端仓库里 `libs/hbb_common` 已检出到这个提交，下文 config.rs / lib.rs 行号都按它）；选项键名常量在客户端自己的 `libs/base/src/config/keys.rs`（hbb_common 只留它自己用到的几个，其余在 base 里）。
服务端对照：原版 hbbs `rustdesk-server@873230e`，第三方 API `rustdesk-api@c5687e1`。
对旧版本的核对：用 `git show <tag>:path` 看了 1.4.2、1.4.6、1.5.0 的 `src/hbbs_http/sync.rs` 和 `src/common.rs`，心跳/sysinfo/策略逻辑从 1.4.2 到 bd92623 基本没变，差异在 §3.4 末尾单列。

标记：【读码】= 读了代码，附位置；【推测】= 推理或未验证。

## 0. 结论速览（给写代码的人）

1. 心跳 `POST {api}/api/heartbeat`，body `{"id","uuid","ver","conns"?,"modified_at"}`；有入站连接约每 3 秒一次，没有时名义 15 秒（按代码推算实际约 18 秒）。
2. 响应里的 `strategy` **只要出现就会被应用**，客户端不拿 `modified_at` 做判断。服务端必须自己控制：**仅当请求里的 `modified_at` != 服务端该设备当前策略版本时，才同时下发 `modified_at` 和 `strategy`**。版本号必须是 ≥1 的整数（0 是客户端"从没收到过"的默认值）。
3. `strategy.config_options` 写进的是 **Config（全局选项，RustDesk2.toml 的 `[options]`）**，而且是在跑心跳的那个进程里写。Windows 安装版里这是以 SYSTEM 身份跑的 `--server` 进程。
4. 下发 `relay-server: ""` 对原版客户端有效：键被删掉，被控端下一次收到打洞请求时现读、回退到 hbbs 给的中继。
5. **`enable-ipv6-punch` / `enable-udp-punch` 没法经心跳策略打开**：它们是 LocalConfig 选项，只有控制端读，而且读的是控制端用户进程自己的 RustDesk_local.toml。被控端根本不检查这个开关。另外**原版 hbbs 不转发 `socket_addr_v6`**，porta-server 必须补上转发，否则 IPv6 打洞对谁都不通。详见 §4 和 §9。
6. sysinfo 回纯文本 `SYSINFO_UPDATED`，必须逐字节相等（不能带换行，也不能带 JSON 引号）。**不要对"未知设备"回 `ID_NOT_FOUND`**：客户端会每 3 秒重传一次。

## 1. 心跳请求

### 1.1 谁发、何时发【读码】
- 心跳线程由 `RendezvousMediator::start_all` 启动：`rustdesk@bd92623:src/rendezvous_mediator.rs` L281 `crate::hbbs_http::sync::start()`。也就是说它跑在**运行会合中介（被控服务）的那个进程里**。
  - Windows 安装版：服务以 `"<exe>" --server` 拉起 `--server` 进程，用的是 winlogon 的令牌，即 SYSTEM 身份（`src/platform/windows.rs` L813-823 `launch_server` → `launch_privileged_process`）。
  - SYSTEM 进程的配置目录被 `patch()` 改写到 `C:\Windows\ServiceProfiles\LocalService\AppData\Roaming\RustDesk\config\`（hbb_common `src/config.rs` L460-467 `fn patch`）。所以心跳写的 Config 和 LocalConfig 都在这个目录下，不是用户 `%APPDATA%` 那份。
  - 便携版（未安装）：UI 进程连不上 IPC 时自己 `start_server(true, …)`（`src/server.rs` 约 L745），心跳就跑在 UI 进程里【推测：没跟到底】。
- **不发心跳的情况**：
  - `conn-type=outgoing`（仅主控的定制客户端）：`start_all` 在 L276-280 死循环，根本不调 `sync::start()`。
  - `heartbeat_url()` 返回空：内置选项 `register-device=N`（`Config::no_register_device()`，common.rs L1224），或者 API 地址是官方的 `*.rustdesk.com`（`is_public`）。sync.rs L281-290；这时还会把 `PRO` 置 false（L100-103）。
  - `stop-service` 为 `Y`（sync.rs L104-106）。
- 定时器：`interval_at(now+3s, 3s)`，再套一层 `ThrottledInterval`（两次 tick 至少隔 2.7 秒，不会补发积压的 tick；common.rs `ThrottledInterval`）。第一次 tick 在启动后 3 秒。sync.rs L88-91、L18-20。
- 每次 tick 的顺序：算 url/id → 检查 `stop-service` → 取 `conns` → 视情况**先**上传 sysinfo（见 §5）→ 判断这次发不发心跳 → 发心跳 → 处理响应。整个循环是串行的，HTTP 超时 12 秒（common.rs L1728），所以服务端处理慢会直接拖慢心跳节奏。
- 发送条件（L232-235）：`conns` 为空，且距上次发送不到 `TIME_HEARTBEAT=15s`，就跳过。
  - 有连接：每个 tick 都发，约 3 秒一次。
  - 无连接：名义 15 秒。但 `last_sent` 是在 tick 之后、做完 `get_sysinfo()` 才记的时间（L235），第 5 个 tick 时 elapsed 比 15 秒略少，要等到第 6 个 tick 才发，**实际约 18 秒一次**【推测：按代码推算，没实测】。服务端判离线的阈值建议 ≥ 45~60 秒。

### 1.2 URL【读码】
- `heartbeat_url()` = `get_api_server(Config::get_option("api-server"), Config::get_option("custom-rendezvous-server")) + "/api/heartbeat"`（sync.rs L281-290）。每个 tick 都重新算，改了 `api-server` 下一个 tick 就生效。
- `get_api_server`（common.rs L1223-1266）：
  - Windows 下"从 exe 文件名解析出的 license"里的 api 优先，其次 `api-server` 选项。
  - 都为空时从会合服务器地址推：端口减 2；没写端口就是 `http://host:21114`。
  - 末尾的 `/` 会被去掉。
  - `https://…:21114` 会被去掉 `:21114`，除非内置选项 `allow-https-21114=Y`。
- 同一个 URL 把 `heartbeat` 字符串替换掉，就得到 `.../api/sysinfo`、`.../api/sysinfo_ver`（L193、L211）。

### 1.3 请求头与传输【读码】
- `POST`，`Content-Type: application/json`，**不带 Authorization**（header 参数是 `""`），超时 12 秒（common.rs `post_request_` L1710-1730）。
- HTTP 状态码会被丢弃，只取 body 文本（`post_request_http` 返回 `(status, text)`，`with_tcp_proxy_fallback` 最后只留 text，common.rs L1557-1633）。所以对客户端来说，4xx/5xx 和 200 没区别，只看 body。
- 连接失败或 5xx 时，如果没开 WebSocket、且目标 host 等于配置的 API host，会**回落到"经 hbbs TCP 代理"**：连 hbbs 的 21116，走 `secure_tcp` 后发 `RendezvousMessage.http_proxy_request`（`HttpProxyRequest{method,path,headers,body}`），等 `http_proxy_response`（common.rs L1344-1348 `can_fallback_to_raw_tcp`、L1420-1475 `tcp_proxy_request`；proto 字段 27/28）。原版 hbbs 不认这条消息，客户端只是白等一段时间、然后报错。porta-server 可以以后再实现它（把请求转给进程内的 API 模块），第一期不做也不影响功能【推测】。

### 1.4 请求体字段【读码：sync.rs L236-244】

| 字段 | JSON 类型 | 来源 | 何时出现 |
|---|---|---|---|
| `id` | string | `Config::get_id()`（为空时当场生成） | 总是 |
| `uuid` | string | `crate::encode64(hbb_common::get_uuid())`，标准 base64、带 `=` 填充 | 总是 |
| `ver` | integer (i64) | `hbb_common::get_version_number(crate::VERSION)` | 总是 |
| `conns` | array of int (i32) | `Connection::alive_conns()` | **只在非空时**出现 |
| `modified_at` | integer (i64) | `LocalConfig::get_option("strategy_timestamp").parse::<i64>().unwrap_or(0)` | **总是**出现，从没存过就是 0 |

- `ver` 的算法（hbb_common `src/lib.rs` L264-289 `get_version_number`）：
  - 先按 `-` 切开。第一段按 `.` 逐段 `n = n*1000 + x`，然后把最后一段从个位挪到十位（`n -= last; n += last*10`）。第二段（`-` 后的数字）作为补丁号直接加上，解析失败就当 0。
  - 例：`1.4.2` → 1004020，`1.5.1` → 1005010，`1.1.10` → 1001100，`1.4.2-3` → 1004023。
  - `crate::VERSION` 是构建时由 `hbb_common::gen_version()` 从 Cargo.toml 的 `version` 生成的字符串（lib.rs L228-247）。
- `conns` 的含义【读码】：
  - 是被控端本进程**所有入站连接**的 id，**包括还没通过认证的**（`src/server/connection.rs` L6851-6871 `raii::ConnectionID`，注释写"all connections, including unauthorized connections"）。
  - id 是进程内计数器：`Server::new()` 里初值 `rand::random::<i32>() % 1000 + 1000`（范围 1~1999），每来一个连接 +1（`src/server.rs` L136、L536-539）。进程重启就重新随机，所以**服务端必须按设备 id 区分 conn_id，而且它不是全局唯一的**。
  - 同一个 id 也出现在审计接口的 `conn_id` 里（connection.rs L1566、L1614、L1640）。
- 服务端解析建议（Rust/serde）：

```rust
#[derive(Deserialize)]
struct HeartbeatReq {
    id: String,
    uuid: String,
    #[serde(default)] ver: i64,
    #[serde(default)] conns: Vec<i32>,
    #[serde(default)] modified_at: i64,
    // 不要 deny_unknown_fields：将来 Porta 客户端会加字段（见 §6）
}
```

## 2. 心跳响应

### 2.1 客户端的解析流程【读码：sync.rs L249-273】
- 请求失败（`Err`）：节流打一条 warn 日志，什么都不做。
- body 用 `serde_json::from_str::<HashMap<&str, Value>>` 解析。**不是 JSON 对象就整条忽略**（不报错）。
- 然后**按下面的固定顺序**从 map 里取键，和 JSON 里的键序无关：
  1. **`sysinfo`**：只看键在不在，值是什么都行（`true`、`1`、甚至 `null` 都算存在）。存在就 `info_uploaded.uploaded = false`，把 `Status` 里的 `sysinfo_hash` 清空。效果是**下一个 tick（约 3 秒后）重传 sysinfo**（因为成功上传后 `last_uploaded` 是 `None`，不受 120 秒退避限制）。
  2. **`disconnect`**：按 `Vec<i32>` 解析，失败就忽略。成功就广播给本进程所有连接（`SENDER`，broadcast 容量 16）。格式见 §8。
  3. **`modified_at`**：按 `i64` 解析（必须是 JSON 整数；字符串 `"123"` 或浮点数会解析失败、被静默忽略）。和本次请求发出去的 `modified_at` 不同时，`LocalConfig::set_option("strategy_timestamp", v.to_string())`。
  4. **`strategy`**：按 `StrategyOptions` 解析，成功就打日志 "strategy updated"，然后 `handle_config_options(strategy.config_options)`。**`extra` 解析了但没人用**（全仓库只有结构体定义处出现，见 sync.rs L45-51）。

### 2.2 先后顺序和"每次都带 strategy 会怎样"【读码】
- 顺序是**先存 `strategy_timestamp`、再应用 `strategy`**，两者互相独立：
  - `strategy` **不看 `modified_at`**：响应里有 `strategy` 就应用，哪怕 `modified_at` 没变、甚至没带。
  - `modified_at` 不看 `strategy`：单独回一个 `modified_at` 也会被存下来（可以拿来"确认版本"）。
- 坑一：`modified_at` 先落盘，`strategy` 后解析。如果 `strategy` 解析失败（例如 `config_options` 里有非字符串的值，或者 `strategy` 是 `null`），时间戳已经更新了，这份策略被静默丢弃（没有日志），而且**之后不会重试**，除非服务端再改版本号。
- 坑二：如果服务端每次心跳都带同一个 `strategy`：
  - 客户端每次都会重新执行 `handle_config_options`。磁盘不一定写：`Config::set_options` 在新旧 map 相等时直接 return（hbb_common config.rs L1232-1240）。
  - 但**语义上会每 15~18 秒（有连接时每 3 秒）把这些键强制改回下发值**，用户在本地改了也会被覆盖。日志也会每次刷 "strategy updated"。
  - 带了 `strategy` 却不带 `modified_at` 是最坏的情况：客户端的时间戳不变，下次照旧发旧值，服务端照旧推，形成每次都推的循环。
- **服务端下发规则（建议，可直接实现）**：
  - 每台设备维护一个"生效策略版本号" `rev: i64`，取值 ≥1。全局策略改了、或者这台设备的单独策略改了，就递增。命令行再提供一个"强制重推"子命令，单纯递增 `rev`。
  - 条件：**`req.modified_at != rev`** 时，响应里**同时**带 `"modified_at": rev` 和 `"strategy": {"config_options": {...}}`。否则两者都不带。
  - 用 `!=` 而不是 `<`：`strategy_timestamp` 存在客户端的 LocalConfig 里，换服务器、服务端数据库重置、客户端以前连过 Pro 服务器（时间戳量级可能完全不同）都会让它"比服务端还大"，用 `<` 会永远推不下去。
  - `rev` 不能用 0：0 是客户端没存过时的默认值，用 0 的话新设备永远收不到策略。
  - 想"什么都不改、只登记版本"时，可以回 `{"modified_at": rev, "strategy": {"config_options": {}}}`，空 map 等于不改任何键。
  - 响应丢了也没关系：客户端没收到就不会存时间戳，下次照旧带旧值，服务端会再推一次，天然幂等。

### 2.3 响应体建议格式

```json
{
  "modified_at": 7,
  "strategy": { "config_options": { "relay-server": "" } },
  "sysinfo": true,
  "disconnect": [1234]
}
```
- 总是回 HTTP 200 + JSON 对象（没东西要下发就回 `{}`）。状态码客户端不看，但 200 方便排障。
- 任何键都不要给 `null`。`config_options` 的值一律是字符串，`"Y"`/`"N"`/`""`，数字也要写成字符串。
- 不要发 `extra`（原版客户端忽略它）；Porta 自己的东西以后另起键名。

## 3. `handle_config_options` 的精确语义

### 3.1 代码【读码：sync.rs L292-309】
```rust
let mut options = Config::get_options();                 // 当前全局选项（合并了默认和覆盖层）
let default_settings = config::DEFAULT_SETTINGS.read().unwrap().clone();
for (k, v) in config_options {
    if v.is_empty() && default_settings.get(k).map_or("", |v| v).is_empty() {
        options.remove(k);                               // 空值且无内置默认 → 删键
    } else {
        options.insert(k, v);                            // 非空，或空值但有非空内置默认 → 写入（可能是 ""）
    }
}
Config::set_options(options);
```

### 3.2 写到哪里【读码】
- 写的是 **Config 的全局选项**，即 `CONFIG2.options`，落盘到 `RustDesk2.toml` 的 `[options]`（hbb_common config.rs L1220-1240）。**不是 LocalConfig**。
- 键不受白名单限制，任意字符串都能写进去，但只有读 `Config::get_option` 的地方才会受影响。
- 是**增量合并**：只改 `config_options` 里列出的键，其余选项原样保留。要"撤销"以前推过的键，就再推一次空值。
- `Config::get_options()`（L1220-1225）= `DEFAULT_SETTINGS` ← `CONFIG2.options` ← `OVERWRITE_SETTINGS` 依次覆盖合并。
- `Config::set_options()` 先 `purify_options`，用 `is_option_can_save` 过滤（L1227-1240、L2757-2770）：
  - 键在 `OVERWRITE_SETTINGS` 里 → 丢掉（定制客户端锁死的键，服务端推了也没用）。
  - 值等于 `DEFAULT_SETTINGS` 里的默认值 → 丢掉（不存，读的时候自然回落到默认）。
  - 过滤后和内存里的 map 相等就直接 return，不写盘。
- 写完**立即在本进程生效**：`Config::get_option` 每次都现读内存里的 `CONFIG2`（L1242-1250 `get_or(OVERWRITE, CONFIG2.options, DEFAULT)`）。
- UI 进程每秒经 IPC 拉一次 `Options(None)`（`src/ui_interface.rs` L1436），UI 显示的选项最多晚 1 秒跟上。

### 3.3 "内置默认值"是什么【读码】
- 指 `config::DEFAULT_SETTINGS`（hbb_common config.rs L76），也就是定制客户端配置里 `default-settings` 中属于 `KEYS_SETTINGS` 的那些键。由 `read_custom_client` → `read_custom_client_advanced_settings` 填充（`src/common.rs` 约 L2490-2640）。
- 定制客户端配置要用 RustDesk 官方私钥签名（`read_custom_client` 里用固定公钥 `5Qbw…` 验签），所以**原版客户端的 `DEFAULT_SETTINGS` 是空的**。对原版客户端来说，空值一律删键。
- 同类的还有 `OVERWRITE_SETTINGS`（`override-settings`）、`DEFAULT_LOCAL_SETTINGS`/`OVERWRITE_LOCAL_SETTINGS`（LocalConfig 用）、`BUILTIN_SETTINGS`、`HARD_SETTINGS`。原版客户端都是空的。

### 3.4 对几个具体键的效果

| 键 | 选项所属 | 推 `""` 的效果 | 推 `"Y"` 的效果 | 依据 |
|---|---|---|---|---|
| `relay-server` | Config（`KEYS_SETTINGS`，base keys.rs L325） | 键被删除。被控端下次处理打洞请求时 `get_relay_server` 读到空，回退到 hbbs 给的中继 | 写成固定中继地址（推地址字符串时） | 【读码】见下 |
| `enable-ipv6-punch` | **LocalConfig**（`KEYS_LOCAL_SETTINGS`，keys.rs L261） | 会写进/删掉 **Config** 里一个没人读的同名键，**没有效果** | 同左，**没有效果** | 【读码】§4 |
| `enable-udp-punch` | **LocalConfig**（keys.rs L260） | 同上，**没有效果** | 同上，**没有效果** | 【读码】§4 |

- `relay-server` 的读取方（全仓库 `"relay-server"`/`OPTION_RELAY_SERVER` 的读取只有这几处）：
  - 被控端 `src/rendezvous_mediator.rs` L1321-1331 `fn get_relay_server`：本地 `Config::get_option("relay-server")` 优先 → hbbs 下发的 `relay_server` → `会合host:端口+1`。
  - 调用点：`handle_punch_hole`（L1110）和 `handle_intranet`（L762），**每收到一次 `PunchHole`/`FetchLocalAddr` 就现读一次**。heartbeat 和会合中介在同一个进程，所以策略写完，下一次连接就用新值【读码；端到端没实测】。
  - **`handle_request_relay`（L661-686）不经过 `get_relay_server`**，直接用 `RequestRelay.relay_server`，也就是控制端/hbbs 给的值。所以"本地写死中继"只影响 `PunchHole`/`FetchLocalAddr` 这两条路径。
  - `hbb_common/src/websocket.rs` L487 也读它，只在 WebSocket 模式下用来拼中继的 ws 地址。
  - 控制端（`src/client.rs`）不读 `relay-server`，中继地址用 hbbs 回的 `PunchHoleResponse.relay_server`/`RelayResponse.relay_server`（client.rs L1026、L1126）。
- 1.4.x 的差异【读码：`git show 1.4.2/1.4.6:src/hbbs_http/sync.rs`】：
  - `handle_config_options` 里是 `if v.is_empty() { options.remove(k) }`，没有 `DEFAULT_SETTINGS` 那层判断。对原版客户端效果完全一样。
  - 1.4.2 的 `heartbeat_url` 用 `url.contains("rustdesk.com")` 判断官方服务器，`is_public` 也是这个实现。
  - 1.4.2 缺 `preset-address-book-alias/password/note`、`preset-device-username/name`、`preset-note` 这几个 sysinfo 字段。
  - 心跳字段、间隔、响应处理顺序都一样。

### 3.5 其他副作用【读码】
- 心跳路径改选项**不会触发 `CheckIfRestart`**。IPC 改选项时会 new 一个 `CheckIfRestart`，drop 时如果发现会合服务器、`api-server`、ws、`disable-udp` 等变了，就重启会合中介（`src/ipc.rs` L773-818、L1035-1048）；心跳路径没有这一步。
  - 所以经策略改 `custom-rendezvous-server`、`key` 这类键，不会立刻重连，要等会合连接自己断开重连、或者进程重启才生效【推测：生效时机】。`relay-server` 每次现读，不受影响。
- 竞态：UI 改设置时，会把它缓存的**整张** options 表经 IPC 推给服务进程（`ui_interface::set_option` L423-462）。如果正好落在策略写入后的 1 秒缓存刷新窗口里，策略写的值可能被旧缓存覆盖回去【推测：理论窗口，概率很低】。
- 安全面：服务端能推任意 Config 选项，包括 `whitelist`、`approve-mode`、`verification-method`、`api-server`、`custom-rendezvous-server`、`key`，等于有远程改配置的完全能力。客户端唯一的保护是 HTTPS 证书校验（`allow-insecure-tls-fallback` 默认关，hbb_common `tls.rs` L84-87）。这一点要写进 Porta 的威胁模型【读码】。

## 4. IPv6 / UDP 打洞开关：到底谁读、读哪里

### 4.1 读取逻辑【读码】
- `src/common.rs` L1294-1299 `get_ipv6_punch_enabled()` = `option2bool("enable-ipv6-punch", get_local_option("enable-ipv6-punch"))`。UDP（L1287-1292）、WebRTC 同理。
- `get_local_option`（common.rs L1308-1323）：
  - 读 **`LocalConfig::get_option(key)`**（hbb_common config.rs L2200-2208：`OVERWRITE_LOCAL_SETTINGS` → `LOCAL_CONFIG.options` → `DEFAULT_LOCAL_SETTINGS`，**不会回落到 Config**）。
  - 对 `enable-udp-punch`、`enable-ipv6-punch`、`enable-webrtc` 三个键：值为空、且 `!is_public(Config::get_rendezvous_server())`（会合服务器不是 `rustdesk.com` 或 `*.rustdesk.com`）时，返回 `"N"`。官方服务器上为空则返回 `""`，即视为开启。
- `option2bool`（hbb_common config.rs L2826-2838）：`enable-` 开头的键，值 `!= "N"` 就算开启。所以 `"Y"` 或任何非 `"N"` 的非空值都算开。
- UI 上的开关：桌面设置页的 "Enable IPv6 P2P connection" 复选框（`flutter/lib/desktop/pages/desktop_setting_page.dart` L629-633，`isServer: false` 表示是本地选项）。勾选写入的值是 `"Y"`，取消写 `"N"`（`flutter/lib/common.dart` L1632 `bool2option`，这三个键被特意排除在 `enable-*` 默认规则外）。
- 命令行 `--option k v` 走 `ipc::set_option`，写的是 Config，同样改不了这三个键（`src/core_main.rs` 约 L523）。

### 4.2 谁读这个开关【读码】
- **控制端（发起方）读**，全仓库只有 `src/client.rs` 用到：
  - L361-366 `tcp_punch_allowed`：其他直连方式都关掉时，TCP 打洞兜底。
  - L492：测 IPv6。
  - L518：开了才绑 v6 socket，把自己的 v6 地址放进 `PunchHoleRequest.socket_addr_v6`。
  - L1038：收到 `PunchHoleResponse.socket_addr_v6`、且自己有 v6 socket 时，才去连对方的 v6 地址。
- 控制端的会话跑在**用户的 UI 进程**里，读的是用户自己的 `%APPDATA%\RustDesk\config\RustDesk_local.toml`。
- **被控端不检查任何开关**：`src/rendezvous_mediator.rs` L1097 `let punch_v6 = peer_addr_v6.port() > 0 && !relay;`（`relay` = 本机走 ws 或代理，或者 `PunchHole.force_relay`）。`FetchLocalAddr` 路径（L769）同理。1.4.2、1.4.6、1.5.0 都一样【读码：git show 各 tag】。
- 结论：
  - 心跳策略写的是 Config，在 Windows 安装版上还是 SYSTEM 进程的 Config。无论怎么推，都改不到控制端用户进程的 LocalConfig，**原版客户端没法经心跳打开 IPv6/UDP 打洞**。
  - 推了 `enable-ipv6-punch: "Y"` 也无害，只是在 SYSTEM 的 RustDesk2.toml 里多一个没人读的键。
  - 被控端也不需要打开任何开关。

### 4.3 第一期要让原版客户端用上 IPv6 打洞，实际要做的【读码 + 推测】
1. **服务端**：porta-server 必须补上原版 hbbs 缺的 v6 字段转发（见 §9 风险 1）。这是必要条件。
2. **控制端**：每台发起控制的机器上，由用户手动勾选 "Enable IPv6 P2P connection"（写 LocalConfig `enable-ipv6-punch = "Y"`）。也可以在客户端退出后手改 `RustDesk_local.toml` 的 `[options]` 里加 `enable-ipv6-punch = 'Y'`；运行中改会被内存里的配置覆盖回去【推测】。
3. **被控端**：什么都不用做；有公网 IPv6 就行（`start_ipv6` → `crate::get_ipv6_socket()`）。
4. **Porta 客户端**：可以把这三个键的私服默认值改成 `"Y"`，或者让 `get_local_option` 认服务端下发的值。这是第二期客户端改动【推测】。
- 不要打开 `enable-udp-punch`：架构文档 §3.8 已经说明现版 hbbs 会丢 UDP 来的 `PunchHoleSent`。另外原版 hbbs 连 `udp_port` 都不转发，UDP 打洞本来就不通（§9 风险 1）。

## 5. sysinfo 上报

### 5.1 何时上传【读码：sync.rs L108-131、L211-230】
- `need_upload = (!uploaded || 记下的用户名 != 当前 get_sysinfo()["username"]) && (last_uploaded 为 None || 距上次 >= 120s)`
- `uploaded` 被重置为 false 的情况：
  - URL 变了，或者 `Config::get_id()` 变了（L108-111，同时 `PRO=false`）。
  - 心跳响应带 `sysinfo` 键（L251-255）。
  - 进程重启：状态都在内存里。
- 用户名变化：
  - Windows 登录前用户名可能是空的，登录后变成真实用户名，会再传一次。切换用户也会再传。这里比较的是**覆盖前**的原始用户名，`preset-device-username` 覆盖不影响这个判断。
  - 成功上传后 `last_uploaded = None`，所以用户名一变，下一个 tick 立刻重传，不受 120 秒退避限制。
- `is_public(&url)` 分支里的 `sysinfo_hash` / `sysinfo_ver` 逻辑（L182-210）**是死代码**：`heartbeat_url()` 对官方服务器已经返回空，走到这里的 url 必然不是官方的，所以 `/api/sysinfo_ver` 永远不会被调用。1.4.2 同样如此（当时 `is_public` 就是 `contains("rustdesk.com")`）。**porta-server 不用实现 `/api/sysinfo_ver`**。

### 5.2 请求体字段【读码】
`POST {api}/api/sysinfo`，`Content-Type: application/json`，不带认证。body 是一个 JSON 对象，**所有值都是字符串**：

| 字段 | 来源 | 何时出现 / 格式 |
|---|---|---|
| `cpu` | `get_sysinfo()` | `"{品牌}, {主频}GHz, {逻辑核数}/{物理核数} cores"`。取不到主频时没有前半段，只剩 `"{n}/{m} cores"`。主频 = MHz/1024，保留 2 位小数，f64 显示（如 `3.6`、`4`） |
| `memory` | `get_sysinfo()` | `"{x}GB"`，x = 总内存/1024³，保留 2 位小数，f64 显示（如 `15.86GB`、`16GB`） |
| `os` | `get_sysinfo()` | `"{distribution_id} / {long_os_version}"`；Windows 再加 `" - {os_version}"`（例如 `windows / Windows 11 Pro - 10.0.26100`【推测：具体文本取决于 sysinfo crate】） |
| `hostname` | `get_sysinfo()` → `hostname()` | 小写主机名（`whoami_hostname` 里 `make_ascii_lowercase`），macOS 去掉 `.local`。如果设了 `preset-device-name`，被它覆盖（L172-175） |
| `username` | `get_sysinfo()` → `platform::get_active_username()` | 非空、且 Windows 下不是 `SYSTEM` 时才有（common.rs L963-969）。设了 `preset-device-username` 时被覆盖（L168-171） |
| `version` | `crate::VERSION` | **客户端版本号字符串**，就是 Cargo.toml 的 `version`，如 `"1.4.2"`、`"1.5.1"` |
| `id` | `Config::get_id()` | 总是 |
| `uuid` | `encode64(get_uuid())` | 总是，和心跳里的同一个值 |
| `preset-address-book-name` / `-tag` / `-alias` / `-password` / `-note` | `Config::get_option(...)` | 非空才有。**password 是明文** |
| `preset-user-name` | 内置选项 `get_builtin_option` | 非空才有 |
| `preset-strategy-name` | 内置选项 | 非空才有 |
| `preset-device-group-name` | 内置选项 | 非空才有 |
| `preset-note` | `Config::get_option` | 非空才有 |

- `get_sysinfo()` 在 common.rs L929-971；预设字段在 sync.rs L133-179。
- 内置选项读的是 `BUILTIN_SETTINGS`（common.rs L2652-2659），原版客户端为空。
- `preset-*` 这类 Config 选项原版客户端默认为空，但**服务端经策略推了就会有**。例如推 `preset-address-book-name`，客户端下次上传 sysinfo 时就会带上。注意推完不会立刻触发重传，可以配合心跳响应的 `sysinfo` 键【推测：可作为"自动入地址簿"的实现手段】。
- 服务端解析建议：用 `serde_json::Value` 或者字段全 `Option<String>` 的结构体，不要拒绝未知字段。

### 5.3 响应与客户端行为【读码：sync.rs L211-230】

| 服务端 body（逐字节比较，不 trim） | 客户端行为 |
|---|---|
| `SYSINFO_UPDATED` | `info_uploaded = uploaded(url, id, 用户名)`，`last_uploaded = None`，`PRO = true`。之后除非用户名变化、url/id 变化、服务端要求、进程重启，否则不再上传 |
| `ID_NOT_FOUND` | `last_uploaded = None`、`uploaded` 仍为 false → **下一个 tick（约 3 秒）立刻重传**，没有退避 |
| 其他任何 body（包括 `"SYSINFO_UPDATED"` 带引号、带 `\n`、JSON、404 页面） | `last_uploaded = now` → 120 秒后重试 |
| 请求失败 | 同上，120 秒后重试 |

- `PRO=true` 的副作用：IPC 查询 `hide_cm` 时会返回 `password_security::hide_cm()`（`src/ipc.rs` L978-983）；Windows 上 CM 启动失败时不再上报 `CmErr`（connection.rs L2875）。rustdesk-api 现在也是这么回的，行为不变。
- axum 实现：handler 返回 `&'static str "SYSINFO_UPDATED"` 即可，body 正好是这 15 个字节。
- **`ID_NOT_FOUND` 的用法建议**【推测】：
  - 只用于短暂状态，例如设备刚启动、hbbs 还没收到它的 `RegisterPk`/`RegisterPeer`（第一次 sysinfo 在启动后 3 秒就发了，可能早于注册）。
  - 对确实不认识、或者要拒绝的设备，回别的文本（比如 `REJECTED`），让客户端按 120 秒退避。
  - 否则每台这样的设备会每 3 秒打一次 sysinfo。
  - `docs/research/03` 第 7 节第 3 条写的"未知设备回 ID_NOT_FOUND"要按这里修正。
- 设备记录可以在 sysinfo 里建（rustdesk-api 的做法：按 id 查，没有就新建，`http/controller/api/peer.go` `SysInfo`）。心跳里遇到没有 sysinfo 记录的设备，就在响应里带 `"sysinfo": true` 让它补传。这也覆盖了"rustdesk-api 换成 porta-server 时，客户端进程没重启、以为已经传过"的情况。

## 6. 客户端类型 / 版本识别

### 6.1 现有协议里能看到版本的地方【读码】
- **HTTP**：
  - sysinfo 的 `version`：字符串，只在 sysinfo 上传时有。
  - 心跳的 `ver`：整数，每次心跳都有。从 `ver` 可以反推出 `a.b.c`：`a = ver/1_000_000`，`b = (ver/1000)%1000`，`c = (ver%1000)/10`，补丁号 = `ver%10`。
- **会合协议**（`hbb_common@5d52530:protos/rendezvous.proto`）：
  - `RegisterPeer {id, serial}`、`RegisterPk {id, uuid, pk, old_id, no_register_device}`：**都没有版本字段**。所以设备光注册、没人连它时，hbbs 不知道它的版本。
  - `PunchHoleRequest.version`（字段 6）：**控制端**的 `crate::VERSION`（`src/client.rs` L959）。原版 hbbs 完全不读它（`rustdesk-server@873230e:src/rendezvous_server.rs` 里没有 `ph.version`）。
  - `PunchHoleSent.version`（5）、`LocalAddr.version`（5）、`RelayResponse.version`（7）：**被控端**的 `crate::VERSION`（`rendezvous_mediator.rs` L728、L842、L1140）。原版 hbbs 只拿它判断"是否为空"，非空才给 pk 签名（`rendezvous_server.rs` L1245-1265 `get_pk`）。
  - `KeyExchange.version` / `IdPk.kx_version`：密钥交换协议版本（`KX_VERSION_LATEST = 1`，hbb_common tcp.rs L31）。只有服务端先宣告 ≥1，客户端才会回选，对老服务端恒为 0。这是能力位，不是客户端类型。
  - `PunchHoleRequest.token` / `RequestRelay.token`：**控制端 LocalConfig 里的 `access_token`**，也就是 API 登录令牌（`src/ui_session_interface.rs` L1984）。porta-server 自己签发令牌，所以能据此认出发起连接的是哪个账号（以及登录时上报的 id/uuid）。这可以部分解决架构 §3.7 说的"服务端不知道发起方是谁"，前提是控制端登录过【读码：令牌来源；推测：用途】。
- 原版客户端不再发送 `SoftwareUpdate`（全仓库搜不到 `set_software_update`），原版 hbbs 里那段代码是死的。

### 6.2 以后怎么区分 Porta 客户端和原版（建议）【推测】
1. **不要改 `crate::VERSION` 的格式**。对端拿 `PeerInfo.version` 过 `get_version_number` 做功能门控，例如 `MIN_VERSION_RELATIVE_MOUSE_MODE`（common.rs L212-221，client.rs L3661）。Porta 版本号另起字段，上游版本号保持原样跟随合并。如果非要加后缀，只能用纯数字补丁号（如 `1.5.1-2`），`-porta.1` 这种会被解析成补丁 0。
2. **HTTP 层（第一期就能用）**：Porta 客户端在心跳和 sysinfo 的 body 里加一个新键，例如 `"porta": {"ver": "0.1.0", "proto": 1}`。服务端有这个键就记为 Porta，否则记为原版。原版客户端和 rustdesk-api 都不受影响：Go 的 JSON 绑定忽略未知字段，porta-server 自己的结构体也不要 deny。缺点是未认证、可以伪造，只适合做资产清单。
3. **会合层（建议做）**：给 `RegisterPeer`、`RegisterPk` 加一个新的 proto 字段，比如 `string client_info = 100;`，内容是 `porta/<ver>`。proto3 的未知字段会被原版 hbbs 忽略。这样设备一注册上来，服务端就知道它的类型，不依赖它有没有配 API 地址、发没发心跳。同一批改动可以把架构 §3.7 里"发起方 id"的新字段加进 `PunchHoleRequest`。
4. **最终方案**：设备签名（仿 `/api/switch-grant` 的 Ed25519 签名，sync.rs L322-386）。能签名的就是 Porta 客户端，这和 §3.1 的退出条件一致。
5. 应用名（`APP_NAME`、`is_custom_client`）不会出现在任何上报里，不能拿来识别。

## 7. uuid 格式与 id 变化

### 7.1 uuid【读码】
- `hbb_common::get_uuid()`（lib.rs L318-377）：
  - 优先用 `machine_uid::get()` 的字符串的**原始字节**（有进程内缓存）。
  - 失败时回落到**设备公钥** `Config::get_key_pair().1`（32 字节）。
  - Windows 上 `machine_uid` 读的是注册表 `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid`，形如 `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` 的 36 个字符【推测：crate 实现没在本地核对】。
- 心跳和 sysinfo 里的 `uuid` = `base64::encode(上面的字节)`：标准字母表、带 `=` 填充（common.rs L2100 `encode64`）。36 字节编码后是 48 个字符，公钥回落时是 44 个字符。
- 和 hbbs 的对应关系：
  - `RegisterPk.uuid`（bytes）发的是**同一份** `get_uuid()` 原始字节（rendezvous_mediator.rs L1264-1270）。原版 hbbs 把它存进 `peer.uuid blob`（`rustdesk-server@873230e:src/database.rs` L42、L76）。
  - 所以**`base64_decode(heartbeat.uuid) == peer.uuid`** 可以作为兼容期的一道轻量校验：心跳、sysinfo 自称的 id 必须和 hbbs 注册记录的 uuid 对得上【推测：建议做法】。
  - 注意 uuid 不是秘密，克隆出来的虚拟机还可能重复，这只是挡住随手伪造。
  - 例外：改 ID 的 `check_id` 里，`RegisterPk.uuid` 直接用 `machine_uid::get()` 的字节，不走公钥回落（`src/ui_interface.rs` L1514-1520）。只有 machine_uid 取不到的机器上，两者才会不一致。

### 7.2 id 变化【读码】
- id 变化的来源：
  - 用户在 UI 里改 ID：`change_id_shared` 先用 `RegisterPk{old_id, id, uuid}` 问 hbbs，成功后经 IPC 写 `id`（ui_interface.rs L1502-1560）。
  - hbbs 回 `UUID_MISMATCH` 时客户端自动换一个 10 位随机 ID（`handle_uuid_mismatch` → `Config::update_id`，rendezvous_mediator.rs L1276-1289；config.rs L1276-1283）。
- 心跳线程每个 tick 都重新读 `Config::get_id()`。发现和上次成功上传 sysinfo 时的 id 不同，就把 `uploaded` 置 false、`PRO=false`，下一次用**新 id、同一个 uuid** 重传 sysinfo（sync.rs L108-111）。心跳也立刻改用新 id。
- 服务端建议【推测】：
  - 设备主键用 id（地址簿、hbbs 都按 id）。
  - sysinfo/心跳来了一个新 id，而它的 uuid 和某个旧设备记录相同时，记一条"id 变更"：迁移或标记旧记录，不要当成两台不同的设备。
  - 能对上 hbbs 的 `RegisterPk.old_id` 更好。

## 8. disconnect 字段【读码】
- 格式：心跳响应里 `"disconnect": [<i32>, ...]`，元素是心跳 `conns` 里报上来的 conn_id（sync.rs L256-260，`serde_json::from_value::<Vec<i32>>`）。类型不对就整个忽略。
- 客户端把整个数组广播给本进程所有连接：
  - 普通会话：`conns.contains(&id)` 时先发关闭原因 `"Closed manually by web console"`（不重试），再 `on_close("web console", true)` 断开（connection.rs L1067-1073）。
  - 端口转发会话：直接 `bail!("Closed manually by the web console")`（connection.rs L1384-1388）。
  - 数组里不存在的 id 被忽略。
- 只有设备在发心跳时才能踢。有连接时心跳是 3 秒一次，所以最快 3 秒左右生效。
- 服务端建议【推测】：每台设备维护一个"待断开集合"，每次心跳把它和 `req.conns` 的交集放进响应；某个 conn_id 不再出现在 `conns` 里（说明已经断了），或者超过 TTL（比如 1 分钟），就把它从集合里删掉。不要发一次就删：响应可能丢。

## 9. 影响实现方案的意外 / 风险

1. **原版 hbbs 不转发 v6（以及 UDP、WebRTC 相关）字段**【读码：`rustdesk-server@873230e:src/rendezvous_server.rs`，`src/` 下搜不到 `socket_addr_v6`、`udp_port`、`force_relay`、`upnp_port`、`webrtc`】：
   - `handle_punch_hole_request`（L806-811）重新构造 `PunchHole` 时只填 `socket_addr`、`nat_type`、`relay_server`。`FetchLocalAddr`（L794-798）只填 `socket_addr`、`relay_server`。
   - `handle_hole_sent`（L671-675）和 `handle_local_addr`（L705-709）重建 `PunchHoleResponse` 时也丢掉了 `socket_addr_v6`。只有 `RelayResponse`、`RequestRelay` 是原样转发的（L541-574）。
   - 后果：被控端收不到控制端的 v6 地址（`peer_addr_v6.port() > 0` 不成立），控制端也收不到被控端的 v6 地址，**开源版 hbbs 下 IPv6 打洞根本不会发生**。
   - porta-server 第一期至少要补这几处：
     - `PunchHole.socket_addr_v6 = ph.socket_addr_v6`
     - `FetchLocalAddr.socket_addr_v6 = ph.socket_addr_v6`
     - `PunchHoleResponse.socket_addr_v6 = phs.socket_addr_v6`（来自 `PunchHoleSent`）
     - `PunchHoleResponse.socket_addr_v6 = la.socket_addr_v6`（来自 `LocalAddr`）
   - 顺带要决定转不转 `force_relay`、`udp_port`、`upnp_port`、`control_permissions`、`webrtc_sdp_*`。这条应该和负责 02（会合与中继）的笔记对一下。
2. **"经心跳策略打开 IPv6 打洞"对原版客户端不成立**（§4）：
   - 开关是 LocalConfig 选项，只有控制端读，而且读的是用户进程的 LocalConfig；心跳写的是（SYSTEM 进程的）Config。
   - 架构文档 §3.6、§3.8 和 AGENTS.md 里"第一期经心跳策略开 IPv6 打洞""两端都要打开 enable-ipv6-punch"的说法要改：被控端不需要开关，控制端要手动勾选，服务端要补转发。
   - `enable-udp-punch` 同理。
3. **`strategy` 无条件应用**（§2.2）：服务端必须按 `req.modified_at != rev` 控制下发，而且 `strategy` 和 `modified_at` 必须一起发；否则会每次心跳都把用户的本地设置覆盖回去。架构 §3.7 前提一说的"只在首次接入或策略变更时下发"，靠的就是这条规则。
4. **`strategy` 解析失败会丢策略且不重试**（§2.2 坑一）：`config_options` 的值必须全是字符串，任何键都不能给 `null`。建议服务端在下发前，用和客户端一样的结构体反序列化自检一遍。
5. **`ID_NOT_FOUND` 会导致每 3 秒重传 sysinfo**（§5.3），不能用来回应"未知设备"。
6. **心跳跑在被控服务进程里**：
   - 仅主控（outgoing-only）、`stop-service=Y`、`register-device=N` 的客户端不发心跳、不传 sysinfo。§3.1 退出机制想靠 sysinfo 统计"所有设备的客户端版本"，会漏掉这些设备，以及从没被连过的纯控制端。
   - 补救办法：会合层加版本字段（§6.2 第 3 条）；或者用登录接口和打洞请求里的 token、`PunchHoleRequest.version` 辅助统计【推测】。
7. **经策略改 `custom-rendezvous-server`/`api-server`/`key` 不会立刻重连**（§3.5）。`relay-server` 不受影响。
8. **conn_id 不是全局唯一**：每个进程从 1~1999 的随机值开始递增，重启就重置（§1.4）。审计、踢人、回落率统计都要按（设备 id、conn_id、时间）组合来区分。
9. 心跳 body 不带认证，`id`/`uuid` 可以伪造，伪造者还能拉到下发给这台设备的策略。兼容期至少做 §7.1 的 uuid 对照（和 `docs/research/03` §7 问题 2 呼应）。
10. HTTPS 由反向代理终结时，服务端要从 `X-Real-IP`/`X-Forwarded-For` 取客户端 IP（rustdesk-api 用的是 gin 的 `c.ClientIP()`）。只信任来自反代地址的这两个头【推测：部署项】。
