## 0. 结论速览

1. **候选中继列表不走 `strategy.config_options`，走心跳响应里新加的顶层键 `porta`**。原版客户端解析心跳响应时只摘自己认识的四个键（`sysinfo`、`disconnect`、`modified_at`、`strategy`），别的键直接忽略【读码】；而 `config_options` 里的任何键都会被原样写进原版客户端的 `RustDesk2.toml`，而且只在策略版本变化时下发、用户还能在本地改，不适合当数据通道。不需要新接口。
2. **测什么**：到每台中继 `host:21117` 的 TCP 建连耗时（DNS 解析单独计时、不算进去），每轮每台测 3 次取最小值，建连成功立刻正常关闭。和 porta-server 健康检查的测法一致（`server/src/router/mod.rs` `check_relay`）。每 5 分钟一轮，带抖动；有代理或走 WebSocket 时不测。
3. **谁测**：跑心跳的那个进程（Windows 安装版是 SYSTEM 身份的 `--server` 进程，便携版是 UI 进程本身）【读码：`rendezvous_mediator.rs` L281 `sync::start()`】。被控端和发起方用的是同一份测量：一台机器只跑一个测速循环，代码放 `libs/porta/src/route/probe.rs`。
4. **发起方的数据怎么到服务端：推荐在 `PunchHoleRequest` 里加"发起方自己的 id"（字段号 1000），服务端用这个 id 去查发起方心跳上报过的测量值**，而不是像方案原文那样把测量值本身塞进打洞请求。原因：发起连接的是 UI 进程，测量结果和候选列表都在服务进程里，UI 进程拿不到（UI 进程的 Config 只在启动时经 `SyncConfig` 整份同步一次，之后只有 id、salt、options 和 NAT 类型、socks 代理、解锁 PIN 等少数几项会在 UI 调对应的 IPC 时零星写回【读码：`src/server.rs` `start_server` 的 `SyncConfig` 分支、`src/ipc.rs` `get_id`/`get_options_`/`set_options`/`get_nat_type_`/`get_socks_`，第二次核对补全】；测速结果和候选列表放在服务进程的内存里，没有现成通道），要拿就得新增 IPC 消息。方案原文说要带测量值，理由正是"没有发起方 id、服务端查不到"，补上 id 就同样解决了。**这是对方案措辞的偏离，需要维护者拍板**（§6 问题 1）。
5. **`RequestRelay` 不需要加字段**：回落中继时用哪台中继，在打洞阶段就由被控端定了，`RequestRelay.relay_server` 只是把这个值带回去【读码】。
6. **被控端改动精确位置**：`rendezvous_mediator.rs` L1321 `RendezvousMediator::get_relay_server`，现在的优先级是"本地 `relay-server` 选项 > hbbs 给的 > hbbs 主机端口 +1"。只有 `handle_punch_hole`（L1110）和 `handle_intranet`（L762）调它；回落中继、对称 NAT 时被控端主动发起中继，用的都是它的结果。改成"服务端是 porta-server 时，hbbs 给的值优先"，挂钩 2~3 行。**必须加"服务端是 porta-server"这个前提**，否则 Porta 客户端连原版 hbbs 时，用户本地填的中继会被原版 hbbs 的轮询结果覆盖。
7. **服务端**：测量值只放内存（`Router` 里一张按设备 id 的表，最多 1 万条，15 分钟过期），不建表。代价模型按"整端替换"接入：某一端的测量覆盖了全部候选中继，这一端才用实测值，否则这一端整端用估计值，避免同一端里实测值和估计值混排带来的系统偏差。`conn_attempt` 只扩展 `route_reason` 的取值，另加两列记选中中继两段的延迟和来源，给以后校准第一级的常数用（§6 问题 4）。
8. **开销和中继侧**：每台设备每 5 分钟 N × 3 次 TCP 建连，N = 4 时一天约 3500 次、约 2 MB 流量（估算）。hbbr 对"连上就关"的连接只是一个等首帧的任务读到 EOF 后退出，不打日志、不计数、不自动拉黑（拉黑名单只能手工维护）【读码】。porta-server 自己的健康检查每 3 秒就对每台中继做一次同样的建连（每台中继每 5 分钟 100 次，每台设备每 5 分钟 3 次），设备在 30 台左右以内时，它比所有客户端加起来还多。

## 2. 读码结论

### 2.1 心跳响应：客户端怎么处理未知键

- 心跳循环在 `sync.rs` `start_hbbs_sync_async`：把响应解析成 `HashMap<&str, Value>`，依次 `remove("sysinfo")`、`remove("disconnect")`、`remove("modified_at")`、`remove("strategy")`，剩下的键不看【读码：sync.rs L249-273】。所以**顶层新键对原版客户端完全无害**。第三方 rustdesk-api（Go）不会发这个键，跟它无关。
- `strategy.config_options` 交给 `handle_config_options`：对每个键，值非空就 `options.insert(k, v)`，值为空且没有内置默认值就删键，最后 `Config::set_options` 落盘【读码：sync.rs L292-309】。**没有白名单**，未知键也照样写进 `RustDesk2.toml` 的 `[options]`。`set_options` 里的 `purify_options` 只丢掉两类键：内置覆盖设置（`OVERWRITE_SETTINGS`）里有的键，和值等于内置默认值的键【读码：`hbb_common/src/config.rs` `is_option_can_save`，核对时补充】。
- `strategy` 只在服务端判定 `req.modified_at != rev` 时才下发（`server/PORTA.md` §10），设计上就是"变更时推一次"，用户之后在本地改了也不会被覆盖。
- 结论：`config_options` 能"装下"候选列表（值得是字符串，只能塞 JSON 字符串），但有三个问题：原版客户端也会把它写进配置文件；用户能在本地改坏；服务端要按客户端类型给不同的有效选项，`rev` 的计算也得把客户端类型算进去。**不用它**。

### 2.2 心跳请求：服务端怎么处理未知键

- porta-server 的 `HeartbeatReq` 只有 `id`、`uuid`、`ver`、`modified_at`，没有 `deny_unknown_fields`，未知键会被忽略【读码：`server/src/api/device.rs` `HeartbeatReq`】。
- 但 `parse_json` 解析失败会回 400【读码：`server/src/api/mod.rs` `parse_json`】。如果新加的 `porta` 子对象用强类型结构体，里面某个字段类型不对就会让整个心跳失败。**新键要先当 `serde_json::Value` 收，再宽松解析**，解析不了就当没带。
- 第一期笔记 01 §6.2 已建议用心跳 body 里的 `porta` 键来区分 Porta 客户端，本篇沿用这个键名，`device.client_type` 可以在同一处记成 `'porta'`。

### 2.3 心跳和会合在哪个进程里跑

- `RendezvousMediator::start_all` 里调 `crate::hbbs_http::sync::start()`【读码：`rendezvous_mediator.rs` L281】，所以心跳和"收打洞请求、决定中继"的被控端逻辑**在同一个进程里**。Windows 安装版是服务拉起的 `--server` 进程（SYSTEM 身份，配置目录被改写到 LocalService 的 profile 下，见第一期笔记 01 §1.1）；便携版是 UI 进程自己。
- 发起连接的是 UI 进程（`client.rs` `_start_inner` 构造 `PunchHoleRequest`，全仓库只有 L953 这一处【读码】）。UI 进程的 `Config` 只在 `start_server(false, …)` 时向服务进程发一次 `SyncConfig` 整份同步【读码：`src/server.rs` `start_server` else 分支、`src/ipc.rs` `Data::SyncConfig`】；之后只有零星写回：UI 调 `ipc::get_id()` 时把服务进程的 id、salt 写进本进程 Config，调 `ipc::get_options()`/`set_options()` 时写回 options，NAT 类型、socks 代理、解锁 PIN 等几项同理（`get_nat_type_`、`get_socks_`、`set_unlock_pin`）【读码：`src/ipc.rs` `get_id`、`get_options_`、`set_options`，核对时补充；其余几项为第二次核对补全】，都是 Config 里的持久项，服务进程内存里的状态没有这样的通道；界面看到的选项是 `ui_interface.rs` 里每秒经 IPC 拉一次的 `OPTIONS` 镜像【读码：`ui_interface.rs` `check_connect_status_`】，那是主 crate 里的状态，`libs/porta` 拿不到。
- 所以：**被控端那一侧，测量、候选列表、决定中继都在同一个进程，直接共享内存就行；发起方那一侧，测量在服务进程、发起在 UI 进程，中间隔着 IPC**。这是 §0 第 4 条推荐"带 id 而不带测量值"的根本原因。

### 2.4 打洞请求和回落中继的完整链路

服务端选中继、被控端最终拍板、发起方只是照用：

1. A（发起方 UI 进程）发 `PunchHoleRequest{id: B, token, …}` 到 hbbs【读码：client.rs L953】。消息里没有 A 自己的 id；登录过的 A 带 `token`，porta-server 能反查到登录时记下的 `device_id`（`server/src/auth.rs` `token_owner`），但这是一次查库，`conn_tracker` 为了不在热路径上查库把它放到了后台（`server/PORTA.md` §8）。
2. porta-server `handle_punch_hole_request`（TCP、UDP 两个入口 `handle_tcp_punch_hole_request`、`handle_udp_punch_hole_request` 共用它）调 `router.select(...)`，把结果放进 `PunchHole.relay_server`（或 `FetchLocalAddr.relay_server`）转给 B【读码：`server/src/rendezvous_server.rs`】。原版 hbbs 在这里是轮询（`rustdesk-server@873230e:src/rendezvous_server.rs` `get_relay_server`，忽略两端 IP）。
3. B 收到后在 `handle_punch_hole`（L1042）/ `handle_intranet`（L753）里调 `self.get_relay_server(ph.relay_server)`【读码：L1110、L762】，结果：
   - 正常打洞：写进 `PunchHoleSent.relay_server`（L1135 附近）回给 hbbs，hbbs 原样转成 `PunchHoleResponse.relay_server` 给 A【读码：`server/src/rendezvous_server.rs` `handle_hole_sent`】。
   - 同内网：写进 `LocalAddr.relay_server`，同样转给 A。
   - 对称 NAT 或强制中继（`relay_v4`）：B 自己 `create_relay(initiate=true)`，把这个中继写进 `RelayResponse.relay_server` 发给 hbbs，再转给 A【读码：L1117-1132、`create_relay` L688-751】。porta-server 的 `RelayResponse` 分支在两种情况下改写它：A 在 hbbs 的局域网里时改成 hbbs 的 `local_ip`；它等于 hbbs 自己的 `local_ip` 时重新调 `router.select`；其余情况原样转发【读码：`server/src/rendezvous_server.rs` `RelayResponse` 分支，核对时更正】。
4. A 记下 `relay_server = ph.relay_server`（client.rs L1026）。直连失败（或强制中继）时，`request_relay` 把**这个值**放进 `RequestRelay.relay_server` 再发一次（client.rs L1551-1560、L1788-1849）；porta-server 不再选路，原样转给 B（`server/src/rendezvous_server.rs` `RequestRelay` 分支），B 的 `handle_request_relay` 直接用 `rr.relay_server`，不再调 `get_relay_server`【读码：L661-686】。
5. A 拿到的 `relay_server` 为空时根本不回落中继（client.rs L1551 `if !relay_server.is_empty()`）。

结论：**回落时用哪台中继，是 B 在第 3 步用 `get_relay_server` 定的**，hbbs 的选择只是 B 的输入之一。所以第二级在服务端选好之后，客户端只需要改 B 的 `get_relay_server`，`RequestRelay` 不需要带任何新东西。

### 2.5 `get_relay_server` 现在的逻辑

```rust
// rustdesk@bd92623:src/rendezvous_mediator.rs L1321 RendezvousMediator::get_relay_server
let mut relay_server = Config::get_option("relay-server");
if relay_server.is_empty() { relay_server = provided_by_rendezvous_server; }
if relay_server.is_empty() { relay_server = crate::increase_port(&self.host, 1); }
```

本地选项优先。第一期的变通是服务端经心跳下发 `relay-server: ""` 把本地值删掉（`server/PORTA.md` 迁移 0001 里的全局 `strategy_option` 行），这就是方案 §3.1 兼容债务第 3 条。

### 2.6 会合协议的字段号

- `PunchHoleRequest` 现有字段 1~12，`rendezvous.proto` 全文件最大的字段号是 29【读码：`porta-cardo@7c05bbd:protos/rendezvous.proto`】。
- 方案 §3.3 定的是"新字段号用高位段（例如从 1000 起）"，本篇取 1000。protobuf 规定字段号 1~536,870,911，19000~19999 留给实现自己用；16~2047 的字段标签编码占 2 字节【官方：https://protobuf.dev/programming-guides/proto3/ "Assigning Field Numbers"】。1000 起的段落在 2 字节区间，离上游现在的最大号 29 很远。
- 未知字段：proto3 解析时保留未知字段【官方：同页 "Unknown Fields"】。两边用的都是 rust-protobuf 3.7（`porta-cardo` 和 `rustdesk-server@873230e:libs/hbb_common/Cargo.toml` 都写 `protobuf = "3.7"`）【读码】。原版 hbbs 解析带 1000 号字段的 `PunchHoleRequest` 不会出错，只是看不见它；它转给 B 的 `PunchHole` 是新构造的消息（`rustdesk-server@873230e:src/rendezvous_server.rs` L806），porta-server 也一样，所以这个字段不会被转到 B 那里。原版客户端只发、不收 `PunchHoleRequest`，不受影响。

### 2.7 hbbr 怎么对待"连上就关"的连接

`rustdesk-server@873230e:src/relay_server.rs`（porta-server 里的 `src/relay_server.rs` 这段逻辑相同）【读码】：

- `io_loop` 每接受一个连接就进 `handle_connection`：回环来源当控制台命令处理；来源在 `BLOCKLIST` 里就直接丢；否则 `spawn` 一个 `make_pair`。
- `make_pair_` 等首帧最多 30 秒（`timeout(30_000, stream.recv())`），首帧不是 `RequestRelay` 或连接关了，任务就结束。**整个过程不打日志**（只有收到 `RequestRelay` 后才有 "New relay request"/"got paired" 这些日志），不进 `USAGE`，也不触发任何自动封禁。`blacklist`/`blocklist` 只能从文件或控制台手工加。
- 所以"建连成功马上关"在 hbbr 看来什么都没发生；如果客户端连上后不关，每条占一个任务 30 秒，不会更糟。
- 对照：porta-server 健康检查对每台中继**每 3 秒**建连一次（`server/src/router/mod.rs` `HEALTH_INTERVAL`、`check_relay`），5 分钟就是 100 次，只配一台中继也照查。原版 hbbs 也是 3 秒一轮，但只在配了两台及以上中继时才检查（`rustdesk-server@873230e:src/rendezvous_server.rs` 主循环 `timer_check_relay` 分支的 `relay_servers0.len() > 1`、`check_relay_servers`，第二次核对更正）。

### 2.8 porta-server 的路由现状

- `Router::select`：先查 `device_policy.relay_pin`（按 B 的 id，每次查库），有就直接用；否则 `decide(a_ip, b_ip)`【读码：`server/src/router/mod.rs`】。
- `cost::score`：每台可达候选 `cost = (rtt(A,R) + rtt(B,R)) × weight`；一端位置未知时用 `2 × rtt(已知端, R)`；两端都未知返回 `None` 走轮询。`reason` 取 `geo`/`geo_a`/`geo_b`/`rr`/`fixed`/`none`【读码：`server/src/router/cost.rs` `score`、`pick`】。
- `RouteQuery` 里有 `b_id`、`a_token`，没有 A 的 id【读码】。
- `RelayResponse` 分支（B 主动中继、写的是 hbbs 自己地址时）也调 `select`，传的 `b_id` 是空串【读码：`server/src/rendezvous_server.rs` `RelayResponse` 分支】。
- `conn_attempt` 记了 `relay_offered`、`route_reason`、`b_relay`（迁移 0001），定稿由 `conn_tracker` 在后台完成（`server/PORTA.md` §8）。

## 3. 设计

### 3.1 下发候选列表（问题 1）

**推荐：心跳响应加顶层键 `porta`，只发给 Porta 客户端，带版本号按需下发。**

请求（Porta 客户端在心跳 body 里加）：

```json
"porta": { "v": 1, "relays_rev": 7, "rtt": { "relay1.example.com:21117": 23, "relay2.example.com:21117": 61 },
           "rtt_age": 42, "down": ["relay3.example.com:21117"] }
```

响应（只在请求带了 `porta` 键时出现）：

```json
"porta": { "v": 1 }                                                  // relays_rev 一致时
"porta": { "v": 1, "relays_rev": 8, "relays": ["relay1.example.com:21117", "..."], "probe_interval": 300 }  // 不一致时
```

- `relays` 是 `[[relay]]` 的 `host` 原串，和 `PunchHole.relay_server` 下发的是同一个字符串，所以客户端测的和服务端选的能逐字对上。全部配置的中继都发（包括健康检查暂时判为不可达的），可达性由服务端在选路时再过滤。
- `relays_rev`：对列表做哈希（同 `strategy` 的 `rev` 算法），进程重启载入新配置、控制台 `rs` 替换后自然变化（porta-server 没有配置热重载【读码，核对时更正】）。不每次都发列表：心跳空闲时约 15~18 秒一次、会话中每 3 秒一次【读码：sync.rs L18-20、L232-235】，列表每次都带的话每台设备一天多出几 MB 无用流量【推测】。
- `{"v":1}` 即使没有变化也每次都回：它同时是"服务端是 porta-server"的标记，§3.4 的被控端改动要用。
- 原版客户端：请求里没有 `porta` 键，服务端就不回这个键；就算回了，原版客户端也会忽略（§2.1）。

**备选 A：`strategy.config_options` 加一个 `porta-relays` 键。** 代价：原版客户端也会写进配置文件；值只能是 JSON 字符串；用户能在本地改坏；要按客户端类型给不同的有效选项。不选。

**备选 B：新接口 `GET /api/porta/v1/relays`。** 好处是 UI 进程也能直接拉。代价：多一个接口、多一套限速和认证；在 §3.3 推荐的方案下 UI 进程根本不需要列表。只有维护者在 §6 问题 1 选"带测量值"时才需要它（或者新增 IPC 消息）。

**明确不做**：把中继权重、位置、健康状态发给客户端。客户端只测、不选，选路信息留在服务端。

### 3.2 客户端测速（问题 2）

**测什么**：到 `host:21117`（没写端口时补 21117，同 `check_port(host, RELAY_PORT)`）的 TCP 建连耗时。
- 先解析 DNS（3 秒超时），解析时间不算；再计时 `TcpStream::connect`（3 秒超时）。TCP 三次握手的 SYN→SYN-ACK 约等于一次往返，和 hbbr 实际承载的 TCP 路径一致；hbbr 只有 TCP 和 WebSocket，没有 UDP 可测【读码】。
- 每台中继连续测 3 次，间隔约 200 毫秒，取最小值：SYN 丢一次就要等 1 秒以上重传，最小值能滤掉这种偶发尖刺；选路要的是基础延迟【推测】。各中继并发测。
- 建连成功后立刻正常关闭（drop，发 FIN），不发任何数据，不发 `RequestRelay`。3 次都失败的放进 `down`。
- 地址族：客户端真正连中继时（client.rs `create_relay`），`ipv4_to_ipv6` 只在中继地址是 IPv4 字面量、而连会合服务器的套接字是 IPv6 时，把它改写成 `<ip>.nip.io`（给 NAT64 用），主机名原样不动；之后 `connect_tcp` → `FramedStream::new` 按 `lookup_host` 返回的顺序逐个地址尝试，用第一个连上的【读码：`hbb_common/src/socket_client.rs` `ipv4_to_ipv6`、`hbb_common/src/tcp.rs` `FramedStream::new`，核对时更正：原文以为是按会合连接的地址族改写主机】。测速照同样的规则解析和挑地址（按解析顺序、取第一个连上的），双栈中继测的和实际走的就是同一个地址族。porta-server 的 `check_relay` 只取解析出的第一个地址，和客户端略有不同。
- 开了代理（`Config::is_proxy()`）或 WebSocket（`use_ws()`）时**不测、不报**：实际中继走代理或 21119 的 WSS，直连测的数字没有代表性。服务端拿不到这台设备的测量，自然退回估计值。

**多久测一次**：收到列表后 10~30 秒内随机时刻测第一轮，之后每 `probe_interval`（默认 300 秒）一轮，每轮加 ±10% 抖动，避免同一出口后面的很多设备同时测；列表 `relays_rev` 变了立即重测一轮。`stop-service` 打开时（心跳本来就不跑）也不测。不做"网络变化时立刻重测"：上游没有现成的网络变化事件可挂，最长滞后 5 分钟可以接受【推测】。

**放哪里**：`libs/porta/src/route/`
- `probe.rs`：测速循环、结果缓存（`static` 里的 `Mutex<Option<ProbeResult>>`，带测量时刻）。
- `mod.rs`：心跳挂钩用的两个函数：`heartbeat_extra() -> Option<serde_json::Value>`（生成请求里的 `porta` 对象）、`on_heartbeat_response(&Value)`（读响应里的 `porta`：更新列表、设置"服务端是 porta-server"标记）；以及 §3.4 被控端用的 `relay_preference(provided: &str) -> Option<String>`。
- `libs/porta` 现在只依赖 `hbb_common` 和 `base`，`hbb_common` 里有 tokio 和 serde_json，够用【读码：`client/libs/porta/Cargo.toml`】。

**谁驱动**：跑心跳的进程。心跳循环跑在独立线程里的单线程 tokio 运行时上（`sync.rs` `start_hbbs_sync_async` 带 `#[tokio::main(flavor = "current_thread")]`）【读码】，测速循环在 `on_heartbeat_response` 第一次拿到列表时 `tokio::spawn` 到这个运行时上就行，不另开线程。（核对补充：这个运行时每 3 秒的 tick 里会同步调用 `get_sysinfo()` 等阻塞函数，可能把测速计时拉长，见文末核对记录 B3。）第三期心跳整体搬进 `libs/porta` 的新 API 客户端后，测速模块和它放在一起，挂钩也随之从 `sync.rs` 挪走。

**怎么上报**：§3.1 的请求格式。
- `rtt` 的键是列表里的原串，值是整数毫秒（至少 1）；`down` 是 3 次都失败的中继；`rtt_age` 是这轮测量距现在的秒数，服务端用"收到时刻 − rtt_age"算测量时刻，不依赖两边时钟一致。
- 每次心跳都带最近一轮的结果（几十到几百字节）。这样服务端不需要落库，进程重启后下一次心跳就补上了；心跳本身已经有每来源限速（`server/PORTA.md` §9.3）。
- 还没测完第一轮时只带 `v` 和 `relays_rev`。

**sync.rs 挂钩**（第三期心跳改走新 API 客户端之前的过渡写法，各一行）：

```rust
// 发请求前
if let Some(p) = porta::route::heartbeat_extra() { v["porta"] = p; }
// 解析响应后
if let Some(p) = rsp.remove("porta") { porta::route::on_heartbeat_response(&p); }
```

**备选**：UI 进程也跑一个测速循环，专门给发起方用。代价：UI 进程没有候选列表（要新接口或新 IPC），同一台机器测两遍；只在维护者选"带测量值"时才有意义。

**明确不做**：测带宽或丢包；测 hbbs 本身；连接建立后按实际会话延迟再修正；中途换中继（方案 §3.7 已定不做）。

### 3.3 发起方：打洞请求的新字段（问题 3）

**推荐（偏离方案原文，需拍板）：带发起方 id。**

```proto
message PunchHoleRequest {
  ...
  string webrtc_sdp_offer = 12;
  // Porta fields start at 1000 (docs/architecture.md §3.3).
  string porta_from_id = 1000;   // 发起方自己的设备 id；服务端用它查发起方心跳上报的测量
}
```

- 客户端改动：`client.rs` L953 的结构体字面量里加一行 `porta_from_id: porta::route::self_id(),`（`client.rs` 是方案 §3.3 列的热点文件，只加这一行）。UI 进程里的 id 来自启动时同步的 `Config`；编码时要核对 UI 进程里 `Config::get_id()` 和服务进程的一致（改 ID 后界面经 IPC 同步）【推测】。核对补充：界面显示 ID 用的 `ui_interface::get_id()` 走 `ipc::get_id()`，它向服务进程取 id，不一致时写回本进程 Config【读码：`src/ui_interface.rs` `get_id`、`src/ipc.rs` `get_id`】，所以界面取过 ID 后两边一致；但服务进程没起来、本进程 id 又为空时，`Config::get_id()` 会就地生成一个新 id 并落盘，`self_id()` 要留意这种情况。
- 服务端：`handle_punch_hole_request` 把 `ph.porta_from_id`（截到 253 字节）放进 `RouteQuery.a_id`；`conn_tracker` 也可以顺手用它填 `a_device_id`，未登录的发起方也能记下是哪台设备。
- 伪造：这个 id 不认证。A 冒用别人的 id，只会让 A 自己这次连接按别人的测量选路，不影响别人。设备签名做好以后可以只采信签过名的（见风险 2）。
- 发起方没有测量（服务进程没跑、心跳没配、刚开机）时自然退回估计值。

**备选（方案原文）：带测量值本身。**

```proto
message RelayRtt { string host = 1; uint32 rtt_ms = 2; }
message PortaRouteHint { repeated RelayRtt rtt = 1; uint32 age_s = 2; repeated string down = 3; }
// PunchHoleRequest 里：
PortaRouteHint porta_route = 1000;
```

- 好处：发起方的测量来自发起连接的那个进程，开了分用户 VPN（只有用户会话走 VPN、SYSTEM 服务不走）这类情况下更准。
- 代价：UI 进程得先拿到候选列表并自己测，或者从服务进程取结果，两条路都要新东西（§3.1 备选 B 的新接口，或在上游的 `ipc.rs` 里加 IPC 消息）。字节数也大一些（N × 约 30 字节，离 16 KB 帧上限很远，不是问题）。

**不选：只靠 `token` 反查发起方。** 登录过的发起方不加字段也能查到设备 id，但未登录的查不到，而且每次打洞都要多一次查库（`conn_tracker` 正是为了不在热路径上查库才把反查挪到后台的，`server/PORTA.md` §8）。可以作为没带 `porta_from_id` 时的兜底，第一版不做。

**字段号**：1000（方案 §3.3）。建议在 `rendezvous.proto` 文件头写一行注释，说明 Porta 字段占 1000~1999，以后别的消息也从这里取号；不要碰 19000~19999【官方】。

**原版的行为**：原版 hbbs 收到带 1000 号字段的请求照常处理，看不见这个字段，也不会转给 B；原版客户端不收这条消息（§2.6）。Porta 客户端连原版 hbbs 时只是多发几个字节。

**`RequestRelay` 不用加**：中继在打洞阶段就由 B 定了（§2.4），`RequestRelay` 只是把定好的值带回去，porta-server 收到后也不再选路。`conn_attempt` 里的 `relay_only`（没有匹配打洞记录的 `RequestRelay`）是同一会话的重试，同样不需要。

### 3.4 被控端：服务端下发值优先（问题 4）

改 `rendezvous_mediator.rs` L1321 `get_relay_server`，函数开头加一个挂钩：

```rust
fn get_relay_server(&self, provided_by_rendezvous_server: String) -> String {
    if let Some(r) = porta::route::relay_preference(&provided_by_rendezvous_server) {
        return r;
    }
    // 以下是上游原样
    let mut relay_server = Config::get_option("relay-server");
    ...
}
```

`relay_preference` 只在两个条件同时满足时返回 `Some(provided)`：
1. 这个进程最近一次心跳响应里有 `porta` 键（服务端是 porta-server）；
2. `provided` 非空。

否则返回 `None`，走上游原逻辑。理由：
- **不加条件 1 会出问题**：Porta 客户端连原版 hbbs（或 RustDesk 官方服务器）时，hbbs 给的是轮询结果，用户在本地特意填的中继会被它覆盖。
- `provided` 为空（porta-server 没配中继）时退回本地选项，再退回"hbbs 主机端口 +1"，和上游一样。
- 固定中继这个需求由服务端的 `device pin-relay` 承担（方案 §3.7），被控端本地的 `relay-server` 选项在连 porta-server 时就不再生效了。这要在界面或文档里说明（§6 问题 3）。
- 心跳第一次成功之前（开机后几秒），标记还没设上，这期间按上游逻辑走。可以接受【推测】。
- 两个调用点（`handle_punch_hole`、`handle_intranet`）和 B 主动发起中继的分支都经过这个函数，一处挂钩全覆盖（§2.4）。`handle_request_relay` 不经过它，也不需要。

上了这个改动以后，兼容债务第 3 条的客户端一半就清掉了。服务端那一半（全局下发 `relay-server: ''`）要等原版客户端退出后再删，在那之前它对 Porta 客户端无害：Porta 客户端本来就不看这个本地值了。

**备选**：直接颠倒上游的优先级（hbbs 给的 > 本地），不看服务端类型。只改 1 行，但有上面说的问题。不选。

**明确不做**：让发起方决定中继；B 收到 hbbs 的中继后自己再按测量结果改选（方案 §3.7 已否决"被控端自己选"）。

### 3.5 服务端（问题 5）

**存哪里：内存，不建表。** 在 `Router` 里加：

```rust
struct Measured { at: Instant, rtt: HashMap<String, u32>, down: HashSet<String> }  // 键是中继 host 原串
measured: Mutex<HashMap<String /* device id */, Measured>>
```

- 只收已经通过心跳 uuid 校验的设备（`server/PORTA.md` §9.3）；只保留当前配置里有的 host，最多 32 个；毫秒值限在 1~10000；`rtt_age` 超过 900 秒的整条丢弃。
- 条目上限 1 万（同 `device` 表），满了淘汰 `at` 最老的。最坏占用约 1 万 ×（id 253 字节 + 32 × 约 40 字节）≈ 15 MB【推测：估算】；正常几十台设备只有几十 KB。
- 过期：测量时刻超过 15 分钟（3 轮）的条目在读取时视为不存在，每小时随现有定时器清一次。
- 不落库的理由：数据 5 分钟就旧，进程重启后下一次心跳（15 秒内）就补上了；落库只会多一份写锁竞争，第一期为会合模块的写库压了很多次延迟。

**代价模型怎么接：整端替换。**
- `RouteQuery` 加 `a_id: &str`（来自 `porta_from_id`，没有就空串）。`select` 按 `a_id`、`b_id` 各取一份测量。
- 对每一端：测量没过期，并且 `rtt` ∪ `down` 覆盖了当前全部可达候选，这一端就用实测值；否则这一端整端用 GeoIP 估计值。
- `down` 里的中继（这一端连不上）从这一对设备的候选里去掉；全被去掉时忽略 `down`，退回原来的候选。这能覆盖"hbbs 连得上、某台设备连不上"的情况，这是健康检查看不到的。
- 一端实测、另一端位置未知也没有测量时，沿用第一期的 `2 × rtt(已知端, R) × weight`。
- `reason` 新增：`rtt`（两端实测）、`rtt_a`/`rtt_b`（只有一端实测，另一端用估计值）。原有的 `geo`/`geo_a`/`geo_b`/`rr`/`fixed`/`none` 含义不变。固定中继仍然最先判断。
- 为什么不逐台中继混用：估计值是距离 × 绕路系数、再加跨运营商和跨境惩罚（`server/src/router/cost.rs` `leg_rtt`），不含最后一公里（家宽、Wi-Fi）的延迟，系统性偏低。同一端里一部分中继用实测、一部分用估计，没测到的中继会显得更近而被选中。整端替换下，测量列表和服务端列表是同一份，正常情况下总是全覆盖，只有刚加中继后的几分钟会退回估计。
- 残留偏差：一端实测、另一端估计时，实测端多出的最后一公里延迟对所有中继是同一个常数；权重全是 1 时不影响选哪台，权重不同时会有偏差（见风险 3）。

**和 `conn_attempt` 的关系**：
- `route_reason` 列直接容纳新取值（迁移 0001 里是 text），不用改结构。
- 推荐另加两列（迁移 0004）：`route_a_ms`、`route_b_ms`（real，可为空），记选中中继两段的延迟，正数是实测、负数是估计（或者另加一个标记列）。这样以后能用"同一对设备的实测值 vs 估计值"校准第一级的 `detour` 和惩罚常数（方案 §3.7 写了"以后可以用第二级的实测数据校准"），也能评估第二级到底有没有选出不同的中继。每行多 16 字节左右，对 `server/PORTA.md` §8 的行大小上限估算影响可以忽略。
- 有了 `porta_from_id`，`a_device_id` 可以在热路径上直接填（未登录的发起方也有），后台反查令牌只补 `a_user`。（核对提示：这一列现在只取自令牌行，是认证过的值；改填不认证的 `porta_from_id` 会改变它的含义，见核对记录 B7。）
- 第二级不改 `conn_attempt` 的定稿逻辑和中继回落率的统计口径。

**明确不做**：中继权重按流量自动调整（方案 §3.7 已定以后再说）；用 hbbs 到中继的健康检查 RTT 替代客户端测量（那是 hbbs 到中继的距离，不是设备到中继的）；把测量历史落库。

### 3.6 开销与隐私（问题 6）

**连接数和流量**（估算，没实测）：
- 每台设备每轮 N × 3 次建连。N = 4 时每 5 分钟 12 次，一天 288 轮约 3500 次。
- 一次"建连后马上关"约 7~10 个包（三次握手 + 双方 FIN/ACK），每包 60~80 字节，约 0.6 KB；一天约 2 MB，一个月约 60 MB【推测】。按方案 §3.9 的中继计费口径（双向计费），中继侧收到的那一半对流量预算可以忽略。
- 中继侧：20 台设备 × 4 台中继时，每台中继每 5 分钟收到 20 × 3 = 60 次建连；porta-server 的健康检查每台中继每 5 分钟就有 100 次。
- 家用路由器的 NAT 表：每次建连占一条，几十秒内回收，每 5 分钟十几条，可以忽略。

**中继会不会当成异常**：不会（§2.7）。hbbr 不打日志、不计数、不自动封禁。要注意的只是中继所在的云平台或主机上另装的入侵检测（fail2ban 之类）：正常关闭（FIN）而不是 RST，测 3 次而不是更多，频率 5 分钟一轮，这些和普通客户端行为没有区别【推测】。

**隐私**：
- 中继每 5 分钟看到一次设备的公网 IP。中继都是自建的，而且真正走中继时本来就会看到。
- 服务端多知道每台设备到各中继的延迟。服务端已经有设备的公网 IP 和 GeoIP 位置，延迟没有多泄露什么；数据只在内存里，15 分钟过期。如果按 §3.5 加列，`conn_attempt` 会保留每次连接选中中继两段的延迟，随这张表 90 天删除。
- 候选列表会发给任何通过心跳 uuid 校验的设备。注册本身不认证（`server/PORTA.md` §9.3），所以等于公开中继地址。中继地址本来就会在每次连接时下发给客户端，hbbr 配了 `-k` 才能用，不是秘密。

## 5. 风险

1. **偏离方案原文**：§3.3 推荐带 id 而不是带测量值。如果维护者坚持原文，发起方那一侧要多出"UI 进程拿列表并测速"（新接口）或"从服务进程取结果"（改上游 `ipc.rs`）的工作量。
2. **上报不认证**：知道某台设备 id 和 uuid（uuid 不是秘密，第一期笔记 01 §7.1）的人能冒充它上报假的测量，把它的连接引到一台差的中继上。只影响质量，不影响安全：中继流量本身端到端加密，中继看不到内容。设备签名（第三期同批）做好以后，只采信签过名的心跳里的测量。
3. **实测与估计混用的偏差**：一端实测、另一端估计，权重又不全是 1 时，实测端的最后一公里延迟会让代价略偏。第二级普及后两端多数都是实测，影响会变小；校准数据靠 §3.5 的新列。
4. **测量代表性**：测的是 TCP 握手，不是会话期间的排队延迟；服务进程（SYSTEM）和用户会话的网络路径可能不同（分用户 VPN、按应用分流的代理）。开了代理或 WebSocket 时干脆不测。
5. **"服务端是 porta-server"的判断依赖心跳**：没配 API 地址、心跳失败或被限速回 `{}` 时，被控端退回上游逻辑，本地写死的中继会重新生效。porta-server 限速时回 `{}`（`server/PORTA.md` §9.3），要改成限速时也带 `{"porta":{"v":1}}`，或者客户端把标记保留到下一次明确的否定（例如 API 地址变了）为止【推测：两种都行，编码时定】。
6. **地址族不一致**：测速如果不照客户端连中继时的解析顺序挑地址（§3.2），双栈中继测的和实际走的可能不是同一个地址族；照同样的规则实现就能避免。
7. **没有实测**：本篇所有开销数字都是估算；"整端替换"能不能比第一级选得更好，要等上线后从 `conn_attempt` 的数据看。
