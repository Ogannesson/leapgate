# 第三期调研 02：设备签名

> Porta 是当时的工作名，2026-10-24 改名为 Leapgate（跃门）。

基线：客户端 `rustdesk@bd92623`；客户端的 hbb_common 是 `porta-cardo@6521d14`（基于上游 `5d52530`，`config.rs` 里和密钥相关的代码没改过）；服务端 `porta-server@c79181b`（第一期合入后的 main），契约 `server/PORTA.md`。
标记：【读码】= 读了代码，附位置；【推测】= 推理或未验证；【实测】本篇没有。
分工：同期笔记 `03-上报改走libs-porta.md` 定新上报接口的路径、请求和响应格式、`libs/porta` 里 HTTP 客户端的结构；本篇定"怎么证明是这台设备"：签什么、放在哪、怎么防重放、公钥从哪来、公钥变了怎么办、过渡期怎么区分。两篇的衔接点见 §2.8。

---

## 0. 要回答的问题

1. 客户端已有的 Ed25519 密钥对怎么生成、存在哪；`RegisterPk` 上报的 `pk` 是不是它；porta-server `peer` 表里的 `pk` 能不能直接当验签公钥。
2. 签名方案：签什么、放在哪、怎么防重放（时间窗、nonce 缓存怎么封顶）、容忍多大的时钟偏差；对比"设备私钥签每个请求""从 KeyExchange 派生会话密钥做 HMAC""服务端签发设备令牌"三种做法。
3. 公钥什么时候会变（重装、换机器、uuid 变化、`UUID_MISMATCH`、改 ID），对签名信任链有什么影响；第一期 porta-server 的 `update_pk` 和"只换 IP"分支要不要改。
4. 过渡期：原版客户端不签名，服务端怎么区分、怎么继续接受；"只接受 Porta 客户端"开关打开后怎么表现；一台设备开始签名后，要不要拒绝它之后的不签名上报（防降级）。
5. 签名还能保护什么：登录、地址簿这类用户令牌接口要不要绑设备；和第四期 Exit Node 的关系。
6. 服务端改动点：`PORTA.md` §9.3 的校验链怎么改，需要哪些新表、新列。

## 0.1 结论速览

1. **公钥现成，不用另发**：设备密钥对是 `Config::get_key_pair()` 首次调用时用 libsodium 生成的 Ed25519 密钥对，明文存在客户端主配置文件里；`RegisterPk` 上报的 `pk` 就是它的公钥；上游点对点握手里被控端也用同一把私钥签身份，控制端拿 hbbs 转来的 `peer.pk` 验。所以 `peer.pk` 本来就是这台设备的身份根，可以直接当验签公钥【读码】。
2. **推荐"设备私钥签每个请求"**（Ed25519，签名放请求头，签名内容 = 域分隔前缀 + 方法 + 接口名 + 设备 ID + 时间戳 + 请求体哈希）。上游自己就有一个照这个思路做的接口 `/api/switch-grant`，连"服务端拒收时间戳时回 `server_time`、客户端重签重试一次"的时钟纠偏都有，照着做即可【读码】。KeyExchange 派生密钥不可行：KeyExchange 只认证服务端，不认证客户端，而且设备注册走 UDP、平时根本不做 KeyExchange【读码】。服务端签发令牌要先有一次签名做引导，零件只多不少。
3. **签名只和 `peer.pk` 的登记一样可信，而第一期的登记规则允许换掉它**：同一 uuid、同一来源 IP 的 `RegisterPk` 可以把 `pk` 换成任意值【读码】，而 uuid 不是秘密（Windows 上就是注册表里的 MachineGuid，任何本机用户都能读；`RegisterPk` 经明文 UDP 发送；HTTP 上报里也带着）【读码】。所以要配一条 **"公钥锁定"**：设备第一次签名验证通过后，在 `peer` 行上记下锁定时间，之后这个 ID 只认这把公钥，换公钥的 `RegisterPk` 一律回 `UUID_MISMATCH`。这条顺带堵住了上游点对点身份链上的同一个口子（同出口 IP 的人换掉公钥后能冒充设备接受连接）【推测】。
4. **防降级按设备，不按全局**：锁定过的设备，兼容路径上的不签名上报按"uuid 不符"处理；没锁定的设备（原版客户端、第三期以前的 Porta）照第一期规则继续接受。全局开关"只接受 Porta 客户端"打开后，兼容上报路径整体拒收。
5. **防重放用"时间窗 ±60 秒 + 每设备最近 64 条签名 + 下限"**，每设备约 1.5 KB 内存、条目数封顶，不落库；时钟偏差靠服务端回时间、客户端记偏移量解决，所以时间窗可以收窄。
6. **签名真正要保护的是"设备归属"**：第一期登录时绑定设备只比 uuid，任何知道 uuid 的人都能把别人的设备挂到自己名下【读码】。现在这只影响组面板显示，到第四期 Exit Node 的"出口只列给设备主人"就成了权限问题。登录请求从 Dart 发出，第三期签不了；在新界面轨道把登录下沉到 `libs/porta` 之前，Exit Node 的主人只认命令行指定的或经签名登录绑定的（§2.6）。
7. **顺带发现，和签名有关但要单独修**：同一台 Windows 上装着原版和 Porta、两者又指向同一个 porta-server 时，两边按 MAC 地址生成的默认 ID 相同、uuid 也相同，会抢同一个 ID【推测：读码推出，没实测】（§1.8）。
8. **服务端改动量小**：`peer` 表加一列 `pk_pinned_at`，新增一个验签模块（约 200 行，含防重放）；`uuid_matches` 改成同时读锁定状态；`RegisterPk` 加一处锁定判断；命令行加"看公钥指纹 / 重置锁定"两个子命令（重置的写法要改，见 §5.2 第 8 条）。不需要改 proto。

## 1. 读码结论

### 1.1 设备密钥对：怎么生成、存在哪、谁在用【读码】

- 生成：`porta-cardo@6521d14:src/config.rs` `Config::get_key_pair`。先看进程内缓存 `KEY_PAIR`，没有就读主配置文件（`Config::load_("")`）；配置里 `key_pair.0`（私钥）为空时调 `sign::gen_keypair()`（sodiumoxide，即 libsodium 的 Ed25519）生成，起一个线程写回 `CONFIG` 并 `store()`。类型 `KeyPair = (Vec<u8>, Vec<u8>)`，顺序是 (sk, pk)，sk 64 字节（种子 + 公钥）、pk 32 字节。
- 存放：主配置文件 `{APP_NAME}.toml`（`Config::file_("")`）。Windows 安装版里注册、心跳、审计都跑在以 SYSTEM 身份运行的 `--server` 进程里（第一期笔记 01 §1.1），配置目录被 `fn patch` 改写到 `C:\Windows\ServiceProfiles\LocalService\AppData\Roaming\<APP_NAME>\config\`。`key_pair` 不加密，`Config::store` 只处理永久密码（`prepare_config_for_store`）和 ID（写成 `enc_id`），`key_pair` 原样写入。
- 用户进程也有一份【读码，核对时补】：Windows 上不带参数启动的界面进程在 `rustdesk@bd92623:src/core_main.rs` 里起 `start_server(false, …)`，走 `src/server.rs` `start_server` 的 else 分支：连主 IPC、发 `Data::SyncConfig(None)`，拿到服务进程的整个 `Config`（含 `key_pair`）后 `Config::set` 并落盘到用户 `%APPDATA%` 下的配置。所以用户进程的 `Config::get_key_pair()` 一般就是服务进程那一把。例外：界面进程在同步完成前就调过 `get_key_pair`，进程内缓存 `KEY_PAIR` 会留着它自己生成的那把（`Config::set` 只在 macOS 上清这个缓存）；服务没在跑时界面进程自己当服务，用的也是自己的。`Data::ConfirmedKey` 的处理函数只在 `key_confirmed` 为真时回密钥对，而且 bd92623 里没有调用方（`src/ipc.rs`）。
- 谁在用这把密钥：
  - `RegisterPk.pk`：`rustdesk@bd92623:src/rendezvous_mediator.rs` `RendezvousMediator::register_pk`，`pk = Config::get_key_pair().1`，同时带 `uuid = hbb_common::get_uuid()` 和 `id = Config::get_id()`。**上报的 pk 就是这把密钥的公钥。**
  - 点对点身份：`rustdesk@bd92623:src/server.rs` `identity_handshake`，被控端用私钥对 `IdPk{id, pk: 临时 box 公钥}` 签名（`SignedId`）发给控制端。
  - 上游的设备签名 API：`rustdesk@bd92623:src/hbbs_http/sync.rs` `register_switch_grant`（见 §1.3）。
  - 界面显示公钥指纹：格式由 `common.rs` `pk_to_fingerprint` 决定（公钥 hex，每 4 个字符一组）。桌面版界面经 IPC 向服务进程要（`src/ipc.rs` 的 `fingerprint` 选项，服务进程算 `pk_to_fingerprint(Config::get_key_pair().1)`，`key_confirmed` 为假时不给）；`src/ui_interface.rs` `get_fingerprint` 直接调的那支只在移动端编译。所以设备界面上显示的就是服务进程那把、也就是注册到 `peer.pk` 的公钥。控制端会话里也会显示对端验过的指纹（`src/client/io_loop.rs` `set_fingerprint`）。服务端命令行可以按同一格式打印，供维护者肉眼比对（§2.4）。
- 公钥变化时客户端会自己重注册：`rendezvous_mediator.rs` `CheckIfResendPk`（配置同步后缓存公钥变了就把 `key_confirmed` 置假，下一轮重发 `RegisterPk`）。上游注释说这针对的是"配置还没从 root 同步过来时已经用新生成的公钥注册了"的情况。它唯一的构造点在 `src/server.rs` `sync_and_watch_config_dir`，并且带 `#[cfg(target_os = "macos")]`，Windows 上从不触发。

### 1.2 `peer.pk` 已经是点对点身份的信任根【读码】

- porta-server `src/rendezvous_server.rs` `get_pk`：控制端打洞时，服务端从内存 `PeerMap` 取目标的 `pk`，用会合服务器私钥签 `IdPk{id, pk}` 后放进 `PunchHoleResponse`/`RelayResponse`。
- 控制端 `rustdesk@bd92623:src/client.rs` `secure_connection`：用配置里的服务器公钥 `key` 解开 `IdPk`，拿到目标的 `pk`，再用它验被控端发来的 `SignedId`。验过了才建立端到端加密。**验不过时 TCP、UDP、中继连接不断开**：退回不加密连接（日志 "pk mismatch, fall back to non-secure"），之后 `src/client/io_loop.rs` 弹"Insecure Connection"提示（`confirm_insecure_connection`），用户点继续就以明文会话连下去，点关闭才断开；只有 WebRTC 直接断开。（核对时更正：原文写"验不过就断开"。）
- 所以"`peer` 表里这个 ID 对应哪把公钥"在上游体系里早就决定了"谁能以这个 ID 接受连接"。拿它来验 HTTP 上报的签名，信任根是同一个，不新增任何密钥。
- 第一期已经保证 `pk` 正好 32 字节（`PORTA.md` §6 第 7 条；`rendezvous_server.rs` `RegisterPk` 分支开头的长度检查），能直接 `sign::PublicKey::from_slice`。

### 1.3 上游现成的设备签名范例：`/api/switch-grant`【读码】

`rustdesk@bd92623:src/hbbs_http/sync.rs` `register_switch_grant` / `switch_grant_signed_msg`：

- 被签内容：`"switch-grant\0" ‖ id ‖ "\0" ‖ verifier ‖ "\0" ‖ timestamp`，字段用 NUL 分隔，前缀做域分隔，时间戳是十进制 unix 秒。
- `sign::sign_detached`，签名 base64 后和 `id`、`timestamp` 一起放进 JSON 请求体。
- 服务端回 `{"accepted": false, "server_time": …}` 时，客户端用服务器时间重签、重试一次；第二次还被拒就放弃。
- 这是 RustDesk Pro 服务端的接口，porta-server 没实现。服务端用多大的时间窗看不到（闭源）【推测】。

Porta 照这个思路做，有三处不同：签名放请求头而不是请求体（请求体按原始字节签，不必规范化 JSON）；被签内容里加接口名和请求体哈希（switch-grant 只有一个接口、请求体就是被签字段本身）；加防重放（switch-grant 只靠时间戳）。

### 1.4 uuid 不是秘密【读码】

- `hbb_common::get_uuid()`（`porta-cardo@6521d14:src/lib.rs`）：桌面平台取 `machine_uid::get()`，Windows 上是注册表 `HKLM\SOFTWARE\Microsoft\Cryptography` 下的 `MachineGuid`（核对时读了依赖源码：`machine-uid@381ff57:src/lib.rs` `get_machine_id`，即 Cargo.lock 里的版本）。普通用户能不能读是 Windows 默认 ACL 的事，没核对；不过上游登录本来就在普通用户的界面进程里读它（`flutter_ffi.rs` `main_get_uuid`）。取不到时退回用 **公钥** 当 uuid。
- 它出现在：`RegisterPk`（明文 UDP）、心跳和 sysinfo 请求体、被控端审计请求体（`src/server/connection.rs` `post_conn_audit` 等）、登录请求体（Dart `flutter/lib/models/user_model.dart` `login` 发出，uuid 取自 `bind.mainGetUuid()` → `src/ui_interface.rs` `get_uuid`）。API 走明文 HTTP 时链路上谁都看得见。
- 结论：第一期 §9.3 的 uuid 校验只能挡"没在 hbbs 注册过的 ID"，挡不住冒充，契约里也是这么写的。

### 1.5 第一期注册规则对 `pk` 的约束【读码】

porta-server `src/rendezvous_server.rs` `RegisterPk` 分支 + `src/peer.rs` `PeerMap::update_pk`，对已有条目：

| 请求和库里的比较 | 结果 |
|---|---|
| uuid 不同 | `UUID_MISMATCH`（客户端收到后换一个随机 ID，`rendezvous_mediator.rs` `handle_uuid_mismatch` → `Config::update_id`） |
| uuid 相同、IP 不同、pk 不同 | `UUID_MISMATCH` |
| uuid 相同、IP 相同、pk 不同 | **接受，换成新 pk**（`changed = true` → `update_pk`） |
| uuid 相同、pk 相同、IP 不同 | 接受，只换地址（"只换 IP"分支，先改内存再写库） |
| 条目 uuid 为空 | 当作新登记，接受。注意：库里已有这一行（`guid` 非空）时，`database.rs` `update_pk` 只写 `id`、`pk`、`info`，**不写 `uuid`**，所以内存里换成新 uuid、库里仍是空（核对时补） |

- 第三行就是口子：知道 uuid、又和设备共用出口 IP（同一个家庭或公司 NAT、运营商级 NAT 地址池）的人，可以把这个 ID 的公钥换成自己的。换完以后设备本身不会察觉（它的 `key_confirmed` 还是真，不会重发 `RegisterPk`）；服务端只在 `RegisterPeer` 发现 IP 变了、内存条目的 pk 为空、或条目不在内存里（例如闲置 24 小时被淘汰）时才要它重发（`update_addr`）。
- 第四行让任何人从别的地址用"原 uuid + 原公钥"把这个 ID 的地址指向自己（直接发 `RegisterPk` 即可，公钥相同就接受）。冒充者拿不出私钥，控制端的 `SignedId` 验证会失败，但按 §1.2，上游的后果不是直接断开，而是弹"不安全连接"提示：用户点继续，就进了冒充者那一端的明文会话；点关闭才只是拒绝服务。（核对时更正：原文写"后果是连接失败（拒绝服务），不是冒充"。）这是上游原有的问题，不在本篇范围。
- 改 ID：上游客户端经 21116/TCP 发不带 `pk` 的 `RegisterPk{old_id, id, uuid}`（`src/ui_interface.rs` `change_id` → `check_id`）；porta-server 在 TCP 上对 `RegisterPk` 一律回 `NOT_SUPPORT`（`rendezvous_server.rs` TCP 分支），第一期不支持改 ID（`PORTA.md` §1）。本地手改 `id` 选项的设备会以新 ID 重新注册，旧 `peer` 行留着。

### 1.6 KeyExchange 不认证客户端【读码】

- porta-server `src/kx.rs` 和 `PORTA.md` §6 第 1 条：服务端先发用会合私钥签过的临时公钥，客户端回 `KeyExchange{keys: [客户端临时 box 公钥, 密封的对称密钥]}`，客户端这一侧没有任何签名。它证明的是"对面是持有会合私钥的服务端"，不证明客户端是谁。
- 设备平时用 UDP 注册（`RegisterPeer`/`RegisterPk`），只有走代理、WebSocket 或禁用 UDP 时才用 TCP，而这几种 porta-server 第一期都不做注册（`PORTA.md` §1 的"不做"清单和 §11 "走代理或 WebSocket 的客户端"一条；客户端选 TCP 的条件见 `rendezvous_mediator.rs` `RendezvousMediator::start`）。HTTP API 又是另一条连接（21114）。三条通道之间没有共享状态。

### 1.7 HTTP 栈的约束（引自笔记 03 §1.3、§2.4）

- 上游 `post_request` 的 `header` 参数只支持一个 `Key: Value`；`libs/porta` 调不到主 crate 的 HTTP 函数（会成环）。笔记 03 推荐 `libs/porta` 自己用 reqwest 0.12、严格校验 TLS、不做 TCP 代理回退，这样请求头不受限制。
- Porta 客户端的默认 API 地址：构建时注入了 `PORTA_API_SERVER` 就用它；没注入时按内置会合服务器推出 `http://<会合主机>:21114`（`client/libs/porta/src/brand.rs` `default_api_server`），即明文 HTTP。现有构建脚本（`scripts/windows/`）没注入这个变量，所以眼下默认就是明文 HTTP。用户自己填了会合服务器、没填 API 地址时，上游 `get_api_server_` 推出的也是 `http://…:21114`。
- 同机 nginx 默认丢弃名字里带下划线的请求头（`underscores_in_headers off`）【推测：按 nginx 文档的已知行为，本次没联网核对】，所以 Porta 的请求头名只用连字符。

### 1.8 顺带发现：原版和 Porta 共存、指向同一个服务器时会抢同一个 ID【推测：读码推出，没实测】

- 默认 ID 由 `Config::gen_id` → `get_auto_id` 按 MAC 地址后 4 字节算出（`porta-cardo@6521d14:src/config.rs`），和 `APP_NAME` 无关；uuid 是整机共用的 MachineGuid。第二期笔记 02 §2.1 写的"两边 ID、密钥对各是各的"只对密钥对成立：配置文件确实分开，但两边从同一块网卡算出的默认 ID 相同。
- 两边都指向 porta-server 时：后注册的一方 `RegisterPk` 同 uuid、同 IP、不同 pk，按 §1.5 第三行被接受，公钥被换掉；之后两边都发 `RegisterPeer`，IP 相同，`update_addr` 只更新端口、不要求重发公钥，于是这个 ID 的地址在两个进程之间来回切换，控制端连上哪一个看运气，连到公钥不符的那一个时 `SignedId` 验不过。
- 公钥锁定（§2.4）不能完全解决它：锁定只拦 `RegisterPk`，先注册的原版之后只发 `RegisterPeer`。根治是让 Porta 的默认 ID 和原版错开（例如在 `porta-cardo` 的 `get_auto_id` 里把 MAC 和一个固定的 Porta 盐一起哈希，只影响首次生成 ID 的设备）。见 §3 问题 8。
- 各自指向不同服务器（原版指向旧 hbbs、Porta 指向 porta-server）时不受影响。

## 2. 设计

### 2.1 认证机制选型（问题 2）

| | A. 设备私钥签每个请求（推荐） | B. KeyExchange 派生会话密钥做 HMAC | C. 服务端签发设备令牌 |
|---|---|---|---|
| 证明的是什么 | 持有 `peer.pk` 对应的私钥 | 和服务端做过一次 KeyExchange，**不证明是哪台设备**（§1.6） | 令牌发出时证明过一次，之后只证明"持有令牌" |
| 新增的密钥或秘密 | 无 | 每条 TCP 连接一个会话密钥 | 每台设备一枚令牌，要存客户端配置、服务端存哈希 |
| 引导 | 无（公钥在注册时已经上报） | 设备平时走 UDP 注册，要另开 TCP 连接做 KeyExchange；会合模块和 API 模块要共享会话表 | 首次领令牌本身要证明设备身份，只能用 A 的签名，或者"首次使用即信任" |
| 服务端状态 | 只有防重放缓存（有界，可选） | 会话表，随连接生灭，API 请求要找到对应会话 | 令牌表、吊销、轮换 |
| 每请求开销 | 一次 Ed25519 验签，几十微秒【推测：按 libsodium 常见性能估，未实测】 | 一次 HMAC | 一次哈希查表 |
| 上游先例 | `/api/switch-grant`（§1.3） | 无 | 无（Pro 的设备注册令牌是用户令牌，不是设备令牌） |
| 结论 | 推荐 | 不可行 | 不推荐：比 A 多一枚要保管、要吊销的秘密，而且引导还得靠 A |

验签开销的量级：上报类请求每来源每分钟最多 1000 次（`PORTA.md` §9.3），真实设备在会话中每 3 秒一次心跳。验签放在来源限速之后、查到公钥之后，签名不对的请求最多花一次验签。

### 2.2 签什么、放在哪（问题 2）

**放在请求头**（推荐），一个头装下全部字段：

```
Porta-Device-Auth: v1 id=<base64url(设备ID)>, t=<unix 秒>, s=<base64url(签名 64 字节)>
```

- 用独立的头，不用 `Authorization`：以后签名登录、地址簿这类请求（§2.6）要同时带用户令牌 `Authorization: Bearer …` 和设备签名，两者不能抢同一个头。笔记 03 §2.4 暂写的是 `Authorization: Porta-Device …`，建议统一成这里的写法。
- 设备 ID 用 base64url：开了"主机名当 ID"的设备，ID 里可能有请求头不允许的字符。
- 新接口的请求体里**不再带 `id`**，设备身份只从这个头来，免得头和体里的 ID 不一致时要再定一条"以谁为准"的规则。uuid 照样可以放在请求体里（延迟补绑还要用它，见笔记 03 §2.5），但不参与认证。

**被签内容**（字段按顺序拼接，NUL 分隔，和 switch-grant 同一种写法）：

```
"porta-device-v1\0" ‖ 方法 ‖ "\0" ‖ 接口名 ‖ "\0" ‖ 设备ID ‖ "\0" ‖ 时间戳(十进制) ‖ "\0" ‖ sha256(请求体原始字节)
```

- 域分隔前缀 `porta-device-v1\0`：同一把私钥还在签点对点握手的 `IdPk`（protobuf，首字节是 `0x0a`）和 switch-grant（`switch-grant\0` 开头），前缀不同，一处的签名不可能被拿到另一处冒用。
- **接口名，不签完整 URL 路径**：接口名是 `/api/porta/v1/` 之后的部分（例如 `heartbeat`、`audit/conn`）。反代把 `/xxx/api/` 改写成 `/api/` 时前缀会变，后缀不变；主机名也不签，同理。签接口名是为了让给审计签的名不能拿去当心跳用。
- 请求体签哈希，不签规范化 JSON：服务端第一期本来就用 `Bytes` 收请求体、自己解析（`PORTA.md` §9.1 第 2 条），对原始字节算 sha256 即可，不存在两边序列化不一致的问题。
- 不单设 nonce 字段：Ed25519 签名是确定性的，同一条消息签出来完全相同，防重放直接拿签名本身当去重键（§2.3）。审计请求体里上游已有的 `nonce` 照旧用于审计去重，和这里无关。

**备选：签名放请求体**，形如 `{"payload": "<原 JSON 字符串>", "sig": …}`。好处是不依赖请求头，任何 HTTP 栈、任何反代都原样转发；坏处是 JSON 套 JSON，服务端要解两层，请求体上限要按套一层后的大小算。笔记 03 已经推荐 `libs/porta` 自己用 reqwest，请求头不受限制，所以不推荐。

**服务端校验顺序**：头格式和长度（ID 解码后 ≤ 253 字节，签名正好 64 字节）→ 来源限速（和兼容路径共用额度）→ 时间窗 → 按 ID 取 `peer.pk` 和锁定状态（先查内存 `PeerMap`，没有再查主池；`update_pk` 先写库后改内存，两处的公钥一致【读码】）→ 验签 → 防重放 → 第一次验签通过就锁定公钥（§2.4）。任何一步失败回 401 + `{"error": "<原因>", "time": <服务器 unix 秒>}`，原因取 `bad_auth`、`stale_time`、`replay`、`unknown_device`、`bad_signature` 之一。Porta 客户端没有 TCP 代理回退，新路径不受"不回 5xx"那条约束（笔记 03 §2.3）。

### 2.3 时钟和防重放（问题 2）

**时钟偏差**：

- 客户端记一个"服务器时间偏移量"：心跳响应里的 `time`（笔记 03 §2.3 已经加了这个字段）每次都更新它，401 带回的 `time` 也更新它，然后立刻重签重试一次（照 switch-grant）。签名用的时间戳 = 本机时间 + 偏移量。
- 有了这套纠偏，时间窗可以收窄到 **±60 秒**：客户端每次尝试最多 12 秒，审计每次重试都重签（笔记 03 §2.4），60 秒足够。本机时钟差几小时的设备，第一次请求被拒后拿到服务器时间就恢复。
- 备选 ±300 秒（Kerberos 的默认值）：不依赖纠偏也能容忍常见偏差，代价是防重放缓存要覆盖 5 分钟，条目多 5 倍。有纠偏就不需要。

**防重放**（推荐）：每台设备在内存里一个小结构：

- `max_ts`：收到过的最大时间戳；`floor`：下限；`ring`：最近 64 条已接受请求的 `(时间戳, 签名前 16 字节)`。
- 接受条件：`|t − now| ≤ 60`，`t ≥ max_ts − 30`，`t > floor`，且 `(t, 签名前 16 字节)` 不在 `ring` 里。接受后放进 `ring`；`ring` 满了挤掉最老的一条，并把 `floor` 提到被挤掉那条的时间戳（之后时间戳不晚于它的请求一律拒收，被拒的合法请求由客户端重签重试）。
- 允许 30 秒内乱序：同一设备的心跳和审计分别走不同的 HTTP 请求（审计在 `connection.rs` 的发送队列里，心跳在同步线程里），到达顺序可能和签名顺序不同；登录以后如果也签名，会从另一个进程发出。所以不能要求时间戳严格递增。
- 新建条目（服务端刚启动，或条目被淘汰后再来）时 `floor = now − 30`：重启前截获的请求在重启后最多还能重放 30 秒，和乱序容忍度相同。
- 封顶：表最多 4096 台设备，满了淘汰最久没来过的。每条约 64 × 24 字节 ≈ 1.5 KB，合计约 6 MB。刻意造假设备的人（注册不认证，自带密钥对就能签出有效签名）最多让真实设备的条目被淘汰、重放窗口回到 30 秒，不会让内存增长。
- 不落库：要防的是"截获后重放"，而截获的前提是 API 走明文 HTTP 或 TLS 被攻破；上报类接口被重放的后果也有限（心跳刷新在线时间、旧 sysinfo 覆盖新 sysinfo、审计已有 nonce 去重）。为这个在每次请求时写库不划算。

**备选：只靠时间窗**，不做缓存。零状态，代价是 ±60 秒内可以原样重放。在全程 HTTPS 的部署里几乎没有区别；默认地址是明文 HTTP（§1.7），所以推荐做缓存。

### 2.4 公钥锁定：让签名有意义（问题 1、3）

**做法**（推荐）：

- `peer` 表加一列 `pk_pinned_at INTEGER`（NULL = 未锁定）。
- 某个 ID 的第一个签名请求验证通过时，执行 `update peer set pk_pinned_at = ? where id = ? and pk = ? and pk_pinned_at is null`，只锁定刚才验过的那把公钥（带上 `pk = ?`，防止验签和锁定之间会合模块恰好换了公钥），成功后同步改内存 `PeerMap` 条目上的 `pinned` 标记（`PeerMap` 已经在 `AppState` 里由 API 和会合模块共用，`PORTA.md` §3）。之后每个签名请求只读这个标记，不再写库。
- 会合模块 `RegisterPk`：条目已锁定、请求里的 `pk` 和库里的不同 → 回 `UUID_MISMATCH`，不管 uuid 和 IP 是否相同。其余情况照第一期规则（§1.5）。`PeerMap::get` 从库里加载条目时一并读出锁定状态。`update_pk` 不碰这一列。
- 为什么回 `UUID_MISMATCH`：它在上游的语义就是"这个 ID 已被另一台机器占用"，客户端收到后换一个随机 ID、带着新公钥重新注册（§1.5）。对冒充者，结果是它换了个 ID、和被冒充的设备无关了；对共存时后注册的原版客户端（§1.8 里先锁定的是 Porta 时），结果是它换成自己的 ID，冲突消失。
- 命令行：
  - `device key <id>`：打印公钥指纹（和客户端 `pk_to_fingerprint` 同一格式，维护者可以和设备界面上显示的指纹比对）、锁定时间、uuid 长度。
  - `device key reset <id>`：清掉锁定，同时把这一行的 `uuid` 和 `pk` 置空（库和内存都改），下一次任何来源的 `RegisterPk` 都按新登记接受（`peer.uuid` 为空时的分支，§1.5 末行）。用于设备丢了密钥、又想保住原 ID 的情况。**前提不成立，见核对记录**：这一行的 `guid` 还在，新登记走的是 `database.rs` `update_pk`，它不写 `uuid`，库里的 uuid 会一直是空的：兼容路径的 `uuid_matches`（读库）从此不符，条目每次被淘汰或服务重启后又回到"谁先注册谁拿走"。实现时要么改成删掉这一行（让下次注册走 `insert_peer`，受新 id 限额约束），要么让这条分支同时写 `uuid`。

**公钥会变的场景**，以及锁定后的结果：

| 场景 | 客户端发什么【读码】 | 第一期结果 | 加锁定后（设备已锁定） |
|---|---|---|---|
| 正常重启、升级 | 同 ID、同 uuid、同 pk | 不变 | 不变 |
| 换了网络 | 同 ID、同 uuid、同 pk、新 IP | "只换 IP"分支，接受 | 不变 |
| 卸载重装，配置文件被删 | 同 ID（MAC 算出来的）、同 uuid、**新 pk** | 同 IP 接受换公钥；换了 IP 回 `UUID_MISMATCH`，客户端换随机 ID | 一律 `UUID_MISMATCH` → 客户端换随机 ID、新 ID 重新锁定。想保住原 ID：维护者先 `device key reset` |
| 重装系统 | MachineGuid 变了 → **新 uuid**；配置没了 → 新 pk | `UUID_MISMATCH` → 换随机 ID | 同左 |
| 把整个配置拷到另一台机器 | 同 ID、同 pk、**新 uuid** | `UUID_MISMATCH` → 换随机 ID，但保留同一对密钥 | 同左。两个 ID 共用一把公钥不影响签名：被签内容里有设备 ID，一个 ID 的签名不能拿去冒充另一个 |
| `machine_uid` 取不到 | uuid 退回用公钥（§1.4） | uuid 和公钥一起变 | 同"重装系统" |
| 配置同步后公钥变了（`CheckIfResendPk`） | 同 ID、同 uuid、新 pk | 同 IP 接受 | `UUID_MISMATCH` → 换 ID。`CheckIfResendPk` 只在 macOS 上构造（§1.1），Windows 上不会出现这一行；Windows 的配置同步方向是服务进程到界面进程（§1.1），服务进程的配置是权威的 |
| 用户在本地手改 ID | 新 ID、同 uuid、同 pk | 新 ID 当新设备登记 | 新 ID 未锁定，第一次签名时锁定；旧 ID 的行和锁定留着，可以用命令行删 |
| 改 ID（`RegisterPk.old_id`） | 经 TCP，不带 pk | `NOT_SUPPORT` | 不变。以后要支持改 ID，应当要求设备签名，新 ID 继承旧 ID 的公钥和锁定 |

**锁定是"首次使用即信任"**：锁定的是第一次签名时 `peer` 表里的那把公钥，而它当初来自不认证的 `RegisterPk`。如果有人在设备第一次签名之前就从同一出口 IP 换掉了公钥，锁定的就是冒充者的公钥，真设备之后会收到 `UUID_MISMATCH` 并换 ID。维护者能察觉（设备 ID 变了），也能用 `device key` 比对指纹。要彻底堵上，需要锁定前由维护者手工确认指纹，见 §3 问题 4 的备选。

**没选的备选**：

- 不锁定，签名只证明"持有当前登记的公钥"。零改动，但同出口 IP、知道 uuid 的人换掉公钥后就能签出有效的上报（§1.5），签名形同虚设。
- 锁定后对换公钥的 `RegisterPk` 静默丢弃或回新的结果码（例如在 proto 里加 `KEY_MISMATCH`），设备保住原 ID、但一直离线，直到维护者重置。优点是设备 ID 不会悄悄变；缺点是要改 proto、Porta 客户端要处理新结果码，丢了密钥的设备在维护者处理前一直不可用。对只有维护者和几个朋友的部署，"换 ID 但能用"比"保住 ID 但离线"好。
- 允许用旧私钥签名的"公钥轮换"请求：只有密钥还在、主动轮换时才用得上，Porta 目前没有主动轮换的需求。不做。

### 2.5 过渡期：区分、防降级、退出兼容（问题 4）

**区分**：靠路径区分，不靠请求头有没有签名。笔记 03 推荐新接口放在 `/api/porta/v1/` 下：

- 兼容路径（`/api/heartbeat`、`/api/sysinfo`、`/api/audit/*`）：完全照第一期 §9.3，原版客户端和第三期以前的 Porta 走这里。
- Porta 路径：必须带有效签名，不签名回 401，不退回 uuid 校验。

**防降级**（推荐做）：一台设备一旦锁定，兼容路径上以它的 ID 发来的不签名上报按"uuid 不符"处理（心跳回 `{}`、sysinfo 回 403 空 body、审计回 200 空 body 不入库，和第一期 §9.3 的"不符"完全一样，原版客户端不会走错分支）。

- 实现：`uuid_matches` 现在查的是 `select uuid from peer where id = ?`，改成同时读 `pk_pinned_at`，锁定了就返回"不符"。查库次数不变。
- 例外：控制端会话结束写备注那条 `/api/audit/conn`（"有 note 键、没有 uuid 键"）不受影响。它是控制端发的，请求里的 `id` 是被控端的 ID，被控端锁没锁定和发请求的人无关（见 §2.6）。
- 为什么要做：不做的话，签名只多了一条"更安全的路"，冒充者照样走兼容路径的老路伪造上报。
- 客户端一侧的防降级（服务端某天回 404 时 Porta 客户端要不要退回兼容路径）由笔记 03 §3 问题 2 定，它推荐不退。两边合起来才完整：服务端拒收已锁定设备的不签名上报，客户端也不主动降级。
- 代价：同一个 ID 上，Porta 锁定以后再换回原版 RustDesk 上报就收不到了。但实际上换回原版时配置目录不同、公钥不同，按 §2.4 它会收到 `UUID_MISMATCH` 并换成新 ID，以新设备身份正常上报，不会卡住。

**"只接受 Porta 客户端"开关**（`docs/architecture.md` §3.1 退出机制第 3 步，配置项建议放 `porta.toml` 的 `[api]` 下，例如 `porta_only = false`）打开后：

- 兼容上报路径对所有 ID 按"不符"处理（同上面三种回法）。
- Porta 路径不变。还没锁定的设备第一次签名时照常锁定（"首次使用即信任"继续有效），不要求预先登记。
- 账号、地址簿、组面板接口**第三期不受这个开关影响**：Porta 客户端的这些请求在新界面轨道之前还是从 Dart 发出、不签名，关掉它们等于把 Porta 自己也关在外面。等新界面轨道把它们下沉到 `libs/porta` 并签名以后，开关再扩大到这些接口。这和 `docs/architecture.md` §5"退出兼容在第三期和新界面轨道都完成后"一致。
- 会合层不受这个开关影响：原版客户端照样能注册、能点对点连接。§3.1 说"退出之后原版 RustDesk 客户端连不上 Porta 服务端"，要在会合层做到，需要一个原版没有的标记，最自然的是给 `RegisterPk`/`RegisterPeer` 也加设备签名（新 proto 字段，原版不带）。这超出第三期范围，见 §3 问题 6。

### 2.6 签名还能保护什么（问题 5）

**设备归属（登录绑定）**：这是签名最该保护、第三期却最难保护的一块。

- 现状【读码】：登录请求带设备的 `id`、`uuid`，`uuid_matches` 通过就把 `device.user_id` 设成登录的人（`PORTA.md` §11；`server/src/api/account.rs` 用 `on conflict(id) do update set user_id = excluded.user_id`，已有主人的设备也会被改绑）；延迟补绑时，心跳会把设备挂给"令牌表里 `device_id`、`device_uuid` 和它相同、最近用过的那个账号"。uuid 不是秘密（§1.4），所以任何有账号的人都能用别人的 ID 和 uuid 登录一次，把别人的设备挂到自己名下；即使设备的心跳签了名，延迟补绑挑中的仍可能是冒充者的令牌。
- 现在的后果：设备出现在冒充者的组面板里（`PORTA.md` §11 说"归属只决定设备在组面板里列在谁名下，不影响策略和连接权限"）。
- 第四期的后果：Exit Node"出口只列给设备主人和被授权的人"（`docs/architecture.md` §3.9），归属就成了权限。
- 要堵上，登录请求本身得由设备签名，证明"这次登录发生在这台设备上"。登录在 Dart 里发出（第三期不改）；用户进程按读码一般拿得到服务进程那把私钥，但有例外、没实测（§1.1）。所以：
  - 第三期：登录绑定不改；令牌表加一列 `device_verified`（第三期一律 0）。
  - 新界面轨道把登录下沉到 `libs/porta` 时，登录请求同时带用户凭据和 `Porta-Device-Auth`，验签通过才绑定、才记 `device_verified = 1`；已锁定设备只接受签名登录的绑定。
  - 第四期 Exit Node 的出口目录只认两种主人：签名登录绑定的，和维护者用命令行指定的（新增 `device owner <id> <user>`）。
- 备选：第三期就在 Dart 登录处加几行挂钩，经 `porta_ffi.rs` 调 `libs/porta` 签名。动的是上游 Dart 热点文件，且新界面轨道会整块重写它，属于白做。不推荐。

**会话备注**（`/api/audit/conn` 的 note 那条）：现在不认证，靠"每种连接类型最多改 4 行"封顶写入量（`PORTA.md` §9.3）。签名之后可以要求：签名的设备 ID 必须等于那几条审计记录里的 `peer_id`（发起会话的控制端），这样只有当事控制端能写备注。备注在控制端的 Dart 里发出，同样要等新界面轨道；第三期不动，记作兼容债务。**前提不成立，见核对记录**：这条备注请求是控制端界面进程里的 Rust 代码发的（`rustdesk@bd92623:src/ui_session_interface.rs` `send_note`，经 `post_request` 发到 `/api/audit/conn`，由 Dart 调 `flutter_ffi.rs` `session_send_note` 触发），不在 Dart 里；Dart 里那个 `PUT /api/audit`（`flutter/lib/common/widgets/dialog.dart`）是另一个接口，porta-server 第一期没实现。所以签它不必等新界面轨道，但要在上游热点文件 `ui_session_interface.rs` 里加挂钩，而且要在界面进程里签名（私钥情况见 §1.1）。第三期动不动仍由维护者定。

**用户令牌要不要绑设备**（类似 OAuth 的 DPoP：每个用户请求都要带设备签名，令牌被偷了在别处用不了）：不推荐第三期做。令牌和设备私钥放在同一个用户的配置目录里，能偷到令牌文件的人多半也能偷到私钥；服务端库里只存令牌的 sha256，数据库泄露也拿不到令牌。收益只剩"令牌经明文 HTTP 被看到"这一种情况，而它应该靠 HTTPS 解决。等登录下沉以后再评估。

**和 Exit Node 的关系**（第四期）：

- 出口能力是设备属性，经心跳上报（`docs/architecture.md` §3.9）。这个字段只在 Porta 路径的签名心跳里认，兼容路径上出现就忽略。否则任何人都能伪造别人的心跳，把别人的出口状态改成开或关，让目录显示错误。
- 出口目录只列已锁定的设备。
- 控制端真正连到出口设备时，照常走点对点认证：控制端用 hbbs 转来的 `peer.pk` 验 `SignedId`（§1.2），再过设备密码。公钥锁定让这一步也不会被同出口 IP 的人换掉公钥（§1.5）。注意上游验不过时不断开、而是弹不安全连接提示让用户选（§1.2），出口场景下要不要改成直接断开，第四期再定。
- 主人认定见上面"设备归属"。

**响应签名**（笔记 03 §3 问题 3(b) 交给本篇一起定）：推荐做。

- 原因：请求签名只防伪造上报，防不住篡改下发。默认 API 地址是明文 HTTP（§1.7），中间人能往心跳响应的 `strategy` 里塞任意选项，写进被控服务的 Config。
- 做法：服务端用会合服务器私钥（`get_server_sk` 的结果，`PORTA.md` §3 已经预留"API 侧要签名时挪进 `AppState`"）签 `"porta-server-v1\0" ‖ 请求的签名 ‖ sha256(响应体)`，放进响应头 `Porta-Server-Sig`。把请求的签名放进去，旧的响应就不能拿来回复新的请求。
- 客户端用配置里的服务器公钥 `key`（控制端本来就用它验 `IdPk`）验证。配了 `key` 时，验不过或缺少这个头就当作请求失败、不应用下发；没配 `key` 时不验（和现在一样不设防）。
- 代价：服务端私钥挪进 `AppState`；每个 Porta 路径响应多一次签名（和验签同一个量级）；客户端多一次验签。
- 备选：只要求 HTTPS、严格校验证书（笔记 03 §3 问题 3(a)）。对默认的明文地址不起作用，两条最好都做。

## 3. 需要维护者拍板的问题

1. **认证机制**：设备私钥签每个请求（推荐），还是服务端签发设备令牌。
2. **签名放哪**：独立请求头 `Porta-Device-Auth`（推荐），还是放进请求体。要同时请笔记 03 把 `Authorization: Porta-Device …` 改成这个头。
3. **防重放**：时间窗 ±60 秒 + 每设备最近 64 条签名（推荐，约 6 MB 封顶、不落库），还是只靠时间窗。
4. **公钥锁定**：
   - (a) 第一次签名自动锁定（推荐），还是锁定前要维护者在命令行比对指纹、手工确认（更严，但每台新设备都要人工处理一次）。
   - (b) 已锁定设备换了公钥时回 `UUID_MISMATCH`、让客户端换 ID（推荐），还是加新结果码、保住 ID 但离线到维护者重置。
5. **防降级**：设备锁定后，兼容路径上的不签名上报按"不符"处理（推荐），还是一直接受到全局开关打开为止。
6. **会合层的"只接受 Porta"**：§3.1 说退出以后原版连不上，要在会合层做到，需要给注册加签名（新 proto 字段）。是放进第三期，还是退出兼容前单独做（推荐后者），还是退出时只关 HTTP API、会合层继续对原版开放。
7. **响应签名**：Porta 路径的响应由服务端用会合私钥签名、客户端配了 `key` 就强制验证（推荐），还是只靠 HTTPS。
8. **共存时的 ID 冲突**（§1.8，和签名无关但这次发现）：在 `porta-cardo` 的 `get_auto_id` 里让 Porta 的默认 ID 和原版错开（推荐，只影响首次生成 ID 的设备，已有 ID 的不变），还是不改、在文档里要求共存时两者指向不同服务器。建议先在测试机上实测确认这个冲突。
9. **Exit Node 的主人认定**（第四期前要定）：只认签名登录绑定的和命令行指定的（推荐），还是第三期就在 Dart 登录处加挂钩签名。

## 4. 风险

- **锁定把"公钥被换"变成"设备换 ID"**【推测】：凡是真实设备的公钥会变的场景（§2.4 表里配置被删、配置同步），锁定后都会让设备静默换成随机 ID，地址簿里存的旧 ID 就失效了。维护者要知道这件事，并在设备换 ID 后用 `device key reset` 或改地址簿。建议在命令行列设备时标出"同一 uuid 有多个 ID"的情况，方便发现。
- **首次使用即信任的窗口**：设备第一次签名之前，同出口 IP、知道 uuid 的人能抢先换掉公钥，锁定的就是它的。对只有维护者和几个朋友的部署风险低；需要更严时用 §3 问题 4(a) 的手工确认。
- **兼容路径的老问题都还在**：第三期之后原版客户端照样不认证，§1.5 的公钥替换和地址劫持对未锁定的设备照旧成立。锁定只保护 Porta 设备。
- **防重放和多进程**：如果以后用户进程（登录）和服务进程（上报）都签名，两边的时间戳不保证递增，靠 30 秒乱序容忍度和按签名去重兜住；两个进程在同一秒对完全相同的内容签名会被当成重放，只发生在真正重复的请求上，影响可以忽略。
- **用户进程里的私钥是不是服务进程那一把，读码看一般是、没实测**（§1.1，核对时补）：界面进程启动时经 IPC 把服务进程的整个配置（含 `key_pair`）同步过来并落盘，但同步前调过 `get_key_pair` 的界面进程会在进程内缓存里留着自己生成的那把。影响的是以后在用户进程里签名登录（以及会话备注）的方案。新界面轨道开工前要实测 Windows 安装版里用户进程的 `Config::get_key_pair()` 拿到的是不是服务进程那一把；不稳的话改成经 IPC 让服务进程代签。上游自己的设备签名 `register_switch_grant` 就是在服务进程里签的（由 `src/ipc.rs` 的 `SwitchSidesRequest` 处理函数调用）。
- **libsodium 验签的边界行为**【推测】：`libsodium-sys 0.2.7` 打包的 libsodium 版本、它的 `crypto_sign_verify_detached` 是否拒绝小阶公钥和非规范签名，这次没核对。影响有限：公钥由注册方自选，弱公钥只影响注册方自己的 ID。实现时用 libsodium 自带的验签，不自己拼。
- **反代改写路径**：被签内容只含接口名，反代改写前缀不受影响；但反代如果改写了请求体（例如压缩或字符集转换），哈希会对不上。常见反代配置不会改写请求体【推测】。
- **时间纠偏可被中间人利用**：明文 HTTP 下中间人能伪造 401 里的 `time`，把客户端的偏移量拨歪，让它之后的请求都被拒（拒绝服务）。他本来就能直接丢弃请求，危害没有变大；配了响应签名以后，401 响应也应当带签名，客户端只采信验证通过的 `time`。

2. §1.5 第二条：地址劫持的后果因此不只是拒绝服务，用户点继续就会进冒充者那一端的明文会话。上游原有问题，本篇推荐（§2.9 不做会合层签名）不变，但风险比原文写的大。§2.6 Exit Node 一条也补了这句提醒。
3. §1.1 / §2.4 表：`CheckIfResendPk` 只在 macOS 上构造（`server.rs` `sync_and_watch_config_dir`，`#[cfg(target_os = "macos")]`），Windows 上不触发；原文"上游注释说主要是 macOS/Linux 的问题"不准确，注释没提平台，是调用点只在 macOS。
4. §1.1：用户进程的私钥从【推测】改为读码结论：界面进程启动时经主 IPC `SyncConfig(None)` 把服务进程整个 `Config`（含 `key_pair`）同步过来并落盘；例外是同步前已缓存自己生成的密钥对，以及服务没在跑的情况。`Data::ConfirmedKey` 只在 `key_confirmed` 为真时回密钥对，bd92623 里没有调用方。§2.6、§4 的相应说法同步改了。上游自己的 `register_switch_grant` 在服务进程里签名（`ipc.rs` `SwitchSidesRequest`）。
5. §1.1：桌面界面的指纹经 IPC 从服务进程拿（`ipc.rs` 的 `fingerprint` 选项），`ui_interface.rs` 直接调 `pk_to_fingerprint` 的那支只在移动端。结论（界面指纹就是 `peer.pk` 的指纹，可以和命令行比对）不变，反而更确定。
6. §1.1：`Config::store` 除永久密码外还把 ID 加密成 `enc_id`；`key_pair` 原样写入的结论不变。
7. §1.4：`machine_uid` 在 Windows 上读 `HKLM\SOFTWARE\Microsoft\Cryptography` 的 `MachineGuid`，已读依赖源码确认（`machine-uid@381ff57`），从【推测】改为读码；"普通用户可读"仍是推断。登录请求体在 Dart（`user_model.dart` `login`）里发出，原文写的 `ui_interface.rs` 只是 uuid 的来源。
8. §1.5 表末行，以及 §2.4 `device key reset`：`database.rs` `update_pk` 只写 `id`、`pk`、`info`，不写 `uuid`。已有行的 uuid 被置空后，重新登记只改内存、库里一直是空。`device key reset` 的设计依赖"重新登记会写回 uuid"，**前提不成立**，已在推荐旁标注，并写了两种修法（删行，或让这条分支写 uuid）。
9. §1.5 第一条：服务端要求重发公钥的条件除了 IP 变了，还有内存条目 pk 为空、条目不在内存里（`update_addr`）。
10. §1.6：引用"`PORTA.md` §11 末条"不对，相应内容在 §1 的"不做"清单和 §11 中间"走代理或 WebSocket 的客户端"一条。
11. §1.7：默认明文 HTTP 的前提是构建时没注入 `PORTA_API_SERVER`（现有构建脚本没注入）。§2.5 引用"`PORTA.md` §3.1 退出机制"应为 `docs/architecture.md` §3.1，已改。
12. §2.6 会话备注：备注请求由控制端界面进程的 Rust 代码发出（`ui_session_interface.rs` `send_note`），不在 Dart 里；"要等新界面轨道"的理由**前提不成立**，已在原推荐旁标注，第三期动不动留给维护者。另外补充：登录绑定用 `on conflict … do update set user_id`，已有主人的设备也会被改绑，比原文说的"挂到自己名下"更直接。

### 5.3 无法核实或仍存疑
- `MachineGuid` 键的默认 ACL 是否允许普通用户读：没查 Windows 文档，只有"上游登录在普通用户进程里读它"这一间接证据。
- §1.8 共存时抢同一个 ID：读码链条成立，但两边实际拿到的 MAC 是否同一块网卡（`mac_address::get_mac_address` 取第一块非回环网卡，装了 TUN 等虚拟网卡时可能变）、原版是否早已换过 ID，都要在测试机上实测。
- 界面进程在配置同步完成前会不会调 `get_key_pair`（决定 §1.1 那个例外会不会真发生）：没逐个追调用时序，要实测。
- RustDesk Pro 服务端 `switch-grant` 的时间窗（闭源）、nginx 对带下划线请求头的默认行为、libsodium 0.2.7 打包版本对小阶公钥和非规范签名的处理、Ed25519 验签耗时：本次都没核对，原文已标【推测】。
