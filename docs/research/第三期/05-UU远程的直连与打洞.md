# 第三期调研 05：网易 UU 远程为什么能直连、打洞率高

> 2026-10-23 写。起因：维护者把网易 UU 远程当备用控制通道，在 RustDesk 局域网直连失败的同一个环境里（路由器透明代理只代理 TCP、Windows 台式机开着 mihomo TUN、家宽是 CGNAT 加原生 IPv6，详见笔记 04），UU 能发现局域网直连，UDP 打洞成功率也高。本文回答它怎么做到的、Porta 能借鉴什么。
> 对象：维护者的 Windows 台式机上装的 UU 远程，`bin\` 下二进制文件版本 4.40.1.2090（注册表卸载项仍写着 4.39.2.1561，像是自动升级后没更新）；官网同期最新版是 4.42.0。只做了黑盒只读观察：查二进制里的字符串、看进程的 socket、读许可证清单。没抓包、没反汇编、没解密日志。
> 对照基线：`rustdesk@bd92623`、`rustdesk-server@873230e`、`hbb_common@ed07431`、`porta-client@6bb19b190`、`porta-server@d8403ad`。
> 证据标记：【实测】维护者的台式机上看到的；【官方】网易官方页面；【一手】RFC、论文、开源代码或厂商官方技术文档；【旁证】第三方文章、论坛；【推测】推断，后面写依据。每条都经过独立复核，被复核削弱的按复核后的说法写。

## 1. 结论先行

- **UU 的连接层是网易改过的 libwebrtc（内部叫 nrd-webrtc），用标准 ICE 收集候选、做连通性检查，中继用 TURN**【实测】。ICE（Interactive Connectivity Establishment，RFC 8445）的做法是：两端把自己所有可能的地址（"候选"）都交给对方，再对每一对候选实际发探测包，哪对通就用哪对。网易在上面加了一套自己的增强打洞（按 NAT 类型选策略、端口预测、多随机端口）。
- **局域网直连能成，是因为判定靠客户端实测，不靠服务端比公网 IP**【推测，证据链完整】。UU 把多块网卡的地址都当候选，实际观察到一条从以太网连到 MacBook 局域网地址的直连 TCP。所以路由器把 Mac 的 TCP 代理到香港、两端公网出口不一致，对它没有影响；TUN 的 198.18.0.1 也在候选里，但连不通只是被淘汰，不挡别的候选。
- **打洞率高，可能是几样东西叠加的结果，目前分不清各占多少**：全程走 UDP，不受"只代理 TCP"影响；IPv6 全局地址是一等候选，两端都有原生 IPv6 时根本不用打洞；IPv4 上有 NAT 类型判定、端口预测、多随机端口这些增强手段【实测：代码存在；是否触发未知】。**没有** UPnP 端口映射【实测】。
- **RustDesk/Porta 差在这几处**【一手】：服务端拿 TCP 来源和 UDP 注册地址比，判断同一内网；NAT 类型用 TCP 测，开 TUN 时很可能误判成对称 NAT 而直接走中继；开源服务端根本不在 UDP 上回 `TestNatRequest`，所以 UDP 打洞**从来不会被请求**（本文新发现，现有文档没记）；每条路径只有一个候选，没有 ICE 式的多候选检查。
- **最值得借鉴的三项**（§6）：服务端同网判定改用同一种协议的观测，并让局域网候选也带上 IPv6；IPv6 直连默认开并实测；修 UDP 打洞时把"服务端不回 UDP TestNat"和"登录状态下不等 udp_port"一起修，否则回落率数据说明不了 UDP 打洞的效果。
- **最大的不确定**：UU 日志是加密的，读不出最终选中的是哪种候选对（局域网 TCP、局域网 UDP、IPv6 还是 IPv4 打洞）。维护者感受到的"打洞率高"里，IPv6 直连和 IPv4 增强打洞各占多少，要靠 §7 的实测分清。

所以 UU 不是自研点对点协议，也不是 QUIC 或 KCP 自己打洞：**建链是 ICE，打洞增强是网易在 ICE 上加的，KCP/QUIC 是建链之后的传输层**。网上流传的"P2P 穿透率 95%""自研 UTUNNEL 协议"没有一手出处，后者出自疑似仿冒的非网易域名（§8）。

## 3. 为什么在"只代理 TCP + 本机开 TUN"下还能发现局域网直连（问题 2）

### 3.1 有证据的部分【实测，2026-10-23 一次会话中用 `Get-NetUDPEndpoint`、`Get-NetTCPConnection` 按进程看】

1. **候选覆盖多块网卡**。发起连接的同一秒，GameViewer 进程给一批本地地址各开了一个 UDP socket（端口连号）和一个 TCP 监听（端口连号），包括：mihomo TUN 的 IPv4 和 IPv6、以太网的 2 个 IPv6 全局地址和 2 个 ULA（唯一本地地址，`fd00::/8`，只在本地网络有效）、以太网和 WLAN 的 192.168.x、Tailscale 的 IPv4，再加一个 `0.0.0.0`（"任意地址"，出口由系统按路由选）。不是每个地址都有：VMware 网卡、链路本地 `fe80`、以太网的 DHCPv6 地址、WLAN 上的全部 IPv6、Tailscale 的 IPv6 都没开。
2. **实际在用一条局域网直连 TCP**：本地落在以太网的 192.168.x，连到 MacBook 的 192.168.x，会话开始约 30 分钟后仍是 Established。关键细节：这个 socket 绑的是 `0.0.0.0`，**以太网源地址是系统按直连网段路由选的**，不是绑在以太网候选上。这和笔记 04 方案 A 的思路一样：不绑源地址、连局域网地址时系统自然走物理网卡，不进 TUN。
3. 当时还看到从 5 个本地 IPv6 地址各向 Mac 的 ULA 发起过 TCP 连接、随后关闭，复核时已消失，无法复查。

### 3.2 推断的部分

- **局域网判定靠 ICE 连通性检查**【推测】：两端交换全部候选，对候选对实际探测。依据是 §2 的 ICE 字符串、§3.1 的多网卡候选和实际直连。只要做了 ICE 检查，局域网直连就不依赖"两端公网 IP 相同"，背景里 RustDesk 失败的两个原因（公网 IP 对不上、只报 198.18.0.1）都绕过去了。
- **服务端有没有参与局域网判定，不知道**：二进制里有 `is_lan_connection`、`local_ip`、NAT 类型字段，可能只是统计标记，也可能有服务端提示。Mac 端当时开没开 TUN、报了哪些候选，从台式机上看不到。
- **最终选中的是 TCP 对还是同网卡上的 UDP 对，不知道**。UU 的 ICE 同时有 UDP 候选和 TCP 被动/主动候选（ICE-TCP，RFC 6544），看到 TCP 在用不代表媒体走 TCP。

### 3.3 纠正两个容易得出的错误结论

- **"UU 按网卡建 socket，所以绕开了 TUN"不成立**。被控服务那条到网易信令服务器的长连接停在物理网卡上，只是因为它比 mihomo 早 30 秒启动；它绑的是 `0.0.0.0`，按现在的路由表应该走 TUN。UU 的中继连接是**每个网络各建一份**：以太网（绑以太网地址）、TUN（绑 198.18.0.1）、`0.0.0.0`（被路由进 TUN）各连两台中继服务器，形态像"每个网络对两台 TURN 各分配一次"【推测】。它是把各网卡都试一遍，而不是专门绕 TUN。第三方博客（https://blog.sinovale.com/7507.html ，2026-10-23 查）在 macOS 上也看到 UU 连服务器的 socket 绑在 TUN 地址上，靠代理软件的 DIRECT 规则才从真实网卡发出【旁证】。
- **"网易加了网卡黑名单，剔除了 TUN"不成立**。`streamer.dll` 在 `rtc_base\network.cc` 旁边有一张网易自加的关键字表（tap-windows、wintun、vpn、wireguard、tailscale、zerotier……和 vmware、hyper-v、virtualbox、vmnet……），上游 WebRTC 没有这张表。但 Tailscale 在表里照样被绑定，说明它不用来剔除网卡，更可能用于加网络代价或分类【推测】。mihomo 网卡的描述是 `Meta Tunnel`，不含表里任何关键字。VMware 网卡没绑定是上游 `IsIgnoredNetwork` 本来就按描述里的 `VMnet` 过滤的【一手：https://webrtc.googlesource.com/src/+/refs/heads/main/rtc_base/network.cc ，2026-10-23】。

## 4. 打洞率高可能来自哪些手段（问题 3）

| 手段 | UU 有没有 | 证据 | 对维护者环境的意义 |
|---|---|---|---|
| 全程 UDP，STUN 与数据同一 socket | 有（ICE 本来如此） | §2 | 路由器只代理 TCP，UU 的 UDP 走家宽。**台式机例外**：mihomo TUN 也接管 UDP，按 mihomo 源码，同一 socket 的 UDP 走哪个出站由第一个包匹配的规则决定，DIRECT 时行为接近端点无关映射加端点无关过滤（`MetaCubeX/mihomo@3f27ef39:tunnel/tunnel.go` `handleUDPConn`、`constant/adapters.go` `NewPacketAdapter`）【一手】，所以 TUN 大概率不破坏 UDP 打洞，前提是 STUN/中继服务器命中 DIRECT【推测】 |
| IPv6 全局地址作候选 | 有 | 以太网的 2 个全局地址和 2 个 ULA 都绑定了；绑定的 IPv6 正好 5 个，对得上上游 `SelectIPv6Networks` 的默认总上限 5（按网卡类型轮选）；Wi-Fi 上的 IPv6 按上游默认被跳过【实测 + 一手：上游 `p2p/client/basic_port_allocator.cc`】 | 家宽 CGNAT 但有原生 IPv6，两端都有 IPv6 时不需要打洞，只要穿过家用网关的状态防火墙。很可能是"打洞率高"的一大来源【推测，未证实】 |
| NAT 类型判定 + 按两端类型组合选策略 | 有代码 | NAT 类型 `None/Cone/LinearSymmeric/RandomSymmeric`（拼写照原文），8 个两两组合策略名，`best lcoal stun can group nat type`、`select_local_nat_type`【实测：字符串】 | 判定方法（几个 STUN 服务器、怎么分组）看不出来【推测】 |
| 端口预测（猜对称 NAT 下一个端口） | 有代码，可跳过 | `predicted_port:`、`predict punch address:`、`, skip port prediction`【实测：字符串】 | 只对按顺序分配端口的 NAT 有效（RFC 5128 §3.5）【一手】 |
| 多随机端口碰撞（生日悖论式） | 有代码 | `find enough random remote ports for punching`、`created new random port:`、`Added punch port to allocator`【实测：字符串】；"生日式"是推测，没有这个字样 | 一端对称、一端锥形时有效；Tailscale 给的数据：对称一侧开 256 个端口、探测 1024 次成功率 98%；两端都对称基本无望【一手：https://tailscale.com/blog/how-nat-traversal-works ，2026-10-23】 |
| 防火墙探测、已直连就停止打洞 | 有代码 | `PunchCheckFireWall`、`found firewall, stop punch`、`has writable p2p connection, stop punch`、`peer connection is already p2p, skip punching`【实测：字符串】 | 避免无谓的大量发包 |
| 打洞分 lite / full 两档 | 有 | `uuyc-cli.exe` 的 `--disable-lite-punch`（true=full, false=lite）；切换走本机 CLI → 界面 → 被控服务的 IPC，由 `punch_mode_setting_manager.cpp` 写入设置【实测】。云端是否下发默认值或覆盖，没有证据；云端配置缓存里没有打洞字段 | 重型打洞可以按需开关 |
| UPnP / NAT-PMP / PCP 端口映射 | **没有** | 8 个二进制里都搜不到 `AddPortMapping`、`WANIPConnection`、`natpmp`；SSDP 搜路由器的代码只用于识别路由器型号、配合远程开机【实测】 | 不靠端口映射。CGNAT 下映射也只作用在内层 NAT，对远端没用【一手：Tailscale 同上】 |
| 中继兜底、丢包高时切中继 | 有 | §2 | 官方说中继复用加速器节点，只是宣传口径【官方：https://uuyc.163.com/blog/yxiaobangyun.html】 |

注意：维护者台式机的 Windows 防火墙设置和普通用户不同，也没有 UU 的放行规则【实测】，所以"能被直接连入"不能推广到开着默认防火墙的普通用户。

## 5. RustDesk / Porta 现在差在哪（问题 4）

| 差距 | 代码位置 | 等级 |
|---|---|---|
| 同网判定只拿"控制端打洞请求的 TCP 来源 IP"和"被控端 UDP 注册 IP"比；地址族不同直接判否；WebSocket 一律判否。porta-server 这段和原版逐字相同 | `rustdesk-server@873230e:src/rendezvous_server.rs` `handle_punch_hole_request`；`porta-server@d8403ad` 同名函数 | 一手 |
| NAT 类型用 TCP 测：同一本地端口先后连 21116、21115，来源端口相同记 ASYMMETRIC、不同记 SYMMETRIC，只分两类；只看 socks/WebSocket，看不出 TUN | `rustdesk@bd92623:src/common.rs` `test_nat_type`、`test_nat_type_` | 一手 |
| 开 TUN 或透明代理时，TCP 被代理重新发出，很可能测成 SYMMETRIC；任一端 SYMMETRIC，被控端对 IPv4 直接走中继（IPv6 不受影响） | `src/rendezvous_mediator.rs` `handle_punch_hole` 的 `relay_v4` | 代码一手；"会测成 SYMMETRIC"是推测，要看服务进程日志的 `Tested nat type` |

| 配了 key 又登录了 API 时（`legacy_secure`），控制端根本不等 UDP NAT 测试结果，就算服务端修好，登录用户的 `udp_port` 也多半是 0 | `rustdesk@bd92623:src/client.rs` `_start_inner` | 一手 |
| 自建服务器下 UDP 打洞、IPv6 打洞、WebRTC 默认关 | `src/common.rs` `get_local_option` | 一手 |
| 每条路径每个地址族只有一个候选，被控端把 UDP socket `connect` 死在一个地址上；没有候选配对、优先级、连通性检查。唯一完整的 ICE 是上游的 WebRTC 路径（webrtc-rs），但开源 hbbs 和 porta-server 都不转发 offer 和 `IceCandidate`，实际不可用 | `src/client.rs` `connect`；`src/rendezvous_mediator.rs` `udp_nat_listen`；`hbb_common@ed07431:src/webrtc.rs` | 一手 |
| 没有 UPnP、端口预测、多端口打洞（proto 里的 `upnp_port` 是空字段） | 全仓 grep | 一手 |
| Porta 第三期第一项已补上局域网多候选：物理网卡最多 8 个候选、控制端不绑源地址并发 TCP 连全部候选。但只有 IPv4、只有 TCP，**仍要先过服务端的同网判定**，所以路由器透明代理那个原因还在 | `porta-client@6bb19b190:libs/porta/src/lan.rs`、`src/porta_hooks.rs`；`client/PORTA.md` §3 | 一手 |

和 UU 对照：UU 是"候选全给对方，客户端实测"；RustDesk 是"服务端先判一次走哪条路，每条路一个地址"。透明代理和 TUN 恰好让服务端的两个判断（同网、NAT 类型）都失真。

## 6. Porta 可以借鉴什么（问题 5）

按"收益/成本"从高到低。"第三期已定"指 AGENTS.md 里的第三期设计（发起方 ID 字段 `porta_from_id`、设备签名等）。

| # | 借鉴项 | 收益 | 实现成本 | 服务端 | proto | 建议 |
|---|---|---|---|---|---|---|
| 1 | **同网判定改用同一种协议的观测**：服务端用打洞请求里的发起方 ID 查发起方服务进程的 UDP 注册 IP，和被控端的 UDP 注册 IP 比，与现有 TCP 比较取"或"；结果只决定"要不要下发局域网候选"，能不能连由客户端实测 | 直接修掉"路由器只代理 TCP"那个原因 | 小 | 改 `handle_punch_hole_request` | 复用第三期已定的 `porta_from_id` | 第三期。`porta_from_id` 不认证，伪造能骗出被控端的局域网地址，等设备签名上线后对验签通过的设备启用。前提：发起方服务进程在跑且已注册；开 TUN 的机器上会合服务器的 UDP 要命中 DIRECT。误判代价是晚 1~2 秒（最坏约 4 秒）回落中继 |
| 2 | **局域网候选带上 IPv6**（以太网的全局地址和 ULA），候选总数设上限、按网卡类型排序，链路本地不报 | 两端都有 IPv6 时多一条局域网路；ULA 不受 IPv4 网段撞号影响 | 小到中 | 不用改（`porta_local_addrs` 单个 18 字节已够放 IPv6 地址加端口） | 不用改 | 第三期，跟第一项一起做。UU 的上限是总共 5 个 IPv6（上游默认），可以照抄 |
| 3 | **IPv6 直连默认开并实测**（Porta 客户端默认打开 `enable-ipv6-punch`） | CGNAT 家宽回家直连最可靠的一条路，可能也是 UU"打洞率高"的主要来源 | 小（第二期已计划） | 第一期已转发 IPv6 | 已有 | 第二期默认开；第三期验收时按 §7 实测 TUN 下能否拿到全局 IPv6 |
| 4 | **网卡分类**：虚拟机网卡过滤，TUN/VPN 降权而不是只看 `198.18.0.0/15`；名字和描述都要看（mihomo 网卡描述是 `Meta Tunnel`） | 少浪费检查次数，少挑错网卡 | 小 | 不用改 | 不用改 | 第三期，在现有 `lan.rs` 过滤规则上补描述判断 |
| 5 | **修 UDP 打洞的前置障碍**：服务端在 UDP 上回 `TestNatRequest`、接受 UDP `PunchHoleSent`（两处都要防反射，共用一套防伪造随机数）、转发 `udp_port` 和 `is_udp`；客户端去掉"登录后不等 `udp_port`"；注册保活压到 15~25 秒（CGN 空闲超时中位数约 35 秒，Richter 等 IMC 2016） | 不修这些，UDP 打洞根本不运行，回落率数据也说明不了"修 UDP 打洞值不值" | 中 | 要改 | 可能加随机数字段 | 第三期。架构 §3.8 原定"看回落率再定修不修"，建议补一句：先修前置障碍，或至少知道现有数据里 UDP 打洞是零 |
| 6 | **NAT 类型改用 UDP 测**，并且两台服务器或两个端口，至少能分清"映射是否随目的地变化" | 避免 TUN/透明代理下被 TCP 测成对称而放弃 IPv4 直连 | 中 | 要多一个 UDP 观测点 | 可能要加字段 | 第三期，跟第五项一起 |
| 7 | **评估直接用上游现成的 WebRTC/ICE 路径**：porta-server 转发 offer/answer 和 `IceCandidate`，自建 STUN（可选 TURN） | 一步拿到 UU 同款的多候选连通性检查，不用自写 ICE 状态机 | 中（服务端转发不难，难在评估 webrtc-rs 和上游这条路径的成熟度） | 要改（`server/PORTA.md` 目前把 WebRTC 信令转发列为不做） | 字段已有 | 第三期设计时立一个小评估项，结论再决定是否进第四期【推测：上游这条路径的稳定性没有验证】 |
| 8 | **先走中继、后台持续升级直连**（ZeroTier、libp2p DCUtR 的做法，后者用 RTT/2 同步两端拨号，实测条件成功率约 70%） | 连接立即可用，直连成功后切过去 | 大（会话中切换传输） | 基本不用改 | 要加升级协商消息 | 第四期以后 |
| 9 | **按两端 NAT 类型选策略、端口预测、多随机端口，分 lite/full 两档** | 只对"一端对称 NAT"有效；国内家宽也有对称 NAT 的个例 | 大（端口池、限速、可能触发运营商风控） | 要下发 NAT 类型和模式 | 要加字段 | 最后做，先看第五、六项之后的回落率 |
| 10 | UPnP / NAT-PMP / PCP | UU 自己都没做；CGNAT 下无效 | 中 | 不用改 | 不用改 | 不做 |

还有两条不是功能，是做法：探测必须认证对端身份（不同网络里会出现相同的私网地址，两端都开 TUN 时 198.18.0.1 甚至就是自己，RFC 8445 §7.3、RFC 5128 §3.3.2）【一手】，Porta 局域网候选现在靠 `secure_connection` 握手校验已满足；以及信令可以走代理，P2P 候选按物理网卡来，这是 Porta 已在走的方向。

## 7. 需要维护者配合实测的问题（问题 6）

1. **UU 最终走的是哪种连接**。在 UU 连接后看界面里有没有连接信息或统计面板（官方指南提到的"连接方式"P2P/Relay），记下局域网连 MacBook、外网连回家两种场景的显示。
2. **IPv6 贡献多少**。外网（手机热点）连回家时，分别在"以太网 IPv6 开着"和"临时在网卡属性里取消勾选 IPv6"两种状态下各连 3 次，记 P2P/Relay。如果关了 IPv6 后直连明显变少，"打洞率高"主要来自 IPv6。
3. **TUN 的影响**。局域网连 Mac：台式机 TUN 开/关、Mac TUN 开/关四种组合各连一次；同时在 Clash Verge 的"连接"页按进程名看 GameViewer 的 UDP 走的是 DIRECT 还是代理。
4. **Mac 端候选**。Mac 开着 Clash Verge TUN 时，在 UU 会话中跑 `lsof -nP -i | grep -i uu`（只读），看 UU 是否同样在 utun 和物理网卡上各开 socket。
5. **家宽 NAT 类型**。用 NatTypeTester 一类工具在台式机上测一次 UDP 映射和过滤行为，TUN 开、关各一次。这决定 UDP 打洞率高是网络条件好还是 UU 算法强，也决定 Porta 第九项值不值得做。
6. **RustDesk 的 NAT 类型是否被测成对称**。看两台机器 RustDesk **服务进程**日志里的 `Tested nat type`（服务进程不以当前用户运行，日志不在 `%APPDATA%\RustDesk\log`）。
7. **最终选中的候选对**（可选，需要维护者授权）：用系统自带的 `pktmon` 抓 1 分钟 UU 会话的包，看数据走 UDP 还是 TCP、IPv4 还是 IPv6。没有授权就不做。
8. 第 2、3 项建议在开着默认 Windows 防火墙的另一台机器上再做一次，避免本机防火墙设置造成的偏差。

## 8. 已排除或不采用的说法

- "UU 用自研 UTUNNEL 协议"：出自非网易域名的疑似仿冒站，且声称支持 Linux 被控，不采用。
- "官方标称 P2P 穿透率约 95%"：只出现在一篇 CSDN 文章里，没给出处，复核时站点打不开。官方博客唯一的数字是一个自述测试场景（电信连联通）"连接成功率 100%"，没有方法和样本。品玩说"利用了游戏加速器的打洞技术"，也没有出处。
- "UU 的信令长连接绑物理网卡、绕开 TUN"：是启动时间的巧合，见 §3.3。
- "打洞模式由云端建房间时下发"：本机看到的是本地 IPC 链路，云端是否参与没有证据，见 §4。
- "uuyc-mux 是网络多路复用"：它是 psmux（Windows 上的 tmux 替代品），和打洞无关。
- linux.do 一则帖子（https://linux.do/t/topic/2400034 ，2026-10-23 查）说 UU 只要能访问对端内网 IP 就判"内网"：楼主自己的猜测，且没排除"两端看到的 IP 相同"，只能当弱旁证，不作依据。
- 网易相关专利（CN120179269A，更新后重连）、网易云信的 RTC 演讲：都和 UU 远程的打洞无关。
