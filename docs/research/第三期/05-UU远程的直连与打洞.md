# 第三期调研 05：网易 UU 远程为什么能直连、打洞率高

> 2026-10-23 写。起因：维护者把网易 UU 远程当备用控制通道，在 RustDesk 局域网直连失败的同一个环境里（路由器透明代理只代理 TCP、Windows 台式机开着 mihomo TUN、家宽是 CGNAT 加原生 IPv6，详见笔记 04），UU 能发现局域网直连，UDP 打洞成功率也高。本文回答它怎么做到的、Porta 能借鉴什么。
> 对象：维护者的 Windows 台式机上装的 UU 远程，`bin\` 下二进制文件版本 4.40.1.2090（注册表卸载项仍写着 4.39.2.1561，像是自动升级后没更新）；官网同期最新版是 4.42.0。初稿只做了黑盒只读观察：查二进制里的字符串、看进程的 socket、读许可证清单。没抓包、没反汇编。
> **2026-10-23 维护者解密了一份控制端日志，下列结论据此更新。** 日志来自台式机（发起连接的一方），分三类：连接日志（libwebrtc 的 ICE 层：候选收集、STUN/TURN、候选对、选路）、串流日志（网易的传输层：数据通道、NAT 分析、会话结束统计）、应用日志（界面进程：信令、设置）。里面有两次会话，对端是同一台局域网里的 MacBook（设备 ID 相同、平台字段是 macOS、UU 自己统计 `is_lan_connection=1`）：会话 1 约 4 小时 53 分，会话 2 约 66 分钟（日志截止时还在连）。没有外网对端的会话，也没有被控端日志。
> 对照基线：`rustdesk@bd92623`、`rustdesk-server@873230e`、`hbb_common@ed07431`、`porta-client@6bb19b190`、`porta-server@d8403ad`。
> 证据标记：【实测】维护者的台式机上看到的；【实测：解密日志】上面那份控制端日志里明确写着的；【官方】网易官方页面；【一手】RFC、论文、开源代码或厂商官方技术文档；【旁证】第三方文章、论坛；【推测】推断，后面写依据。每条都经过独立复核，被复核削弱的按复核后的说法写。

## 1. 结论先行

- **UU 的连接层是网易改过的 libwebrtc（内部叫 nrd-webrtc），用标准 ICE 收集候选、做连通性检查，中继用 TURN**【实测】。ICE（Interactive Connectivity Establishment，RFC 8445）的做法是：两端把自己所有可能的地址（"候选"）都交给对方，再对每一对候选实际发探测包，哪对通就用哪对。网易在上面加的增强打洞（按 NAT 类型选策略、端口预测、多随机端口）是**后备**：ICE 启动时打开，5 秒后检查一次，那时还没直连才动手【实测：解密日志】。
- **两次局域网会话最终都是 UDP host↔host 直连，以 IPv6 为主**【实测：解密日志】。大部分时间是台式机以太网的 IPv6（全局地址或 ULA）对 Mac Wi-Fi 的 IPv6，IPv4 局域网对只在网络变化的间隙用过几十毫秒；从没选中过 TCP 和中继。从点连接到 ICE 连通约 0.25~0.4 秒。初稿看到的那条"在用的局域网 TCP"其实是 ICE-TCP 的备用对，检查通过但没被选中（§3.1）。
- **局域网直连靠客户端的 ICE 实测，不靠服务端判定**【实测：解密日志】。Mac 的检查包直接打到台式机的各个 host 候选上，甚至比 answer 还先到；日志里没有任何服务端下发的局域网提示。所以路由器把 TCP 代理到境外、台式机开 TUN 都没影响：TUN 上 198.18.0.1 那个 IPv4 socket 连不到 Mac，只是被淘汰。
- **这两次会话里增强打洞根本没跑**【实测：解密日志】。NAT 分析判两端都是 Cone（锥形 NAT），已经直连，跳过打洞；端口预测、多随机端口、防火墙探测都没触发；中继分配了、一直在后台当备份，没切过去。所以"打洞率高"里 IPv4 增强打洞占多少，这份日志答不了，它只说明局域网场景下 UU 靠的是标准 ICE 加 IPv6。**没有** UPnP 端口映射【实测】。
- **IPv6 用上了，但只有 host 候选**【实测：解密日志】：UU 下发的 STUN/TURN 服务器都只有 IPv4，IPv6 拿不到反射地址，IPv6 直连就是两端地址直接互通，在同一局域网里正好成立。
- **RustDesk/Porta 差在这几处**【一手】：服务端拿 TCP 来源和 UDP 注册地址比，判断同一内网；NAT 类型用 TCP 测，开 TUN 时很可能误判成对称 NAT 而直接走中继；开源服务端根本不在 UDP 上回 `TestNatRequest`，所以 UDP 打洞**从来不会被请求**（本文新发现，现有文档没记）；每条路径只有一个候选，没有 ICE 式的多候选检查。
- **最值得借鉴的三项**（§6，日志带来的调整见表后）：局域网候选带上 IPv6、能不能连交给客户端实测（UU 实际走的就是这条），服务端同网判定改用同一种协议的观测；IPv6 直连默认开并实测；修 UDP 打洞时先修前置障碍，范围限于普通的反射地址打洞，端口预测这类重手段排最后。
- **还不确定的**：外网场景（手机热点连回家）UU 走什么、IPv6 直连和 IPv4 打洞各占多少，这份日志没覆盖，要再解密一份外网场景的日志（§7）。

所以 UU 不是自研点对点协议，也不是 QUIC 或 KCP 自己打洞：**建链是 ICE，打洞增强是网易在 ICE 上加的后备，KCP/QUIC 是跑在 ICE 传输上的数据通道实现**。网上流传的"P2P 穿透率 95%""自研 UTUNNEL 协议"没有一手出处，后者出自疑似仿冒的非网易域名（§8）。

## 3. 为什么在"只代理 TCP + 本机开 TUN"下还能发现局域网直连（问题 2）

### 3.1 进程 socket 观察，以及日志的核对【实测，2026-10-23 一次会话中用 `Get-NetUDPEndpoint`、`Get-NetTCPConnection` 按进程看】

1. **候选覆盖多块网卡**。发起连接的同一秒，GameViewer 进程给一批本地地址各开了一个 UDP socket（端口连号）和一个 TCP 监听（端口连号），包括 mihomo TUN 的 IPv4 和 IPv6、以太网的 IPv6 和 192.168.x、WLAN 的 192.168.x、Tailscale 的 IPv4，再加一个 `0.0.0.0`（"任意地址"，出口由系统按路由选）。VMware 网卡、链路本地 `fe80`、Tailscale 的 IPv6 都没开。
   【实测：解密日志】证实并补全：每个网络各一个 UDP host 候选和一个 TCP host 候选；IPv4 网络（TUN、以太网、WLAN、`0.0.0.0`）另有反射候选（srflx）和中继候选；IPv6 只有 host；没有 mDNS 和链路本地候选。初稿的地址清单要更正两处：会话 1 开始时以太网是 3 个 IPv6 全局地址、没有 ULA（唯一本地地址，`fd00::/8`），路由器下发的 ULA 约 10 分钟后才出现，之后反复出现又消失；WLAN 的 IPv6 **不是按网卡类型跳过**，而是被 IPv6 总数 5 个的上限挤掉的（以太网只有 3 个 IPv6 时，WLAN 的全局地址就入选了）。
2. **那条局域网 TCP 是 ICE-TCP 的备用对，没承载会话**（初稿写"实际在用"，被日志推翻）。初稿看到：本地落在以太网的 192.168.x，连到 MacBook 的 192.168.x，会话开始约 30 分钟后仍是 Established；这个 socket 绑的是 `0.0.0.0`，以太网源地址是系统按直连网段路由选的。日志证实了这些细节，但它只做过一次连通性检查（往返 3~4 ms），之后从没被选中，会话 1 那条在约 28 分钟时被剪枝。两次会话共有 11 条 ICE-TCP 对检查通过，多数是 Mac 主动连进来的 IPv6 TCP，一条都没被选中；选中的始终是 UDP【实测：解密日志】。"不绑源地址、连局域网地址时系统自然走物理网卡"这一点对 UDP 也成立：`0.0.0.0` 的 UDP socket 发往 Mac 局域网地址时，Mac 看到的源是台式机的 192.168.x、端口不变，没进 TUN【实测：解密日志】，和笔记 04 方案 A 的思路一致。
3. 当时还看到从 5 个本地 IPv6 地址各向 Mac 的 ULA 发起过 TCP 连接、随后关闭，复核时已消失。这和 ICE-TCP 主动连接检查后被剪枝关闭的行为一致【推测】。

### 3.2 日志给出的答案（初稿只能推断）

- **局域网判定靠 ICE 连通性检查**【实测：解密日志】。会话 1 里 Mac 的第一个检查包比 answer 还早约 30 ms 打到台式机的 IPv6 host 候选，台式机先把它记成"对端反射候选"（prflx，RFC 8445 §7.3.1.3：检查包先于信令到达时的标准做法），几十毫秒后 Mac 的候选经信令到达，换成 host↔host。UU 的 ICE 参数偏激进：弱连接时的检查间隔 8 ms（上游默认 48 ms），这是建链快的原因之一。
- **日志里看不到服务端参与局域网判定**【实测：解密日志】。信令里只有 offer/answer/候选。客户端在建链前把自己的出口 IP 报给服务端（§2），服务端有条件比两端出口，但日志里看不到它起作用。`is_lan_connection=1` 只出现在会话结束统计里，和选中对的类型（host↔host）写在一起，像是事后按选中对算的统计标记【推测】。
- **最终选中的是 UDP 对**【实测：解密日志】。两次会话共 56 次选路全是 UDP；会话 1 结束统计写的是 host、udp、两端 ULA、本地以太网。会话 2 先选 IPv4 局域网 host 对，0.5 秒后换成以太网 ULA 对 Mac 的 IPv6 全局地址，此后到日志截止没再换。Mac 那端走 Wi-Fi。会话 1 平均延迟 7.8 ms、丢包约 0.05%、端到端帧延迟中位数 18 ms。
- **Mac 端开不开 TUN 都不影响结果**【推测：从候选反推】。会话 1 里 Mac 报了 198.18.x 和 mihomo 默认的 `fdfe::/16` 候选（UU 在 Mac 上把 utun 当作独立网络枚举，代价 999），会话 2 没有，推断那时关了 TUN；两种状态下选中的都是物理网卡上的 host 对。Mac 的反射地址和台式机是同一个家宽出口，说明路由器确实没代理 UDP。
- **网络变化时持续收集候选、立即重选路径**【实测：解密日志】。会话 1 里系统报了 11 次网络变化（ULA 出现又消失、台式机关开 TUN），每次 UU 都在 0.02~0.31 秒内回到以太网 host 对，最长 13 秒稳定到最终那一对；ICE 只断过一次，同一毫秒恢复。中间会短暂落到 WLAN 的 IPv6、TUN socket 上的反射对，甚至两端反射地址经家宽 NAT 回环（hairpin，同一 NAT 后面的两台机器用公网映射地址互连）的对，每次几十到几百毫秒。代价是每次选路变化都把码率重置到起点：会话 1 统计里传输卡顿 69 次、共约 25 秒，还有一次约 3 秒的中断，推断主要来自这些切换【推测】。ULA 消失后，旧端口再发包报"地址不可用"，ULA 不稳定会直接让对应候选失效。

### 3.3 纠正两个容易得出的错误结论

- **"UU 按网卡建 socket，所以绕开了 TUN"不成立**。被控服务那条到网易信令服务器的长连接停在物理网卡上，只是因为它比 mihomo 早 30 秒启动；它绑的是 `0.0.0.0`，按现在的路由表应该走 TUN。UU 的中继是**每个 IPv4 网络各分配一套**：每个网络对 4 个入口（2 个 TURN/UDP、2 个 TURN over TLS 443）各分配一次，初稿在 TCP 视角看到的"两台中继"是那两个 TLS 入口【实测：解密日志】。TUN 上的 STUN、TURN（包括 TLS 443）看到的来源都是家宽出口，和以太网相同，说明 mihomo 把它们按 DIRECT 走了【推测：依据是反射地址相同】；TUN 刚关开的那一刻 TLS 会失败。它是把各网卡都试一遍，而不是专门绕 TUN；唯一刻意绑物理网卡的是查出口 IP 那一步（§2）。第三方博客（https://blog.sinovale.com/7507.html ，2026-10-23 查）在 macOS 上也看到 UU 连服务器的 socket 绑在 TUN 地址上，靠代理软件的 DIRECT 规则才从真实网卡发出【旁证】。
- **"网易加了网卡黑名单，剔除了 TUN"不成立**。`streamer.dll` 在 `rtc_base\network.cc` 旁边有一张网易自加的关键字表（tap-windows、wintun、vpn、wireguard、tailscale、zerotier……和 vmware、hyper-v、virtualbox、vmnet……），上游 WebRTC 没有这张表。日志落实了它的作用【实测：解密日志】：网易在自己的网卡枚举层给网卡分类，VMware 在这一层就被滤掉，根本没交给 WebRTC；Tailscale 被归成 VPN，网络代价 2050（上游同类是 51，推断网易给 VPN 加了约 2000【推测：和上游常量对比】），但没被剔除，照样报 host 候选，只是发不出外网，排在最后。mihomo 网卡的描述是 `Meta Tunnel`，没被认成 VPN，按"未知"类型拿上游默认代价 50；候选优先级反而最高（按网卡类型排序时"未知"排第一），网易没在优先级上给它降权。网络代价依次是：以太网 0、WLAN 10、TUN 50、`0.0.0.0` 999、Tailscale 2050。

## 4. 打洞率高可能来自哪些手段（问题 3）

| 手段 | UU 有没有 | 证据 | 对维护者环境的意义 | 解密日志里（两次局域网会话） |
|---|---|---|---|---|
| 全程 UDP，STUN 与数据同一 socket | 有（ICE 本来如此） | §2 | 路由器只代理 TCP，UU 的 UDP 走家宽。台式机的 mihomo TUN 也接管 UDP，同一 socket 的 UDP 走哪个出站由第一个包匹配的规则决定，DIRECT 时行为接近端点无关映射加端点无关过滤（`MetaCubeX/mihomo@3f27ef39:tunnel/tunnel.go` `handleUDPConn`、`constant/adapters.go` `NewPacketAdapter`）【一手】。日志证实 TUN 上 UDP 的反射地址就是家宽出口，TUN 不破坏 UDP 打洞【实测：解密日志】；但 TUN 路径发往个别目的地时映射端口会变，更可能是 mihomo 引入的，按 STUN 判出的 NAT 类型对 TUN 路径偏乐观【推测】 | 56 次选路全是 UDP |

## 6. Porta 可以借鉴什么（问题 5）

按"收益/成本"从高到低。"第三期已定"指 AGENTS.md 里的第三期设计（发起方 ID 字段 `porta_from_id`、设备签名等）。

| # | 借鉴项 | 收益 | 实现成本 | 服务端 | proto | 建议 |
|---|---|---|---|---|---|---|
| 1 | **同网判定改用同一种协议的观测**：服务端用打洞请求里的发起方 ID 查发起方服务进程的 UDP 注册 IP，和被控端的 UDP 注册 IP 比，与现有 TCP 比较取"或"；结果只决定"要不要下发局域网候选"，能不能连由客户端实测 | 直接修掉"路由器只代理 TCP"那个原因。UU 自己没有这一步（日志里看不到服务端判同网），Porta 保留它只是为了决定发不发局域网地址 | 小 | 改 `handle_punch_hole_request` | 复用第三期已定的 `porta_from_id` | 第三期。`porta_from_id` 不认证，伪造能骗出被控端的局域网地址，等设备签名上线后对验签通过的设备启用。前提：发起方服务进程在跑且已注册；开 TUN 的机器上会合服务器的 UDP 要命中 DIRECT（UU 的日志说明 mihomo 下这通常成立）。误判代价是晚 1~2 秒（最坏约 4 秒）回落中继 |

**日志带来的变化**：
- **IPv4 打洞的实际贡献**：局域网场景里是零（ICE 0.3 秒内就直连，增强打洞被跳过）；外网场景仍未知。所以第九项继续排最后；第五项的理由从"UU 打洞率高"改成"Porta 现在的 UDP 打洞是零，且这类 Cone 家宽上普通打洞大概率够用"，仍放第三期。
- **IPv6 局域网候选**：从"可能有用"升为"UU 实际在用的主路径"，第二项和第一项同等重要。要注意 TUN 占名额、ULA 会变。
- **TCP 候选**：UU 的 ICE-TCP 局域网对都能通（往返 3~4 ms，IPv4 和 IPv6 都有），只是按优先级 UDP 先被选中。Porta 的传输本来就是 TCP，第三期第一项"局域网 TCP 多候选"的方向没问题；补 IPv6 TCP 候选在日志里也是能通的。
- **TUN 下的反射地址**：TUN 上的 UDP 拿到的就是家宽出口，"TUN 不破坏 UDP 打洞"从推测变成有日志支持；但 TUN 路径对个别目的地会换映射端口，第六项判 NAT 类型时要留余量。
- **WebRTC/ICE 评估**：UU 的局域网成功全部来自上游 ICE 的标准能力，第七项价值上调。

还有两条不是功能，是做法：探测必须认证对端身份（不同网络里会出现相同的私网地址，两端都开 TUN 时 198.18.0.1 甚至就是自己，RFC 8445 §7.3、RFC 5128 §3.3.2）【一手】，Porta 局域网候选现在靠 `secure_connection` 握手校验已满足；以及信令可以走代理，P2P 候选按物理网卡来，这是 Porta 已在走的方向。

## 7. 需要维护者配合实测的问题（问题 6）

局域网连 MacBook 时 UU 最终走哪种连接，已由解密日志回答（UDP host↔host，IPv6 为主，§3.2）；台式机 TUN 开着、Mac TUN 开或关时都能直连；初稿第 7 项的抓包也不再需要。剩下：

1. **外网连回家时 UU 走哪种连接**。用手机热点连回家，之后解密那次的控制端日志（最好连同被控端日志），看最终选中的候选对、NAT 分析结果、增强打洞有没有跑、12 秒超时后做什么。
2. **IPv6 贡献多少**。同样是外网连回家，分别在"以太网 IPv6 开着"和"临时在网卡属性里取消勾选 IPv6"两种状态下各连 3 次，看日志里选中的是 IPv6 对、IPv4 反射对还是中继。如果关了 IPv6 后直连明显变少，"打洞率高"主要来自 IPv6。
3. **核对 TUN 开关时间**。日志推断会话 1 里台式机在会话开始约 28 分钟时关过 TUN、约 2 分钟后重开，Mac 在会话 1 开着 TUN、会话 2 关着。请维护者对一下当天的操作，确认推断。
4. **路由器 ULA 为什么反复变**。会话 1 里路由器下发的 ULA 每隔 20~75 分钟出现或消失一次，每次都触发 UU 换路径和短暂卡顿。Porta 打算用 ULA 做局域网候选，要不要查路由器的 IPv6 前缀下发设置，由维护者决定。
5. **家宽 NAT 的过滤行为**。日志已给出映射行为（UU 判为 Cone；几乎同时的绑定端口连号，拉长时间在几个区间跳；同出口回环能通），过滤行为看不到。用 NatTypeTester 一类工具在台式机上测一次，TUN 开、关各一次。这也决定 Porta 第九项值不值得做。
6. **RustDesk 的 NAT 类型是否被测成对称**。看两台机器 RustDesk **服务进程**日志里的 `Tested nat type`（服务进程不以当前用户运行，日志不在 `%APPDATA%\RustDesk\log`）。
7. 第 1、2 项建议在开着默认 Windows 防火墙的另一台机器上再做一次，避免本机防火墙设置造成的偏差。

## 8. 已排除或不采用的说法

- "UU 用自研 UTUNNEL 协议"：出自非网易域名的疑似仿冒站，且声称支持 Linux 被控，不采用。
- "官方标称 P2P 穿透率约 95%"：只出现在一篇 CSDN 文章里，没给出处，复核时站点打不开。官方博客唯一的数字是一个自述测试场景（电信连联通）"连接成功率 100%"，没有方法和样本。品玩说"利用了游戏加速器的打洞技术"，也没有出处。
- "UU 的信令长连接绑物理网卡、绕开 TUN"：是启动时间的巧合，见 §3.3。
- "打洞模式由云端建房间时下发"：本机看到的是本地 IPC 链路，云端是否参与没有证据，见 §4。
- "uuyc-mux 是网络多路复用"：它是 psmux（Windows 上的 tmux 替代品），和打洞无关。
- linux.do 一则帖子（https://linux.do/t/topic/2400034 ，2026-10-23 查）说 UU 只要能访问对端内网 IP 就判"内网"：楼主自己的猜测，且没排除"两端看到的 IP 相同"，只能当弱旁证，不作依据。
- 网易相关专利（CN120179269A，更新后重连）、网易云信的 RTC 演讲：都和 UU 远程的打洞无关。
- 初稿的三处说法，被解密日志推翻或更正：那条局域网 TCP 是"在用的连接"（实为 ICE-TCP 备用对，§3.1）；"Wi-Fi 上的 IPv6 按上游默认被跳过"（实为被 5 个名额的上限挤掉）；"每个网络对两台 TURN 各分配一次"（实为 4 个入口）。
