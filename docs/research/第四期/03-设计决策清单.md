# 第四期（应用出口）设计决策清单

- 日期：2026-10-27
- 依据：本目录的 `01-客户端读码.md`、`02-服务端读码.md`，以及对两份笔记关键说法的一轮读码核对。行号以 leapgate-client main `a57605c2f` 和 leapgate-server main `d830ac2`（核对时的 HEAD）为准。
- 本文只是设计讨论，没有改代码、没有构建或运行程序。

这份清单是第四期"应用出口"写实施契约之前要定的事。应用出口指被控端充当出口节点：控制端本机开一个 SOCKS5/HTTP CONNECT 代理，流量经远程会话从被控端发出去。已定的架构在 `docs/architecture.md` §3.9，这里不再复述。共 80 条决定，其中 11 条要你拍板，其余按评审推荐默认，你不同意可以逐条推翻。条目编号沿用评审分组：A 权限与授权，B 被控端怎么连目标，C 协议和本地代理，D 服务端目录，E 吞吐和中继，F 界面。另外 A3（服务端不再把控制端的登录令牌转给被控端）和第四期没有依赖，可以马上作为独立修复做。

文中几个词：
- 多路复用隧道（mux）：上游 1.5.0 起的端口转发模式，一条远程会话里开多个通道，每个通道一个目标。出口的每个代理连接就是其中一个通道。
- 裸管道：旧式端口转发，登录后整条连接切成明文透传到一个固定目标（`connection.rs:1340` 的 `set_raw`）。
- CM：被控端的连接管理小窗，负责审批、显示谁连进来了。
- ICE：第三期自研的直连打洞（契约 05）；hbbr：上游原版中继程序。
- TestDelay：被控端每秒向控制端发一次的测延迟报文，顺带让会话保持活跃。
- fake-ip TUN：mihomo 这类代理软件的一种模式，系统 DNS 返回 198.18.0.0/15 的假地址，流量进虚拟网卡再由代理软件转发。
- 哨兵登录目标：约定好的特殊登录目标值，被控端看到它就按出口处理（C1）。
- opened：被控端对"开通道"请求的应答帧（PortForwardOpened），里面带成功与否和失败文案；控制端发的开通道请求叫 open。
- origin-form / absolute-form：HTTP 请求行的两种写法，分别是 `GET /path` 和 `GET http://host/path`，后者是发给普通 HTTP 代理的写法。
- 上游回落路径：客户端还没确认服务端是 Leapgate 时，改走上游 `src/hbbs_http/sync.rs` 的心跳和策略处理。

## 要你拍板的

### E1 吞吐实测放在什么时候
- 问题：`architecture.md:344` 和 §5（`:423`）要求"第四期动手前先实测多路复用隧道吞吐，再定 CHANNEL_WINDOW"（每个通道的流控窗口，现为 256 KiB，`client/src/port_forward_mux.rs:23`），这和 2026-10-26 定的"开发期间只做单测和一次冒烟"冲突。
- 推荐：第一版窗口不动，吞吐实测并进开发完成后的统一验收，判定规则预先写进契约。设 F = 256 KiB ÷ RTT，U 是不经隧道直接上下载的基线速度。单流达到 0.8 × min(F, U) 算符合预期；F < U 且单流低于你给的目标值时，先调到 512 KiB 复测，最多到 1 MiB（E2）；单流低于 0.6 × min(F, U) 说明瓶颈在窗口之外，窗口不动、另立问题。测法用 Windows 自带的 `curl.exe --socks5-hostname`，ICE 和强制中继两条路径各测单流下载、4 个并行下载、单流上传。开发期那次冒烟只确认能用，顺手记一下速度。`architecture.md:344`、`:423` 照此改写。
- 备选：(a) 开工前用现有构建对 mux 端口转发测一次（约 1~2 小时无人值守），但不管测出什么第一版都不会改窗口，而且字面上违反 10-26 的规矩；(b) 不测，直接调到 1 MiB：被控端最坏缓存涨 4 倍，ICE 路径还被 KCP 约 1.15 MiB 的在途上限封顶，可能白调。
- 为什么要你定：§3.9 和 §5 是你 10-22 确认的步骤，10-26 的规矩比它晚，但没有点名覆盖它。另外要你在验收前给一个单流目标值，例如"常用路径上单连接至少 X Mbit/s"。窗口值随 open/opened 帧通告，以后改只动 2 行，新旧版本照样互通，晚改不会被锁死。

### A2 出口授权在哪里执行
- 问题：服务端目录只用来发现出口、被控端认证是唯一关口；还是服务端签发出口凭证、被控端验签后才放行。
- 推荐 (a)：服务端只做目录和授权表（D2、D3）。被控端放行出口的条件是出口开关（A5）加上游现有认证（密码、点击确认、2FA，`connection.rs:3045-3095`），不加签发接口和 proto 字段。允许手填 ID 使用出口，没登录账号也能用，只是看不到目录。契约写三条已知限制：撤销授权只影响目录，挡不住知道设备密码的人，也不断开已有会话，要切断某人就改密码或关出口开关；做不到"只给某人用出口、不给远控"；被控端看到的控制端身份都是对方自报的，出口审计落不到账号。以后升级到 (b) 是纯增量，授权表不用改。
- 备选 (b)：服务端用会合私钥签一张出口凭证（出口 ID、用户、签发时间、5 分钟有效期），被控端在密码校验之前验签。好处是授权名副其实，没被授权的账号连试密码的机会都没有，CM 能显示服务端证明过的账号名。代价约 2~3 人日；没配 Key、连原版服务端、用"ID@其他服务器"时出口一律不可用；撤销最晚 5 分钟生效；A1、A3 变成硬前提。另两种做法（服务端在打洞请求里按连接类型拦；服务端下发允许的控制端 ID 列表）核对时已证实挡不住，不列入。
- 为什么要你定：(a) 是 §3.9"两层控制"原文（`architecture.md:331`）的直接实现，不管服务端是什么、走哪条路径，行为都一样。但"列给谁、谁才能用"也能理解成 (b)。在默认配置下 (b) 的安全增量有限：知道密码的人本来就能远控桌面，enable-tunnel 又默认开着，他们还能用普通端口转发连任意一个 host:port。"撤销授权不切断访问"需要你知情接受。

### A8 局域网默认拒绝挡不住知道密码的人
- 问题：§3.9 写"默认禁止访问被控端局域网和本机端口"（`architecture.md:336`），读起来像对所有出口用户的保证；但 enable-tunnel 以 `enable-` 开头、空值算开，也就是默认开，普通端口转发又不过滤目标（`connection.rs:2969-2976` 只做规范化），知道设备密码的人照样能碰局域网。
- 推荐：不改 enable-tunnel 的默认值，也不给普通端口转发加过滤，只在契约里写清它防什么、不防什么。防的是：经出口浏览的第三方网页借出口攻击被控端局域网（DNS 重绑定、对路由器管理页的 CSRF）；以后开了系统代理时，控制端访问自家局域网的请求被送到对面去。不防的是：密码持有者用普通端口转发或远控桌面去碰局域网。出口开关旁的说明加一句："要让出口用户碰不到局域网，请同时关掉'允许 TCP 隧道'"。
- 备选：把 enable-tunnel 默认改成关：改变第一到三期已有的上游默认，用端口转发和 RDP 的用户升级后要手动打开；普通端口转发也套上出口过滤：转发到本机 3389、局域网 NAS 这类正常用法会被挡住。
- 为什么要你定：§3.9 原文的保证实际只在关掉 TCP 隧道时成立。

### A9 架构里"已信任的设备"那半句要更正
- 问题：`architecture.md:331` 写"真正连接仍要过被控端认证（设备密码或已信任的设备）"，但上游的已信任设备只免 2FA、不免密码（`connection.rs:2850-2861`）。
- 推荐：不新增免密码或免审批的机制。原文括号改成"设备密码，或被控端有人点击接受；开了 2FA 时，已信任的设备免 2FA"，并注明 2026-10-27 读码更正。
- 备选：新增"已信任设备免密码使用出口"：能用的凭据只有对方自报的硬件 ID、设备 ID 和名字，等于没有认证，否则就得自造一套会话票据；原文不动：契约和架构对不上，后来的人会以为已信任设备可以免密码。
- 为什么要你定：改的是你逐条确认过的架构原文。

### B4 按网段放行能放到多大
- 问题：放行配置放在哪、用什么语法、能打开哪些地址。
- 推荐：放在被控端本地的 Config 选项 `leapgate-exit-allow-nets`。必须放 Config，因为被控端服务进程读不到界面进程写的 LocalConfig（`rendezvous_mediator.rs:1074-1076`）。这个 key 和出口开关用同一套防远程写入的保护（A7）。语法是 CIDR 或单个地址，用逗号、空白或换行分隔，不带端口、不写域名；解析用主 crate 已有的 cidr-utils 0.5，界面照抄上游 IP 白名单对话框。放行列表只能打开 B3 的"软拒"档（私网、100.64/10、ULA、本机所在网段、解析得到的 198.18/15），打不开"硬拒"档（回环、本机所有地址、链路本地和云主机元数据地址、保留地址、控制端送来的 198.18/15 字面量）。已知限制：家宽 IPv6 前缀会变，按全局 /64 写的放行第二天就失效，实际只有 ULA 能稳定放行。
- 备选：服务端命令行按设备配置、经签名心跳下发：工作量是本地方案的三四倍，等于让服务端运维者替设备主人打开局域网；放行列表能打开一切：最贴原文，但一条宽泛的规则会把本机上只信任局域网的服务和代理端口一起放出去；第一版不做放行，或只做一个"允许局域网"勾选框：原文的"按网段放行"落空或粒度太粗。
- 为什么要你定：原文是"可以按网段放行"，推荐规定回环和本机地址在任何规则下都打不开，比原文收窄了。存放位置和语法可以按推荐默认。

### B9 出口流量从被控端物理网卡出去
- 问题：被控端自己开着代理、全隧道 VPN，或配了 RustDesk 的代理设置时，出口流量走哪条路。
- 推荐：一律从被控端物理网卡出去，这是 B2 的直接结果。出口 IP 是被控端的宽带出口（路由器做透明代理时是路由器的出口），不经本机的 TUN 代理、全隧道 VPN 和 RustDesk 的 socks 设置。被控端开关旁写一句"出口流量从本机网卡直接出去，不经过本机的代理或 VPN"。
- 备选：跟着系统路由走：能借主人的公司 VPN 进内网、借主人的代理翻墙；但被控端开 fake-ip TUN 时，局域网默认拒绝可以被 sslip.io 这类把 IP 写进域名的服务、DNS 重绑定或代理软件改写目标绕过，违反 P-2，朋友还会消耗主人的代理流量。做成主人可选的"出口经本机代理"开关、默认关：多一个模式，打开时过滤保证不再成立，要单独接受这条和 P-2 冲突的例外。
- 为什么要你定：§3.9 只说"让控制端的流量从被控端出去"，没说被控端有代理或 VPN 时怎么走。按推荐，两类用法做不了：经出口进主人公司的内网；国内的被控端上，被墙的网站经出口也打不开。

### B10 路由器做 fake-ip 时，域名目标怎么办
- 问题：路由器做 fake-ip（例如 OpenClash 的 fake-ip 模式），被控端物理网卡的 DNS 也只回 198.18.x，出口拿不到真实地址。
- 推荐：默认拒绝，回给控制端"被控端所在网络的 DNS 返回了 fake-ip 地址"；IP 字面量目标照常能用。唯一的开口是主人在放行列表里写 198.18.0.0/15，含义是明确接受"路由器转到哪里都行，包括局域网"；这条只放行被控端自己解析得到的 198.18.x，控制端送来的 198.18 字面量仍按 B3 硬拒。不加 DoH，也不写死公共解析器。已知限制两条：路由器用的不是默认 fake-ip 网段时判不出来，会被当成公网放行；被控端本机的 mihomo 开了 strict-route、挡掉物理网卡发出的 53 端口查询时（推测），只能回落系统解析拿到本机的假地址，域名目标同样失败，放行也没用。
- 备选：加一个"允许无法核实的目标"开关：效果和放行 198.18/15 相同，多一个实体；198.18/15 永不放行：这类网络里出口完全不能用域名；改用写死的公共解析器或 DoH：要选服务商，查询记录交给第三方，还要新写 DoH 客户端。
- 为什么要你定：默认是安全的，但在常见的路由器 fake-ip 网络里，出口默认用不了域名，体验影响大。这类网络里，域名目标要能用，只能由主人配一条环境相关的放行规则，和 P-2 的"不接受要用户配环境规则"有张力；推荐的理由是默认的安全不依赖这条配置，配置只用来解锁功能。请确认这样算不算违反 P-2。你自己家路由器给局域网的 DNS 是不是 fake-ip，冒烟时确认（B15）。

### C5 本地代理什么时候回"连接成功"
- 问题：本地代理收到连接后，是马上回成功，还是等被控端真正连上目标再回。
- 推荐 (A)：隧道层的结果准确回报，通道层乐观地先回成功；不加 proto 字段，不改上游 mux 的 open 流程。隧道已建好时，先写成功应答再开通道；隧道还没建时先登录，登录失败、对端不支持、连接没加密时回 SOCKS 0x01 / HTTP 502。单个通道被拒沿用现有逻辑，关掉本地连接。被控端换掉 `server/port_forward_mux.rs:228` 的失败文案：被出口策略拒绝时用一条不带地址的固定文案，控制端按文案去重（`src/port_forward_mux.rs:651-674`），一阵拒绝只弹一次框；198.18 字面量用专门文案（C12）；连不上、超时回空文案，不弹框。
- 备选 (B)：等被控端回 opened 再应答，PortForwardOpened 加一个字段号 1000 的原因码。好处是 curl、git 能报出准确原因（SOCKS 0x02/0x04/0x05，HTTP 403/502/504），和 OpenSSH `-D`、Tor 的做法一致。代价是每条新 TCP 连接的首包多等一个隧道往返，经中继约 60~100 ms；上游 mux 文件要改约 20~30 行；proto 超出 §3.9 写的"最多加一个标记字段"。浏览器不显示 SOCKS 错误码，对浏览器用户几乎没有区别。(C) 等 opened 但不加原因码；(D) 什么都不改：失败文案带地址、去重不起作用，一个页面 10 秒内最多连弹 8 个框，不可接受。
- 为什么要你定：三个评审视角 1 比 2 分成两边，取舍在首包延迟和命令行工具的错误码之间，选 (B) 还会超出架构原文。B12 的原因码集合两种选法都要：选 (A) 时，原因码只用于被控端日志（B7）和策略拒绝、198.18 字面量那两条固定文案，其余失败回空文案；每个原因码配一条英文文案只在选 (B) 时需要。

### C7 "设为系统代理"进不进第一版
- 问题：§3.9 对系统代理写的是"可以做"、默认关。
- 推荐：不进第一版。出口行显示两个可复制的地址 `socks5h://127.0.0.1:<端口>` 和 `127.0.0.1:<端口>`（HTTP CONNECT），附 Firefox 和 Chrome/Edge 的配置方法（Chrome/Edge 用 SwitchyOmega 这类扩展，或 `--proxy-server` 启动参数）。以后要做时先满足几条约束：注册表写 `http=`/`https=`，不写 `socks=`（Chromium 怎么解读 WinINet 的 `socks=` 没核实）；同时支持 absolute-form 的普通 HTTP 代理；ProxyOverride 排除本机地址和 Leapgate 自己的服务器；只在注册表当前值仍是我们写的时候才还原。
- 备选：写 HKCU 下 WinINet 的系统代理：约 300 行，和 Clash Verge 这类软件的系统代理互相覆盖，控制端崩溃后整机浏览器上不了网，而且整个用户会话的流量都会从别人的网络出去；写 `socks=`：可能被当成 SOCKS4，而 C4 不做 SOCKS4；改做"用出口打开浏览器"按钮：起一个独立配置目录、带 `--proxy-server` 的 Edge/Chrome 实例，约 50 行，不碰系统设置，但没有平时的书签和登录状态，参数没在本机验证，也是架构里没有的新功能。
- 为什么要你定：不做的话，Chrome/Edge 用户要装扩展或改启动参数才能用，这是面向朋友的易用性取舍。

### C13 控制端日志记不记通道目标
- 问题：控制端日志要不要记每个出口通道连了哪个 host:port。
- 推荐：逐通道的目标和成败只用 trace 级别，不进日志文件。日志文件只记隧道级事件（建立、直连还是中继、断开原因、终止性错误）和按类别计数的限频日志，不带地址。被控端怎么记见 B7。
- 备选：失败的通道带上 host:port、用限频的 info 记：排障方便，日志文件里会留下一部分浏览记录；所有通道带目标用 debug 记：违反仓库的日志规则，日志文件可能被刷满。
- 为什么要你定：这是隐私和可排障性之间的取舍，也决定无人值守验收能从日志里看到什么。推荐取最保守的一种。

## 按推荐默认的

### A 权限与授权
- A1 设备主人加固：已锁定公钥的设备，登录只在没有主人时绑定（`server/src/api/account.rs:362-375` 的冲突分支改成 `coalesce`）；延迟补绑（`OWNER_FROM_TOKEN`，`device.rs:163-165`，设备无主时用该设备上最近用过的令牌补主人）只认锁定之前签发的令牌；新增命令 `device owner <device> <user|none>`，存储位置见 D14。理由：`server/LEAPGATE.md:548` 本来就把这两项排进第四期；不加补绑条件的话，攻击者没绑上也会留下令牌，真主人一登出就会被补成主人。备选"已锁定设备整个关掉补绑"会让先登录、后注册的新装设备失去补绑。
- A3（同 D11）令牌不再转给被控端：作为独立修复，在目录上线前合入。`rendezvous_server.rs:936` 转给被控端的 RequestRelay 不再填 token，同步改测试 `:3925-3928` 和 `server/LEAPGATE.md:348`，客户端不改。理由：控制端的 API 令牌是不绑设备、永不过期的 Bearer 凭据，现在经 UDP 明文转给被控端，任何被控端都能冒充控制端账号读地址簿，以后还能读出口目录；没有任何被控端读这个字段，删掉没有兼容风险。不强制用户重新登录，已经泄露的令牌写进已知限制。
- A4 登录范围摘要（`login_scope_digest`：被控端把第一次登录的目标做成摘要，同一连接里再登录换目标就拒绝）：C1 用哨兵目标，摘要本身不用改，出口标记会被自然锁住，"先让主人批一个普通转发、再换成出口"会被拒。逐通道的目标不进摘要。CM 只显示"作为出口"，不列通道目标和通道数。备选"实时列出通道目标"要加 IPC 和 Dart 列表，还会把控制端访问的网站摆在被控端屏幕上。
- A5 出口开关独立判断：只认自己的 `== "Y"`，不经 `permission()`、`is_permission_enabled_locally` 和 `option2bool`（`connection.rs:2680-2727`），不映射进 ControlPermissions（会合报文里携带的权限位图），不看 access-mode（上游的"完全访问 / 仅共享屏幕 / 自定义"设置），也不要求 enable-tunnel。逐通道检查放在 `server/port_forward_mux.rs` 的 `on_open` 开头，`connection.rs:2392-2394` 的闭包不动。理由：走 `permission()` 的话，access-mode=full 和没有认证的 ControlPermissions 都能打开它；这也是唯一能让局域网过滤真正起作用的配置。备选"出口和 enable-tunnel 都要开"让主人做不到只开出口。这是对 §3.9"这是一个新的权限项"的细化：出口不放进权限卡片，也不受访问模式管，所以主人把访问模式设成"仅共享屏幕"以后出口照样开着，和上游"仅共享屏幕就是全部权限关闭"的直觉不同。备选 (c)：access-mode=view 时强制关出口，约 1 行。请留意这一条。
- A6 隧道重建时的认证：照上游，复用本窗口内存里上次验证通过的密码，认证失败时照上游弹密码框或 2FA 框；被控端用点击确认、只有临时密码都允许；建隧道期间到达的本地连接排队，失败时一起回失败。开关旁放一句静态说明："无人值守的出口请设固定密码，审批方式选'只用密码'"。备选"出口模式必须能无人值守"会一刀切掉"主人在场、临时借出口"的用法，也越过了上游认证的语义。
- A7 开关的 key：叫 `leapgate-allow-exit`，存在 Config，Rust 只经 A5 的判断函数读；Dart 设置页自己传 getter，因为默认 getter 会把这个前缀的空值显示成勾上。另在上游回落路径 `src/hbbs_http/sync.rs:296` 的 `handle_config_options` 开头加一行，丢掉 `leapgate-` 开头的 key，和 `merge_strategy`（`libs/leapgate/src/report/heartbeat.rs:281`）共用同一个判断函数。理由：只有"`leapgate-` 前缀加自己判 Y"能同时做到策略写不了、默认关；不加 sync.rs 这一行，客户端还没确认服务端是 Leapgate 时，原版服务端的策略就能打开出口，不满足 P-2。B4 的放行网段同样适用。
- A10（同 C6、F11）本地监听：只绑 127.0.0.1，不加认证，不设 SO_REUSEADDR（上游端口转发在 `port_forward.rs:84` 设了）。端口由用户填，界面预填一个避开常见代理端口和 Windows 动态端口段的建议值（例如 21180），被占用就直接报错，不自动换。已知限制：本机任何程序和同机其他 Windows 账户都能用这个端口。备选"用户名密码认证"会让 Chrome 这类浏览器用不了（未查一手来源）。
- A11 出口登录的检查顺序：最前面是上游的 IP 白名单（连接建立时，`connection.rs:1507` 的 `on_open` 调 `check_whitelist`）和 ID 白名单（进入 `login_request` 的 match 之前，`:2923`）；接着是登录分支里的出口关口，依次查出口开关、是否多路复用、是否加密；最后才是密码、点击确认、2FA。失败时逐项说明原因，例如 "Exit node is not enabled on the remote device"。暴露的信息和上游在认证前就回 "No permission of IP tunneling" 同级。
- A13 被授权人在目录里看到的字段见 D2：不给系统用户名、系统版本和 IP。

### B 被控端怎么连目标
- B1（含 A12）解析与连接：出口模式不调 `normalize_port_forward_target`，也不把 "host:port" 字符串交给 `TcpStream::connect`。域名只解析一次，逐个地址过滤，实际连接的必须就是通过过滤的那个地址，这样 DNS 重绑定无从下手。答案里有的地址被拒、有的通过时，丢掉被拒的，最多留 8 个。用简化的 Happy Eyeballs：IPv6、IPv4 交错，250 ms 错峰，最多试 4 个；解析最多 2 秒、连接最多 8 秒、整体最多 10 秒。普通端口转发的 3 秒不变。备选"有一个被拒就整个拒、沿用 3 秒"会让正常域名打不开，IPv6 不通时第一个地址就耗尽时间。
- B2 DNS 和源地址：每次开通道时枚举物理网卡（`lan::nics()`，`lan.rs:340-349`），连接绑在物理网卡地址上；DNS 问那块网卡自己的 DNS 服务器（把 ICE 的 `ice/dns.rs` 查询代码挪成共用模块，结果分成"有地址 / 明确没有 / 没答案"三种），只有问不到时才回落系统解析；找不到物理源地址时不退回不绑网卡的连接；不读 RustDesk 的代理设置。备选"系统解析、不绑网卡"在开 fake-ip TUN 时要么完全用不了，要么能被绕进局域网。前提待冒烟确认（B15）。
- B3 默认拒绝的地址：一个纯函数，先把映射地址（::ffff:0:0/96）和 NAT64 地址（64:ff9b::/96）里的 IPv4 取出来判。硬拒：保留地址（含 Teredo、6to4、本地用途 NAT64）、回环、链路本地（含 169.254.169.254）、本机所有网卡地址、本机公网 IPv4（B11）、open 请求里本来就是 198.18/15 的字面量（原因码 `fake_ip_literal`，配 C12 的文案）；软拒：私网、100.64/10、fc00::/7、本机每个全局 IPv6 所在的 /64、本机 IPv4 所在的链路网段、被控端自己解析得到的 198.18/15（原因码 `fake_ip`）；其余允许。198.18 字面量和解析结果分开处理，是因为字面量是控制端本机 fake-ip 分配的，被控端或它的路由器用的是另一套映射，放行了也只会把连接送到不相干的目标。不复用 ICE 的地址分类函数，两者语义不同。
- B5 拒绝裸管道：在 `connection.rs:2969` 登录分支的权限检查之后加一处，非多路复用的端口转发登录一律拒绝，位置在密码校验和审批弹窗之前；文案指向上游设置页的 "Reuse one connection for port forwarding" 选项，不写上游品牌名。对所有端口转发生效，按 `architecture.md:107` 不用等兼容期结束。备选放在 `connect_port_forward_if_needed` 里：点击确认模式下主人会先白点一次审批。
- B6 资源上限：沿用上游的结构上限（每条隧道 256 个通道，每通道 256 KiB 额度），不另设出口会话数、连接中并发数和通道空闲超时。被控端单会话的待发缓存最坏约 64 MiB，反方向的接收缓存同样约 64 MiB；主循环卡在一次发送上最多 120 秒（`connection.rs:2985-2994`），都写进已知限制。备选的出口专用上限会切断 SSH 这类长时间空闲的正常连接，会话数上限还会被断网后没清掉的旧会话占住。
- B7 被控端日志：只在拒绝时打一行限频 warn（`leapgate exit: <控制端 ID> refused <ip>:<port> (<原因>)`），只记地址、不记域名；成功和普通失败只记 trace；不上报服务端审计。限频用 `throttled_log!`（60 秒），它的限频状态是挂在调用点上的进程级 static（`libs/hbb_common/src/log_throttle.rs:87-99`），所以整个进程每 60 秒最多一行，带累计次数，主人只能看到每分钟的第一个被拒地址。要让每类原因都看得到，可以按原因码分开设多个限频点。设置页两边各写一句隐私说明。备选"记每个通道的 host:port"会把控制端的上网记录长期留在主人的磁盘上。
- B8 关掉出口开关时：新通道当场被拒；已有的出口会话在被控端每秒一次的定时器分支里检查开关，下一秒断开，写法照抄同一分支里的 "Timeout" 判断，约 3 行挂钩。理由：出口会话靠 TestDelay 保活、不会自己结束，只拒新通道在滥用时等于没关。备选"只拒新通道"和 enable-tunnel 的语义一致，但契约要写明关开关不断已有会话。
- B11 本机公网 IPv4：复用 ICE 的 STUN 探测，从物理 IPv4 源地址向会合服务器问一次，结果缓存 10 分钟，归入硬拒；查不到时打一行日志并写进已知限制。理由：公网 IPv4 的家宽上，经 NAT 回环访问自己的 WAN 地址多半能打开路由器管理页。备选"不做"会留着这个口子。
- B12 失败原因码：`invalid_target`、`reserved`、`loopback`、`link_local`、`local`、`lan`、`fake_ip`、`fake_ip_literal`、`nxdomain`、`resolve_failed`、`no_route`、`timeout`、`refused`、`unreachable`。选 C5 (A) 时，原因码只用于被控端日志（B7）和两条固定文案（策略拒绝、198.18 字面量）；选 (B) 时才给每个原因码配一条固定的英文文案，随 opened 传回。
- B13 这些过滤规则只作用于出口模式：普通端口转发的规范化、3 秒超时和不过滤目标一个字不改，只有 B5 例外。
- B14 不按目标端口限制（例如不封 25 端口）：出口使用者都经过了授权和被控端认证。
- B15 开发期那次冒烟加五项：(a) 被控端开 mihomo fake-ip TUN，strict-route 开和关两种情况下，绑物理网卡地址的 TCP 是否从物理网卡出去（第三期的 S3 实测只测过 UDP）；(b) 同样两种情况下，从物理网卡发往 DNS 53 端口的查询会不会被挡；(c) 你家路由器给局域网的 DNS 答案是不是 198.18.x；(d) 私网地址、本机地址、本机公网 IP 回环、169.254.169.254 都被拒，按控制端看到的结果判定（连接被关，选 C5 (A) 时还有一次弹框），日志只确认出现过 `leapgate exit:` 前缀的行（B7 的限频下 60 秒内只会有第一类拒绝的那一行）；(e) 用 1.5.0 以前的原版控制端或关掉多路复用的控制端连一次，收到 B5 的文案，被控端不弹审批。

### C 协议和本地代理
- C1 出口标记：登录请求不改 proto，用一个哨兵登录目标 `PortForward{host="leapgate-exit.invalid", port=1, multiplex=true}` 表示出口，整串精确比较。应答侧在 Features（`libs/base/protos/message.proto:100-104`）加 `bool leapgate_exit = 1000`，被控端恒填 true，表示"本构建能处理出口登录"。ConnType 照旧填 PORT_FORWARD。契约写明这个标记只用来选模式，不作为授权依据。备选"给 PortForward 加字段"要改 `client.rs` 和摘要函数，还要和占位值两套并存；新加 ConnType 根本传不到被控端。
- C2 哨兵在被控端怎么流转：登录时照旧规范化，得到 "leapgate-exit.invalid:1"，作为登录目标和 CM 显示值；`on_open` 在出口模式下跳过规范化和 `:128` 的目标比较。`.invalid` 只走 DNS，不会像单段主机名那样触发局域网里的 LLMNR/NetBIOS 广播；正常 DNS 下得到 NXDOMAIN，被控端开着 fake-ip 时可能分到 198.18.x 并被 TUN 接住（C3 ④），所以安全不靠解析失败，靠的是控制端的出口路径里根本没有裸管道分支。端口 1 能通过 `ui_session_interface.rs:2013` 的过滤。
- C3 对端不支持时：出口有自己的监听，从不进裸管道。登录后检查三项（是多路复用、对端有 `leapgate_exit` 位、流已加密），任何一项不满足就丢掉连接、本地回失败、报一次"对方不支持作为出口"。兼容表写进契约：① 两端都是第四期、出口开着：正常；② 被控端是第四期、出口关着：密码校验和审批之前就回登录错误；③ 被控端是原版 1.5.0 以上或第三期以前的 Leapgate：点击确认模式下对方会先看到一张一闪而过的端口转发卡片，控制端发现没有出口位后立即断开；④ 被控端是 1.5.0 以前的原版：对方去连哨兵、解析失败，就算连上了控制端也不发任何数据；⑤ 原版或旧版控制端连第四期被控端：发不出出口请求，普通端口转发照旧，裸管道按 B5 拒绝；⑥ 服务端是原版或第四期以前的版本：出口照常能用，只是没有目录。
- C4 本地代理：手写最小实现，放 `libs/leapgate/src/exit/proxy.rs`，同一个端口按首字节分流。SOCKS5 只支持无认证和 CONNECT，域名原样交给被控端，控制端绝不在本地解析；SOCKS4 回拒绝码；HTTP 只认 CONNECT 请求行，忽略所有请求头（绝不按 Host 头选目标），其他方法以及 origin-form、absolute-form 请求回 501 后关闭。握手限时 10 秒，请求头上限 8 KiB。不引入 fast-socks5 和 httparse。网页里的 fetch 和 WebSocket 发不出 CONNECT，也发不出 0x05 开头的字节，所以 DNS 重绑定到本机的网页借不到出口。
- C6 本地监听见 A10。
- C8 代码落点：被控端在 `connection.rs` 登录分支加一处出口关口，Features 加一行，`server/port_forward_mux.rs` 的 `on_open` 和 `run_controlled_channel`（`:197` 的连接处）各加挂钩，连接逻辑放 `libs/leapgate`；控制端另写一个出口监听，上游在 F1 的位置（`ui_session_interface.rs` 的 `start_one_port_forward` 开头）加一处分流，`port_forward.rs` 再做几处可见性调整。分流不放在 `port_forward::listen`，因为那里拿到的只是 `impl Interface`（`port_forward.rs:72-83`），推不了 F4 要用的 `set_connection_type`，而 `start_one_port_forward` 拿得到 `Session<T>`。备选"被控端另写一份出口通道处理"会把经过多轮审查的连接期时序复制成两份。契约要注明：§3.9 写的"改 `on_open` 那一处判断"细化为过滤点在实际连接那一步，因为 `on_open` 只看得到字符串，挡不住域名解析到内网。
- C9 建隧道失败后的重试：按上游返回值分成终止性失败（被拒、用户取消、对端不支持、没加密：关掉监听，重开映射才再试）和临时性失败（对端离线、超时、中继失败：冷却 10 秒，之后的下一个本地连接再试）；登录期间到达的本地连接排队等结果。备选"每接受一个本地连接就重新登录一次"会把浏览器的几十个并发连接放大成对端的弹窗刷屏和登录失败锁定。
- C10（同 E6、F9）要求加密：被控端在出口关口要求 `stream.is_secured()`，控制端登录后也检查。出口复用 `connect_and_login_mux`，而这个函数在 `Client::start` 之后，只要流没加密、又不是直接 IP 访问，就会先调 `confirm_insecure_connection` 弹上游的"不安全连接"确认框（`port_forward.rs:421-425`），所以写成已知限制：非直接 IP 访问且连接没加密时，控制端会先弹一次这个确认框，用户点继续后登录照常发出，最后才被两端的加密检查拒掉。备选是给 `connect_and_login_mux` 加一个参数，出口调用时不确认、直接返回失败（C8 本来就要改 `port_forward.rs`）。要求加密的理由：没配 Key 时整条流是明文，链路上的人能看到目标，还能往已认证的会话里插入新通道白用出口；Leapgate 构建默认注入服务器 Key，正常使用不受影响。直接按 IP 连接的方式不能当出口用，写进已知限制。
- C11 Leapgate 控制端不再回落裸管道：在 `port_forward.rs` 里让 `mux_enabled()` 恒为真，对端没回多路复用就丢弃连接并报"对方版本过旧"，单独一个提交。这是落实 §3.9 已定的"Leapgate 客户端只发起多路复用模式"，代价是不能再对 1.5.0 以前的原版被控端做端口转发和 RDP。
- C12 198.18 字面量：控制端不预先过滤；被控端按 B3 硬拒，放行列表打不开，拒绝时用专门文案，提示"请在代理设置里改用远程 DNS（socks5h）"。
- C14（同 E5、F13）隧道生命周期：懒建立，第一个本地连接到来时才建；空闲时不拆，窗口开着就一直在，由 TestDelay 保活。经中继时占一对 hbbr 连接，每月约耗 1~2 GB 额度（推测）。想重试直连或解除 hbbr 降速，关掉窗口再开即可。备选"空闲 N 分钟就拆"要加计时器，在点击确认或临时密码模式下，每次重建都要有人操作。
- C15 写进已知限制：局域网默认拒绝只约束出口模式（同 A8）。

### D 服务端目录
- D1 出口状态只放内存：Leapgate 签名心跳加一个布尔字段 `exit`，服务端存进 `LeapgateHb`（`server/src/peer.rs:110`），不加数据库列。理由：目录只需回答"此刻在线且开着出口的有哪些"，心跳一停状态自然过期；落库要改多轮审查过写锁的 `touch`，还会留下清不掉的旧值。心跳不上报放行网段，以免泄露内网拓扑。
- D2 目录接口：`GET /api/leapgate/user/v1/exits`，用用户令牌认证，只返回此刻可用的出口，字段是 `id`、`hostname`、`owner`、`own`；不返回 IP、系统信息和离线设备。不放在 `/api/leapgate/v1/` 下，因为那个前缀会被当成设备上报接口处理（`api/mod.rs:403-414`）。`LEAPGATE_FEATURES` 加 "exit"，只表示服务端有目录接口，控制端靠它判断服务端支不支持目录（F3）。客户端只在打开目录时取一次，不轮询。
- D3 授权表 `exit_grant`：新迁移 0007，每行是一个设备 ID 加一个用户或一个组；`device_id` 不加外键，不改设备表的淘汰规则；用户、组被删时级联清掉授权，组授权按组成员实时生效；不加过期时间、授权人、创建时间列。备选里加外键 cascade 会在设备行被淘汰时静默丢授权，加外键但不写 on delete 会让新设备建行全部报错。
- D4 命令行：顶层命令 `exit grant|revoke <device> --user <u>|--group <g>` 和 `exit list`，放在 `cli/manage.rs`，照 `ab grant/revoke` 写。grant 之前查 peer 表，确认这个 ID 已注册，挡手误，也挡"先授权、后被人抢注"；不检查在线和开关状态。revoke 的输出写明"只影响目录，已有会话不断"。
- D5 不专门统计出口会话：连接类型是控制端自报的，只走中继的那一路记录恒为 0，ICE 胜出时记的也是上游信令的结果，算出的比例不准。中继成本看 hbbr 用量和账单。以后要区分出口会话，首选在被控端连接审计的 `auth` 字段里加标记。
- D6 "可用出口"的判据：心跳里的 `exit` 和被控端是否接受出口，用 `libs/leapgate` 里同一个判定函数；服务端要求 UDP 注册在 30 秒内、Leapgate 心跳在 180 秒内（和 ICE 共用一个常量）、`exit` 为真，三条同时成立。目录只是建议性的，谎报只影响谁的目录里出现这台设备，不扩大谁能连。
- D7 管理员没有全局视图，要看全部用命令行 `exit list`。
- D8 目录响应不签名：目录不是关口，现有签名构造要绑定设备的请求签名，套不到用户接口上。
- D9 `device key reset --forget` 后，授权和设备主人会按 ID 被下一个注册这个 ID 的设备继承：只在 `server/LEAPGATE.md:618` 补说明，不改命令行为。
- D10 服务端策略不能下发出口开关：`leapgate-` 前缀本来就被 `strategy set` 拒收（`cli/ops.rs:87-90`），不用改代码。
- D12 条件项：只有 A2 选 (b) 时才做凭证接口 `POST /api/leapgate/user/v1/exits/{id}/ticket`。
- D13 `server/LEAPGATE.md:549`（§11）"补错归属后果有限"的论证要改写：设备归属现在还决定它出现在谁的出口目录里。§12 新增"出口目录"小节，新增 §9.6 写两个接口前缀的分工。
- D14 A1 的"命令行指定主人"只保留一个来源：`device owner` 直接写 `device.user_id`，同时插一行 `device_policy`，借用已有的淘汰保护（`device.rs:183`、`:189` 只看有没有这一行）。出口设备都锁定了公钥，A1 的 `coalesce` 生效后登录不会再覆盖。这样组面板（`server/src/api/group.rs:99-113`）、命令行设备列表（`server/src/cli/ops.rs:318`）、登出清主人（`account.rs:431`）、延迟补绑（`device.rs:313`、`:443`）和出口目录读的是同一个主人。备选是在 `device_policy` 加新列 `owner_id`，那就要定义"有效主人 = coalesce(device_policy.owner_id, device.user_id)"，并把上面这些读主人的地方全部改用它，否则同一台设备在组面板和出口目录里会挂在不同的人名下。
- D15 契约的"明确不做"集中列出 D 组有意不做的八项：离线出口、实时状态命令、授权过期、出口统计、目录签名、管理员全局视图、上报放行网段、淘汰保护。

### E 吞吐和中继
- E2 CHANNEL_WINDOW 第一版不改。契约写明：常量只在 `client/src/port_forward_mux.rs:23` 定义一处，被控端导入的是同一个；以后调大时，`UPDATE_THRESHOLD`（`:30`）必须钉成字面量 128 KiB，否则和 256 KiB 的旧对端互连时通道会静默卡死（读码推出，调的时候用单测钉住）；ICE 路径整条隧道另受 KCP 约 1.15 MiB 的在途上限约束，调过 1 MiB 没有收益。
- E3 hbbr 放宽：只加一个环境变量 `SINGLE_BANDWIDTH=256`（单位 2^20 bit/s，两个方向合计），其余参数用默认值，保留降速规则（降速阈值随之变成会话平均约 169 Mb/s）。变量名必须全大写加下划线，已发布的 1.1.15、1.1.16 只认这种写法。随第一期部署那次重启生效，重启后在启动日志里核对 `SINGLE_BANDWIDTH: 256Mb/s` 这一行，同时把 hbbr 镜像钉到具体版本。路由不读连接类型，想少用贵的中继就用现成的 `[[relay]] weight`。不做月流量机制。备选 `DOWNGRADE_THRESHOLD=0.33` 更省额度；关掉降速的话，对称千兆的出口约 2 小时就可能用掉一个月额度（推测）。
- E4 路径偏好不为出口特判，已知限制写三条：隧道里所有通道共用一条有序连接，丢一个包所有通道一起停（队头阻塞），整条隧道在链路上只算一条流的拥塞窗口；ICE 走的 KCP 不做拥塞控制，长时间大流量可能挤满被控端上行，逃生口是现成的 `allow-kcp-congestion-control`；隧道选定路径后不再换。
- E7 被控端所有通道共用一条无界发送队列，下载跑满时新通道的应答要排队（8 条下载、上行 20 Mbit/s 时约 0.8 秒，推测）：第一版接受，统一验收时加一项测量。
- E8 `relay-fallback-delay`（ICE 和中继竞速时等 ICE 的时长，默认 2.5 秒）的输入框只在 WebRTC 勾选框打开时显示：第四期不改界面。
- E9 随契约一起更正架构和笔记里的几处文字，见下一节。

## 核对时更正的事实
- 笔记说没加方括号的 IPv6 字面量拼成 "host:port" 后会解析失败：不对。std 在最后一个冒号处切开，"::1:80" 能切成 `::1` 和 80。这是按 std 实现推断的，本机没装 rust-src，也没运行验证，要用单测钉住。出口路径按 B1 不再交字符串，不受影响。
- 选项前缀规则有例外：`stop-service`、`direct-server`、`force-always-relay` 三个 key 和 `allow-` 开头的一样只认 "Y"（`config.rs:2840-2852`）。"服务端策略能写任何 key"要收窄：定制客户端强制的 key 写不进去，策略也只写得到 Config、写不到 LocalConfig。
- "ControlPermissions 有值就覆盖本地开关"说得太宽：只对 `permission()` 映射的 12 个 key、位值为 1 或 2、非 Android 时才覆盖；ICE 路径建连接时传的是 `ConnectionMeta::default()`，根本不生效；leapgate-server 也从不设置它。但 Windows 默认用 UDP 会合，这个报文没有认证、不校验来源，所以出口不映射进它。
- "在授权之后拒绝裸管道"不准确：`connect_port_forward_if_needed` 里那个位置是认证通过之后、`authorized = true`（`connection.rs:1903`）之前，点击确认模式下用户会先看到弹窗。
- 上游从 1.5.0 起也有多路复用端口转发（上游提交 `3fc11c0f`）。拒绝裸管道影响的只是 1.5.0 以前的原版控制端和关掉 `enable-port-forward-mux` 的控制端，不是所有原版控制端。
- 笔记 02 §5 说 RequestRelay 带着 conn_type 转给被控端：控制端发给会合服务器的 RequestRelay 从不填 conn_type（`client.rs:1842-1850`），被控端收到的恒为 0，服务端在这里也没法按连接类型拦。按 IP 直连只在被控端打开 `direct-server`（只认 "Y"，默认关）时才有，不是任何被控端都能被绕开。
- 设备主人：绑定代码实际在 `account.rs:355-378`；锁定公钥挡不住改绑（锁定状态的匹配也算通过）；另有一条笔记没写的延迟补绑通道（A1）。
- "新授权表要照 `device_policy` 加淘汰保护"是设计选择，不是代码逼出来的：`device_policy` 不引用设备表，淘汰设备行不会连带删策略（D3）。
- hbbr 参数：运行中还能从本机 127.0.0.1 用 TCP 连主端口，发 `dt`/`t`/`ls`/`tb`/`sb` 改参数，不只是环境变量和 .env；空闲断开实际发生在静默 31~34 秒，不是 30~33 秒，而且写死在代码里；873230e 的参数名不分大小写、横线下划线通用，已发布的 1.1.15、1.1.16 只认全大写加下划线；设 0 不能关掉限速，会回到默认值；降速后的 32 Mb/s 按会话计算，不是所有降速会话共用。
- 出口会话不会被 hbbr 空闲断开：被控端每秒的 TestDelay 走的就是同一条中继流，服务端笔记里那条风险只对裸管道成立。被控端的"无操作自动断开"对端口转发会话也不生效（`connection.rs:2272`）。
- "两端的窗口常量各改一处"不成立，常量只定义在一处（E2）。

## 明确不做
- UDP 出口（SOCKS5 UDP ASSOCIATE、QUIC、纯 UDP 的游戏和语音）：§3.9 定了只支持 TCP，浏览器会自动退回 TCP。
- 全局出口（编排 Tailscale/Headscale）、自研虚拟网卡 VPN、嵌入 tsnet 或 wireguard-go：§3.9、§4 定了不做或不排期。
- 改 hbbr 代码，或只给出口会话单独限速：§4 定了只调参数，而且 hbbr 配对时看不到连接类型（`relay_server.rs:461-492`），只能整台放宽。
- 在会合信令上强制拦截未授权的出口连接：连接类型是控制端自报的，转给被控端的报文不带它，ICE 还会绕过打洞请求，拦了也只是建议性的。
- 把出口权限映射进 ControlPermissions：报文没认证，下标只能在 14~31 里选、可能和上游以后的新项撞号，ICE 路径也不用它。

## 写契约前还缺的事实
- 多路复用隧道的实际吞吐（直连或 ICE、经中继，单流和多流），测不测、何时测由 E1 定。
- std 在 Windows 上怎么解析不带方括号的 IPv6 "host:port"：要写单测钉住。
- 安装版被控端的出口连接由哪个进程、哪个账户发出（服务进程是不是以 SYSTEM 身份跑在用户会话里），便携版又是怎样。这影响 DNS、TUN 是否接管、出站防火墙，以及无人登录或锁屏时能不能当出口。
- 被控端开着 mihomo TUN、路由器 fake-ip、全隧道 VPN（含 Tailscale exit node）时，绑物理网卡地址的出站 TCP 会不会绕过它们。第三期的 S3 只测了 UDP，这决定 B2 能否成立（B15 (a)(b)）。
- 被控端怎么可靠地拿到自己的公网 IPv4：B11 的 STUN 在原版服务端或 UDP 不通时拿不到，Leapgate 心跳响应也不带服务端看到的地址（服务端 `device.rs:491`）。
- 被控端局域网网段怎么拿：`lan::Nic` 没有 IPv4 前缀长度（`lan.rs:76-91`），IPv6 临时地址的前缀长度报 128（`lan.rs:130`），要确认 GetAdaptersAddresses 能否可靠给出在链网段。
- 隧道懒重建时只有临时密码的情况：A6 已按 `client.rs:4704`、`connection.rs:1905-1908` 定了复用密码的做法，但临时密码在 30 秒会话窗口之外重建是否一定失败，还要单测或冒烟确认。
- Windows 系统代理下各浏览器的实际行为：Chromium/Edge 把 `socks=` 当 SOCKS4 还是 SOCKS5；http 网址是否以 absolute-form 发给 HTTP 代理；Firefox 是否跟随系统代理、SOCKS5 时是否远程解析 DNS；主流浏览器是否支持 SOCKS5 用户名密码；改注册表后要调用哪个刷新接口。要查一手来源，影响 C4、C6、C7。
- 控制端开着 fake-ip 时，Chrome、Edge、Firefox、curl 是否把域名交给代理解析（B3、C4、C12）。
- 端口转发窗口最小化时监听和隧道还在不在、能否常驻（窗口关掉即停，F1 已按 `port_forward_page.dart:86` 的 `_ffi.close()` 定了）；被控端 CM 卡片在长时间会话下的表现，例如 `allow-hide-cm` 这类选项。
- 被控端的连接审计对端口转发会话报哪些字段，会不会带上登录占位值或目标字符串（B7、C2）。
- 现有部署的 hbbr 实际设置的限速变量名和取值（内部记录写着设过限速，但 1.1.15 只认全大写加下划线，名字写错就不生效，没核实），以及中继每月流量还剩多少。写 E3 的放宽值之前要查。
