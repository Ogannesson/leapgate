## 1. 多路复用帧格式与流控（`src/port_forward_mux.rs`）

**帧**【读码】：`libs/base/protos/message.proto:960-998`。`Message.union` 的 tag 33 是 `PortForwardChannel`（1032 行），里面是 oneof 五种：
- `open{channel_id, host, port, window}`：只能从控制端发往被控端
- `opened{channel_id, success, message, window}`：只能从被控端发往控制端
- `data{channel_id, bytes}`
- `close{channel_id}`
- `window_update{channel_id, add}`

方向发反的帧会被忽略：控制端 `on_frame` 的 643 行、被控端 `handle` 的 98 行。

**每个 `open` 帧都带目标 host/port**【读码】：构造函数是 `open_msg`（160 行）。可是控制端的 `TunnelHandle::open`（536 行）只用映射自己的 `remote_host`/`remote_port` 去调它（`src/port_forward.rs:106`、`:368`）。

**常量**（11-36 行）【读码】：

| 常量 | 值 | 含义 |
|---|---|---|
| `INITIAL_WINDOW` | 64 KiB | 收到 `opened` 前可以先发的量，协议里固定 |
| `MIN_FRAME_CHARGE` | 64 | 每个 data 帧至少按这么多扣窗口，协议里固定 |
| `CHANNEL_WINDOW` | 256 KiB | 通道窗口 |
| `MAX_FRAME` | 64 KiB | 单帧上限 |
| `MAX_PACKET` | 128 KiB | 隧道建立后整包上限，只对 TCP 流生效：`cap_packet_size`（44 行） |
| `UPDATE_THRESHOLD` | 128 KiB | 攒到这么多才回一次 `window_update` |
| `MAX_CHANNELS` | 256 | 每条隧道的通道数上限 |
| `DATA_QUEUE_FRAMES` | 128 | 控制端数据队列长度 |
| `MAX_SEND_CREDIT` | 256 KiB | 发送额度上限，对端通告多少都不超过它 |

**流控**【读码】：信用窗口。
- 接收方 `RecvWindow`（58 行）：每收一帧扣 `charge(len)=max(len,64)`，扣成负数算违约，通道立刻关掉。往本地 socket 写出去的量累计到 `UPDATE_THRESHOLD` 就发一次 `window_update`（`drained`，89 行）。
- 发送方 `SendCredit`（103 行）：读本地 socket 前先拿额度，额度不够 64 就挂起等。
- 控制端开通道时先拿 `INITIAL_WINDOW` 的额度，收到 `opened` 后用 `raise_initial` 补到对端通告的窗口（144 行）。
- 被控端在 `opened` 发出去之前就把自己的接收窗口放大到 `CHANNEL_WINDOW`（`server/port_forward_mux.rs:234`）。

**通道数**【读码】：两端都是每条隧道最多 256 个。
- 控制端：`open` 的 551 行，满了就报 "too many port forward channels"。
- 被控端：`on_open` 的 112 行，满了回 `opened(false, "Too many port forward channels")`。
- 通道号由控制端从 1 开始递增分配，会跳过还在用的号（557 行）。

**调度**【读码】：控制端 `tunnel_loop`（697 行）是独占这条流的单个任务，`select!` 三个分支：控制队列（只有 `window_update`）、读流、数据队列（`open`/`data`/`close` 同一个有序队列），用的是 tokio 默认的随机公平。被控端的帧在 `Connection` 主循环里处理（`connection.rs:4112` → `handle_port_forward_channel`，2387 行）。被控端发出去的帧走连接自己的无界 `inner.tx`（`FrameSink::Direct`），被控端最多缓存多少目标数据，只靠发送额度限制（33-36 行注释）。

## 2. 被控端 `on_open`（`src/server/port_forward_mux.rs`）

**"目标必须等于登录目标"**【读码】：`PortForwardMux::on_open`（105 行），检查依次是：
- 108 行：没有权限，回 "No permission of IP tunneling"
- 112 行：通道数满
- 116 行：通道号重复，静默忽略
- 120-125 行：用 open 里的 host/port 组一个 `PortForward`，交给 `Connection::normalize_port_forward_target` 规范化（`connection.rs:1789`）。规则：host 为空当 `localhost`；`"RDP":0` 换成 `localhost:3389`；最后得到 `format!("{}:{}", host, port)`。
- **128-137 行：`if addr != self.login_target`，记一条 warn，回 `opened(false, "Port forward target not authorized")`**

`login_target` 在 `PortForwardMux::new` 时传入，取的是 `self.port_forward_address`（`connection.rs:1814`），也就是登录分支 2975-2976 行规范化后的字符串。比较的是规范化之后的字符串，**不会解析域名**。

**解析和连接**【读码】：`run_controlled_channel`（185 行）。第 197 行是 `timeout(CONNECT_TIMEOUT_MS=3000, TcpStream::connect(&addr))`，`addr` 是 `"host:port"` 字符串。也就是说：
- 解析和连接由 tokio 的 `ToSocketAddrs` 一步做完【读码】，内部走系统解析器（getaddrinfo，放在阻塞线程池里），解析出多个地址时逐个试【推测，tokio 的行为】。
- **调用方看不到解析出来的地址，也就没法先检查再决定连不连**【读码】。要在连之前过滤，得改成先 `lookup_host`、逐个检查、再 `connect(SocketAddr)`。
- 3 秒超时把解析和连接一起算在内。
- 另外，IPv6 字面量没有方括号，`format!` 拼出来的是 `::1:80` 这种串，解析不了【推测】。

**失败回报**【读码】：
- 连接失败或超时：在有序队列里回 `opened(false, unreachable_message(addr, is_rdp))`（228 行），文案固定是 "Failed to access remote {addr}. Please make sure it is reachable/open."（248 行），具体错误只记 debug 日志（227 行）。
- 连接期间收到的数据超过 `INITIAL_WINDOW`，或者违约：回 `close`（209、217 行）。
- 控制端收到 `opened(false)`：同一条原因 10 秒内只弹一次，最多记 8 种（`first_report`，`port_forward_mux.rs:433-436`、655 行），通过 `interface.on_error` 弹出来（719 行）。

## 3. 控制端怎么发起

**ConnType**【读码】：`PORT_FORWARD=2`、`RDP=3`，定义在 `libs/hbb_common/protos/rendezvous.proto:22-29`（cardo 子模块），会合请求里会带上（37、179 行）。Flutter 会话按 `is_port_forward`/`is_rdp` 选类型（`src/flutter.rs:1313-1318`）。

**LoginRequest**【读码】：`message.proto:68-87`，`union` 里的 `PortForward port_forward = 8`，定义是 `{host=1, port=2, multiplex=3}`（50-54 行），由 `src/client.rs:3890-3893` 组装。被控端用 `PeerInfo.features.port_forward_mux` 回答它支不支持 mux（`Features`，100-104 行；被控端在 `connection.rs:2027-2030` 设置）。

**本地监听**【读码】：一个映射对应一个本地端口，一个监听，一条隧道。
- `ui_session_interface.rs:2004-2031` 对每个 `AddPortForward(port, host, port)` 起一个 `start_one_port_forward`（2079 行），它调 `port_forward::listen`（`port_forward.rs:72`）。
- `listen` 绑 `127.0.0.1:{port}`（84 行），每个监听有自己的 `Tunnel`（94 行）。
- 映射存在 `PeerConfig.port_forwards: (local_port, host, port)` 里（`add_port_forward`，`ui_session_interface.rs:618`）。
- `port<=0` 或 `remote_port<=0` 的映射直接丢掉（2012 行）。

**mux 和裸管道怎么区分**【读码】：
- 窗口级开关：`lc.port_forward_mux = mux_enabled()`（`ui_session_interface.rs:1988`；`port_forward.rs:553`，选项 `enable-port-forward-mux`，不设就是开）。
- 每次 accept 调 `tunnel.claim()`（103 行）：
  - 第一次 accept 是 `Claimed`，走 `establish_tunnel`（347 行），也就是 `connect_and_login_mux`（400 行），登录时带 `multiplex=true`。
  - 对端 `PeerInfo` 里有 mux 能力：`set_muxed`，之后每次 accept 都在同一条隧道上 `handle.open`（105-109 行）。
  - 对端没有 mux 能力：`set_legacy`，这个映射之后都走裸管道 `connect_and_login`（159 行）。裸管道登录完 `set_raw()`（258 行），每个本地连接各自登录一次。
- **隧道是懒建立的**：第一个本地连接到来才去连对端、登录，那个连接已经发出的字节先缓存，最多一个 `CHANNEL_WINDOW`（496 行），隧道建好后作为第一个通道的 `prebuf` 发出去（367 行）。隧道断了状态回到 `Unset`，下一次 accept 重新建（746 行）。

**一个会话能不能对不同目标开通道**【读码】：线格式和 `TunnelHandle::open(host, port, …)` 都支持，但 `listen` 只传映射固定的目标，被控端也会拒掉和登录目标不一样的 `open`（§2）。同一个窗口里的多个映射，各自有独立的对端连接和登录（`port_forward_login_turn` 让登录串行，`client.rs:2866`）。

## 5. 加一个"允许作为出口"的选项

- **key**【读码】：在 `libs/base/src/config/keys.rs` 加 `pub const`（参照 45 行的 `OPTION_ENABLE_TUNNEL`）。文件末尾的测试要求不能和 hbb_common 的 key 重名。`KEYS_SETTINGS`（271 行起）是允许出现在 DEFAULT/OVERWRITE（定制客户端）里的 key 列表，`enable-tunnel` 在里面（281 行）；新 key 要不要放进去由契约定。
- **默认值**【读码】：`option2bool`（`libs/hbb_common/src/config.rs:2840`）的规则：`enable-` 开头的 key 只要值不是 `"N"` 就算开（空值也算开）；`allow-` 开头的只有值是 `"Y"` 才算开；其他 key 不是 `"N"` 就算开。`is_permission_enabled_locally` 最后就是用它判断（2691 行）。所以一个默认关的开关，用 `allow-` 前缀、或者自己读值并把空值当关，就不用另设默认值；用 `enable-` 前缀的话，得在 DEFAULT_SETTINGS 或 `libs/leapgate/src/options.rs` 里写成 `N`。要注意：`leapgate-` 开头（比如 `leapgate-allow-exit`）既不是 `enable-` 也不是 `allow-` 开头，交给 `option2bool` 时走"不是 N 就算开"那一支，**空值会被当成开**。
- **设置页**【读码】：`flutter/lib/desktop/pages/desktop_setting_page.dart:1248-1250`，"Enable TCP tunneling" 这个 `_OptionCheckBox` 在 Permissions 卡片里（1210 行起）。卡片顶部的 access-mode 选成 full 或 view 时，所有勾选框都显示 `fakeValue` 并且灰掉。key 常量在 `flutter/lib/consts.dart:125`。
- **服务端能不能远程改**【读码】：
  - Leapgate 心跳：`merge_strategy` 跳过 `leapgate-` 开头的 key（`libs/leapgate/src/report/heartbeat.rs:272-292`），其他 key 照单全收。
  - 服务端不是 Leapgate 时，回落上游 `sync.rs`（`leapgate::report::tick` 返回 false，107-108 行）。上游 `handle_config_options`（`src/hbbs_http/sync.rs:296`）**对 key 不做任何过滤**，`leapgate-` 前缀的也能写进去。
  - `ControlPermissions` 是固定的枚举，没有"出口"这一项，所以会合服务器管不到新 key【读码】。前提是新 key 不走 `permission()`。

## 6. Leapgate 自有代码里可以复用的

- **地址分类**【读码】：分类函数不在 `lan.rs`，在 `libs/leapgate/src/ice/sig.rs`：`classify`（107 行，分成 PrivateV4/PublicV4/Ula/GlobalV6/Drop）、`excluded_v4`（121 行）、`excluded_v6`（133 行）、`is_ula`（143 行）、`is_global`（147 行，只判 `2000::/3`）。都是 `pub(crate)`，`ice::sig` 本身也是私有模块，所以只有 `libs/leapgate` 内部能用。`lan.rs:147` 另有一个 `excluded_ip`（IPv4），`route/probe.rs:216` 有一个 `is_public`。
- **直接拿来做出口过滤，语义对不上**【读码 + 推测】：
  - 这几个函数是给候选地址用的。`198.18/15` 和 `100.64/10` 都算 Drop。
  - 被控端开着 mihomo fake-ip 时，系统解析域名返回的是 `198.18.x`，照这个规则过滤，域名目标会全部被拒（仓库里同类的现象见契约 05 的 F1）。
  - `64:ff9b::/96`（NAT64）、IPv4 映射地址都算 Drop。
  - `2002::/16`（6to4）、`2001::/32`（Teredo）算全局地址，可能嵌着私网 IPv4。
  - "本机"还包括被控端自己的公网 IPv4 和全局 IPv6 地址，这几个函数判断不了。要和 `lan::nics()`（Windows 才有实现，其他平台返回空，340 行）比对。
- **心跳请求体**【读码】：结构体 `Req` 在 `report/heartbeat.rs:56-70`，组装在 `body()`（139-152 行），各字段来自 `Payload`（48 行）和 `payload()`（202 行）。加一个"出口能力"字段要动 `Req` 和 `body()`，值的来源可以照 `route::probes()` 的写法直接在 `body()` 里读。`report/` 不在上游文件里，不算挂钩。

## 9. SOCKS5

- **结论**【读码】：没有 SOCKS5 服务端实现。
- 现有的都是客户端：hbb_common 依赖 `tokio-socks`（rustdesk-org fork，`libs/hbb_common/Cargo.toml:37`），用在 `proxy.rs:462-473`（`Socks5Stream::connect…`），给出站代理用；`reqwest` 的 `socks` 特性（根 `Cargo.toml:92`、`libs/leapgate/Cargo.toml:12`）也是客户端。
- `hbb_common::TargetAddr`（`lib.rs:39`，即 `tokio_socks::TargetAddr`：Ip 或 Domain+port）这个类型可以拿来表示目标，握手和应答要自己写或者加 crate。
- 被控端连目标是直接 `TcpStream::connect`，不走本机配置的 SOCKS 代理【读码】。
