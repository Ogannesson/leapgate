## 1. Leapgate 心跳 `/api/leapgate/v1/heartbeat`

- 路由在 `src/api/mod.rs:83`，请求体上限 32 KB（`LEAPGATE_HEARTBEAT_BODY_LIMIT`，`:61`）；处理器是 `src/api/device.rs:527` 的 `leapgate_heartbeat`；认证用提取器 `SignedBody`（`src/api/devauth.rs:68`、`:79`）【读码】。
- 请求体 `LeapgateHeartbeatReq`（`device.rs:467`）：`uuid`、`ver`、`leapgate`（客户端 `libs/leapgate` 的版本号）、`strategy_rev`、`sysinfo_hash`、`sysinfo`（原始 JSON）、`routing_rev`、`probes`。设备 id 只认签名头，请求体里没有 id 字段【读码】。
- 各字段去向【读码】：
  - `leapgate` → 只放内存，`Peer.leapgate_hb = LeapgateHb { at, leapgate_ver }`（`src/peer.rs:105`、`:110`），不写库。ICE 判断对端支不支持就读它（`src/ice_signal.rs:219` `b_supports_ice`：180 秒内收到过、版本不低于 0.3.1、公钥已锁定）。
  - `probes` → 交给 `Router::record_probes`，同样只在内存；心跳里没带就调 `forget_probes`。
  - `sysinfo` → `store_sysinfo` 写 `device.sysinfo`，同时拆出 `hostname`、`username`、`os`、`version` 四列。
  - `uuid`、`ver`、来源 IP → `touch`（`device.rs:397`）写进 `device` 表的 `ver`、`last_seen_at`、`last_ip`，并把 `client_type` 写成 `'leapgate'`。`touch` 只在某个值变了、或距上次写 `last_seen_at` 超过 60 秒（`LAST_SEEN_STEP`）时才写库；第一次见到的设备新建一行，受表上限约束（`make_room`）。
- 响应 `LeapgateHeartbeatResp`（`device.rs:491`），用会合私钥签名后返回（`signed_json`）。字段【读码】：
  - 每次都有：`api: 1`、`features`（目前是 `["ice"]`，`:462` `LEAPGATE_FEATURES`）、`time`。
  - 按需：`need_sysinfo`；`strategy {rev, options}`，客户端报的 `strategy_rev` 和服务端不一致时才带；`routing {rev, probe_interval_secs: 300, relays}`，候选中继列表，最多 32 台，客户端报的 `routing_rev` 和服务端不一致时才带。
- "出口能力"放哪里，两种现有写法可以照抄（只陈述事实，不做选择）：
  - 只放内存：在 `LeapgateHb` 里加字段，和 ICE 支持的写法一样。服务端重启后要等下一次心跳才恢复（空闲时心跳 15 秒一次，会话中 3 秒一次，见 `device.rs` 里 `LAST_SEEN_STEP` 的注释）。出口目录本来就只列在线设备（组面板判断在线的办法是 `last_reg_time` 在 30 秒内，`src/api/group.rs:18`），内存能满足"在线且开了出口"这个条件【推测】。
  - 写库：给 `device` 表加一列，由 `touch` 照"变了才写"的规则一起比较和写入。要注意两点【读码】：`device` 行会被淘汰（上限 1 万行，`EVICTABLE`，`device.rs:180`），淘汰时只保护在 `device_policy` 表或设备级 `strategy_option` 里有行的设备；`touch` 的 `select` 和 `update` 两条语句都要跟着改。
  - "放行网段摘要"这种变长内容，没有现成的落点，`device.sysinfo` 是原文存的。
- 迁移：现有 `0001`~`0006`，下一个是 `migrations/0007_*.sql`【读码】。

## 2. 设备主人、用户组、共享簿的权限模型

- 设备主人就是 `device.user_id`（`0001_init.sql` 第 92 行，注释写的是"最近在这台设备上登录的账号"）。没有单独的绑定表。`peer.user` 列是 hbbs 原版留下的，代码里没用到（`peer.rs:95` 被注释掉）【读码】。
- `device.user_id` 在这几处被写【读码】：
  - 登录：`src/api/account.rs:359`~`375`。只要 `peer` 表里有这个 id、uuid 也对得上，就执行 `on conflict(id) do update set user_id = excluded.user_id`，也就是**后登录的人覆盖前一个主人**；公钥锁定与否不影响这一步。
  - 延迟补绑：`OWNER_FROM_TOKEN`（`device.rs:163`），只在 `user_id` 为空时由心跳或 sysinfo 补上。
  - 登出：`account.rs:431` 清空本人的绑定。
  - 删用户：外键 `on delete set null`。
- `server/LEAPGATE.md` §11 原文写着"设备主人"这个身份的加固（已锁定设备的登录不再覆盖已有主人、命令行指定主人）**放到第四期，和 Exit Node 一起做**【读码】。
- 用户组【读码】：`user_group(id, name unique, share_devices, note, created_at)`；成员表 `group_member(group_id, user_id)`，两列都是外键 `on delete cascade`。连接池开了 `foreign_keys(true)`（`src/database.rs:98`）。
- 共享簿的权限【读码】：
  - 授权表 `ab_rule(ab_guid, user_id | group_id, rule ∈ {1, 2, 3})`，`check` 约束保证用户和组二选一；两个部分唯一索引，`(ab_guid, user_id)` 和 `(ab_guid, group_id)`。簿主人不写进这张表，天然拥有完全控制。
  - 有效权限的 SQL 是 `RULE_SQL`（`src/api/ab.rs:33`）：主人得 3；否则取 `max(rule)`，条件是 `r.user_id = 我` 或 `r.group_id in (select group_id from group_member where user_id = 我)`。
  - 检查函数 `check`（`ab.rs:84`），权限不够或没有权限回 403。
- 出口授权能不能直接复用 `ab_rule`【读码 + 推测】：
  - 直接复用不了。`ab_rule.ab_guid` 是外键，指向 `ab(guid)`，授权对象只能是地址簿，不能是设备；要复用就得"把设备放进某本共享簿、给簿授权"，那样出口授权就和地址簿内容、簿权限三级的语义绑在了一起。
  - 单独建 `exit_grant(device_id, user_id | group_id)` 更省事：照抄 `ab_rule` 的二选一 `check` 约束和两个部分唯一索引；查询照抄 `RULE_SQL` 的"本人或所在组"子查询，再加上主人 `device.user_id = 我`。
  - `device_id` 用不用外键要先想清楚：`device` 行会被淘汰。`device_policy` 的做法是不引用 `device`，同时在 `EVICTABLE` 里加 `not exists` 保护；`exit_grant` 照这个做，就要在 `EVICTABLE` 的两个分支里各加一条。
  - 删组、删用户靠外键级联，和 `ab_rule` 一样。

## 3. 命令行

- 注册分三层【读码】：
  1. `src/main.rs:10` 的 `CLI_COMMANDS` 白名单，决定这次启动是命令行还是服务；
  2. `src/cli/mod.rs:150` 的 `exec` 按顶层命令分给 `manage::exec`（user/group/ab）或 `ops::exec`（device/strategy/stats）；
  3. 各自内部再按 `(cmd, sub)` 用 `match` 分发。
- 新命令都要同步改【读码】：
  - `USAGE`（`cli/mod.rs:33`）；
  - `changes_database`（`:117`）：只读的子命令要列成 `false`，不然输出末尾会多一行数据库路径；目前 `device` 下只有 `list` 和不带 `reset` 的 `key` 算只读；
  - 带值的选项登记进 `VALUE_FLAGS`（`:180`），开关选项登记进 `BOOL_FLAGS`。
- 授权类命令的模板是 `ab grant/revoke`（`src/cli/manage.rs:269`）【读码】：
  - `Target::take`（`:332`）取 `--user` 或 `--group`，必须且只能给一个；
  - 写库用 `insert … on conflict(…) where … is not null do update`；
  - revoke 时按 `rows_affected` 区分"本来就没有"和"已撤销"两种输出。
- 设备类命令的模板是 `device pin-relay`（`src/cli/ops.rs:39`）：直接 upsert `device_policy`；服务端每次连接都按主键查库、不缓存，所以写完立即生效，不用通知运行中的服务【读码】。
- `device key reset`（`ops.rs:61`、`:242` `key_reset`）不一样：它改的是内存里缓存着的 `peer`，所以写完库还要经控制台 `kl <id>` 让服务端重新载入【读码】。
- 出口授权如果每次都查库，照 `pin-relay` 的写法就够了，不用控制台【推测】。

## 4. API 认证

- 用户令牌：提取器 `CurrentUser`（`src/api/mod.rs:261`、`:270`）【读码】。
  - 取 `Authorization: Bearer`，按 sha256 查 `token` 联 `user`，要求 `status = 1`；不通过回 401；每次使用都会更新 `token.last_used_at`。
  - 用在：`/api/currentUser`、`/api/logout`、组面板三个接口（`/api/users`、`/api/peers`、`/api/device-group/accessible`）、全部 `/api/ab/*`。
- 设备签名：提取器 `SignedBody`，用在且只用在 `/api/leapgate/v1/` 下的四个接口：`heartbeat`、`audit/conn`、`audit/file`、`audit/alarm`【读码】。
- 不认证的：`/api/heartbeat`、`/api/sysinfo`、`/api/audit/*`（兼容原版的上报接口，只校验 uuid）；`/api/login`、`/api/login-options` 也不需要认证【读码】。
- "列出我能用的出口"照抄的模板：`group::peers`（`src/api/group.rs:93`）【读码】。
  - 它是 `GET`，参数是 `CurrentUser` 加分页；可见范围拼成一段 SQL 条件（`visible`，`:37`）；在线状态逐个查内存（`pm.get_in_memory`，看 `last_reg_time`）。
- 路径前缀的副作用【读码】：
  - `/api/leapgate/v1/` 前缀会让 `is_leapgate`（`mod.rs:404`）把内部错误回成 503，而不是 400 或 200；`is_report`（`:410`）也会把它算成上报接口，超时改用 `REPORT_TIMEOUT`。
  - 所以，用用户令牌认证的新接口如果放在这个前缀下，错误语义和超时都会跟着设备上报走。
  - 这个前缀下目前没有任何一个接口用用户令牌。

## 5. 会合模块：服务端在连接时能看到什么

- `PunchHoleRequest`（`libs/hbb_common/protos/rendezvous.proto:33`）里有 `conn_type`（`ConnType` 枚举里 `PORT_FORWARD = 2`、`RDP = 3`），还有 `token`。`token` 是控制端的 API 登录令牌，客户端从 `LocalConfig` 的 `access_token` 读出来传下去（客户端 `src/ui_session_interface.rs:1984`）【读码】。
- 服务端怎么用这两个字段【读码】：
  - `handle_punch_hole_request`（`src/rendezvous_server.rs:1338`）把 `conn_type`、`token` 记进结果记录。`conn_attempt.a_user` 是写库时由后台用 `auth::token_owner` 反查出来的，不在请求的热路径上。
  - `RouteQuery` 里也有 `a_token` 和 `conn_type`（`src/router/mod.rs:51`），但路由模块没有读它们。
  - 转给 B 的 `PunchHole`（`:1498`）不带 `conn_type`，也不带控制端身份。
- `RequestRelay`（`rendezvous_server.rs:898`~`942`）带着 `conn_type` 和 `token` 原样转给 B；`token` 截到 64 字节，真实令牌 43 字节，会被完整转发【读码】。
  - 上游 hbbs 也是这样做的（`rustdesk-server@873230e:src/rendezvous_server.rs:541`）。
  - 被控端的 `rendezvous_mediator.rs` 不读这个字段（客户端 `a57605c2f` 里 grep 不到对 `rr.token` 的使用）。
- ICE 信令 `LeapgateIceOffer`（`rendezvous.proto:306`）只有 `session`、`id`、`licence_key`、`params`、`proofs`，没有 `conn_type`，也没有令牌【读码】。
- 能不能在服务端拦，以下都是【读码】：
  - 要拦的话，`handle_punch_hole_request` 是现成的拦截点：这里能拿到 `conn_type` 和令牌，拒绝时回 `PunchHoleResponse.failure`。
  - 但这只是建议性的拦截，挡不住以下几条路：
    - `conn_type` 是控制端自己填的；
    - ICE 路径不经过打洞请求；
    - hbbr 配对只认 uuid，不问会合服务器（见第 6 节）；
    - 客户端直接按 IP 连，根本不经过服务端。
  - 被控端能知道的控制端身份：`LoginRequest`（客户端 `libs/base/protos/message.proto:68`）里只有 `my_id`、`my_name` 这类控制端自报的字段，没有服务端证明过的账号。
- 另一条现成通道【读码】：`PunchHole`、`RequestRelay` 里有上游的 `ControlPermissions`（`rendezvous.proto:54`，带 `tunnel = 7` 位）。客户端 `src/server/connection.rs:2700` 起会用它覆盖本地权限开关。这个字段 leapgate-server 从来不填，消息也没有签名。

## 6. hbbr 限速（上游 `rustdesk-server@873230e:src/relay_server.rs`）

- 读取方式【读码】：
  - 五个参数都经 `get_arg` 读，来源是环境变量或工作目录下的 `.env`。名字不分大小写，`-` 和 `_` 通用（`common.rs:153` `get_arg_opt`）。
  - hbbr 的命令行只有 `-b`、`-p`、`-k`（`src/hbbr.rs`）。
  - 只接受大于 0 的值（`check_params`，`:108`~`159`），设成 0 不能关掉限速。
  - 单位里的 "Mb" = 1024 × 1024 bit。
- 参数一览【读码】：

| 参数 | 默认值 | 语义 |
|---|---|---|
| `SINGLE_BANDWIDTH` | 128 Mb/s（`:44`） | 每对中继连接一个限速器（`relay`，`:516`），**两个方向合计** |
| `TOTAL_BANDWIDTH` | 1024 Mb/s（`:43`） | 整个进程共用一个限速器（`io_loop`，`:343`），所有会话、两个方向合计 |
| `LIMIT_SPEED` | 32 Mb/s（`:42`） | 被降速的会话、以及来源 IP 在黑名单里的会话改用这个限速 |
| `DOWNGRADE_THRESHOLD` | 0.66（`:40`） | 降速阈值 = 0.66 × 单连接上限，按 128 算约 84.5 Mb/s |
| `DOWNGRADE_START_CHECK` | 1800 秒（`:41`） | 会话超过这个时长后开始检查是否降速 |

- 降速的判据（`:587`~`597`）【读码】：会话累计流量 `total`（会话开始以来、两个方向合计）> 已过时长 × 阈值，也就是**整个会话的平均速率**超过约 84.5 Mb/s。从第 30 分钟起每秒检查一次，一旦降速，这个会话到结束都不恢复。
- 计时【读码】：
  - 空闲断开：两个方向都超过 30 秒没收到数据就 `bail!("Timeout")`（`:564`）。定时器 3 秒一跳，实际在 30~33 秒之间断开。
  - 首帧等待：连上后 30 秒内要收到第一帧（`:463`）。
  - 配对等待：先到的一方最多等对方 30 秒（`:491`）。
- 运行时调整【读码】：从本机回环地址用 TCP 连主端口（不能走 WebSocket），发控制台命令 `sb`、`tb`、`ls`、`dt`、`t`（`check_cmd`，`:162`），另有 `ba`/`br` 加删黑名单、`Ba`/`Br` 加删封禁名单、`u` 看用量。生效时机：
  - `tb` 立即生效（`set_speed_limit`）；
  - `sb`、`ls`、`dt` 在 `relay()` 开头读取，只影响新建的会话；
  - `t` 每秒读一次，现有会话也生效。
- hbbr 看不到 `conn_type`，也看不到设备或用户：配对只认 `RequestRelay.uuid` 和 key（`make_pair_`，`:461`）。所以"只给出口会话放宽限速"在现有 hbbr 里做不到，只能整台放宽【读码】。
- leapgate 树里的 hbbr 和上游比【读码】：
  - `src/hbbr.rs` 完全一致。
  - `src/relay_server.rs` 自 `873230e` 以来只有一次提交改动（`735d58b`，适配新版 hbb_common），diff 只有 WebSocket `send_raw` 那一行（`Binary(bytes.to_vec())` 改成 `Binary(bytes)`）。
  - 限速逻辑和上面的数字与上游逐字相同；`LEAPGATE.md` §1 也写明了 hbbr 不改逻辑。
- 架构 §3.9 写的"连续跑满 30 分钟"不准确：实际判据是整个会话的平均速率，会话开头的空闲时间也算进分母【读码】。

## 7. 连接记录与"出口会话走中继的比例"

- `conn_attempt.conn_type`（`0001`，取自 `PunchHoleRequest.conn_type`）已经有了，写库在 `src/conn_tracker.rs:821`：`req.map_or(0, |r| r.conn_type)`【读码】。
- 两个缺口，都是【读码】：
  - 没匹配到打洞记录、单独记成一行 `relay_only` 的回落请求，`conn_type` 填 0。原因是 `RelayRequest` 结构（`conn_tracker.rs:182`）没带这个字段，尽管 `RequestRelay` 消息本身带着 `conn_type`（`rendezvous_server.rs:935` 转发时也用到了）。
  - `ice_result` 表（`0006`）没有 `conn_type`，ICE 信令里也没有这个字段。
- 统计函数是 `ConnTracker::stats`（`conn_tracker.rs:1035`），由命令行 `stats --days` 调用。它按 `outcome` 分组，不分 `conn_type`【读码】。
- 最小改动【推测】：
  1. `stats` 里加一个按 `conn_type = 2` 过滤的版本（或加命令行参数）；
  2. `RelayRequest` 补上 `conn_type`，让 `relay_only` 那一行也能记下来。
- ICE 胜出时，同一次连接在 `conn_attempt` 里仍按上游信令照常记一行（`LEAPGATE.md` §8），带着 `conn_type`。所以只看 `conn_attempt` 按 `conn_type` 统计的中继比例会偏高；`ice_result` 那边没法按出口过滤，除非 OFFER 或 RESULT 里加字段【读码 + 推测】。
