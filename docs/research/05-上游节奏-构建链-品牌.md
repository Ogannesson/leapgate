### 3.2 其他平台差异【读码】
- **Linux**：在 `rustdesk-org/run-on-arch-action` 里用 **ubuntu18.04** 容器编（为了 glibc 兼容），apt 装 clang、cmake、nasm、libgtk-3-dev、libpulse-dev、libva-dev、libxdo-dev、gstreamer 开发包等，再走 vcpkg（Linux triplet）。产物是 deb、rpm、AppImage、Flatpak；另有 `build-rustdesk-linux-drm` 变体（`--drm` 特性，独立包名）。
- **Android**：NDK **r28c**、`cargo-ndk 3.1.2`、`flutter/build_android_deps.sh` 用 vcpkg 编 Android triplet，`flutter/ndk_arm64.sh` 等脚本出 so，签名用 secret `ANDROID_SIGNING_KEY`；另有 F-Droid 构建脚本 `flutter/build_fdroid.sh`。
- **macOS**：Rust **1.81**（`MAC_RUST_VERSION`，cidre 要求），runner `macos-15-intel` 和 `macos-14`（arm），可选 `screencapturekit` 特性；签名、公证用 `rcodesign 0.22.0` + secret `MACOS_P12_BASE64`，产物 dmg。
- **Windows arm64**：`windows-11-arm` runner、Flutter 3.44.9、运行时打源码补丁 `.github/patches/apply_flutter_3.44_source_patches.sh`，不开 `vram`。

### 3.3 CI 缓存手段【读码】
- vcpkg 二进制缓存：`VCPKG_BINARY_SOURCES: "clear;x-gha,readwrite"`，即 GitHub Actions cache 后端，配合 `lukka/run-vcpkg@v11`。**这个后端只在 GitHub Actions 里能用**；换到 Forgejo Actions 或本机要改成 vcpkg 的 `files,<目录>,readwrite`（本地/共享目录）或 NuGet 源【推测：vcpkg 文档里的通用能力，未在本仓库里出现】。
- Rust 编译缓存：`Swatinem/rust-cache@v2`。
- 桥接代码只生成一次，作为 artifact 传给各平台（`bridge.yml` → `actions/download-artifact`）。
- 没有自建的预编译依赖包；ffmpeg 等全靠 vcpkg 现编 + 缓存。

### 3.4 干净 Windows 机器上搭起来的复杂度【推测，依据上面读到的配置】
要装：VS 2022 Build Tools（C++ 工作负载 + Windows SDK）、Rust 1.75（rustup 钉版本）、LLVM 15.0.6、Python 3、Git、vcpkg（钉 `9e593bb1`）并 `vcpkg install --triplet x64-windows-static`、Flutter 3.24.5 并打 dropdown 补丁、替换成 `rustdesk/engine` 的自制 x64 引擎、`cargo install flutter_rust_bridge_codegen 1.80.1` 和 `cargo-expand 1.0.95` 生成桥接代码（CI 是在 Linux 上生成的，Windows 本地生成没验证过）、出 MSI 还要 .NET/NuGet + WiX v4。
- 首次 vcpkg 编 ffmpeg/aom/libvpx 这一步最慢，可能要 1 小时级别；Rust 全量 release 编（`lto = true`、`codegen-units = 1`，见 `Cargo.toml [profile.release]`）几十分钟级别（CI 日志里提到 Rust 编译约 25 分钟）。
- 坑主要在版本钉死（Rust 1.75 太旧，很多新 crate 已经要求更高的 MSRV；Flutter 3.24.5 + 自制引擎 + 源码补丁）。整体判断：熟手 1 天能搭起来出 exe，MSI 和签名另算半天；建议把这套环境固化成 Windows 构建虚拟机或 CI runner 镜像，而不是每次手搭。
- 上游自己正在升 Flutter（注释写明 Win7 支持恢复后全平台统一升到 3.44），Porta 如果重写 UI，最好直接从新 Flutter 起步，不要继承 3.24.5 + 自制引擎这一套【推测】。

## 4. rustdesk-server 构建【读码】
- 就是普通 Cargo 项目：`Cargo.toml` `[package] name = "hbbs"`，三个 bin（`hbbs`、`hbbr`、`rustdesk-utils`），依赖 `hbb_common`（子模块）、axum 0.5、sqlx 0.6（sqlite）、sodiumoxide、tokio-tungstenite 0.17 等，`build.rs` 很简单。直接 `cargo build --release` 即可，没有 vcpkg/Flutter。
- CI（`.github/workflows/build.yaml`）：Linux 用 `actions-rs` 的 stable 工具链 + `cross` 编 4 个 musl 目标（x86_64、aarch64、armv7、i686），Windows 用 `windows-2022` 编 x86_64-pc-windows-msvc；另出 Debian 包（`debian/`，crossbuild-essential）。
- Docker 镜像不在 Dockerfile 里编译，而是把 CI 编好的 musl 静态二进制 COPY 进去：
  - `docker-classic/Dockerfile`：`FROM scratch` + `COPY hbbs hbbr`。
  - `docker/Dockerfile`：`busybox:stable` + s6-overlay 3.2.0.0，同时跑 hbbs/hbbr，带 healthcheck，暴露 21115~21119。
  - `docker/build-push-action@v5` 多架构推送。
- 仓库里还有一个 `ui/`（Tauri 的服务端托盘 UI，Windows 用），和 Porta 关系不大。

## 5. 品牌改动面

### 5.1 核心常量【读码】
- `rustdesk@bd92623:libs/hbb_common/src/config.rs`
  - `APP_NAME: RwLock<String> = "RustDesk"`（第 72 行）——**运行时可改**，绝大多数名字从它派生。
  - `ORG: RwLock<String> = "com.carriez"`（第 57 行）——macOS/Linux 配置目录（`directories_next::ProjectDirs::from("", &org, &APP_NAME)`，第 795 行）。
  - `RENDEZVOUS_SERVERS = ["rs-ny.rustdesk.com"]`、`RS_PUB_KEY`（第 117~118 行）——默认公共服务器和公钥，Porta 要换成自己的。
  - `PROD_RENDEZVOUS_SERVER`、`APP_DIR`、`DEFAULT_SETTINGS` / `OVERWRITE_SETTINGS` / `HARD_SETTINGS` / `BUILTIN_SETTINGS`。
  - 派生路径：`Config::path`、`log_path`、`ipc_path`（`/tmp/{APP_NAME}`、`Library/Logs/{APP_NAME}`）、地址簿缓存文件 `{APP_NAME}_ab`、`{APP_NAME}_group`。
- `rustdesk@bd92623:src/common.rs`
  - `get_app_name()`（第 1179 行）读 `APP_NAME`。
  - `is_rustdesk()`：`APP_NAME == "RustDesk"`。
  - `get_uri_prefix()`：`format!("{}://", app_name.to_lowercase())` → 改名后 URL scheme 自动变成 `porta://`。
  - `is_custom_client()`（第 2662 行）：`get_app_name() != "RustDesk"`。
  - `is_public()` / 默认 API `https://admin.rustdesk.com`（第 1264、1277 行）——指向官方服务，需要换。
- Windows `rustdesk@bd92623:src/platform/windows.rs`：服务名（`service_dispatcher::start(crate::get_app_name(), ...)`，第 552 行）、卸载注册表项 `get_subkey()`（`HKLM\...\Uninstall\{app_name}`，第 1336 行）、默认安装路径 `get_default_install_path()`（`Program Files\{app_name}`，第 1432 行）、主程序 `{app_name}.exe`、URL 协议注册（`HKCR\{ext}`，第 1604~1619 行）——**全部从 `get_app_name()` 派生**。

结论【读码】：Rust 侧改一行 `APP_NAME` 默认值（加 `ORG`），服务名、注册表、安装路径、配置目录、URL scheme、翻译里的名字就都跟着变了。

### 5.3 写死、要手改的地方【读码】
- Windows Flutter 外壳：`flutter/windows/CMakeLists.txt` `BINARY_NAME "rustdesk"`、`librustdesk.dll` 路径；`flutter/windows/runner/Runner.rc` 的 FileDescription / ProductName / OriginalFilename；`flutter/windows/runner/main.cpp` 里 `LoadLibraryA("librustdesk.dll")`，导出符号 `rustdesk_core_main_args`、`get_rustdesk_app_name`，默认 `L"RustDesk"`；图标 `flutter/windows/runner/resources/app_icon.ico`。
- Rust crate：`Cargo.toml` `[lib] name = "librustdesk"`、`[package.metadata.bundle] name = "RustDesk"`、`identifier = "com.carriez.rustdesk"`。

### 5.5 上游的"自定义客户端"机制，开源版能不能用【读码】
- 机制：`src/common.rs` `load_custom_client()` 读 exe 旁边的 `custom.txt`（macOS 在 `../Resources`），交给 `read_custom_client()`：base64 解码 → 用写死的公钥 `KEY = "5Qbwsde3unUcJBtrx9ZkvUmwFNoExHzpryHuPUdqlWM="` 做 `sign::verify` → 解析 JSON，`app-name` 写进 `APP_NAME`，`default-settings`/`override-settings` 写进对应设置表，其他键进 `HARD_SETTINGS`。
- 这个 `custom.txt` 必须用 RustDesk 官方私钥签名，也就是 Server Pro 的"定制客户端生成器"产出的东西。**开源用户拿不到私钥，不能直接用这个机制**。
- 但 Porta 自己有源码，有两种更简单的做法：① 直接改 `APP_NAME` 默认值和 `ORG`，内置服务器地址、公钥写进 `DEFAULT_SETTINGS`/`RENDEZVOUS_SERVERS`/`RS_PUB_KEY`；② 把 `KEY` 换成自己的公钥，沿用 `custom.txt` 流程（适合"一份二进制、多套配置"，Porta 用不上）。推荐 ①。
- 副作用要知道【读码】：只要 `APP_NAME != "RustDesk"`，`is_custom_client()` 就为真，会改变 22 处 Dart、19 处 Rust 的行为：默认选项（`flutter/lib/common.dart` 第 3987~3993 行：语言、主题、访问模式默认 `custom`、审批模式默认 `password-click` 等）、隐藏部分官方入口、MSI 更新路径（`src/updater.rs`、`src/platform/windows.rs` 第 1554、3807 行）、`verified_update.rs` 的签名更新流程。这些是给 Pro 定制客户端设计的，Porta 改名后会自动进入这条分支，要逐条确认是不是想要的。另外上游自动更新（`src/updater.rs`、`api.rustdesk.com/version/latest`）必须关掉或者换成自己的更新源。

## 6. 结论：跟随合并 vs 硬分叉

### 6.1 两种做法的持续成本【推测，依据第 1、2 节的统计】
- **跟随上游定期合并（整个仓库）**：上游一年约 780 个提交、每 1~2 个月一个版本，Porta 要改的 `rendezvous_mediator.rs`、`client.rs`、`server/connection.rs`、hbb_common `config.rs` 正是上游最热的区域；还要应付像 `libs/base` 这样一年一两次的 crate 大搬家。UI 重写之后，`flutter/lib`（7.5 个月改了 138 个文件中的 92 个）的合并会全部冲突，没有意义。估计每个上游小版本要花 1~3 人日解冲突、再验证一遍，一年 6~8 次，加上大重构时的额外成本。对一个个人项目，这个负担偏重。
- **硬分叉**：一次性成本最低，之后不再付合并成本；代价是上游的安全修复、新平台支持（Wayland/DRM、macOS 新系统、Windows arm64）、编解码改进都要自己追。远程桌面是暴露在网络上的高权限软件，上游 2026 年仍有不少安全加固（下载路径校验 #16601、websocket 帧分配加固、`ipc/auth.rs`、`windows/acl.rs`），完全不追不可接受，只能手动 cherry-pick。

### 6.2 折中做法：引擎跟随，UI 和服务端独立（可行）
合并边界建议这样划【推测，依据 2.3 的稳定性数据】：

1. **原样跟随（尽量零改动）**：`libs/scrap`、`libs/enigo`、`libs/clipboard`、`libs/virtual_display`、`libs/portable`、`libs/remote_printer`、`libs/base`，以及 `src/server/` 里的抓屏、输入、音频服务。这些改动少、上游修复价值高。
2. **薄补丁层（会冲突，但范围可控）**：`libs/hbb_common/src/config.rs`（APP_NAME、ORG、默认服务器、公钥）、`src/common.rs`（is_custom_client 分支、官方 URL）、`src/rendezvous_mediator.rs` / `src/client.rs`（智能路由入口）。原则：在这些文件里只加"钩子"（调用 Porta 自己模块的一行或几行），真正的逻辑放进新文件或新 crate（例如 `libs/porta_*`、`src/porta/`），让每次合并的冲突只落在几十行上。上游 `AGENTS.md` 自己也提倡"最小侵入"，补丁风格能对上。
3. **完全独立**：Flutter UI（直接从新版 Flutter 重写，只依赖 `src/flutter_ffi.rs` 这一层 FFI，Porta 新增的接口放进单独的 ffi 文件）、服务端（上游一年约 40 个提交，基本不动，独立维护成本很低；只需要和客户端保持 `rendezvous.proto` 兼容）、API 服务、构建/打包/签名流水线（上游的签名服务、更新签名、`x-gha` 缓存都用不了，本来就要自己做）。
4. **节奏**：只在上游正式 tag（不是 main）时合并引擎部分，每次只看 `libs/`、`src/`（不含 `src/ui`、`src/lang`）的 diff；不需要的功能（例如 DRM 登录界面抓屏、Sciter 旧 UI `src/ui/`）可以干脆删掉，减少冲突面。

风险【推测】：`src/flutter_ffi.rs` 是两层之间的胶水，上游 UI 有新功能时它也会改（6 个月 22 个提交），Porta 的新 UI 要么跟着补，要么固定在自己用到的子集上。

## 7. 需要拍板的方向性问题
1. 合并策略：按 6.2 的"引擎跟随 tag、UI/服务端独立"走，还是直接硬分叉、只 cherry-pick 安全修复？这决定代码组织方式（补丁层 + 新 crate，还是随意改）。
2. 平台范围：只做 Windows + Linux，还是 Android/macOS 也要？macOS 公证、Android 签名、Windows 代码签名证书都要另花钱、另搭环境。
3. Windows 代码签名：要不要买证书（不签的话 SmartScreen 会拦，虚拟显示/打印机驱动也装不上）。如果不签，是否放弃虚拟显示驱动、打印机驱动这些需要驱动签名的功能。
4. 新 UI 是继续 Flutter（能直接复用 flutter_rust_bridge 这一层），还是换技术栈？换栈的话 `flutter_ffi.rs` 这层边界要重新定义。
5. 构建环境：自建 Forgejo Actions Windows runner，还是继续借用 GitHub Actions（上游流水线大部分能复用，`x-gha` 缓存可直接用）？
