# 上报与认证：新上报路径、设备签名、公钥锁定

> 标注：【读码】读过现版源码；【推测】推断，没有实测。代码锚点对照 porta-client `6bb19b190`、porta-server `d8403ad`。笔记 02、03 指 `docs/research/第三期/02-设备签名.md`、`03-上报改走libs-porta.md`，读码过程不复述，只引用节号。

## 1. 目标与范围

**做什么**：Porta 客户端的心跳、sysinfo、被控端审计改走 `/api/porta/v1/`，每个请求用设备私钥签名；服务端验签、防重放，第一次验签通过后锁定这台设备的公钥；服务端用会合私钥给响应签名，客户端配了 Key 就验签；Porta 路径只认严格校验的 TLS。原版客户端照走第一期的兼容接口。

**对应已定决策**（AGENTS.md 第三期设计）：第 1 条（上报走新路径）、第 2 条（设备签名、首次锁定）、第 4 条（响应签名、严格 TLS）。第 3 条 `porta_from_id` 归 02 块。本块另外提供两样别的块要用的东西：客户端的能力缓存（§4.4），服务端内存里"最近一次验签心跳"的记录（§3.6）。

**实施顺序**：第 1 批（见 README.md）。本块不改 proto，不依赖第 0 步的 proto 提交；02、04 块依赖本块的心跳 handler 和能力缓存。迁移 0004 归本块，先于 02 块的 0005。

**术语**：
- **兼容路径**：第一期的 `/api/heartbeat`、`/api/sysinfo`、`/api/audit/*`，不认证。
- **Porta 路径**：`/api/porta/v1/*`，必须带设备签名。
- **锁定（pin）**：服务端在 `peer` 行上记下"这个 ID 只认这把公钥"，之后换公钥的注册一律被拒。
- **能力缓存**：客户端记住"这个 API 地址是 porta-server，支持哪些特性"。

## 2. 协议与接口

### 2.1 请求签名头

```
Porta-Device-Auth: v1 id=<base64url(设备ID)>, t=<unix 秒>, s=<base64url(签名 64 字节)>
```

- base64url 一律不带填充（RFC 4648 §5），服务端严格解码；字段顺序固定 `id`、`t`、`s`，用 `, ` 分隔，不接受别的写法。
- 被签内容（字节直接拼接）：
  ```
  "porta-device-v1\0" ‖ 方法 ‖ "\0" ‖ 接口名 ‖ "\0" ‖ 设备ID ‖ "\0" ‖ 时间戳(十进制 ASCII) ‖ "\0" ‖ sha256(请求体原始字节)
  ```
  方法大写（`POST`）；接口名是 `/api/porta/v1/` 之后的部分（`heartbeat`、`audit/conn`）；sha256 取原始 32 字节。算法 Ed25519 detached（libsodium `crypto_sign_detached`），私钥 `Config::get_key_pair().0`。
- 请求体不带 `id`，身份只从这个头来。审计体是上游组好的 JSON，客户端发送前删掉 `id` 键；服务端忽略体里的 `id`。`uuid` 照样放在体里，只用于延迟补绑（`server/PORTA.md` §11），不参与认证。

### 2.2 响应签名头

```
Porta-Server-Sig: <base64url(签名 64 字节)>
```

- 被签内容：`"porta-server-v1\0" ‖ 请求的签名(64 字节) ‖ sha256(响应体原始字节)`。
- 用会合私钥签（`get_server_sk` 的结果，和签 `IdPk`、做 KeyExchange 的是同一把）。
- Porta 路径上 2xx 和 401（`bad_auth` 除外）签名；`bad_auth` 的 401 和 400、404、405、413、429、503 一样不签名，客户端也不读它们的内容。`bad_auth` 是请求头解析不出签名，没有可绑定的请求签名，签了客户端也验不过。客户端不接受空的请求签名段：要是为 `bad_auth` 补一种"请求签名段为空"的验法，截下的旧 `bad_auth` 401 就能被重放，用来拨歪时钟偏移。
- 服务端没有私钥（`-k` 传的是公钥）时不带这个头。这种部署本来就连不上登录过的客户端（`server/PORTA.md` §6 第 1 条）。

**客户端验签规则**：
- 服务器公钥：本地 `key` 选项非空就用它，否则用构建时注入的 `RS_PUB_KEY`。和上游 `get_key(true)` 一致，只差 Windows 按 exe 文件名取授权那一支（§9）。
- 取到了公钥（"配了 Key"）：2xx 和 401 缺这个头或验签失败，都按请求失败处理，不应用下发，不采信 `time`。
- 两者都为空：不验签；这时心跳里的 `routing` 不采用、不测速（02 块 `on_heartbeat_ok` 自己判断）。
- `key` 非空但解码不出 32 字节：按配了 Key 处理，所有响应都验不过（fail closed），日志限频一行。

### 2.3 心跳 `POST /api/porta/v1/heartbeat`

请求（JSON 对象，键不出现表示没有）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `uuid` | string | `encode64(get_uuid())`；服务端上限 128 字节，超过回 400 |
| `ver` | int | `get_version_number(VERSION)` |
| `porta` | string | `libs/porta` 的 `CARGO_PKG_VERSION`；服务端换算成 `porta_ver`（§3.6），不落库。**版本号规则**：`libs/porta` 的版本号也是 Porta 的版本号，第三期从 `0.3.0` 起；合入改变客户端协议行为的提交时就前移它，不等发布。本块客户端合入时从 0.1.0 改为 0.3.0（§4.1），04 块客户端合入时前移到 0.3.1，04 块的 `MIN_PORTA_VER` 就取 0.3.1。第三期只前移这两次：02、03 块的客户端改动服务端不按版本区分，合入时不动版本号 |
| `conns` | int 数组 | `Connection::alive_conns()`，没有连接时不带；服务端第三期忽略 |
| `strategy_rev` | int | LocalConfig `strategy_timestamp`，和兼容接口的 `modified_at` 共用 |
| `routing_rev` | int | 02 块：`porta::route::routing_rev()` |
| `sysinfo_hash` | string | 标准 base64（带填充）的 sha256，算在 `sysinfo` 对象单独序列化后的字节上（§3.6） |
| `sysinfo` | object | 只在需要时带（§4.5）；字段同上游 sysinfo，去掉 `id`、`uuid` |
| `probes` | object | 02 块：`porta::route::probes()`，`None` 时不带 |

响应（200）：

```json
{"api": 1, "features": [], "time": 1761200000, "need_sysinfo": true,
 "strategy": {"rev": 812345678901, "options": {"relay-server": ""}}, "routing": {...}}
```

- `api` 固定 1；`features` 是常量字符串数组，本块为空，04 块落地后加 `"udp-punch"`；`time` 是服务器 unix 秒。三者每次都有。
- `need_sysinfo`：只在需要 sysinfo 时出现，值为 `true`。
- `strategy`：只在 `strategy_rev != rev` 时出现；`options` 是全部生效选项，值一律字符串，空串表示删键（`server/PORTA.md` §10）。服务端策略永远不下发 `porta-` 开头的键，两头各守一处：服务端 `strategy set` 拒收 `porta-` 开头的键（`src/cli/`，报错退出）；客户端合并 `strategy.options` 时跳过 `porta-` 开头的键（§4.5 第 6 步）。
- `routing`：02 块决定出不出现、内容是什么。

### 2.5 能力探测

客户端对每个 API 根地址维持三种状态：未知、支持、不支持。

| 状态 | 回应 | 结果 | 这一轮 |
|---|---|---|---|
| 未知 | 2xx、JSON 对象带 `api`，配了 Key 时验签通过 | 支持，写持久缓存（§4.4） | 走 Porta |
| 未知 | 404 / 405，或不带 `api` 的 2xx（反代对未知路径回 200 页面的部署） | 不支持，10 分钟后重探（只记在进程内） | 退回上游 |
| 未知 | 其他：连不上、超时、TLS 错误、401、429、5xx、验签失败的 2xx | 不变 | 跳过，不退回上游 |
| 支持 | 任何失败 | 不变（404 也不退回） | Porta 自己退避重试 |

- 构建时决定的默认 API 地址一开始就是"支持"，不探测：注入了 `PORTA_API_SERVER` 时是它；只注入了会合服务器时是 `brand::default_api_server()` 推出的地址（同样在构建时决定）。代价：构建指向原版 hbbs 时 Porta 永远不退回上游上报，这不是支持的配置。
- 只有 404/405 和"不带 `api` 的 2xx"才退回上游，理由是笔记 02 的防降级：上游路径不签名、可能接受无效证书，还会照单应用心跳下发的选项。不带 `api` 的 2xx 和 404 一样容易伪造，按 404 处理不扩大攻击面，兼容性更好。路径上的攻击者能伪造这两种回应，所以手动填写的地址第一次接触仍是"首次使用即信任"（§9）。
- 换了 API 地址才重新探测。

### 2.6 错误码（Porta 路径不受 `server/PORTA.md` §9.1 第 1 条"不回 5xx"约束）

错误体统一为 `{"error": "<码>", "message": "<人看的说明>"}`，401（`bad_auth` 除外）另带 `"time"`。

| 状态 | `error` | 何时 | 客户端 |
|---|---|---|---|
| 400 | `bad_request` | JSON 解析失败、`uuid` 超长、字段类型不对 | 心跳按退避等下一轮，审计放弃 |
| 401 | `bad_auth` / `stale_time` / `replay` / `unknown_device` / `bad_signature` | §3.2 验签链任一步失败 | 带验过签的 `time` 时更新时钟偏移，重签后立即重试一次（每个请求最多一次）；还失败就按失败处理 |
| 413 | `too_large` | 请求体超过路由上限，或 `sysinfo` 超过 8 KB | 同 400 |
| 429 | `too_many_requests` | 超出来源限速（和兼容路径共用额度） | 心跳退避，审计按 10/30 秒重试 |
| 503 | `internal` | 查库或写库失败、整请求超时、handler panic | 同 429 |

**proto**：本块不改。**迁移**：0004（§3.8）。

### 3.2 验签：`src/api/devauth.rs`

**提取器 `SignedBody`**：实现 `FromRequest<AppState>`，放在 handler 最后一个参数。

```rust
pub(crate) struct SignedBody { pub id: String, pub sig: [u8; 64], pub body: Bytes, pub ip: IpAddr, pub peer: LockPeer }
```

按顺序检查，任何一步失败直接返回拒绝响应：

1. **头格式**：按 §2.1 解析。ID 解码后是 1~253 字节（`MAX_PEER_ID_LEN`）的 UTF-8，签名正好 64 字节，`t` 是十进制 i64。不符 → 401 `bad_auth`。
2. **来源限速**：`ClientIp` 取来源，调 `device::report_allowed(ip)`，和兼容路径共用额度。超出 → 429。
3. **读请求体**：`Bytes::from_request`，路由上的 `DefaultBodyLimit` 照样生效，超限 413。
4. **时间窗**：`|t − now| ≤ 60` 秒，否则 401 `stale_time`。
5. **取公钥**：`state.pm.get_from_main(&id)`（先查内存，没有再查主池并放进内存）。查库出错 → 503。条目不存在，或 `pk` 为空（`insert_new` 建的占位条目）→ 401 `unknown_device`。`update_pk` 先写库后改内存，内存里的公钥不会比库里新【读码：`src/peer.rs` `update_pk`】。
6. **验签**：`sodiumoxide::crypto::sign::verify_detached`（服务端已直接依赖）。失败 → 401 `bad_signature`。
7. **防重放**（§3.3）：不通过 → 401 `replay`。
8. **首次锁定**：条目 `pinned` 为假时执行
   ```sql
   update peer set pk_pinned_at = ? where id = ? and pk = ? and pk_pinned_at is null
   ```
   绑定刚才验签用的 `pk`，走主池。影响 1 行：取条目写锁，`pk` 仍等于那把时把 `pinned` 置真。影响 0 行或写库失败：请求照常放行（写库失败限频 warn，下一个请求再试）。内存和库对不上也没关系：换公钥的写库本身带锁定条件（§3.4），库是唯一的依据。

**拒绝响应**：第 4~7 步的 401 由提取器自己组并签名（"请求的签名"取第 1 步解析出的值）；第 1 步的 `bad_auth` 用 `porta_error` 回 401，不签名、不带 `time`（§2.2）；429、413、503 不签名。

**响应工具**：

```rust
pub(crate) fn signed_json<T: Serialize>(state: &AppState, req_sig: &[u8], status: StatusCode, v: &T) -> Response
pub(crate) fn porta_error(status: StatusCode, code: &'static str, message: &str) -> Response
```

`signed_json` 有 `state.sk` 时按 §2.2 签名，Content-Type 带 `charset=utf-8`，`bad_auth` 以外的 401 也用它（体里带 `time`）；`porta_error` 组 `{"error","message"}`、不签名。

日志照 `server/PORTA.md` §6 第 7 条：每种拒绝原因每分钟最多一条（`throttled_log!`）；ID 先截到 253 字节再用 `{:?}` 打；不打签名和公钥原文。

### 3.3 防重放表

模块内 `static`（`server/PORTA.md` §3"模块的小状态放在模块内"）：

```rust
static REPLAY: Lazy<Mutex<HashMap<String, Replay>>>;   // 键是设备 ID，最多 4096 个
struct Replay { max_ts: i64, floor: i64, ring: VecDeque<(i64, [u8; 16])>, last_seen: i64 }
```

- **接受条件**（时间窗已在第 4 步查过）：`t ≥ max_ts − 30`（同一设备最多乱序 30 秒）；`t > floor`；`(t, 签名前 16 字节)` 不在 `ring` 里。
- **接受后**：放进 `ring`，更新 `max_ts`、`last_seen`；`ring` 超过 64 条时弹出最早那条，`floor = max(floor, 弹出那条的 t)`。
- **新建条目**：`floor = now − 30`。服务重启后，重启前截获的请求最多还能重放 30 秒。
- **表满**且来了新 ID：扫一遍删掉 `last_seen` 最小的。只有验签通过的请求才建条目，灌满它要先持有大量已注册设备的私钥。
- 每条约 1.5 KB，合计约 6 MB；不落库（笔记 02 §2.3）。超过 4096 台活跃设备时的退化见 §9。


- **登录**（`account.rs` L361【读码】）：`Match`、`MatchPinned` 都算相符，登录绑定行为不变：锁定后照样能凭 uuid 改绑主人（第三期没有任何判定依赖"设备主人"：草稿里按主人放行同网判定的做法已排除，见 03 §2.1）。"设备主人"这个身份的加固（已锁定设备的登录不再覆盖已有主人、命令行指定主人）按笔记 02 §2.6 的原计划放到第四期，和 Exit Node 一起做。
- **三个兼容上报**（sysinfo、心跳、被控端审计）：只有 `Match` 放行，`MatchPinned` 也按"不符"。"不符"的回法和第一期一样：sysinfo 403 空 body，心跳 `{}`，审计 200 空 body、不入库。
- 会话备注分支（有 `note`、没有 `uuid`）不受影响（笔记 02 §2.5）。

第三期的防降级只有"已锁定的 ID 拒收不签名上报"这一条。退出兼容用的"只接受 Porta 客户端"开关（`porta_only`，`docs/architecture.md` §3.1 退出机制）第三期不做，挪到退出兼容时按当时的方案再加（README.md §1.2）。

### 3.6 Porta 心跳：`device::porta_heartbeat`

**先抽两个函数**，兼容 handler 也改调它们（笔记 03 §2.5）：

```rust
/// 写设备行，带行数上限和延迟补绑。返回库里现存的 sysinfo 原文（'' 表示还没有）；None 表示没能建行。
pub(crate) async fn touch(db: &SqlitePool, id: &str, uuid: &str, ver: i64, ip: &str, client_type: &str)
    -> Result<Option<String>, sqlx::Error>;
/// 存 sysinfo 原文和拆出的四列，带行数上限和延迟补绑。false 表示没有可淘汰的行。
pub(crate) async fn store_sysinfo(db: &SqlitePool, id: &str, uuid: &str, raw: &str, f: SysinfoFields, client_type: &str)
    -> Result<bool, sqlx::Error>;
```

- `touch` 就是现在 `heartbeat` 里的 select / update / `make_room` + insert，三处改动：`returning` 改取 `sysinfo` 原文（兼容 handler 用 `is_empty()`，行为不变）；select 多读 `client_type`，"什么都没变"的条件加上 `client_type == 参数`，insert、update 都写它，记下最近一次走的路径（笔记 03 §5.2 第 6 条）；`make_room`、`OWNER_FROM_TOKEN`、`LAST_SEEN_STEP` 原样搬进去。
- `store_sysinfo` 是现在 `sysinfo` handler 的事务，写死的 `'rustdesk'` 改成参数。

**`porta_heartbeat(State, SignedBody)` 的流程**：

1. 解析请求体：
   ```rust
   struct PortaHeartbeatReq {
       #[serde(default)] uuid: String, #[serde(default)] ver: i64, #[serde(default)] porta: String,
       #[serde(default)] strategy_rev: i64, #[serde(default)] routing_rev: i64,
       #[serde(default)] sysinfo_hash: String,
       sysinfo: Option<Box<RawValue>>,
       probes: Option<serde_json::Value>,   // 02 块解析；坏值只丢测量，不回 400
   }
   ```
   `uuid` 超过 128 字节 → 400；`sysinfo` 原文超过 8 KB（`MAX_SYSINFO_LEN`）→ 413。
2. **写验签心跳记录**：`signed.peer.write().await.porta_hb = Some(PortaHb { at: Instant::now(), porta_ver })`，`porta_ver = get_version_number(&req.porta)` 限到 `u32`（解析不出为 0）。
   ```rust
   pub(crate) struct PortaHb { pub at: Instant, pub porta_ver: u32 }
   ```
   只存内存，只由本 handler 写（审计不写）。条目被淘汰时记录跟着丢，下一次心跳重写。
3. 带了 `sysinfo`：解析出 `hostname`、`username`、`os`、`version`（可缺省的字符串，类型不对 → 400，各截到 253 字节），调 `store_sysinfo(db, id, uuid, raw.get(), fields, "porta")`。
4. 调 `touch(db, id, uuid, ver, ip, "porta")` 得到 `stored`。
5. `stored` 为 `Some(s)`，且 `s` 为空或 `base64(sha256(s)) != sysinfo_hash` → `need_sysinfo: true`。`None`（没能建行）时不带这个键。
6. `strategy::effective(db, id)`，`rev != strategy_rev` 时带 `strategy`。
7. 其他块的接入点（下表），然后 `signed_json(200)` 回复。查库失败一律 503，不签名。

**其他块的接入点**（都在验签通过、拿到验签得来的设备 ID 之后）：

| 块 | 接入点 | 本块提供 |
|---|---|---|
| 02 路由第二级 | `if let Some(p) = &req.probes { state.router.record_probes(&id, p); }`；`state.router.routing()` 的 rev 和 `req.routing_rev` 不同时响应加 `routing`；响应结构体的 `routing: Option<Routing>` 字段（`skip_serializing_if`）由 02 块加，本块不先占位 | `probes` 收成 `Option<Value>`；心跳请求体上限 32 KB |
| 04 UDP 打洞与 NAT 探测 | 04 块合入后 `features` 一直带 `"udp-punch"`（不加配置开关）；读 `Peer.porta_hb`：`at` 在 180 秒内、`porta_ver` 不低于 `MIN_PORTA_VER`，就判"被控端会回带 nonce" | `features` 字段、`porta_hb` |

03 块不读 `porta_hb`。04 块的 UDP 出口证明（04 §2.5）也不读它，只看服务端自己签发的 token。

**sysinfo 哈希的定论**（笔记 03 风险"两边序列化不一致"）：哈希只算在 sysinfo 这个 JSON 值的原始字节上。服务端用 `RawValue` 原样存这段字节，比对时当场对库里原文算 sha256，不加列（最多 8 KB，开销可忽略）。客户端单独序列化 sysinfo 对象得到 `s`，对 `s` 算哈希；整个请求体用同一个 `serde_json` 紧凑序列化，嵌在里面的那段和 `s` 逐字节相同，单元测试钉住（§6.2）。兼容路径存的是整个兼容请求体，哈希必然不同：设备从兼容路径切到 Porta 路径后重传一次 sysinfo，之后稳定。

### 3.7 Porta 审计：`audit.rs`

- `ConnReq`、`FileReq`、`AlarmReq` 的 `id` 加 `#[serde(default)]`。兼容路径缺 `id` 时原来回 400，现在得到空 ID、按"不符"回 200 空 body；原版客户端总带 `id`，看不到区别。

- 兼容 handler：`Written`、`Skipped` → `ok_empty()`；`Failed` → `ok_internal`，和第一期相同。
- 新增 `porta_conn`、`porta_file`、`porta_alarm(State, SignedBody)`：沿用原结构体和 `clip`，`req.id = signed.id`；`conn` 不走备注分支；`Written`、`Skipped` → `signed_json(200, {"api":1})`；`Failed` → 503，nonce 不登记，客户端重试时能入库。

### 3.10 命令行

- `porta-server device key <id>`：只读库，输出公钥指纹（小写 hex，每 4 个字符空一格，和客户端 `pk_to_fingerprint` 同格式，`porta-client:src/common.rs` L2137【读码】）、锁定时间或"未锁定"、uuid 字节数、同一 uuid 下的其他 ID（重装后换了 ID 的设备由此能看出来，笔记 02 §4 第 1 条）。`changes_database` 算只读。
- `porta-server device key reset <id>`：**只清锁定**，保留 uuid 和公钥。先连控制台发 `key-reset <id>`（简写 `kr`）：服务进程执行 `update peer set pk_pinned_at = null where id = ?`（主池），再 `pm.set_pinned(id, false)`，回显结果。连不上控制台（服务没在跑）就由命令行直接改库，做法同 `geo update`（`server/PORTA.md` §14）。
  - 用途：卸载时删了配置的重装。uuid 来自机器、不变，重装后的设备按现有规则（同 uuid、同 IP 可以换公钥）保住原 ID，没有 uuid 的人抢不走。
  - 时机：要在旧安装**停止运行之后**（卸载完成）、重装的设备重新注册**之前**执行。旧安装还在跑时 reset，它下一次签名心跳（最多 15 秒）就把旧公钥重新锁上，reset 白做。锁定后换了公钥的设备一注册就收到 `UUID_MISMATCH`，客户端随即换成随机 ID（`rendezvous_mediator.rs` `handle_uuid_mismatch` → `Config::update_id`【读码】）。已经换了也能补救：reset 后在设备上把 ID 改回原来的。
- `porta-server device key reset --forget <id>`：**删行**，给 uuid 也变了的情况（换硬件、重装系统）。控制台 `key-forget <id>`（`kf`）：`delete from peer where id = ?` 后 `pm.remove(id)`；连不上控制台就直接删行。删行后下一次注册走 `insert_peer`，受新 ID 限额约束，uuid、公钥按新登记写入；`device`、`device_policy`、`strategy_option` 里按 ID 存的行不受影响。
  - 风险：删行后这个 ID 谁都能注册，抢到的人发一次签名心跳就锁定了自己的公钥。所以只在新设备已经在线（这时它已因 `UUID_MISMATCH` 换成随机 ID）时执行，执行后立刻在设备上把 ID 改回原 ID，空窗只有这几秒。
- 这偏离了已定的"删行或同时写 uuid"写法，见 §8 第 2 项。

### 4.4 `report/mod.rs`：能力缓存和挂钩入口

**持久缓存**：Config 的 options（`Config::get_option` / `Config::set_option`）里的 `porta-api-caps`，值 `<API 根地址>\n<feature,feature,...>`（没有特性时第二行为空）。

- 只由服务进程写：第一次判定"支持"时，以及之后每次成功的心跳：用"当前根地址 + 带回的 `features`"组出整个值，和存的不同就写（只比 features 的话，持久值被清掉后空 features 会被当成没变，补不回来）。值没变不写。
- 界面进程经现有的选项同步读到【读码】：界面进程启动时 `SyncConfig` 整份拉一次（`src/server.rs` L729）；每次发起会话，`ui_session_interface.rs` `io_loop` L1985 调 `get_key(false)` → `ipc::get_options_async` → `get_options_` 把服务进程的整份 options 写进本进程 Config（`src/ipc.rs` L1883~1887）。所以控制端在连接时读到的是服务进程当前的值。
- porta-server 的策略不下发 `porta-*` 键，`handle_config_options` 只改下发的键（`sync.rs` L292~308【读码】），碰不到它。设置导入会清掉它，后果只是重探一次（§9）。
- 为什么不放 LocalConfig：LocalConfig 不同步到界面进程，04 块控制端的开关读不到。

**对外函数**：


- `server_is_porta()`、`has_feature()` 每次调 `api_root()` 算出当前根地址，和持久值比较；不依赖 `CAP`、不依赖 `tick` 先跑过，进程刚启动、刚改地址时也对。构建时决定的默认地址（`PORTA_API_SERVER`，或只注入会合服务器时 `brand::default_api_server()` 推出的地址）在还没有持久记录时 `server_is_porta()` 为真、`has_feature()` 为假（第一次心跳成功后有了 features）。
- `api_root()` 照上游 `common.rs` `get_api_server`、`get_api_server_`（L1224~1266）的规则在 `libs/porta` 里重算一遍：`Config::no_register_device()` 为真返回空；`api-server` 选项非空用它；否则用 `custom-rendezvous-server` 选项（为空用 `PROD_RENDEZVOUS_SERVER`）按 `brand.rs` 的同一条规则推出地址（把 `brand::default_api_server` 里的推导拆成共用函数）；再否则 `brand::default_api_server()`；最后去掉末尾 `/`，https 加 `:21114` 时按 `allow-https-21114` 内置选项处理。`libs/porta` 调不到主 crate 的 `get_api_server`，所以重算；不含 Windows 按 exe 文件名取授权那一支（§9）。
- `tick`、`audit` 的根地址从上游传进来的 `url` 拆（`tick` 去掉末尾 `/api/heartbeat`；`audit` 按最后一个 `/api/audit/` 拆成根地址 + 类型），拆不出来返回 `false` / `None` 走上游。拆出的根地址和 `api_root()` 不同时（重算的规则和上游走样，或按 exe 文件名带了 API 地址），打一条限频 warn `porta report: api root mismatch, using legacy reports`，返回 `false` / `None`，保证"读缓存的地方"和"写缓存的地方"说的是同一个地址。
- `CAP` 的根地址和这次的不同：重置状态，调 `porta::route::reset()`；新地址等于持久值里的根地址或注入地址时置 `Supported`，否则 `Unknown`。判为 `Unsupported` 时也调 `porta::route::reset()`。
- 心跳在同步线程的 current_thread 运行时、审计在服务进程运行时里调用，`CAP` 用 `std::sync::Mutex`，不跨 `.await` 持锁。

**给别的块用的客户端接口**：

| 函数 | 谁用 | 在哪个进程 |
|---|---|---|
| `report::server_is_porta()` | 02 块 `route::relay_preference` | 服务进程（被控端处理打洞） |
| `report::has_feature("udp-punch")` | 04 块 `options::self_hosted_punch_default`、`punch::wait_udp_nat` | 界面进程（控制端发起连接） |

### 4.5 `report/heartbeat.rs`：`tick` 的流程

模块内 `static HB: Mutex<…>`：`last_attempt`、`failures`、`need_sysinfo`、`confirmed_hash`（最近一次被服务端收下的 sysinfo 哈希）。

1. 状态 `Unsupported` 且没到重探时间 → 返回 `false`。
2. **节拍**：`failures > 0` 时间隔 `min(3 秒 × 2^(failures−1), 60 秒)`（3、6、12、24、48、60…）；否则有连接 3 秒、没有 15 秒。没到点：`Unsupported` 返回 `false`，其余返回 `true`（本轮不走上游）。
3. **组包**：
   - `s = sysinfo()` 加 `version` 和上游 sysinfo 用的预置键，照抄 `src/hbbs_http/sync.rs` L136~178 的规则（`preset-address-book-*`、`preset-device-username`/`-name` 覆盖 `username`/`hostname`、`preset-note`，读 `BUILTIN_SETTINGS` 的 `preset-user-name`/`-strategy-name`/`-device-group-name`），**不带** `id`、`uuid`。
   - `bytes = serde_json::to_vec(&s)`，`hash = base64(sha256(bytes))`；`need_sysinfo` 为真或 `hash != confirmed_hash` 时带上 `sysinfo`。
   - `routing_rev = porta::route::routing_rev()`；`probes = porta::route::probes()`，`None` 不带。其余字段照 §2.3。
4. **发送**。401 带验过签的 `time` 时调 `set_server_time`，打 `porta report: 401 {error}, clock offset now {offset}s`，重签后立即重试一次。
5. **判定能力**（§2.5）。第一次判为支持时打 `porta report: {root} supports Porta API, features [{features}]`；判为不支持时打 `porta report: {root} has no Porta API ({status}), using legacy reports`。
6. **成功**（2xx、配了 Key 时验签通过、有 `api`）：
   - `failures = 0`；用 `time` 更新偏移；这次带了 sysinfo 就把 `confirmed_hash` 设成 `hash`；`need_sysinfo` 设成响应里那个键的有无；
   - 按 §4.4 组出 `porta-api-caps` 的整个值，和持久值不同就写；
   - 有 `strategy` 就按 `handle_config_options` 的规则合并进 Config（约 15 行，复制 `sync.rs` L292~308，不调上游私有函数），合并时跳过 `porta-` 开头的键，`rev` 写进 LocalConfig `strategy_timestamp`；
   - **每次**都调 `porta::route::on_heartbeat_ok(resp.get("routing"))`（不管带没带 `routing`：02 块靠它刷新"最近一次成功心跳"的时刻，测速线程据此决定跑不跑）；
   - 返回 `true`。
7. **失败**：验签失败时打 `porta report: server signature check failed`。`failures += 1`（限频日志），返回 `true`。例外：未确认地址回 404/405（判为或仍为不支持）返回 `false`，本轮走上游。

第 4、5、7 步的四行和 §4.4 的 `api root mismatch`，这五行 `porta report:` 开头的日志都用 `throttled_log!`，每种每分钟最多一条，文字固定，§6.3 照此查找。

### 4.6 `report/audit.rs`：`audit` 的流程

1. 状态 `Unsupported` → `None`。
2. 请求体：`v` 克隆后删掉 `id` 再序列化。nonce 不变，**每次尝试都重新签名**。
3. 照上游的重试表发送：间隔 10 秒、30 秒，总时限 120 秒。每次回应：
   - 2xx、验签通过、有 `api` → 状态是 `Unknown` 时置 `Supported` 并写持久缓存（根地址和持久值相同就保留原 features，不同就写空 features），返回 `Some(Ok(String::new()))`。
   - 404/405：状态是 `Unknown` → 置 `Unsupported`，返回 `None`（这条审计交给上游发）；状态是 `Supported` → 放弃，`Some(Err)`。
   - 400、413 → 放弃，`Some(Err)`。
   - 401（立即重试后仍失败）、429、5xx、网络错误、TLS 错误、验签失败 → 按重试表重试，超时后 `Some(Err)`。
4. 如果 Porta 那次其实已经入库、之后又退回上游重发，两条路径共用 nonce 去重表，只记一次。

## 6. 测试

### 6.1 服务端（Linux 测试机 `cargo test`，axum `oneshot` + 临时 SQLite）

- **签名向量**：固定私钥、ID、`t`、请求体，算出签名头期望值；客户端测试用同一组常量（§6.2）。
- **验签链**，每种拒绝原因一条：头格式错 → `bad_auth`，响应不带 `Porta-Server-Sig`、体里不带 `time`；`t` 偏 61 秒 → `stale_time`，响应带 `time` 和合法的服务端签名；不存在的 ID、`pk` 为空的占位条目 → `unknown_device`；改请求体一个字节、改接口名 → `bad_signature`；同一请求发两次 → `replay`。
- **防重放**：30 秒内的乱序接受、超过拒收；64 条之后 `floor` 抬升；表到 4096 个 ID 时淘汰 `last_seen` 最小的。
- **锁定**：
  - 第一个合法请求后库里 `pk_pinned_at` 非空、内存 `pinned` 为真；条件更新遇到公钥已换时影响 0 行，请求仍成功。
  - 库层守卫（§3.4）：锁定后用锁定前取得的内存快照调 `PeerMap::update_pk` 换公钥 → `UUID_MISMATCH`，库里 `pk` 不变，内存 `pinned` 被刷成真；`ip_only` 分支照常 OK；行已被删掉时换公钥的 `update_pk` 回 `SERVER_ERROR`，不回 `UUID_MISMATCH`。
  - 会合测试（现有 harness）：锁定后用另一把公钥发 `RegisterPk` → `UUID_MISMATCH`；同一把公钥换 IP → OK。
- **验签心跳记录**：Porta 心跳成功后 `porta_hb` 的 `at`、`porta_ver` 正确；400 的心跳和 Porta 审计不写它。
- **防降级**：锁定后的设备走兼容心跳得到 `{}`、sysinfo 403 空 body、审计 200 空 body 且不入库；同一设备登录照样绑定；没锁定的 ID 兼容上报照常。
- **Porta 心跳**：没有行、sysinfo 为空、哈希不符时带 `need_sysinfo`，存下后不带；库里的 sysinfo 和请求里那段逐字节相同，哈希等于客户端算的；只在 rev 不同时下发 `strategy`；`client_type` 在 Porta 心跳后是 `porta`、再来一次兼容心跳变回 `rustdesk`；响应签名能用会合公钥验过；sysinfo 超过 8 KB → 413；`probes` 是字符串之类的坏值时照常 200。
- **Porta 审计**：nonce 去重和兼容路径共用；写库失败回 503 且 nonce 没登记；体里的 `id` 被忽略、按头里的 ID 入库；`note` 不触发备注分支。
- **中间件**：Porta 路径的 413、405 体带 `error` 和 `message`；超时和 panic 回 503；`/api/porta/v1/nope` 回 404；兼容路径原有断言全部不变。
- **命令行**：`device key` 的指纹格式；`device key reset`：控制台在跑时库和内存的锁定都清掉、uuid 和 pk 不变，之后同 uuid 同 IP 用新公钥注册 OK；控制台不在时只改库；`--forget`：控制台在跑时内存条目和库行都删掉，之后同 ID 用新公钥注册走新登记、库里 uuid 非空。
- **迁移**：在第一期的库上执行 0004 成功。
- 不测：libsodium 自身、性能数字、TLS。

### 6.2 客户端（`libs/porta` 单元测试，`cargo test -p porta`）

- 签名头：用 §6.1 的同一组常量；`verify_server_sig` 的正反例。
- sysinfo 哈希：整个请求体序列化后，嵌在里面的 sysinfo 那段和单独序列化的结果相同。
- 能力状态机（把"发送"抽成可注入的函数，按回应序列断言状态、返回值和对 `route::reset` 的调用）：未知 + 404 → 不支持、本轮走上游、10 分钟后重探；未知 + 不带 `api` 的 2xx → 同 404；未知 + TLS 错误 / 401 / 503 / 验签失败的 2xx → 状态不变、本轮不走上游；已确认的地址回 404 仍是支持；注入地址和 `brand::default_api_server()` 推出的地址不探测直接支持；换地址 → 重置并调 `reset`。
- 持久缓存：`porta-api-caps` 的读写格式；`server_is_porta()`、`has_feature()` 在 `CAP` 为空（模拟刚启动）时按持久值回答；持久值的根地址和 `api_root()` 不同 → 都为假；`tick` 的 `url` 拆出的根地址和 `api_root()` 不同 → 返回 `false`。

- 心跳：每次成功都调 `on_heartbeat_ok`，响应不带 `routing` 时传 `None`。
- 退避序列：3、6、12、24、48、60、60 秒。
- 策略合并：空值的删键规则和上游 `handle_config_options` 一致。
- 不测：reqwest、代理、TLS 握手本身。Windows 构建通过（`scripts/windows/build-client.ps1`）。

### 6.3 端到端（维护者做；测试机起第三期 porta-server，Windows 装 Porta）

客户端日志看服务进程的日志（被控端心跳、审计都在服务进程里发）。

1. Porta 被控端启动 15 秒内，日志有 `porta report: <根地址> supports Porta API`（注入地址不探测，没有这行），`porta-server device list` 里这台的客户端类型是 `porta`。
2. `porta-server device key <id>` 显示已锁定，指纹和客户端界面上的一致。
3. `strategy set <id> <某个选项> <值>`，15 秒内在客户端生效。
4. 从另一台机器连这台、传一个文件，审计表里有 conn 和 file 记录（没有现成命令时用 `sqlite3` 查 `audit_conn`、`audit_file`）。
5. 把被控端时钟调快 10 分钟：日志出现一次 `porta report: 401 stale_time, clock offset now -600s`（数值在 −600 附近），之后心跳恢复，`last_seen_at` 继续更新。
6. 把客户端的 `key` 改错：日志出现 `porta report: server signature check failed`，策略不再生效。会合层的 KeyExchange 同时失败，这台设备连不上也连不出去，是预期结果。改回后恢复。
7. 把同一个客户端指向第一期 porta-server（用一个**没确认过**、也不是注入的地址，否则按设计不退回）：日志出现 `porta report: <根地址> has no Porta API (404), using legacy reports`，`device list` 显示 `rustdesk`。
8. 重装保 ID：在被控端卸载时删掉配置，重装前在服务端执行 `device key reset <id>`；重装后设备仍是原 ID，`device key` 显示新指纹、重新锁定。
9. 判定通过：1~8 都符合预期，服务端日志里没有持续的 401 或 503。

## 7. 明确不做

- 会合层（`RegisterPk` / `RegisterPeer`）签名，退出兼容前单独定。
- 公钥轮换、私钥加密存放；密钥丢失只靠 `device key reset` 找回。
- 登录、地址簿、会话备注签名；用户令牌绑设备（DPoP 式）；`token.device_verified` 这一列（等签名登录设计时再加）。
- Exit Node 的主人认定，以及"已锁定设备的登录不再覆盖已有主人"、命令行指定主人（第四期，笔记 02 §2.6）。
- 退出兼容用的 `porta_only` 开关（推迟到退出兼容时，§3.5）。
- 服务端签发设备令牌、单独的能力协商接口、单独的 `/api/porta/v1/sysinfo`。
- 心跳下发 `disconnect`；`/api/record`、`/api/switch-grant`。
- Porta 路径的 TCP 代理回退、WebSocket 代发、native-tls 回退、接受无效证书。
- 审计落盘补发队列。
- `is_pro()` 挂钩。
- 跨服务器重放防护（被签内容不含服务端身份）。

## 8. 需要维护者定

本块不涉及 README.md 里的 P-1~P-4。下面两项"不回复即按推荐"；另有两项删减（不加 `token.device_verified`、不做 `porta_only`）也在 README.md §1.2 里按推荐处理，理由见 §3.8、§3.5：

1. **会话备注第三期不动**（笔记 03 §5.3 第 1 条、笔记 02 §2.6）。会话中工具栏"Note"由控制端 `ui_session_interface.rs` `send_note` 发到兼容接口 `/api/audit/conn`，不带凭据。
   - **推荐**：第三期不动。退出兼容时保留兼容接口的备注分支，记进 `docs/architecture.md` §3.1 的兼容债务。代价：备注照旧不认证，靠"每种连接类型最多改 4 行"封顶。
   - **备选**：在 `ui_session_interface.rs` 加一处挂钩，改由 `libs/porta` 发到新接口 `/api/porta/v1/note`。代价：动上游文件；它在界面进程里，能用的凭据只有登录令牌（设备私钥在界面进程里不一定是注册的那把，笔记 02 §1.1），等于多一个接口、多一套认证，收益只是备注不能被伪造。
2. **`device key reset` 默认只清锁定**（按安全审查改了写法，偏离了已定的"删行或同时写 uuid"）。
   - **推荐**：默认只清锁定、保留 uuid 和公钥；uuid 也变了时用 `--forget` 删行（§3.10）。理由：删行让这个 ID 在整个重装过程里谁都能抢，抢到的人锁定自己的公钥后，连这个 ID 的控制端都会连到他那里，服务端还会给他的公钥签名，控制端不报警。只清锁定时，抢 ID 仍要 uuid 和同一出口 IP。代价：多一个 `--forget` 开关；`--forget` 仍有几秒空窗。
   - **备选**：照原定删行。代价如上。

## 9. 已知限制和风险

- **首次使用即信任**：设备第一次签名之前，知道它 uuid（兼容路径的明文心跳和 UDP 注册里都能嗅到）、并且和它共用出口 IP 或能伪造它 UDP 源地址的人，能抢先换掉公钥，锁定的就是冒充者那把。真设备随后换 ID，维护者能从 ID 变化或指纹比对发现（笔记 02 §2.4）。新设备装好后用 `device key <id>` 和设备界面上的指纹核对一次。
- **手动填写的 API 地址第一次接触也是首次使用即信任**：确认支持之前，路径上的攻击者回 404 就能让设备走上游路径，进而下发任意选项。构建时注入的地址不受影响（直接视为支持）。
- **锁定把"公钥变了"变成"设备换 ID"**：卸载时删了配置的重装会让设备换成随机 ID。要保住原 ID，在重装前执行 `device key reset`（§3.10）。
- **共存时 Porta 永远锁定不上**：同一台机器上原版先注册，库里的 `pk` 是原版那把，Porta 的签名一直回 401 `bad_signature`；地址已确认过时它不退回兼容路径，上报持续失败，客户端也不会重发 `RegisterPk`。处理：03 块第 4 项的默认 ID 加盐（根治）；或先停掉这台机器上的原版，再 `device key reset --forget`，让 Porta 重新注册（不停原版的话，可能又被原版抢先注册）。
- **防重放容量**：活跃 Porta 设备超过 4096 台时表持续淘汰，被淘汰设备重建条目时 `floor = now − 30`，它最近 30 秒里被截获的请求可以再重放一次；每个请求还要在全局锁里扫一遍 4096 条。控制 4096 台以上能签名设备的人也能主动把受害设备挤出去。实际危害只是把 `last_ip` 记成重放者的 IP。个人部署碰不到，不加大。
- **防重放的边角**：同一设备 30 秒内发 64 条以上请求时，`floor` 抬到较新的时间戳，同一秒内后续请求会被当成重放；客户端重签重试一次，还失败靠下一轮兜住。心跳 3 秒一次、审计每次会话几条，实际碰不到。
- **自签证书的 API 地址**：Porta 路径只认受信任证书，又不退回上游，这类部署上的 Porta 客户端心跳和审计都停掉（§5）。出路：换受信任的证书；或 API 用明文 HTTP 并配 Key，请求签名防伪造上报、响应签名防篡改下发，只是内容不加密。
- **服务端回滚后客户端不降级**：防降级的代价（§5）。
- **`porta-api-caps` 可能被界面进程清掉或写回旧值**：设置导入会清掉它；界面进程改任何设置时把自己缓存的整份选项写回服务进程（`ui_interface.rs` `set_option` → `ipc::set_options`，缓存约每秒刷新一次），刚写入的值可能被旧值盖掉。服务进程内存里的状态不受影响，下一次成功心跳按 §4.4 补写；补写前的几秒 `server_is_porta()`、`has_feature()` 为假，被控端照上游用本地中继设置。服务进程在补写前重启时，手动地址按未知重探一次。
- **按 exe 文件名带授权的部署**：上游会从 exe 文件名读 API 地址和 Key，`libs/porta` 读不到。这种部署 `tick` 发现根地址对不上，一直走上游兼容路径；本地 `key` 和 `RS_PUB_KEY` 都为空时也不验响应签名。Porta 的构建在编译时注入，不走这条路【推测】。
- **`api_root()` 是上游规则的复制**：上游改了 `get_api_server` 而 `api_root()` 没跟上时，`tick` 打 `api root mismatch` 并退回上游，`server_is_porta()` 为假；不会出现"读写两边各说一个地址"。
- **`device key reset` 和并发注册赛跑**：`--forget` 删行的同时正好有一次 `RegisterPk` 拿着旧条目，它对已删的行写库影响 0 行、内存条目又已移除，回 `SERVER_ERROR`（§3.4）；下一次注册按新设备处理。默认的只清锁定不删行，没有这个问题。
- **明文 HTTP 的默认地址**：签名防伪造、响应签名防篡改，但上报内容（sysinfo、审计）明文可见，保密要靠 HTTPS。
- **上游改动**：上游另加不经过 `post_audit_async` 的审计出口时，新出口会悄悄走兼容路径（锁定的设备上被静默丢弃）；上游改 tick 结构时挂钩 ① 要跟着挪。都写进合并上游的冒烟清单。
- **反代改写请求体**（压缩、转码）会让请求体哈希对不上。常见反代配置不会这样做【推测】。
- **超时**：整请求超时 10 秒、客户端每次尝试 12 秒，和第一期上报接口一样；Porta 路径超时回 503，客户端重试。
