# 02 修订草案：开 fake-ip TUN 的机器上，中继测速每轮都作废

> 标注：【读码】读过源码；【实测】维护者本机 2026-10-25 实测；【推测】推断，没有实测。代码锚点对照 leapgate-client `753c9e7e7`、leapgate-server `d564e30`、上游 `rustdesk-server@873230e`。

## 0. 结论

- **问题**：本机开着 mihomo/Clash 的 fake-ip TUN 时，测速每一轮都被 02 自己的作废规则拦下，第二级一直退回第一级的 GeoIP 估计。02 原来的出路是"用户在代理里把中继排除在 TUN 外"，这违反 P-2（不接受要用户配环境规则），而维护者的目标环境恰好都开 TUN，第二级在那里等于没做。
- **原提议（下称方案乙）**：测速 socket 绑物理网卡，中继域名改问物理网卡的 DNS（复用 05 的 F1）。能拿到数，但量的是"物理网卡直连中继"这条路；真实的中继连接不绑网卡、走系统解析和系统路由，开 TUN 时由代理按规则决定直连还是走节点（§2）。规则让中继走节点、或者开着全隧道 VPN 时，报上去的数对应一条真实连接根本不走的路。今天这些机器是"作废、退回估计"，改成乙反而会报一个错的数。乙既不是"不管开不开 TUN 都对"，也做不到"判别清楚"，不符合 P-2，**不推荐**（§3）。
- **推荐方案甲**：测速连接和真实中继连接走同一条路（不绑网卡、系统解析、系统路由，开 TUN 就进 TUN）。连上后先等 1.5 秒，让代理把上游连好，再发 1 个字节的空帧，量从发出到中继关连接的时间，这正好是真实中继路径的一个往返。依据是 hbbr 收到"不是 `RequestRelay` 的首帧"会立刻静默关连接【读码】，维护者本机经 fake-ip TUN 量到 230~260 毫秒，和物理直连的往返一致【实测】（§4）。所有环境用同一条规则，不用判断开没开 TUN、不用用户配规则，三条作废规则删掉两条。物理网卡 DNS（F1）在甲里用不上。
- **改动**：只改客户端 `libs/leapgate/src/route/probe.rs`，再从 `lan.rs` 删一个函数。服务端、协议、上报格式、上游挂钩都不动（§5）。
- 02 §7 原来写"穿过 TUN 测应用层延迟：hbbr 配对前不回任何数据，没有可测的往返"，这句不对：hbbr 不回数据，但会关连接，关连接本身就是回应。

## 1. 问题

### 1.1 症状和原因【读码：`route/probe.rs`】

- `probe()`（L128~141）用 `ToSocketAddrs` 走系统解析。fake-ip 下得到 `198.18/15` 的假地址（维护者本机解析会合服务器域名得到 `198.18.0.19`），`summarize()` 的 `fake_ip(a.remote)`（L178）让整轮作废。
- `connect_first()`（L143~154）不绑本地地址，连接进 TUN，由 TUN 在本机完成握手，本地地址是 TUN 的（`198.18.0.1`），`!is_physical(a.local)`（L169）同样让整轮作废。
- 作废时清掉旧结果，心跳不带 `probes`，服务端当场删掉这台的测量（02 §3.4），选路退回估计。

### 1.2 为什么不能只靠"可选优化"

02 §9 第 1 条和 README §5 的设计是：识别出代答就作废、退回估计，想要实测就自己把中继排除在代理之外。P-2 定下之后，"要用户配规则"不再是可接受的出路。目标环境里的机器都开 TUN，按现状第二级只在少数不开代理的机器上有数据。

## 2. 真实中继连接走哪条路（两个方案的共同出发点）

- 控制端：`Client::create_relay`（`src/client.rs` L1872）调 `connect_tcp`（L1883）→ `connect_tcp_local(target, None, …)`（`hbb_common/src/socket_client.rs` L150）：不绑本地地址，系统解析，系统路由【读码】。
- 被控端：`create_relay_connection_`（`src/server.rs` L404）同样调 `socket_client::connect_tcp`（L416）【读码】。
- 所以真实中继连接：
  - 不开代理：从物理网卡直连中继。
  - 本机开 TUN（fake-ip）：系统解析得到 `198.18.x`，连接进 TUN；代理把它映射回域名，再按规则处理：要么直连（代理自己从物理网卡发出），要么交给节点（实际路径是"本机 → 节点 → 中继"）。
  - 路由器透明代理：路由器接住握手，再按它的规则发出。
  - 全隧道 VPN（WireGuard 全局、Tailscale 出口节点、公司 VPN）：经 VPN 出去。
- 客户端看不到代理软件的规则。第一级估计用的地址（`rendezvous_server.rs` L1439~1441：A 的打洞请求来源、B 的注册地址）在这些环境里同样是代理或 VPN 的出口，估计值本来就不一定准，所以下面不把"退回估计"当成标准答案，只比较各方案量的是不是真实路径。

**原则**：测量要和被测的流量走同一条路。05 的 ICE 自己的流量就从物理网卡发，所以它解析会合服务器时也问物理网卡的 DNS（F1）；中继流量走系统路由，测速也应该走系统路由。

## 3. 方案乙（原提议）：物理网卡测速 + 物理网卡 DNS

### 3.1 做法

每轮按 05 的网卡排序选出一块能出候选的物理网卡，每个地址族一个地址；中继域名先问这块网卡自己的 DNS 服务器（同 05 §4.3），拿不到再退回系统解析；TCP 连接先绑这个地址再连；作废规则保留 2 毫秒那条，fake-ip 那条挪到解析阶段（见 §3.4）。

### 3.2 测出来的数有没有意义

| 环境 | 乙量到的 | 真实中继连接走的 | 结果 |
|---|---|---|---|
| 不开代理 | 物理直连 | 物理直连 | 一致（和现在一样有数） |
| 本机 TUN，代理规则让中继直连 | 物理直连 | 代理从物理网卡直连，多一次本机转发 | 基本一致，**乙在这里有收益** |
| 本机 TUN，规则让中继走节点 | 物理直连 | 本机 → 节点 → 中继 | **不一致**，可能差几倍。例如中继 X 物理上 10 毫秒、规则让它走往返 150 毫秒的节点；中继 Y 物理上 30 毫秒、规则直连。乙会选 X，实际约 150 毫秒以上，该选的是 Y |
| 全隧道 VPN | 物理直连（绕开 VPN） | 经 VPN | **不一致**。今天这里作废、退回估计，改成乙后报一个错的数，是倒退 |
| VPN 开着"阻断隧道外流量" | 物理网卡连不出去 | 经 VPN | 全部 `down`，服务端按"全 `down` 时忽略"退回估计；只放行局域网时，局域网中继测通、公网中继 `down` 被排除，而真实连接经 VPN 未必到得了局域网中继 |
| 路由器透明代理 | 绑网卡没用，路由器照样接住 | 路由器按规则发出 | 和现在一样靠 2 毫秒、fake-ip 规则作废（路由器做 fake-ip 时，物理网卡 DNS 就是路由器，给的也是假地址） |
| 中继在物理路径上被封、经节点能通 | `down` | 经节点能通 | 被服务端从这台设备的候选里去掉；还能选别的中继，不致命 |

所以乙的数只描述"物理网络上离中继多远"。中继流量本来就走物理网卡时它就是真实值；代理把中继交给节点、或者有全隧道 VPN 时，它描述的是一条真实连接不走的路。客户端分不出这两种情况（§2）。

### 3.3 和原则的关系

P-2 要求规则要么不管开不开 TUN 都成立，要么能判别清楚。乙两头都不满足：它的数只在中继直连时成立，而直连还是走节点由代理规则决定，客户端看不到。要补上"判别"，就得再开一条走系统路由的连接，核对两条路是不是一样快（§7 方案丁），而这条核对连接用的正是甲的机制，有了它乙那一半就多余了。

### 3.4 改动量

- **解析**：`ice/dns.rs` 是 tokio 异步（`tokio::net::UdpSocket`），测速线程是阻塞的 `std` 线程（`probe.rs` 开头注释：放进心跳的单线程运行时会拉长计时）。复用只有两条路：一是在 `dns.rs` 加一个阻塞版 `ask`（`std::net::UdpSocket` 加读超时，约 40 行，把 `query`、`reply_to`、`answers` 改成 `pub(crate)` 复用）；二是在测速线程里起一个单线程运行时去 `block_on`，这违反 `client/AGENTS.md` 的 Tokio 规则（不在库里藏运行时）。
- **假地址的语义**：`dns.rs` 的 `reachable()` 会把 `198.18/15` 过滤掉，答案全是假地址时返回空。测速照搬的话，路由器 fake-ip 环境下中继解析不出地址，3 次都失败进 `down`，服务端会把这些中继当成连不上排除掉。必须另外区分"只解析出假地址"，让它整轮作废。
- **绑地址**：`std::net::TcpStream` 不能先绑再连，要给 `libs/leapgate` 加 `socket2` 依赖（`hbb_common` 用着 0.3，但没有重新导出），或者用 `windows` crate 手写；还要定绑哪块网卡、每个地址族选哪个地址。网卡选得和系统路由不同时（用户手调过网卡跃点数），量的就是另一块网卡。
- **作废规则**：绑了物理地址后"本地地址不在物理网卡上"恒为假，fake-ip 规则挪到解析阶段，2 毫秒规则保留。
- **合计**：非测试代码约 +120~150 行，测试约 +60 行，新增一个依赖项；服务端不动。

### 3.5 结论

不推荐。它在"TUN + 中继直连"这一种情况下有收益，代价是在"走节点"和"全隧道 VPN"两种情况下把现在的"不报"变成"报错的数"，改动也比甲大。

## 4. 方案甲（推荐）：和真实中继连接同路，量到中继关连接

### 4.1 依据：hbbr 怎么处理"不是 `RequestRelay` 的首帧"【读码】

`relay_server.rs` 的 `make_pair_`（上游 `rustdesk-server@873230e` L461~500；leapgate-server `d564e30` 里这个函数和上游逐字相同，`server/LEAPGATE.md` §1 写明 hbbr 不改逻辑；官方发布的 1.1.15、1.1.16 也逐字相同，1.1.15 所带 `hbb_common` 对长度为 0 的帧解码方式也一样）：

- 连上后最多等 30 秒读第一帧；收到前不发任何数据、不关连接。
- 第一帧能解析成 `RendezvousMessage`、但不是 `RequestRelay`，或者根本解析不了，函数直接返回，连接随之关闭：不打日志、不查 key、不进 `PEERS`、不计流量。
- 只发 1 个字节 `0x00` 就是一个长度为 0 的帧：`BytesCodec::decode_head` 读出长度 0，`decode_data(0)` 返回空帧【读码：两条 leapgate-cardo 线的 `bytes_codec.rs` 相同】；空字节解析出默认的 `RendezvousMessage`，`union` 为空，走上面"直接返回"那条路。
- 不用 `RequestRelay` 当探测帧：key 不对时 hbbr 打 warn；key 对、`uuid` 非空时会在 `PEERS` 里挂 30 秒并打 info 日志。
- `handle_connection` 只对来自回环地址的连接走控制台分支，其余先查 `BLOCKLIST` 再进 `make_pair_`【读码】。

所以对 hbbr 来说，"连上、保持安静、收到 1 个字节后关连接"是一个确定的行为：从发出到收到关连接（FIN）正好是一个往返。

### 4.2 实测【实测：2026-10-25，维护者台式机，开着 mihomo fake-ip TUN，有线网卡】

测试中继是 leapgate-server 自带的原版 hbbr（两个端口各测 3 次以上），物理路径往返约 230~260 毫秒。测试脚本放在会话临时目录，不进仓库。

| 连法 | 握手耗时（毫秒） | 发出 `0x00` 到关连接（毫秒） |
|---|---|---|
| IP 字面量（本机路由表本来就不把这台送进 TUN），不绑地址 | 222~276 | 231~259 |
| IP 字面量，绑物理网卡地址 | 231~260 | 236~272 |
| 通配 DNS 域名（系统解析得 `198.18.0.105`，进 TUN），连上立刻发 | 14~35（TUN 在本机完成） | 738~1560 |
| 同上，连上后等 0.6 秒再发 | 同上 | 230~245 |
| 同上，连上后等 1.5 秒再发 | 同上 | 237~260 |
| 同一域名、leapgate-server API 端口上的 HTTP 长连接，稳态请求往返（对照） | — | 247（IP 字面量直连 229~256） |

- 每次都收到干净的关连接（读到 EOF），hbbr 没有发任何数据。
- 连上立刻发时，多出来的 500~1300 毫秒是代理连上游（以及首次解析域名）的时间；等代理连好再发，量到的就是真实路径的一个往返。
- 这台中继在本机代理里是直连还是走节点没有核实；稳态往返和物理直连一致，说明这次走的是同一条物理路径。走节点的情况没有实测（§4.6 第 3 条，§9 第 3 步覆盖）。
- 实施后用 `probe.rs` 的 `try_relay` 本身（等待 1.5 秒）再测一次：经 fake-ip TUN 两个端口 242、249 毫秒，IP 字面量 249、261 毫秒；没有 hbbr 监听的端口，经 TUN 时代理在等待期间就把连接关掉，1.5 秒判失败，IP 字面量 3 秒超时判失败。系统解析这个域名时同时返回了 `198.18.0.105` 和 `fdfe:dcba:9876::64`，印证 §4.3 要把 IPv6 的 fake-ip 段算作公网。

### 4.3 规则

每台中继每轮仍测 3 次、间隔 200 毫秒，各中继并发（不变）。每一次：

1. **解析和连接**（不变）：`check_port(host, 21117)` 后系统解析（fake-ip 下得到 `198.18.x` 照用，这正是真实连接会连的地址），按返回顺序取第一个连上的，`connect_timeout` 3 秒。
2. **等 `SETTLE`（1.5 秒）**：直连时这一步什么都不发生；经本机 TUN 或路由器透明代理时，握手是本地或路由器完成的，代理在这段时间里把上游连好。
3. **等完看一眼**：非阻塞地 `peek` 一次。连接已经关了（读到 EOF 或出错），或者已经收到数据，就判这次失败。hbbr 收到首帧前既不发数据也不关，所以这两种情况都说明对面不是 hbbr：代理连不上上游、代理规则拒绝（REJECT）、中继主机在但 hbbr 没起（上游回 RST，被代理转成关连接），都在这一步变成"这次失败"，3 次都失败就进 `down`。
4. **发 1 个字节 `0x00` 并开始计时**，读到干净的 EOF（`read` 返回 0）停表。3 秒内没读到、读到数据、读到错误（含 RST）都判这次失败。
5. 记下（发出到关连接的耗时，对端地址）。

汇总（纯函数 `summarize`）：

- 成功的取最小值，毫秒向上取整、至少 1；3 次都失败进 `down`（不变）。上报格式和取值范围（1~10000 毫秒）不变，服务端不用改。
- **作废规则只留一条**：对端是公网地址的中继，任一次在 2 毫秒内关，整轮作废、清掉旧结果、退回估计（语义和现在一样）。理由改成：真实路径至少要一个往返，2 毫秒内就关，说明关连接的不是中继，例如代理规则拒绝、本机安全软件一收到数据就断。`is_public` 里 `198.18/15` 本来就算公网；补一处：IPv6 的 fake-ip 段 `fdfe:dcba:9876::/48`（mihomo 一类 TUN 的默认段，05 §2.7 列为丢弃类）现在被当成 ULA 豁免，要比照 `198.18/15` 算公网，否则 IPv6 fake-ip 下这条拦不住。
- **删掉两条规则**：
  - "本地地址不在物理网卡上"：经 TUN 时本地地址就是 TUN 的，真实连接也是这样，不再需要拦。
  - "对端在 `198.18/15` 就作废"：fake-ip 地址进 TUN 后由代理映射回域名，正是真实路径。
- 开了 Leapgate 自己的 Socks5 代理（`Config::is_proxy()`）、WebSocket（`use_ws()`）或没配 Key 时照旧不测（不变）。

每台中继一轮约 3 ×（握手 + 1.5 秒 + 一个往返）+ 0.4 秒，约 5~6 秒，各中继并发，5 分钟一轮。每条测速连接在 hbbr 那边多挂约 1.5 秒，是一个等首帧的任务，不打日志、不计数。

### 4.4 各环境下量到的是什么

| 环境 | 握手由谁完成 | 等完后"发出到关连接"量到的 |
|---|---|---|
| 不开代理 | 中继 | 本机 → 中继，一个往返 |
| 本机 TUN，规则直连 | TUN（本机） | 代理从物理网卡到中继的一个往返【实测，§4.2】 |
| 本机 TUN，规则走节点 | TUN（本机） | 本机 → 节点 → 中继的稳态往返，就是会话实际经历的延迟【推测】 |
| 路由器透明代理 | 路由器 | 同上两行之一，取决于路由器的规则【推测】 |
| 全隧道 VPN | 中继（经 VPN） | 经 VPN 的一个往返 |
| 代理拒绝或连不上上游、hbbr 没起 | 本机或路由器 | 等待期间被关，或 3 秒内没回 → 这次失败 → `down` |

`down` 的含义也随之变对了：现在经 TUN 时握手总是本地成功，`down` 在开 TUN 的机器上从来不会出现；改后它表示"真实路径连不上这台中继"。

### 4.5 和原则的关系

甲不判断有没有开 TUN、开没开 VPN、路由器怎么代理，也不读任何代理软件的配置：测速连接和真实中继连接用同一个解析、同一条路由、同一个代理，量的就是真实路径。属于 P-2 的第一种："不管开不开 TUN 都生效"。用户什么都不用配，02 和 README §5 里"可选优化"那一列对测速不再适用。

### 4.6 已知限制

1. **依赖原版 hbbr 的行为**：非 `RequestRelay` 首帧静默关连接。上游哪天改成等到 30 秒超时，3 秒内没 EOF 就全判 `down`，服务端按"全 `down` 时忽略"退回估计，不会报假数；改成打日志，就是每台设备每 5 分钟 3 × N 行噪音。合并上游 hbbr 时要复查 `make_pair_`（写进 `server/LEAPGATE.md`，§5.3）。
2. **代理连上游超过 1.5 秒**：超出的部分会算进往返，数字偏大，方向是保守的（这台中继显得更远）。
3. **代理等收到数据才让节点去连中继**（懒连接）：会多算一次节点到中继的握手【推测；没有实测走节点的中继】。
4. **经代理时中继主机在、hbbr 没起**：代理收到上游 RST 后关本地连接，一般在 1.5 秒的等待内就发生，判这次失败。晚于 1.5 秒才发生时，会被当成 hbbr 关连接，量出一个偏小的数。服务端健康检查（从服务端直接 TCP 建连，`router/mod.rs` L563~626）会把这台判成不可达、从候选里去掉，所以不影响选路。
5. **代理收到上游的关连接后不及时关本地连接**（例如等到空闲超时）：3 秒内没 EOF，判这次失败；全部这样时服务端退回估计。mihomo 是及时的【实测】，其他代理软件【推测】。
6. **同机房的中继**（往返不到 2 毫秒）和 **fake-ip 下用域名配的局域网中继**会被 2 毫秒下限误杀，整轮退回估计，和现在一样。
7. **测的是服务进程的路径**：控制端的真实中继连接在界面进程（02 §9 第 3 条不变）。代理按进程名分流时，两者是同一个可执行文件，命中同一条规则【推测】。
8. **代理在多个节点间负载均衡**、每条连接选不同节点时，3 次里取最小，数字会偏向最快的节点。
9. 02 §9 第 6 条（系统解析没有超时）、第 7 条（IPv4 字面量中继在只有 IPv6 的网络里进 `down`）不变。02 §9 第 1、9、12 条（开代理默认没有测量、2 毫秒盲区、部分代答有害）随甲消失。

## 8. 需要维护者定的问题

**D2-3：选哪个方案。** 推荐甲；备选乙、丙见 §7。这一条要明确回复，回复前不动代码。

**D2-4：等待时长 `SETTLE`。** 推荐 1.5 秒。本机实测 0.6 秒就够（直连规则、往返约 245 毫秒的中继，代理连上游约 500 毫秒）；走节点、节点协议带 TLS 握手、节点又远时，代理连上游可能要七八百毫秒，留出余量。代价是每轮测速多几秒、每条测速连接在 hbbr 那边多挂一会儿。不回复按推荐。

**D2-5：2 毫秒下限留不留。** 推荐留（改成按"发出到关连接"算，语义仍是整轮作废）。它防的是一种看不见的坏情况：某个中间设备收到数据就断，量出来最快，服务端反而优先选它。代价是同机房中继仍被误杀（和现在一样）。备选：删掉，`summarize` 只剩取最小值和 `down`，同机房中继不再误杀。不回复按推荐。
