## 2. 协议与接口

本块**不新增 proto 字段、不新增 HTTP 接口、不新增迁移**。

- **`LocalAddr.leapgate_local_addrs` / `PunchHoleResponse.leapgate_local_addrs`**（字段号 1000，已有）开始装 IPv6 地址。`AddrMangle::encode` 编 IPv6 是 16 字节地址加 2 字节端口，共 18 字节；服务端 `MAX_MANGLED_ADDR = 18`、`MAX_LAN_CANDIDATES = 8` 不用改【读码：leapgate-cardo `src/lib.rs` `AddrMangle::encode`/`decode`；`server/src/rendezvous_server.rs` L236、L239，`handle_local_addr` L1043~1044】。`decode` 不还原 scope id，所以链路本地地址（`fe80::/10`）本来也不能用，被控端不报。
### 2.1 已排除的方案：按发起方 ID 比 UDP 注册 IP（原第 1 项）

草稿里第 1 项是这样做的：服务端用打洞请求里自报的 `leapgate_from_id`，在内存里找到发起方服务进程的 UDP 注册地址（草稿里的 `same_udp_exit`），和被控端的 UDP 注册地址比 IP，结果和原有 TCP 比较取"或"。

打洞请求不签名，`leapgate_from_id` 是发起方自报的值，服务端没法确认这条请求真的来自那台设备。会合层不签名是已定决策（AGENTS.md 第三期设计"明确不做"）。笔记 05 §6 第 1 项说的"等设备签名上线后对验签通过的设备启用"不成立：设备签名只覆盖 HTTP 上报，验过签的心跳只说明"这台设备在线"，不说明"这条打洞请求是它发的"。下面是当时的分析，留作记录。

**直接比 (a) 的门槛是"能伪造 UDP 源地址、知道 B 的 ID 的人"**，不需要真有一台和 B 同出口的设备：

1. 攻击者正常注册一台自己的设备 X，手里有 X 的 uuid 和公钥；
2. 对 B 发一次普通打洞请求，从回包的 `PunchHoleResponse.socket_addr` 拿到 B 的公网 IP；
3. 伪造源地址为 B 的 IP，发 `RegisterPk{id: X, 原 uuid, 原 pk}`：uuid 相符、公钥没变，`update_pk` 走只换 IP 的分支，X 的 `socket_addr` 变成 B 的 IP，`last_reg_time` 刷新；之后伪造 `RegisterPeer` 保持在线；
4. 发打洞请求带 `leapgate_from_id = X`：新判定为真。

B 随后把局域网候选（私网 IPv4，做了第 2 项后还有 ULA 和全局 IPv6）经服务端回给攻击者，并在通配地址上开一个 18 秒、只收一条连接的监听（做了第 2 项后是双栈）。连进监听仍要过安全握手和登录。原有的 TCP 来源比较伪造不了，所以这是新增的能力。

当时列的几种做法：

- **(a) 直接比**：只看 UDP 注册 IP。门槛如上。
- **(b) 绑定签名心跳的来源 IP**：挡不住，攻击者自己那台 X 的签名心跳和打洞请求本来就从同一个 IP 发出。
- **(c) 给打洞请求加签名**：是真正的认证，但属于会合层签名，和已定决策冲突。
- **(d) 只对有权连 B 的登录用户启用**（当时的推荐）：打洞请求的 `token` 能解析出有效账号，并且这个账号是 B 的主人（`device.user_id`），或者在某本含 B 的共享簿上有任意权限，才走 UDP 比较这一路。草稿里的实现是 `may_reach`（`auth::token_owner` 加新函数 `ab::reaches`），另把 `auth.rs` 里 `token_owner` 的错误日志改成限频（1 行）。问题在于"设备主人"这个身份：登录改绑只凭 uuid、会覆盖原主人，锁定后照样能改绑，所以 (d) 的实际门槛只是"任一账号持有者 + 知道 B 的 uuid + 能伪造 UDP 源地址"；未登录、对 B 无权限的控制端还得靠用户配置"会合服务器的 TCP 也走直连"这条环境规则。

**排除的原因**：这套做法依赖不认证的 `leapgate_from_id`；(d) 又依赖只凭 uuid 就能改绑的设备主人；用不上的情况还要用户配环境规则。维护者对 P-2 的原则是不依赖身份、不假定运行环境、不要用户配规则（README §1.1）。改由 04 块 §2.5 的 UDP 出口证明解决：比同一种协议的观测，由控制端证明自己在那个 UDP 地址上收得到包；不需要 `leapgate_from_id`、令牌或地址簿查询，上面那条伪造构造也不成立（伪造源地址的人收不到 token）。

`leapgate_from_id` 仍然要做，只给 02 块的路由第二级用，由 02 块在第 2 批加（02 §4.5 挂钩 2）。

### 4.1 `libs/leapgate/src/lan.rs`

**谁用这些改动**：网卡枚举改成双地址族、`Nic` 加 IPv6 字段、`has_gateway` 拆成 `has_gateway_v4`/`has_gateway_v6`、`is_physical` 参数改成 `IpAddr`，除了本块的 IPv6 候选，02 块测速的 `physical_snapshot` 要判 IPv6 本地地址，04 块的 `physical_global_v6`（开 TUN 时 IPv6 打洞绑物理网卡，04 §4.4）要用物理网卡的全局 IPv6 和地址分类函数。P-4 已定（ULA + 同 /64 全局地址），下面按这个范围写：`select_candidates` 追加 IPv6、控制端收 IPv6 候选和按 /64 筛（`peer_candidates`、`connect_candidates` 的筛选和 IPv4 先手）、`listen_dual`（连同 `socket2` 依赖）、`src/server.rs` 那条语句（§4.3）。

**网卡枚举 `nics()`（Windows）**

- `Nic` 加字段：`description: String`（`IP_ADAPTER_ADDRESSES_LH.Description`）、`ipv6: Vec<Ipv6Addr>`（只收 `DadState == IpDadStatePreferred` 的单播地址，丢掉链路本地）。
- `has_gateway` 拆成 `has_gateway_v4` / `has_gateway_v6`（`FirstGatewayAddress` 里按地址族分别看有没有非未指定地址）。**IPv4 候选照旧只看 `has_gateway_v4`**，现有 IPv4 行为不变（只有 IPv6 网关的网卡不会因此多出 IPv4 候选，"要求有网关"对 vEthernet 和仅主机网卡的排除也不被削弱）。
- `windows` crate 的 feature 不用加（`SOCKADDR_IN6`、`NL_DAD_STATE` 在已开的 `Win32_Networking_WinSock` 里）【推测：按 windows 0.61 的模块划分，编译时确认】。

**网卡分类 `Nic::is_virtual()`**：现有规则（IfType 23/24/53/131；接口名以 `tun`/`utun` 开头或含 `mihomo`/`wintun`）不变，再加一条：`description` 或 `name` 转小写后含下列任一关键字就算虚拟网卡。

| 类别 | 关键字 | 说明 |
|---|---|---|
| 代理 TUN | `meta tunnel` | mihomo 的 TUN 网卡描述（笔记 05 §3.3） |
| VPN / 隧道驱动 | `wintun`、`wireguard`、`tailscale`、`zerotier`、`tap-windows`、`openvpn`、`vpn` | 取自笔记 05 §3.3 那张关键字表 |
| 虚拟机宿主侧网卡 | `vmware virtual ethernet`、`virtualbox host-only`、`vmnet` | 宿主机给虚拟机用的网卡，不是出口 |

- **不加 `hyper-v`**：Hyper-V 外部虚拟交换机下，宿主机真正上网的就是 `vEthernet (…)`（描述 `Hyper-V Virtual Ethernet Adapter`，有默认网关），物理网卡反而没有 IP。Hyper-V 内部交换机和 WSL 的 `vEthernet` 没有默认网关，现有规则已排除。
- **不加 `virtio`、`vmxnet`、`hyper-v network adapter`** 这类虚拟机里的网卡：Leapgate 装在虚拟机里时那就是唯一的真实网卡。
- **VPN 网卡一律排除，不降权**。被控端的候选只代表"局域网里怎么找到我"；经 VPN 回家的控制端（`client/LEAPGATE.md` §3.4）连的是被控端的物理局域网地址，不需要被控端报 VPN 地址。控制端一侧，落在这些网卡上的连接改用 800 ms 短握手上限，和现在的 Wintun 网卡一致（§3.4 给"经 WireGuard/Tailscale 回家"留的那条路）。

**地址分类**（新增三个私有函数）：

- `excluded_v6(ip)`：回环、未指定、链路本地、组播、`::ffff:0:0/96`（v4 映射地址），以及常见 TUN 软件的默认 IPv6 段 `fdfe:dcba:9876::/48`【推测：取自 mihomo / sing-box 文档的默认值；TUN 网卡本身已被 `is_virtual` 排除，这条只是兜底，端到端第 3 项核对】。
- `is_ula(ip)`：`octets()[0] & 0xfe == 0xfc`。
- `is_global(ip)`：`segments()[0] & 0xe000 == 0x2000`（`2000::/3`）。
- 被控端只报 ULA 和全局单播，且都不在 `excluded_v6` 里。

**`is_physical(nics, ip: IpAddr)`**：参数从 `Ipv4Addr` 改成 `IpAddr`，IPv6 地址在某块在线、非虚拟网卡的 `ipv6` 里就算物理。`handshake_timeout`、`controller_bind_addr` 跟着改调用；02 块的 `physical_snapshot` 复用它。

**被控端选候选 `select_candidates`**：

1. IPv4 部分完全照现在（`sock_local` 是物理地址时排第一，再按"有线优先、链路速度从高到低"排其他物理网卡的地址，用 `has_gateway_v4` 过滤）。
2. **至少有一个 IPv4 候选时**才追加 IPv6。先排除虚拟网卡和 `excluded_v6` 里的地址，再按同样的网卡顺序取，每块合格网卡（在线、非虚拟、`has_gateway_v6 || has_gateway_v4`）最多取 1 个全局地址、1 个 ULA（各取枚举到的第一个），**全局地址排在 ULA 前面**。IPv6 最多 4 个，总数仍不超过 `MAX_CANDIDATES = 8`（IPv4 先占）。端口都用 `sock_local` 的端口。
   - 网卡用"v6 或 v4 网关任一"：只发 ULA 前缀、不发 IPv6 默认路由的局域网（路由器没有 IPv6 上游）里，网卡没有 IPv6 网关，但 ULA 照样能在局域网里用。
   - "先排除再设上限"：TUN 的 IPv6 不占名额（笔记 05 §3.1 里 UU 的上限被 TUN 地址占掉一个）。
3. 为什么要求先有 IPv4 候选：`handle_intranet_` 的挂钩用 `lan.first()` 当 `LocalAddr.local_addr`（给原版控制端用），它必须是 IPv4；IPv6 只排在后面，就不用改那行挂钩【读码：`rendezvous_mediator.rs` L838~839】。代价：没有物理 IPv4 网卡的纯 IPv6 局域网不报候选，照上游走。
4. `sock_local` 一定是 IPv4：上游只在连会合服务器的那条连接是 IPv4 时才调 `handle_intranet_`（L780）。`sock_local` 是 IPv6 时返回空的分支保留。

**监听**：

- `listen_addr` **不改**：候选里有 IPv6 时 IP 必然和 `sock_local` 不同，照旧返回 `0.0.0.0:端口`。
- 新函数 `pub async fn listen_dual(candidates: &[SocketAddr], addr: SocketAddr) -> Option<TcpListener>`：只有 `candidates` 里有 IPv6、且 `addr` 是 `0.0.0.0:端口` 时才动手，用 socket2 建 IPv6 TCP socket，`set_only_v6(false)`、`set_reuse_address(true)`、bind `[::]:端口`、listen（backlog 128，和 hbb_common 的 `DEFAULT_BACKLOG` 一致）、设非阻塞，转成 tokio 的 `TcpListener` 返回 `Some`。其余情况、或任何一步失败（打一条 info 日志）返回 `None`，由调用点照旧 `new_listener(addr, true)` 绑 `0.0.0.0:端口`，IPv4 候选照样能用。没有 IPv6 候选时行为和现在逐字节相同。
- **不用 hbb_common 现成的 `tcp::listen_any`**：它在 Windows 的 IPv6 分支里不设 `SO_REUSEADDR`【读码：leapgate-cardo `src/tcp.rs` `listen_any` L271~】，同端口刚断开的连接还在 TIME_WAIT 时大概率退回 IPv4，IPv6 候选会悄悄失效。
- 双栈 socket 上 IPv4 连接的本地、对端地址是 `::ffff:a.b.c.d`；`create_tcp_connection` 一进来就 `try_into_v4`，白名单和准入照旧按 IPv4 算【读码：`src/server.rs` L226】。
- `libs/leapgate/Cargo.toml` 加 `socket2 = "0.3"`（和 hbb_common 同一主版本，`Cargo.lock` 里已有 0.3.19，不加新包；0.3 的 API 是 `Domain::ipv6()`、`Type::stream()`、`into_tcp_listener()`，和 0.4/0.5 不同）。

**控制端收候选 `peer_candidates`**：除私网 IPv4 外，再收 ULA 和全局单播 IPv6（同一组判法，`excluded_v6` 里的一律丢），端口非零、去重、最多 8 个。v4 映射地址（`::ffff:8.8.8.8`）不在这两类里，会被丢掉，堵住"借 IPv6 编码塞一个公网 IPv4"。

**控制端连候选 `connect_candidates`**：

- 签名改为 `candidates: &mut Vec<SocketAddr>`。枚举完本机网卡后（现在就有这一步），先就地删掉不在本机局域网里的全局 IPv6 候选：保留条件是它的前 64 位和本机某块物理网卡（`is_physical` 意义下）的某个全局地址相同；本机网卡列表为空时全局 IPv6 候选全删。ULA 和私网 IPv4 不做这一步。理由：控制端不能被恶意对端或服务端诱导去连任意公网地址，"和我同一个 /64"把威胁面限制在和私网 IPv4 相同的范围。就地删除是为了让随后的 `lan_fallback` 看到实际试过的列表。
- **IPv4 先手**：`race` 里每个候选的尝试前按类别等一个固定的先手时间，私网 IPv4 不等，全局 IPv6 等 50 ms，ULA 等 100 ms（常量 `V6_GLOBAL_DELAY`、`V6_ULA_DELAY`，按地址类别算，不记任何状态）。原因：
  - Leapgate 没有 ICE 那样的会话中换路径，会话所用的地址在会话中消失（例如路由器撤掉 ULA 前缀，笔记 05 §3.2、§7 第 4 项）会直接断开会话。私网 IPv4 最稳，全局地址其次，ULA 在一些路由器上会反复出现又消失。
  - 被控端的监听只收第一条连接，谁的 TCP 先到谁赢；局域网里 TCP 建连只要几毫秒，50 ms 的先手足够让能通的 IPv4 先到。IPv4 不通（例如被防火墙挡住）时最多晚 50~100 ms 改用 IPv6。
- 剩下的全部并发，TCP 连接等待 1 秒、握手上限 3 秒 / 800 ms 照旧。IPv6 局域网地址有同网段的直连路由（/64），比 TUN 装的默认路由更具体，不绑源地址时从物理网卡出去（和笔记 04 §3.3 IPv4 的结论同理；UU 的日志里 `0.0.0.0` 的 socket 发往局域网地址也是这样，笔记 05 §3.1 第 2 条）【推测，端到端第 2 项确认】。

**`handshake_timeout`**：扩展到 IPv6（本地端是物理网卡的 IPv6 地址才算物理）。TUN 接住的 IPv6 连接本地端是 TUN 的地址，拿 800 ms。

`local_candidates_async`、`encode` 不变。

### 4.4 共存 ID 冲突：leapgate-cardo 客户端线

**前置步骤（先做，结论写回本节再动代码）**：笔记 02 §1.8 是读码推出来的，没实测。在一台 Windows 测试机（可以是虚拟机）上同时装官方 RustDesk 和 Leapgate，两边指向同一个测试用 leapgate-server：

1. 两个界面显示的 ID 是否相同（`get_auto_id` 取 `mac_address::get_mac_address()` 的第一块非回环网卡，装了虚拟网卡时可能不是同一块）。
2. 相同时，从第三台机器连这个 ID 若干次，看是否时而连到 RustDesk、时而连到 Leapgate（连到公钥对不上的一端会弹"未加密连接"确认），服务端日志里这个 ID 是否有 `update_pk` 和来回的地址变化。

ID 相同即确认冲突。ID 不同也照下面实现（换一台网卡顺序不同的机器照样会撞），把观察到的现象写进本节。

**2026-10-27 前置核查的结果（只读，没有另装原版）**：在维护者的台式机上核对，Leapgate 便携版的 ID 和按本机一块网卡的 MAC 用上游算法算出的默认 ID 完全一致。那块网卡当时是断开状态：`mac_address` 不看连接状态，按 `GetAdaptersAddresses` 的顺序取第一块有 MAC 的网卡。同机的原版 RustDesk 把 ID 加密存成 `enc_id`，日志里也不记自己的 ID，没法直接比对。维护者 2026-10-26 定了开发期间不做多轮测试，所以没有另起一份原版去做上面第 1、2 条。两边调用的是同一个函数，在同一组网卡上第一次生成时必然相同；原版的 ID 如果生成在网卡变动之前，或被 `UUID_MISMATCH` 换成了随机 ID，就会不同。按上一段照常实现，冲突本身留给 §6 端到端第 4 项在统一验收时确认。

**改动**【读码：`src/config.rs` `Config::get_auto_id` L1058~1082，`id &= 0x1FFFFFFF;` 在 L1075；`Config::get_id` L1212~1221】：

- 新文件 `src/leapgate_id.rs`（leapgate-cardo 自有）：`pub(crate) fn salt(mac_id: u32) -> u32`，`sha256(b"leapgate-auto-id\0" ‖ mac_id.to_le_bytes())` 取前 4 字节按小端转 `u32`，返回 `(h & 0x0FFF_FFFF) | 0x1000_0000`。结果固定 9 位（268435456~536870911），和同机原版 ID 相撞的概率约 2^-28。用已有的 `sha2`，不加依赖。单元测试放在同一文件。
- `src/config.rs` `get_auto_id` 里 L1075 之后加 2 行：
  ```rust
                  // leapgate: salted, so Leapgate and RustDesk on one machine do not take the same id
                  let id = crate::leapgate_id::salt(id);
  ```
  哈希的输入是上游算出的 `id`（来自 MAC 后 4 字节），和直接哈希 MAC 等价，这样只加行、不改上游的循环。
- `src/lib.rs` 加 `mod leapgate_id;` 1 行。
- 只放客户端线：服务端不生成 ID。不是 proto 改动，不受"两条线各放一份"的约束。

**影响范围**：

- 只影响**首次生成 ID** 的设备（`Config::get_id` 发现 `id` 为空时才调 `gen_id`）。已有 ID 的 Leapgate 设备不变。
- `allow-hostname-as-id` 打开时走主机名，不受影响（这个选项默认关，Leapgate 不打开它）。
- 已装 Leapgate、又要和原版指向同一个服务器的机器，要手动让 Leapgate 重新生成 ID：停服务，删掉服务进程配置文件里的 `id` 和 `enc_id` 两项，再启动。leapgate-server 不支持界面上的"修改 ID"（它走 TCP 上的 `RegisterPk`，leapgate-server 回 `NOT_SUPPORT`，L895）。写进客户端使用说明，不写代码。另一个办法见 01-上报与认证.md §9（对这台机器 `device key reset --forget` 后让 Leapgate 重新注册；默认的 `device key reset` 只清锁定、保留库里原版那把公钥，不够）。
- 和设备签名的关系：公钥锁定只在原版发 `RegisterPk` 时起作用（第一次连这台服务器、IP 变化、内存条目被淘汰），同 IP 常驻时原版只发 `RegisterPeer`，冲突照旧；加盐后两边 ID 不同，锁定各管各的。

## 6. 测试

本块没有服务端测试（不改服务端代码）；同网判定的测试在 04 §6.1。

**客户端单元测试**（`lan.rs`，用构造的网卡列表）：

1. 有线网卡带全局、ULA、链路本地三个 IPv6 → 候选是 IPv4 在前，再跟全局、ULA 各一个，没有链路本地。
2. 只有 IPv6、没有 IPv4 候选 → 空。
3. 网卡有 IPv4 地址、只有 IPv6 网关 → 不出 IPv4 候选（`has_gateway_v4` 规则不变）。
4. 描述为 `Meta Tunnel`、IfType 6 的网卡不出候选；描述 `Hyper-V Virtual Ethernet Adapter`、有网关的网卡出候选；`VMware Virtual Ethernet Adapter for VMnet8` 不出候选。
5. `peer_candidates`：收 ULA 和全局 IPv6，丢 `::ffff:8.8.8.8`、`fe80::1`、`ff02::1`、`::1`。
6. 全局 IPv6 候选按 /64 筛：和本机物理网卡同前缀的留下；不同的，以及本机网卡列表为空时，全删；ULA 不受影响。
7. 先手顺序（`race` 注入尝试函数、tokio 暂停时钟）：IPv4、全局、ULA 都立即成功 → IPv4 胜出；IPv4 失败 → 全局胜出。
8. `listen_dual`：候选含 IPv6、地址 `0.0.0.0:0` 时返回 `Some`，分别从 `127.0.0.1` 和 `::1` 连进来都能 accept；候选不含 IPv6 时返回 `None`（Linux 和 Windows 都能跑，不加平台门控）。

leapgate-cardo：`leapgate_id::salt` 一条测试，固定输入的输出落在 9 位范围内、和输入不同。

不测：网卡枚举本身（系统调用）、关键字表逐项、排序的每种组合。

**端到端验收**（维护者，两台装了 Leapgate 的 Windows 在同一局域网，连同一个 leapgate-server）。判据用"`conn_attempt` 的列 + 控制端日志"两条一起：局域网候选胜出时控制端直接返回，**不打**上游的 `used to establish … connection` 那行【读码：`src/client.rs` L1371~1378 早返回】，所以看 `lan.rs` 的 `LAN candidate … won`。

1. **同网判定**：移到 04 §6.3 第 8 条（UDP 出口证明）。下面第 2、3 条需要同网判定成立：两台不开代理，或者两台到会合服务器的 TCP、UDP 至少有一种出口相同。
2. **IPv6 候选**（两台都有 ULA 或同一 /64 的全局地址）：被控端日志 `Server listening on: [::]:<端口>`；正常情况下控制端日志仍是 IPv4 候选胜出（先手）。在被控端临时加一条 Windows 防火墙入站规则，阻止 Leapgate 程序接受来自私网 IPv4 段的 TCP，再连一次，控制端日志应为 `LAN candidate [<IPv6>]:<端口> won`，`outcome = 'direct_lan'`、`relay_req_count = 0`。测完删掉规则。
3. **TUN 回归**：两台都开 TUN、不配任何规则再连。同网判定成立时（`signal = 'fetch_local_addr'`），判据是控制端日志 `LAN candidate <私网地址>:<端口> won`、`outcome = 'direct_lan'`、没有 `relay_only` 行；判不出时属于 04 §2.5.8 的缺口，记下两台到会合服务器的 UDP 各走哪个出口。顺带用 `Get-NetIPAddress` 记下 TUN 网卡的 IPv6 地址，核对 `excluded_v6` 里的常量。
4. **共存 ID**：前置实测见 §4.4。代码合入后，在一台已装原版 RustDesk 的机器上新装 Leapgate（配置目录里没有旧 ID），两边 ID 不同、同时在线，从第三台分别连两个 ID，各自连到对应的程序、不弹"未加密连接"。

## 7. 明确不做

- 按发起方 ID 比 UDP 注册 IP、按设备主人或地址簿权限放行（原第 1 项，§2.1 已排除的方案）；打洞请求签名属于会合层签名，和 RegisterPk/RegisterPeer 签名一起留到退出兼容前单独定。
- 服务端同时记两个地址族的注册地址、跨地址族比较。
- 新增 `conn_attempt` 列记"同网是哪条规则判的"：用 `a_ip <> b_ip` 就能区分（04 §2.5.4）。
- 纯 IPv6 局域网（没有物理 IPv4 网卡）的候选；IPv6 链路本地候选；UDP 候选。
- 会话中换路径（候选地址消失时切到别的候选）：属于笔记 05 §6 第 8 项，第四期以后；本块只用 IPv4 先手降低风险。
- 按 VPN 网卡降权报候选（一律排除）；按描述排除 Hyper-V 网卡。
- 自动迁移已有设备的 ID；支持界面上的"修改 ID"。
- macOS 客户端（第一阶段只做 Windows）。
- 笔记 05 §6 其他项（UDP 打洞前置障碍、同网判定的 UDP 出口证明、NAT 类型、开 TUN 时 IPv6 打洞绑物理网卡、WebRTC/ICE 评估）在 04 块。

## 8. 维护者的决定

全局清单在 README.md §1.1，这里只列和本块有关的。

- **P-2**：维护者定的原则是不依赖身份、不假定运行环境、不要用户配规则。本块原来的第 1 项不满足，已移到 §2.1"已排除的方案"；同网判定改由 04 块 §2.5 的 UDP 出口证明解决（机制待维护者确认）。本块因此不再改服务端。
- **P-4 已定（2026-10-23）：ULA + 和控制端某块物理网卡同一个 /64 的全局地址，私网 IPv4 优先。** 理由：很多家用路由器只下发全局前缀、不发 ULA，只收 ULA 在这类网络里等于没做；"同一个 /64"把全局地址限制在控制端自己所在网段，威胁面和私网 IPv4 一样。代价：`src/server.rs` 一条语句改成 `match`（偏离"不改调用点"）；`libs/leapgate` 加 `socket2 0.3` 依赖（锁文件里已有）；双栈 bind 在同端口刚断开的连接上能否成功没实测（失败退回 IPv4 监听）；ULA 不稳定的网络里会话可能因地址消失断开（靠 IPv4 先手、全局优先于 ULA 缓解，§4.1）。

**按推荐默认、不单列**：共存 ID 加盐按笔记 02 §3 问题 8 的推荐（先实测，再加盐，§4.4）。

## 9. 已知限制和风险

- **同网判定的限制**在 04 块：误判（共用 CGNAT 公网 IP 的两户人家，04 §9 第 14 条）、判不出（两边 UDP 都被代理且出口不同，04 §2.5.8）、控制端没有 token 时只比 TCP（04 §2.5.6）。
- **被控端前提**：原版被控端开 TUN 仍修不了（§5）。被控端连会合服务器的那条连接是 IPv6 时，上游不调 `handle_intranet_`，没有候选（上游行为）。
- **IPv6 候选的暴露面**：按 P-4 定下的范围，被控端在局域网路径里会把全局 IPv6 地址回给发起方，并在双栈 `[::]:端口` 上监听 18 秒。家用路由器的 IPv6 防火墙放行入站时，这个监听在 18 秒内从公网也连得到，只收第一条连接、不校验对端 IP（上游原样）；连进来仍要过安全握手和登录，和上游 IPv6 打洞路径同级。
- **ULA 不稳定**：路由器反复撤销、下发 ULA 前缀时，落在 ULA 上的会话会在地址消失时断开（Leapgate 没有会话中换路径）。IPv4 先手和全局优先于 ULA 让这种情况只在 IPv4 和全局地址都不通时发生。
- **双栈监听没实测**：Windows 上在刚断开的连接端口上 bind 双栈 `[::]:端口` 能否成功是【推测】；失败时退回 IPv4 监听，那次 IPv6 候选不可用。端到端第 2 项会暴露这个问题。
- **TUN 的 IPv6 段常量**是【推测】，端到端第 3 项核对；TUN 网卡本身已被 `is_virtual` 排除，常量不对的后果有限。
- **描述关键字可能误伤**：描述里含 `vpn` 等字样的真实网卡会被排除，后果是少一个候选、可能回落中继。关键字不覆盖的虚拟网卡会多出一个连不通的候选，并发数多一个。
- **共存 ID**：结论依赖前置实测。已有 ID 的 Leapgate 设备不受加盐影响，迁移后和原版指向同一服务器时要按 §4.4 手动重新生成。`mac_address` 取到的第一块网卡在装了虚拟网卡的机器上可能变化，变化时上游的默认 ID 本来就会不同。
