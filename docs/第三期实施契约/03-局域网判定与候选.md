> 代码锚点基线：porta-client `6bb19b190`、porta-server `d8403ad`、porta-cardo 客户端线 `df76a0c` / 服务端线 `1a46681`；上游对照 `rustdesk@bd92623`、`rustdesk-server@873230e`。

## 1. 目标与范围

第三期第一项（`client/PORTA.md` §3，已合入）让局域网路径在开 TUN 代理的机器上也能用，但它要先过服务端的同网判定，候选只有 IPv4，网卡分类只看接口名和 IfType。本块补四件事：

| # | 做什么 | 依据 | 状态 |
|---|---|---|---|
| 1 | **同网判定加一路 UDP 比较**：服务端用打洞请求里的发起方 ID 找到发起方服务进程的 UDP 注册地址，和被控端的 UDP 注册地址比 IP，结果和现有比较取"或"；新加的这一路只对有权连被控端的登录用户生效 | 笔记 05 §5 第 1 行、§6 第 1 项 | 做不做、信任模型选哪种见 P-2（推荐做，信任模型 (d)） |
| 2 | **局域网候选带上 IPv6**（ULA 和同一 /64 的全局地址） | 笔记 05 §3.2、§6 第 2 项 | 范围见 P-4（推荐 ULA + 同 /64 全局地址） |
| 3 | **网卡分类补"描述"判断**，写清虚拟机网卡、VPN 网卡怎么处理 | 笔记 05 §3.3、§6 第 4 项 | 做 |
| 4 | **原版和 Porta 同机共存时的 ID 冲突**：Porta 首次生成 ID 时加盐 | 笔记 02 §1.8、§3 问题 8 | 按笔记推荐默认，先实测 |

第 1 项要修的场景：路由器透明代理只代理 TCP。控制端的打洞请求走 TCP，服务端看到代理出口 IP；被控端用 UDP 注册，服务端看到家宽 IP。现有判定拿两者比，判"不同网"，局域网路径根本不开始。第 1 项只决定"要不要下发局域网候选"，能不能连由客户端实测（多候选并发 + 握手校验），判错的代价是晚一两秒回落。UU 的解密日志说明局域网直连不该依赖 TCP 路径（笔记 05 §3.2）；第 2 项的 IPv6 候选也挂在同网判定上，所以第 1 项和第 2 项一起做才有完整收益。

第 2 项和第 1 项同等优先：UU 两次局域网会话最终都是 IPv6 host 对（笔记 05 §1、§3.2）。和 Porta 现有的 IPv6 打洞（`handle_intranet` 里的 `start_ipv6`，UDP，需要会合服务器有 IPv6、两端开 IPv6 打洞）相比，IPv6 局域网候选不依赖服务端的 IPv6、能用 ULA（唯一本地地址，`fc00::/7`，只在本地网络有效，不受 IPv4 网段撞号影响）、走 TCP【读码：`client/src/rendezvous_mediator.rs` `handle_intranet` L762~779】。

第 3 项不改变 Wintun 类 TUN 的结果（常见 TUN 代理的网卡 IfType 53、地址在 `198.18.0.0/15`，现版已排除【读码：`lan.rs` `Nic::is_virtual`、`excluded_ip`】），是给不用 Wintun、地址也不在这些网段里的代理和 VPN 软件兜底。

**依赖和顺序**（README.md 的实施顺序）：本块只依赖第 0 步的合并 proto 提交（`PunchHoleRequest.porta_from_id = 1000`），在第 1 批，和 01 块并行。02 块的 `lan.rs` 改动（`physical_snapshot`）排在本块之后，复用本块扩展到 IPv4/IPv6 的 `is_physical`；02 块复用本块加的服务端 `a_id` 行和客户端 `porta_from_id` 挂钩。本块不读 01 块的任何内存字段（信任模型 (d) 读的是已有的令牌、设备、地址簿表，不需要 `Peer.porta_hb`）。

### 2.1 信任模型（第 1 项必须看）

打洞请求不签名，`porta_from_id` 是发起方自报的值，服务端没法确认这条请求真的来自那台设备。会合层不签名是已定决策（AGENTS.md 第三期设计"明确不做"）。笔记 05 §6 第 1 项说的"等设备签名上线后对验签通过的设备启用"不成立：设备签名只覆盖 HTTP 上报，验过签的心跳只说明"这台设备在线"，不说明"这条打洞请求是它发的"。

**直接比 (a) 的门槛是"能伪造 UDP 源地址、知道 B 的 ID 的人"**，不需要真有一台和 B 同出口的设备：

1. 攻击者正常注册一台自己的设备 X，手里有 X 的 uuid 和公钥；
2. 对 B 发一次普通打洞请求，从回包的 `PunchHoleResponse.socket_addr` 拿到 B 的公网 IP；
3. 伪造源地址为 B 的 IP，发 `RegisterPk{id: X, 原 uuid, 原 pk}`：uuid 相符、公钥没变，`update_pk` 走只换 IP 的分支，X 的 `socket_addr` 变成 B 的 IP，`last_reg_time` 刷新；之后伪造 `RegisterPeer` 保持在线；
4. 发打洞请求带 `porta_from_id = X`：新判定为真。

B 随后把局域网候选（私网 IPv4，做了第 2 项后还有 ULA 和全局 IPv6）经服务端回给攻击者，并在通配地址上开一个 18 秒、只收一条连接的监听（做了第 2 项后是双栈）。连进监听仍要过安全握手和登录。原有的 TCP 来源比较伪造不了，所以这是新增的能力。和 B 共用出口的人（同一 CGNAT 公网 IP）在原有判定下本来就能做到，不算新增。

几种做法：

- **(a) 直接比**：只看 UDP 注册 IP。门槛如上。
- **(b) 绑定签名心跳的来源 IP**（草稿里的备选）：挡不住，攻击者自己那台 X 的签名心跳和打洞请求本来就从同一个 IP 发出。不再列。
- **(c) 给打洞请求加签名**：是真正的认证，但属于会合层签名，和已定决策冲突。不在第三期。
- **(d) 只对有权连 B 的登录用户启用（推荐）**：打洞请求的 `token` 能解析出一个有效账号（`auth::token_owner`，账号 `status = 1`），并且这个账号是 B 的主人（`device.user_id`），或者在某本**共享簿**上有任意权限、而这本簿里有 B，才走 UDP 比较这一路；否则只用原有的 TCP 比较。名义上的门槛是"持有这类账号的令牌、并且能伪造 UDP 源地址的人"；登录改绑让"B 的主人"这个身份不难拿到，实际门槛见下面第三条。

(d) 的细节和剩余风险：

- **不算个人簿**：任何登录用户都能往自己的个人簿里加任意 ID，算上它就等于没有门槛。
- 对某本共享簿有读写或完全控制权限的人，能把任意 ID（包括 B）加进这本簿，从而对 B 满足条件。这些人是管理员用命令行明确授权的。
- `device.user_id` 在登录时绑定，前提是登录请求里的 uuid 和 `peer` 表相符（`server/PORTA.md` §11）；知道 B 的 uuid 的人（明文心跳和 UDP 注册里能嗅到）用自己的任一账号登录、自报 B 的 ID 和 uuid，就能把 B 绑到自己名下（`on conflict do update set user_id`，会覆盖原主人）。这比 01-上报与认证.md §9 的"首次使用即信任"宽：那条在设备第一次签名后就关上，登录绑定不看锁定（01 §3.5），B 锁定之后照样能被改绑。所以 (d) 的实际门槛是"任一账号持有者 + 知道 B 的 uuid + 能伪造 UDP 源地址"。个人部署账号少、都是认识的人，接受这个门槛；"设备主人"这个身份的加固（已锁定设备的登录不再覆盖已有主人、命令行指定主人）按笔记 02 §2.6 的原计划放到第四期，和 Exit Node 一起做，第三期不改登录绑定。
- 令牌随打洞请求发出；会合连接没做 KeyExchange（没配 key）时是明文。能嗅到令牌的人已经能调用全部 API，不是本块新增的问题。
- 代价：一次主池查库，只在"TCP 比较为否、UDP 比较为真"时才查（§3.1）；未登录、或登录了但对 B 没有权限的控制端用不上新判定，回到原有判定（路由器透明代理环境下，它们需要按 P-2 的环境规则让会合服务器的 TCP 也直连）。
- 维护者自己的设备都登录同一个账号、都是主人，不用配任何规则就能用。

多出口和未登录情况下的表现：

| 情况 | (a) | (d) |
|---|---|---|
| 控制端 TCP 走单一代理出口、UDP 走家宽 | 判出同网 | 登录且有权限时判出同网 |
| 控制端 TCP 走多出口代理（按连接换出口） | 不受影响（只看 UDP） | 同左 |
| 控制端的 UDP 也被代理（开 TUN、会合服务器的 UDP 没走直连） | UDP 注册 IP 是代理出口，退回原有判定 | 同左 |
| 控制端未登录，或账号对 B 没有权限 | 判出同网 | 退回原有判定 |

## 3. 服务端改动（porta-server）

### 3.1 `src/rendezvous_server.rs` `handle_punch_hole_request`（L1059~1232）【读码】

在 `let same_intranet: bool = !ws && (…);`（L1176~1183）之后、`let socket_addr = AddrMangle::encode(addr).into();`（L1184）之前加：

```rust
            // porta: A's TCP may leave through a proxy its UDP registration skips (contract 03 §3.1)
            let same_intranet = same_intranet
                || (!ws
                    && !forced_relay
                    && self.same_udp_exit(a_id, &id, peer_addr).await
                    && self.may_reach(&ph.token, &id).await);
```

`a_id` 来自 §2 那一行。`forced_relay` 是 L1165 现成的局部变量（`ALWAYS_USE_RELAY`，或掩码下一端在服务端内网、一端不在），在这里的作用域里。`ph.id` 已被移走，`ph.token` 仍可借用（部分移动），`ph.socket_addr_v6` 在后面照旧移走。`same_intranet` 为真时 `||` 短路，原有判定成立的请求不查内存、不查库。

新增两个私有方法（放在 `is_lan` 旁边）：

```rust
    /// Whether device `a_id` (a Porta requester's own id, unauthenticated) registered over UDP
    /// from B's public IP, recently enough to count as online. Memory only.
    async fn same_udp_exit(&self, a_id: &str, b_id: &str, b_addr: SocketAddr) -> bool {
        if a_id.is_empty() || a_id == b_id {
            return false;
        }
        let Some(a) = self.pm.get_in_memory(a_id).await else {
            return false;
        };
        let a = a.read().await;
        (a.last_reg_time.elapsed().as_millis() as i64) < REG_TIMEOUT
            && a.socket_addr.port() != 0
            && try_into_v4(a.socket_addr).ip() == try_into_v4(b_addr).ip()
    }

    /// Whether the requester's login may reach `b_id` (contract 03 §2.1 (d)). Main pool, as the
    /// other lookups of this connection task.
    async fn may_reach(&self, token: &str, b_id: &str) -> bool {
        match crate::auth::token_owner(&self.state.db, token).await {
            Some((user, _, _)) => crate::api::ab::reaches(&self.state.db, user, b_id).await,
            None => false,
        }
    }
```

要点：

- `same_udp_exit` **只查内存**（`PeerMap::get_in_memory`，L322）。在线设备一定在内存里；不在就是不在线，不查库。`Peer.socket_addr` 只由 UDP 的 `RegisterPeer`/`RegisterPk` 写，TCP 上的 `RegisterPk` 回 `NOT_SUPPORT`（L895），所以它就是 UDP 注册地址；从库加载、没注册过的条目 `socket_addr` 端口为 0、`last_reg_time` 已过期【读码：`peer.rs` `Peer::default`】。
- `may_reach` 排在 `same_udp_exit` 之后，所以**只在 TCP 比较为否、UDP 比较为真时**才查库；令牌为空时 `token_owner` 直接返回 `None`，不查库。
- **查库走主池，不走会合池**：`handle_punch_hole_request` 只从 21116/21118 的连接任务调用（UDP 来的 `PunchHoleRequest` 被丢弃，L718~721），`server/PORTA.md` §4.1 规定会合池只给 `io_loop` 用，连接任务查库走主池（同一函数里的 `get_from_main` 和 `router.select` 的固定中继查询已经这样做）。主池取连接最多等 3 秒，卡住的只是这一条连接的任务，不影响 `io_loop`；不另加超时。查库出错按"无权限"处理，退回原有判定。
- 比较前两边都 `try_into_v4`（`server/PORTA.md` §3"新代码比较前先规范化"）；现有那行比较保持原样不规范化（同一节明确要求）。地址族不同时判否，服务端每台设备只存一个注册地址，不做跨地址族比较。
- `a_id == b_id` 必须排除：否则把目标自己的 ID 填进 `porta_from_id`，两边 IP 天然相等。
- `!forced_relay`：强制中继时新加的这一路不生效，免得它绕过强制中继。原有 TCP 那一路保持上游行为不动（同网时照旧发 `FetchLocalAddr`，不看强制中继）。
- `!ws`：和现有判定一样，WebSocket 来的请求不走局域网路径。被控端用 WebSocket 或配了代理时，`handle_intranet` 本来也不开监听（`relay = use_ws() || Config::is_proxy()`）【读码：`client/src/rendezvous_mediator.rs` L764、L780】。
- 判否、退回原有判定的情况：强制中继、发起方服务进程没跑、30 秒内没注册（`REG_TIMEOUT`）、发起方是原版（没有 `porta_from_id`）、本机 ID 为空、令牌无效或账号对 B 无权限。
- 不改 `FetchLocalAddr.socket_addr`：它仍是 A 的 TCP 来源地址，服务端靠它在 `tcp_punch` 里找回 A 的那条 TCP 连接（`handle_local_addr` → `send_to_tcp`）。

统计口径（不新增 `conn_attempt` 列）：`signal = 'fetch_local_addr' and a_ip <> b_ip` 基本就是新规则判出来的（原有规则要求两者相等；例外是服务端配了 `mask`、两端都在服务端所在内网，原有规则也会出现两者不等）；其中 `outcome like 'relay%'` 是判了同网但最后走了中继；`outcome = 'direct_lan'` 只说明被控端回了局域网地址、匹配上的回落请求为 0，控制端 TCP 走多出口代理时回落的 `RequestRelay` 可能匹配不上、另记成 `relay_only` 行，原行仍是 `direct_lan`，所以"判对且连上"要同时排除同一 `b_id`、同一时间窗里的 `relay_only` 行（§6 端到端第 1 项）【读码：`migrations/0001_init.sql` `conn_attempt`、`src/conn_tracker.rs` `outcome`】。

改动量：函数内 +6 行（含注释；另加 `a_id` 那行时 +7），两个新方法约 25 行。

### 3.2 `src/api/ab.rs`：权限查询

新增一个函数，复用同文件的 `RULE_SQL`（§12.1 的有效权限：簿主人为 3，否则取直接授给本人和授给本人所在组的规则的最大值）：

```rust
/// Whether user `user` owns device `id` (`device.user_id`) or has any rule on a shared book that
/// lists it (contract 03 §2.1 (d)). Personal books do not count: anyone can put any id in theirs.
/// An error counts as no.
pub(crate) async fn reaches(db: &SqlitePool, user: i64, id: &str) -> bool {
    let sql = format!(
        "select exists(select 1 from device where id = ?2 and user_id = ?1)
             or exists(select 1 from ab a join ab_peer p on p.ab_guid = a.guid and p.id = ?2
                       where a.personal = 0 and ({RULE_SQL}) is not null)"
    );
    match sqlx::query_scalar::<_, bool>(&sql).bind(user).bind(id).fetch_one(db).await {
        Ok(v) => v,
        Err(e) => {
            hbb_common::throttled_log!(std::time::Duration::from_secs(60), error, "ab::reaches: {e}");
            false
        }
    }
}
```

- 第一段走 `device` 主键。第二段对每本共享簿按 `ab_peer` 主键 `(ab_guid, id)` 查一次，再算 `RULE_SQL`（`ab_rule` 有 `(ab_guid, user_id)`、`(ab_guid, group_id)` 两个唯一索引）；共享簿是命令行建的，通常只有几本。
- 权限不分等级：只读也算（只读的人照样能从共享簿里拿到 B 的 ID 和密码去连它）。

## 4. 客户端改动（porta-client，以及 porta-cardo 客户端线）

### 4.1 `libs/porta/src/lan.rs`

**哪些随 P-4 取舍**：网卡枚举改成双地址族、`Nic` 加 IPv6 字段、`has_gateway` 拆成 `has_gateway_v4`/`has_gateway_v6`、`is_physical` 参数改成 `IpAddr`，这些和 P-4 无关，一律要做：02 块测速的 `physical_snapshot` 要判 IPv6 本地地址，04 §4.4 的修法候选要用物理网卡的全局 IPv6。随 P-4 取舍的只有四样：`select_candidates` 追加 IPv6、控制端收 IPv6 候选和按 /64 筛（`peer_candidates`、`connect_candidates` 的筛选和 IPv4 先手）、`listen_dual`（连同 `socket2` 依赖）、`src/server.rs` 那条语句（§4.3）。地址分类的三个函数跟着用到它们的地方走。P-4 选"只收 ULA"时去掉全局地址和按 /64 筛；选"不做"时这四样都没有。

**网卡枚举 `nics()`（Windows）**

- `GetAdaptersAddresses` 的地址族从 `AF_INET` 改为 `AF_UNSPEC`，同时取 IPv4 和 IPv6。
- `Nic` 加字段：`description: String`（`IP_ADAPTER_ADDRESSES_LH.Description`）、`ipv6: Vec<Ipv6Addr>`（只收 `DadState == IpDadStatePreferred` 的单播地址，丢掉链路本地）。
- `has_gateway` 拆成 `has_gateway_v4` / `has_gateway_v6`（`FirstGatewayAddress` 里按地址族分别看有没有非未指定地址）。**IPv4 候选照旧只看 `has_gateway_v4`**，现有 IPv4 行为不变（只有 IPv6 网关的网卡不会因此多出 IPv4 候选，"要求有网关"对 vEthernet 和仅主机网卡的排除也不被削弱）。
- `windows` crate 的 feature 不用加（`SOCKADDR_IN6`、`NL_DAD_STATE` 在已开的 `Win32_Networking_WinSock` 里）【推测：按 windows 0.61 的模块划分，编译时确认】。

**网卡分类 `Nic::is_virtual()`**：现有规则（IfType 23/24/53/131；接口名以 `tun`/`utun` 开头或含 `mihomo`/`wintun`）不变，再加一条：`description` 或 `name` 转小写后含下列任一关键字就算虚拟网卡。

| 类别 | 关键字 | 说明 |
|---|---|---|
| 代理 TUN | `meta tunnel` | mihomo 的 TUN 网卡描述（笔记 05 §3.3） |
| VPN / 隧道驱动 | `wintun`、`wireguard`、`tailscale`、`zerotier`、`tap-windows`、`openvpn`、`vpn` | 取自笔记 05 §3.3 那张关键字表 |
| 虚拟机宿主侧网卡 | `vmware virtual ethernet`、`virtualbox host-only`、`vmnet` | 宿主机给虚拟机用的网卡，不是出口 |

- **不加 `hyper-v`**：Hyper-V 外部虚拟交换机下，宿主机真正上网的就是 `vEthernet (…)`（描述 `Hyper-V Virtual Ethernet Adapter`，有默认网关），物理网卡反而没有 IP。Hyper-V 内部交换机和 WSL 的 `vEthernet` 没有默认网关，现有规则已排除。
- **不加 `virtio`、`vmxnet`、`hyper-v network adapter`** 这类虚拟机里的网卡：Porta 装在虚拟机里时那就是唯一的真实网卡。
- **VPN 网卡一律排除，不降权**。被控端的候选只代表"局域网里怎么找到我"；经 VPN 回家的控制端（`client/PORTA.md` §3.4）连的是被控端的物理局域网地址，不需要被控端报 VPN 地址。控制端一侧，落在这些网卡上的连接改用 800 ms 短握手上限，和现在的 Wintun 网卡一致（§3.4 给"经 WireGuard/Tailscale 回家"留的那条路）。

**地址分类**（新增三个私有函数）：

- `excluded_v6(ip)`：回环、未指定、链路本地、组播、`::ffff:0:0/96`（v4 映射地址），以及常见 TUN 软件的默认 IPv6 段 `fdfe:dcba:9876::/48`【推测：取自 mihomo / sing-box 文档的默认值；TUN 网卡本身已被 `is_virtual` 排除，这条只是兜底，端到端第 3 项核对】。
- `is_ula(ip)`：`octets()[0] & 0xfe == 0xfc`。
- `is_global(ip)`：`segments()[0] & 0xe000 == 0x2000`（`2000::/3`）。
- 被控端只报 ULA 和全局单播，且都不在 `excluded_v6` 里。

**`is_physical(nics, ip: IpAddr)`**：参数从 `Ipv4Addr` 改成 `IpAddr`，IPv6 地址在某块在线、非虚拟网卡的 `ipv6` 里就算物理。`handshake_timeout`、`controller_bind_addr` 跟着改调用；02 块的 `physical_snapshot` 复用它。

**被控端选候选 `select_candidates`**（P-4 选推荐方案时）：

1. IPv4 部分完全照现在（`sock_local` 是物理地址时排第一，再按"有线优先、链路速度从高到低"排其他物理网卡的地址，用 `has_gateway_v4` 过滤）。
2. **至少有一个 IPv4 候选时**才追加 IPv6。先排除虚拟网卡和 `excluded_v6` 里的地址，再按同样的网卡顺序取，每块合格网卡（在线、非虚拟、`has_gateway_v6 || has_gateway_v4`）最多取 1 个全局地址、1 个 ULA（各取枚举到的第一个），**全局地址排在 ULA 前面**。IPv6 最多 4 个，总数仍不超过 `MAX_CANDIDATES = 8`（IPv4 先占）。端口都用 `sock_local` 的端口。
   - 网卡用"v6 或 v4 网关任一"：只发 ULA 前缀、不发 IPv6 默认路由的局域网（路由器没有 IPv6 上游）里，网卡没有 IPv6 网关，但 ULA 照样能在局域网里用。
   - "先排除再设上限"：TUN 的 IPv6 不占名额（笔记 05 §3.1 里 UU 的上限被 TUN 地址占掉一个）。
3. 为什么要求先有 IPv4 候选：`handle_intranet_` 的挂钩用 `lan.first()` 当 `LocalAddr.local_addr`（给原版控制端用），它必须是 IPv4；IPv6 只排在后面，就不用改那行挂钩【读码：`rendezvous_mediator.rs` L838~839】。代价：没有物理 IPv4 网卡的纯 IPv6 局域网不报候选，照上游走。
4. `sock_local` 一定是 IPv4：上游只在连会合服务器的那条连接是 IPv4 时才调 `handle_intranet_`（L780）。`sock_local` 是 IPv6 时返回空的分支保留。

**监听**（随 P-4）：

- `listen_addr` **不改**：候选里有 IPv6 时 IP 必然和 `sock_local` 不同，照旧返回 `0.0.0.0:端口`。
- 新函数 `pub async fn listen_dual(candidates: &[SocketAddr], addr: SocketAddr) -> Option<TcpListener>`：只有 `candidates` 里有 IPv6、且 `addr` 是 `0.0.0.0:端口` 时才动手，用 socket2 建 IPv6 TCP socket，`set_only_v6(false)`、`set_reuse_address(true)`、bind `[::]:端口`、listen（backlog 128，和 hbb_common 的 `DEFAULT_BACKLOG` 一致）、设非阻塞，转成 tokio 的 `TcpListener` 返回 `Some`。其余情况、或任何一步失败（打一条 info 日志）返回 `None`，由调用点照旧 `new_listener(addr, true)` 绑 `0.0.0.0:端口`，IPv4 候选照样能用。没有 IPv6 候选时行为和现在逐字节相同。
- **不用 hbb_common 现成的 `tcp::listen_any`**：它在 Windows 的 IPv6 分支里不设 `SO_REUSEADDR`【读码：porta-cardo `src/tcp.rs` `listen_any` L271~】，同端口刚断开的连接还在 TIME_WAIT 时大概率退回 IPv4，IPv6 候选会悄悄失效。
- 双栈 socket 上 IPv4 连接的本地、对端地址是 `::ffff:a.b.c.d`；`create_tcp_connection` 一进来就 `try_into_v4`，白名单和准入照旧按 IPv4 算【读码：`src/server.rs` L226】。
- `libs/porta/Cargo.toml` 加 `socket2 = "0.3"`（和 hbb_common 同一主版本，`Cargo.lock` 里已有 0.3.19，不加新包；0.3 的 API 是 `Domain::ipv6()`、`Type::stream()`、`into_tcp_listener()`，和 0.4/0.5 不同）。

**控制端收候选 `peer_candidates`**（随 P-4）：除私网 IPv4 外，再收 ULA 和全局单播 IPv6（同一组判法，`excluded_v6` 里的一律丢），端口非零、去重、最多 8 个。v4 映射地址（`::ffff:8.8.8.8`）不在这两类里，会被丢掉，堵住"借 IPv6 编码塞一个公网 IPv4"。

**控制端连候选 `connect_candidates`**（随 P-4）：

- 签名改为 `candidates: &mut Vec<SocketAddr>`。枚举完本机网卡后（现在就有这一步），先就地删掉不在本机局域网里的全局 IPv6 候选：保留条件是它的前 64 位和本机某块物理网卡（`is_physical` 意义下）的某个全局地址相同；本机网卡列表为空时全局 IPv6 候选全删。ULA 和私网 IPv4 不做这一步。理由：控制端不能被恶意对端或服务端诱导去连任意公网地址，"和我同一个 /64"把威胁面限制在和私网 IPv4 相同的范围。就地删除是为了让随后的 `lan_fallback` 看到实际试过的列表。
- **IPv4 先手**：`race` 里每个候选的尝试前按类别等一个固定的先手时间，私网 IPv4 不等，全局 IPv6 等 50 ms，ULA 等 100 ms（常量 `V6_GLOBAL_DELAY`、`V6_ULA_DELAY`，按地址类别算，不记任何状态）。原因：
  - Porta 没有 ICE 那样的会话中换路径，会话所用的地址在会话中消失（例如路由器撤掉 ULA 前缀，笔记 05 §3.2、§7 第 4 项）会直接断开会话。私网 IPv4 最稳，全局地址其次，ULA 在一些路由器上会反复出现又消失。
  - 被控端的监听只收第一条连接，谁的 TCP 先到谁赢；局域网里 TCP 建连只要几毫秒，50 ms 的先手足够让能通的 IPv4 先到。IPv4 不通（例如被防火墙挡住）时最多晚 50~100 ms 改用 IPv6。
- 剩下的全部并发，TCP 连接等待 1 秒、握手上限 3 秒 / 800 ms 照旧。IPv6 局域网地址有同网段的直连路由（/64），比 TUN 装的默认路由更具体，不绑源地址时从物理网卡出去（和笔记 04 §3.3 IPv4 的结论同理；UU 的日志里 `0.0.0.0` 的 socket 发往局域网地址也是这样，笔记 05 §3.1 第 2 条）【推测，端到端第 2 项确认】。

**`handshake_timeout`**：扩展到 IPv6（本地端是物理网卡的 IPv6 地址才算物理）。TUN 接住的 IPv6 连接本地端是 TUN 的地址，拿 800 ms。

`local_candidates_async`、`encode` 不变。

### 4.4 共存 ID 冲突：porta-cardo 客户端线

**前置步骤（先做，结论写回本节再动代码）**：笔记 02 §1.8 是读码推出来的，没实测。在一台 Windows 测试机（可以是虚拟机）上同时装官方 RustDesk 和 Porta，两边指向同一个测试用 porta-server：

1. 两个界面显示的 ID 是否相同（`get_auto_id` 取 `mac_address::get_mac_address()` 的第一块非回环网卡，装了虚拟网卡时可能不是同一块）。
2. 相同时，从第三台机器连这个 ID 若干次，看是否时而连到 RustDesk、时而连到 Porta（连到公钥对不上的一端会弹"未加密连接"确认），服务端日志里这个 ID 是否有 `update_pk` 和来回的地址变化。

ID 相同即确认冲突。ID 不同也照下面实现（换一台网卡顺序不同的机器照样会撞），把观察到的现象写进本节。

**改动**【读码：`src/config.rs` `Config::get_auto_id` L1058~1082，`id &= 0x1FFFFFFF;` 在 L1075；`Config::get_id` L1212~1221】：

- 新文件 `src/porta_id.rs`（porta-cardo 自有）：`pub(crate) fn salt(mac_id: u32) -> u32`，`sha256(b"porta-auto-id\0" ‖ mac_id.to_le_bytes())` 取前 4 字节按小端转 `u32`，返回 `(h & 0x0FFF_FFFF) | 0x1000_0000`。结果固定 9 位（268435456~536870911），和同机原版 ID 相撞的概率约 2^-28。用已有的 `sha2`，不加依赖。单元测试放在同一文件。
- `src/config.rs` `get_auto_id` 里 L1075 之后加 2 行：
  ```rust
                  // porta: salted, so Porta and RustDesk on one machine do not take the same id
                  let id = crate::porta_id::salt(id);
  ```
  哈希的输入是上游算出的 `id`（来自 MAC 后 4 字节），和直接哈希 MAC 等价，这样只加行、不改上游的循环。
- `src/lib.rs` 加 `mod porta_id;` 1 行。
- 只放客户端线：服务端不生成 ID。不是 proto 改动，不受"两条线各放一份"的约束。

**影响范围**：

- 只影响**首次生成 ID** 的设备（`Config::get_id` 发现 `id` 为空时才调 `gen_id`）。已有 ID 的 Porta 设备不变。
- `allow-hostname-as-id` 打开时走主机名，不受影响（这个选项默认关，Porta 不打开它）。
- 已装 Porta、又要和原版指向同一个服务器的机器，要手动让 Porta 重新生成 ID：停服务，删掉服务进程配置文件里的 `id` 和 `enc_id` 两项，再启动。porta-server 不支持界面上的"修改 ID"（它走 TCP 上的 `RegisterPk`，porta-server 回 `NOT_SUPPORT`，L895）。写进客户端使用说明，不写代码。另一个办法见 01-上报与认证.md §9（对这台机器 `device key reset --forget` 后让 Porta 重新注册；默认的 `device key reset` 只清锁定、保留库里原版那把公钥，不够）。
- 和设备签名的关系：公钥锁定只在原版发 `RegisterPk` 时起作用（第一次连这台服务器、IP 变化、内存条目被淘汰），同 IP 常驻时原版只发 `RegisterPeer`，冲突照旧；加盐后两边 ID 不同，锁定各管各的。

|---|---|---|
| Porta，服务进程在跑、已注册，登录且对被控端有权限 | Porta | 同网判定多一路 UDP 比较；被控端报 IPv4 + IPv6 候选、双栈监听；控制端 IPv4 先手并发试 |
| 同上 | 原版 | 同网判定多一路 UDP 比较。被控端没开 TUN 时能连上（它报物理地址）；开了 TUN 仍修不了（它只报、只监听虚拟地址），和 `client/PORTA.md` §3.5 第 2 行相同，新判出的同网会让这类连接多走一次注定失败的局域网尝试，晚一两秒回落 |
| Porta，未登录、对被控端无权限、服务进程没跑或本机 ID 为空 | 任意 | 同网判定和现在一样（Porta 被控端照样报 IPv6 候选，原有判定判出同网时就用得上） |
| 原版 | Porta | 没有 `porta_from_id`，同网判定和现在一样；`local_addr` 仍是物理 IPv4，原版不读 `porta_local_addrs` |
| 原版 | 原版 | 和现在一样 |
| 任意，经 WebSocket | 任意 | 不走局域网路径，和现在一样 |

服务端是原版 hbbs 时：`porta_from_id` 和 `porta_local_addrs` 都被丢掉，同网判定、候选都和上游一样；Porta 被控端的 `local_addr` 仍是物理 IPv4，监听只在有 IPv6 候选时变成双栈（原版控制端只连 `local_addr`，不受影响），行为不比上游差。

默认 ID：新装的 Porta 和同机原版 ID 不同；已有 ID 的设备不变。

## 6. 测试

**服务端单元测试**（`rendezvous_server.rs` 现有夹具 `harness`、`online(id, addr)`、`to_b()`；令牌、设备、地址簿行直接写库），断言服务端发给 B 的是 `FetchLocalAddr` 还是 `PunchHole`。前提都是：A 的 TCP 来源 IP 和 B 的 UDP 注册 IP 不同，`porta_from_id` 指向一台从 B 的 IP 注册、在线的设备 X。

1. 令牌属于 B 的主人（`device.user_id`）→ `FetchLocalAddr`，且 `socket_addr` 仍是 A 的 TCP 来源地址。
2. 令牌的账号经组在一本含 B 的共享簿上有只读权限 → `FetchLocalAddr`。
3. 令牌的账号只在自己的个人簿里有 B → `PunchHole`。
4. 没有令牌、令牌无效、账号被禁用、账号和 B 无关 → `PunchHole`。
5. `porta_from_id` 等于 B 自己的 ID → `PunchHole`。
6. X 的注册已过期（`last_reg_time` 超过 30 秒）或不在内存里 → `PunchHole`。
7. 同样的请求走 WebSocket（`ws = true`）→ `PunchHole`。
8. A 的 TCP 来源 IP 等于 B 的 UDP 注册 IP、没有令牌 → `FetchLocalAddr`（原有判定不受影响，不查库）。
9. 强制中继成立时，第 1 条同样的请求 → `PunchHole`（新加的一路不绕过强制中继）。强制中继用掩码造出来（A 在掩码内、B 在掩码外，和现有测试 `forced_relay_clears_v6` 同法），和 `ALWAYS_USE_RELAY` 打开时走的是同一个 `forced_relay` 变量；`ALWAYS_USE_RELAY` 是进程级 static，测试里改它会干扰并行的其他测试。

`ab::reaches` 另测：主人、共享簿直接授权、经组授权、共享簿里没有 B、只有个人簿里有 B 五种情况。

**客户端单元测试**（`lan.rs`，用构造的网卡列表）：

1. 有线网卡带全局、ULA、链路本地三个 IPv6 → 候选是 IPv4 在前，再跟全局、ULA 各一个，没有链路本地。
2. 只有 IPv6、没有 IPv4 候选 → 空。
3. 网卡有 IPv4 地址、只有 IPv6 网关 → 不出 IPv4 候选（`has_gateway_v4` 规则不变）。
4. 描述为 `Meta Tunnel`、IfType 6 的网卡不出候选；描述 `Hyper-V Virtual Ethernet Adapter`、有网关的网卡出候选；`VMware Virtual Ethernet Adapter for VMnet8` 不出候选。
5. `peer_candidates`：收 ULA 和全局 IPv6，丢 `::ffff:8.8.8.8`、`fe80::1`、`ff02::1`、`::1`。
6. 全局 IPv6 候选按 /64 筛：和本机物理网卡同前缀的留下；不同的，以及本机网卡列表为空时，全删；ULA 不受影响。
7. 先手顺序（`race` 注入尝试函数、tokio 暂停时钟）：IPv4、全局、ULA 都立即成功 → IPv4 胜出；IPv4 失败 → 全局胜出。
8. `listen_dual`：候选含 IPv6、地址 `0.0.0.0:0` 时返回 `Some`，分别从 `127.0.0.1` 和 `::1` 连进来都能 accept；候选不含 IPv6 时返回 `None`（Linux 和 Windows 都能跑，不加平台门控）。

porta-cardo：`porta_id::salt` 一条测试，固定输入的输出落在 9 位范围内、和输入不同。

不测：网卡枚举本身（系统调用）、关键字表逐项、排序的每种组合。

**端到端验收**（维护者，两台装了 Porta 的 Windows 在同一局域网，连同一个 porta-server，两台都登录同一个账号，`device list` 核对被控端的账号是它）。判据用"`conn_attempt` 的列 + 控制端日志"两条一起：局域网候选胜出时控制端直接返回，**不打**上游的 `used to establish … connection` 那行【读码：`src/client.rs` L1371~1378 早返回】，所以看 `lan.rs` 的 `LAN candidate … won`。

1. **同网判定**：让控制端到会合服务器的 TCP 走代理出口、UDP 直连（路由器透明代理只代理 TCP，或在本机代理里按协议分流）。连接后核对：
   - 控制端日志有 `LAN candidate <私网地址>:<端口> won`，没有 `all N LAN candidates failed`；
   - `conn_attempt` 最新一行 `signal = 'fetch_local_addr'`、`a_ip <> b_ip`、`outcome = 'direct_lan'`、`relay_req_count = 0`，并且同一 `b_id`、同一时间窗里没有 `signal = 'relay_only'` 的行（代理按连接换出口时，回落中继的请求匹配不上会另记成这种行）。
   - 反向核对：控制端退出登录（或停掉控制端的 Porta 服务）再连，`signal` 应回到 `punch_hole`。
2. **IPv6 候选**（两台都有 ULA 或同一 /64 的全局地址）：被控端日志 `Server listening on: [::]:<端口>`；正常情况下控制端日志仍是 IPv4 候选胜出（先手）。在被控端临时加一条 Windows 防火墙入站规则，阻止 Porta 程序接受来自私网 IPv4 段的 TCP，再连一次，控制端日志应为 `LAN candidate [<IPv6>]:<端口> won`，`outcome = 'direct_lan'`、`relay_req_count = 0`。测完删掉规则。
3. **TUN 回归**：两台都开 TUN 重复第 1 项（不加分流），判据同第 1 项（`LAN candidate <私网地址>:<端口> won`、`direct_lan`、没有 `relay_only` 行）。顺带用 `Get-NetIPAddress` 记下 TUN 网卡的 IPv6 地址，核对 `excluded_v6` 里的常量。
4. **共存 ID**：前置实测见 §4.4。代码合入后，在一台已装原版 RustDesk 的机器上新装 Porta（配置目录里没有旧 ID），两边 ID 不同、同时在线，从第三台分别连两个 ID，各自连到对应的程序、不弹"未加密连接"。

- 打洞请求签名（`porta_from_id` 认证）：属于会合层签名，和 RegisterPk/RegisterPeer 签名一起留到退出兼容前单独定。
- 草稿里的备选 (b)（绑定签名心跳的来源 IP）：挡不住 §2.1 的构造。
- 服务端同时记两个地址族的注册地址、跨地址族比较。
- 新增 `conn_attempt` 列记"同网是哪条规则判的"：用 `a_ip <> b_ip` 就能区分。
- 纯 IPv6 局域网（没有物理 IPv4 网卡）的候选；IPv6 链路本地候选；UDP 候选。
- 会话中换路径（候选地址消失时切到别的候选）：属于笔记 05 §6 第 8 项，第四期以后；本块只用 IPv4 先手降低风险。

- macOS 客户端（第一阶段只做 Windows）。

## 8. 需要维护者定的问题

全局清单在 README.md，这里只列和本块有关的。

**P-2 控制端 TCP、UDP 从不同出口出去（路由器透明代理只代理 TCP）。**

- **(3d) 做第 1 项、信任模型 (d)，同时写环境规则"会合服务器的 TCP 也直连"给 UDP 打洞用（推荐）**。理由：UU 证明局域网判定不该依赖 TCP 路径；IPv6 局域网候选也挂在同网判定上；维护者自己的设备都登录、都是主人，不用配规则就能用；(d) 把伪造 UDP 源地址的攻击面限制到持有账号的人。登录改绑只凭 uuid，实际门槛是"任一账号持有者 + 知道 B 的 uuid + 能伪造 UDP 源地址"（§2.1）；个人部署账号少、都是认识的人，接受这个门槛，"设备主人"的加固按笔记 02 §2.6 放到第四期和 Exit Node 一起做，第三期不改登录绑定。本块视角的代价：服务端函数内 +6 行、两个新方法约 25 行、`ab.rs` 一个约 15 行的查询函数、`auth.rs` 改 1 行日志；一次有条件的主池查库（只在 TCP 比较为否、UDP 比较为真时）；未登录的控制端用不上；`device.user_id` 的归属从此也影响同网判定（`server/PORTA.md` §11 要同步）。
- (1) 只写环境规则，不做第 1 项。本块服务端零改动，§3 留作后期设计；代价是透明代理环境下每台控制端所在网络都要配规则（在路由器的透明代理里排除会合服务器），配不了的环境里局域网候选（包括 IPv6）都用不上。客户端的 `porta_from_id` 挂钩照样加（02 块要用）。
- (2a) 做第 1 项、信任模型 (a) 直接比。少一次查库、未登录的控制端也能用；代价是能伪造 UDP 源地址、知道 B 的 ID 的人能骗出 B 的局域网地址（含全局 IPv6），并让 B 开 18 秒、只收一条连接的监听（仍要过握手和登录）。

**P-4 局域网候选带 IPv6 的范围。**

- **ULA + 和控制端某块物理网卡同一个 /64 的全局地址（推荐）**。很多家用路由器只下发全局前缀、不发 ULA，只收 ULA 在这类网络里等于没做；"同一个 /64"把全局地址限制在控制端自己所在网段。本块视角的代价：`src/server.rs` 一条语句改成 `match`（偏离"不改调用点"）；`libs/porta` 加 `socket2 0.3` 依赖（锁文件里已有）；双栈 bind 在同端口刚断开的连接上能否成功没实测（失败退回 IPv4 监听）；ULA 不稳定的网络里会话可能因地址消失断开（靠 IPv4 先手、全局优先于 ULA 缓解，§4.1）。
- 只收 ULA：代价同上（监听那处省不掉），控制端不用比 /64，但在不发 ULA 的网络里没有收益。
- 不做：上游文件零改动；局域网里的全局 IPv6 仍可走现有 IPv6 打洞（需要会合服务器有 IPv6、两端开 IPv6 打洞）。损失的是 UU 实际在用的那条主路径。

三种选法下，网卡枚举改双地址族、`Nic` 加 IPv6 字段、`has_gateway_v4`/`has_gateway_v6`、`is_physical` 改收 `IpAddr` 都照做（02、04 块要用，§4.1 开头），不算 P-4 的代价。

**按推荐默认、不单列**：共存 ID 加盐按笔记 02 §3 问题 8 的推荐（先实测，再加盐，§4.4）。

## 9. 已知限制和风险

- **新判出的同网可能是误判**：两户人家共用运营商 CGNAT 的同一个公网 IP、控制端 TCP 又被代理时（且控制端账号对被控端有权限），会新判成同网。控制端去连对方的私网地址，失败后回落中继，比现在晚约 1~2 秒（候选全被本机 TUN 接住时最多再加 800 ms 短握手）；这次连接也不再尝试 IPv4 TCP 打洞【推测：按 `client/PORTA.md` §3.4 的超时推算，笔记 05 §6 估的最坏约 4 秒】。用 §3.1 的统计口径看误判率。
- **控制端前提**：Porta 服务进程在跑并且 30 秒内注册过；界面进程已登录、账号对被控端有权限；开 TUN 的控制端，会合服务器的 UDP 要走直连。
- **被控端前提**：原版被控端开 TUN 仍修不了（§5）。被控端连会合服务器的那条连接是 IPv6 时，上游不调 `handle_intranet_`，没有候选（上游行为）。
- **信任模型 (d) 的剩余面**（§2.1）：共享簿的读写者能把任意 ID 加进簿；知道 B 的 uuid 的人能在登录时把 B 绑到自己名下（锁定后照样能改绑），所以实际门槛是"任一账号持有者 + 知道 B 的 uuid + 能伪造 UDP 源地址"；令牌在没做 KeyExchange 的会合连接上是明文。个人部署接受这个门槛；"设备主人"的加固放到第四期和 Exit Node 一起做，第三期不改登录绑定。
- **IPv6 候选的暴露面**：P-4 选推荐方案后，被控端在局域网路径里会把全局 IPv6 地址回给发起方，并在双栈 `[::]:端口` 上监听 18 秒。家用路由器的 IPv6 防火墙放行入站时，这个监听在 18 秒内从公网也连得到，只收第一条连接、不校验对端 IP（上游原样）；连进来仍要过安全握手和登录，和上游 IPv6 打洞路径同级。
- **ULA 不稳定**：路由器反复撤销、下发 ULA 前缀时，落在 ULA 上的会话会在地址消失时断开（Porta 没有会话中换路径）。IPv4 先手和全局优先于 ULA 让这种情况只在 IPv4 和全局地址都不通时发生。
- **双栈监听没实测**：Windows 上在刚断开的连接端口上 bind 双栈 `[::]:端口` 能否成功是【推测】；失败时退回 IPv4 监听，那次 IPv6 候选不可用。端到端第 2 项会暴露这个问题。
- **TUN 的 IPv6 段常量**是【推测】，端到端第 3 项核对；TUN 网卡本身已被 `is_virtual` 排除，常量不对的后果有限。
- **描述关键字可能误伤**：描述里含 `vpn` 等字样的真实网卡会被排除，后果是少一个候选、可能回落中继。关键字不覆盖的虚拟网卡会多出一个连不通的候选，并发数多一个。
- **共存 ID**：结论依赖前置实测。已有 ID 的 Porta 设备不受加盐影响，迁移后和原版指向同一服务器时要按 §4.4 手动重新生成。`mac_address` 取到的第一块网卡在装了虚拟网卡的机器上可能变化，变化时上游的默认 ID 本来就会不同。
