# 路由第二级：客户端测速上报、服务端按实测选中继

> 标注：【读码】读过现版源码；【推测】推断，没有实测。代码锚点对照 leapgate-client `68e1259fa`、leapgate-server `bff8a17`、leapgate-cardo 客户端线 `a3d96d4` / 服务端线 `375e2a3`。

## 1. 目标与范围

**做什么**：第一级（第一期已上线）按 GeoIP 估算"设备到中继"的延迟来选中继。第二级让 Leapgate 客户端自己测到每台候选中继的 TCP 建连耗时，随心跳报给 leapgate-server；服务端选中继时，某一端有可用的实测就用实测代替估算。被控端连 leapgate-server 时照用服务端选的中继，不再被本地 `relay-server` 选项盖掉。

**依据**：`docs/research/第三期/01-路由第二级.md`（下称"笔记 01"）。候选中继列表走 Leapgate 心跳响应的 `routing` 键下发，测量走请求的 `probes` 键上报；**旧路径 `/api/heartbeat` 不加任何 Leapgate 键**，笔记 01 §3.1 的顶层 `leapgate` 键方案和 §6 问题 2、6 作废。

**对应的已定决策**（AGENTS.md 第三期设计）：
- 打洞请求带发起方自己的 ID（`PunchHoleRequest.leapgate_from_id = 1000`），服务端用它查发起方心跳上报过的测量。偏离方案 §3.7 原文"把测量值放进打洞请求"，理由见笔记 01 §2.3。
- 上报走 `/api/leapgate/v1/heartbeat`，本块的请求、响应字段都挂在 01-上报与认证.md 的心跳上。
- 其余按笔记 01 推荐：被控端连 leapgate-server 时本地 `relay-server` 不再生效（界面提示留给新界面轨道，本期只写文档）；`conn_attempt` 加两列记选中中继两段延迟（迁移 0005）；测速参数 5 分钟一轮 ±10% 抖动、每台 3 次取最小、15 分钟过期、最多 32 台，`probe_interval` 经心跳下发。

**实施顺序**（README.md）：本块在**第 2 批**，依赖第 0 步的合并 proto 提交和第 1 批的 01 块（服务端 Leapgate 心跳 handler、客户端能力缓存和心跳调用点）；`lan.rs` 的改动排在 03 块之后；迁移 0005 在 01 块的 0004 之后。和 04 块同批并行，后合者变基。

**和笔记 05（UU 远程）的关系**：
- 笔记 05 §6 第 1 项（同网判定加一路 UDP 比较）草稿里曾想复用 `leapgate_from_id`，已排除（03 §2.1），改由 04 块的 UDP 出口证明解决，不读这个字段。`leapgate_from_id` 只给本块用，由本块加两端的读写（§3.5、§4.5 挂钩 2）。
- 本机开 TUN 代理时 TCP 握手由 TUN 在本机完成，路由器透明代理时由路由器完成（笔记 05 §5 表第 3 行），握手耗时量不到中继。2026-10-25 起不再计握手（§4.2）：测速和真实中继连接走同一条路，连上后等代理把上游连好，量到中继关连接。**不判断本机开没开 TUN、路由器怎么代理**，量到的就是真实中继路径的往返，用户不用配任何规则（P-2 的"不管开不开 TUN 都生效"）。原来的"本地地址必须在物理网卡上""对端在 `198.18/15` 就作废"两条规则随之删掉。

**不在本块**：Leapgate 心跳的签名、能力探测、退避、sysinfo（01 块）；同网判定（04 块 §2.5）；UDP 打洞（04 块）。

## 2. 协议与接口

### 2.1 proto

只用第 0 步合并 proto 提交里的 `PunchHoleRequest.leapgate_from_id = 1000`（string，发起方自己的设备 ID）；那个提交同时带 `rendezvous.proto` 文件头的号段注释（Leapgate 占 1000~1999），两条 leapgate-cardo 线内容一致。本块不另做 proto 提交，也不加别的字段：`RequestRelay` 不加（笔记 01 §2.4）。

原版 hbbs 看不见这个字段，也不会转给 B（转给 B 的 `PunchHole` 是新构造的消息，笔记 01 §2.6）【读码】；原版客户端不发。

### 2.2 心跳请求里本块的两个字段

```json
{ "...": "01 块的字段",
  "routing_rev": 7,
  "probes": { "routing_rev": 7, "age_s": 42,
              "rtt":  { "relay1.example.com:21117": 23, "relay2.example.com": 61 },
              "down": ["relay3.example.com:21117"] } }
```

| 字段 | 含义 | 取值 |
|---|---|---|
| `routing_rev` | 客户端手里那份候选列表的版本号；还没有列表时为 0 | 整数 |
| `probes` | 最近一轮有效测量；没有时整个键省略 | 对象 |
| `probes.routing_rev` | 这轮测量用的列表版本 | 整数 |
| `probes.age_s` | 这轮测量结束距现在的秒数。服务端用"收到时刻 − age_s"算测量时刻，不依赖两边时钟 | 0~900 |
| `probes.rtt` | 测通的中继：键是 `routing.relays` 里的原串（逐字），值是 3 次里最小的建连毫秒数 | 1~10000 |
| `probes.down` | 3 次都没连上的中继，原串 | 字符串数组 |

- 列表里每台中继要么在 `rtt`，要么在 `down`。
- 最坏大小：32 台 × 253 字节主机名 ≈ 8.5 KB，在 01 块定的心跳请求体上限 32 KB 以内。

### 2.3 心跳响应里本块的键

```json
{ "api": 1, "features": ["..."], "time": 1761200000,
  "routing": { "rev": 7, "probe_interval_secs": 300,
               "relays": ["relay1.example.com:21117", "relay2.example.com", "relay3.example.com:21117"] } }
```

- 只在请求的 `routing_rev` 不等于服务端当前版本时出现（和 `strategy` 同一种"变了才推"）。
- `relays` 是 `leapgate.toml` `[[relay]] host`（或 `-r`、控制台 `rs` 替换后）的原串，和 `PunchHole.relay_server` 下发的是同一个字符串，测的和选的逐字对得上。全部配置的中继都发（包括健康检查暂判不可达的），最多前 32 台；没有配置中继时为 `[]`，客户端停止测速。
- `rev`：对"`relays` 用 `\n` 连起来 + `\n` + `probe_interval_secs`"做 sha256，取前 8 字节转 `i64` 后与 `i64::MAX` 按位与，为 0 时取 1（和 `server/LEAPGATE.md` §10 策略 `rev` 同一算法）。重启后同一份配置算出同一个 rev。
- `probe_interval_secs` 是服务端常量 300（不做配置项）；客户端收下后限在 60~3600。
- 本块不新增错误码，不新增 `features` 项：客户端只要知道服务端是 leapgate-server（01 块的 `server_is_leapgate()`）就让服务端的中继优先；只有 01 块、还没有本块的 leapgate-server 不发 `routing`，客户端就不测速，不需要单独的特性标记。
- `probes` 解析失败**不**导致 400：服务端只丢这次测量，心跳照常处理（§3.4）。

## 3. 服务端改动（leapgate-server）

### 3.1 测量表：`src/router/measure.rs`（新文件）

```rust
/// One device's latest round. Indexes follow the relay list of `rev`.
struct Measured {
    rev: i64,
    at: Instant,                 // received − age_s
    legs: Vec<Leg>,              // len = min(list len, 32)
}
#[derive(Clone, Copy)]
enum Leg { Unknown, Rtt(u16), Down }

pub(crate) struct Measurements(Mutex<HashMap<String /* device id */, Measured>>);
```

- 按列表下标存、不存主机名：一条约 `id + 32 × 4` 字节，1 万条约 3~4 MB。
- 写入 `record(id, probes: &serde_json::Value, list: &[String], rev, now)`：
  - `serde_json::from_value::<Probes>` 失败、`probes.routing_rev != rev`、`age_s > 900` → 整条丢弃（最多 trace，不打 warn）。
  - `rtt` 的键必须逐字等于列表前 32 台里的某个原串、值在 1~10000，否则这一项留 `Unknown`；`down` 同样只认列表里的原串。
  - id 超过 `MAX_PEER_ID_LEN`（253）不收。
  - 条目上限 `MAX_MEASURED = 10_000`（同 `device` 表）。已有这个 id 就覆盖；满了先删所有过期的，仍满就删 `at` 最老的一条。不需要定时清理。
- 读出 `get(id, rev, now) -> Option<Vec<Leg>>`：`rev` 不是当前版本、或 `now − at > 15 分钟`（`MEASURE_TTL`）视为没有。
- 锁：`std::sync::Mutex`，不跨 await；`decide` 里一次加锁取 A、B 两份。
- 不落库（笔记 01 §3.5）。

### 3.3 `src/router/cost.rs`：整端替换

`Candidate` 加 `pub rtt_a: Option<f64>, pub rtt_b: Option<f64>`（只在这一端用实测时为 `Some`）。规则（理由见笔记 01 §3.5）：

1. **一端"用实测"的条件**：这一端有没过期、版本对得上的测量，并且对当前**每一台可达候选**都不是 `Unknown`。不满足就整端用估计值。
2. **`down` 过滤**：用实测的那一端标 `Down` 的中继从这一对的候选里去掉；去掉后一台不剩时，忽略 `down`、把这一端当作"不用实测"。
3. **每台候选的一段**：`leg_x = rtt_x.or(leg_rtt(估计))`；代价沿用第一期：两段都有 → `(leg_a + leg_b) × weight`；只有一段 → `2 × leg × weight`；都没有 → 不参加排序。
4. **`reason`**：两端都用实测 `rtt`；只有 A `rtt_a`；只有 B `rtt_b`；都没有 → 第一期的 `geo`/`geo_a`/`geo_b`（两端都没位置时返回 `None` 走轮询，同现在）。一端用实测时，即使两端都没位置，`score` 也返回 `Some`。
5. `score` 的返回值多带每台候选的 `(leg_a, leg_b)`，`decide` 把选中那台的两段放进 `RouteDecision`。

中继没有位置、某一端只有估计时，这台在那一端没有值，按第 3 条变成 `2 × 另一段`，和有位置的中继混排；第一期一端位置未知时本来就这样，不另处理。

### 3.4 Leapgate 心跳 handler 里本块的部分

01 块的请求结构体已按统一接口带上 `#[serde(default)] routing_rev: i64` 和 `probes: Option<serde_json::Value>`（先收成 `Value`，解析失败只丢测量，不回 400）。本块在响应结构体加 `#[serde(skip_serializing_if = "Option::is_none")] routing: Option<Routing>`，`Routing { rev, probe_interval_secs, relays }`，并在 handler 里验签通过、拿到**验签得来的设备 ID** 之后加：

```rust
match &req.probes {
    Some(p) => state.router.record_probes(&device_id, p),
    None => state.router.forget_probes(&device_id),
}
let (rev, relays) = state.router.routing();
if req.routing_rev != rev { resp.routing = Some(Routing { rev, probe_interval_secs: PROBE_INTERVAL_SECS, relays }); }
```

测量表的键因此是认证过的设备 ID；只有"拿哪台设备的测量算 A 这一段"用的 `leapgate_from_id` 不认证（§9 第 2 条）。旧路径 `device::heartbeat` 一行不改。

心跳不带 `probes`（显式 `null` 同样算不带）说明客户端手里没有当前列表的有效一轮，例如作废了经代理测的一轮、清掉了旧结果（§4.2 第 4 步），最近一轮已超过 900 秒，服务进程刚启动或刚换到新列表、首轮还没跑完，开了 Socks5 代理、WebSocket 或没配 Key。所以当场删掉这台的记录，选路下一次就退回估计值，不等 15 分钟过期（2026-10-24 端到端第 5 步发现最初的实现只在带 `probes` 时写入、不带时不清，补上了 `forget_probes`）。代价：客户端服务进程重启后第一次心跳就删掉还没过期的旧测量，首轮上报前约 15~60 秒按估计值选路，接受（旧测量可能来自换网之前）。`probes` 带了但被丢弃（形状不对、版本不对、太旧）时不删旧记录，照旧。心跳根本没发出去（断网）时服务端收不到任何东西，旧记录照常保留到过期。

### 4.1 `libs/leapgate/src/route/mod.rs`（新）

进程内状态（`static Mutex<Option<State>>` + `Condvar`），只在服务进程里有内容：

```rust
struct State {
    rev: i64,
    interval: Duration,
    relays: Vec<String>,
    confirmed_at: Instant,          // last successful Leapgate heartbeat
    result: Option<ProbeResult>,    // { rev, at: Instant, rtt: Vec<(String, u32)>, down: Vec<String> }
}
```

给 01 块心跳代码（`libs/leapgate` 里的 heartbeat，Leapgate 自己的文件）调的四个函数，签名以本表为准：

| 函数 | 01 块什么时候调 | 做什么 |
|---|---|---|
| `pub fn routing_rev() -> i64` | 组心跳请求 | 手里列表的 rev，没有为 0 |
| `pub fn probes() -> Option<serde_json::Value>` | 组心跳请求 | `result.rev == rev` 且测量不超过 900 秒时生成 §2.2 的 `probes`，否则 `None` |
| `pub fn on_heartbeat_ok(routing: Option<&serde_json::Value>)` | **每次**成功的心跳（2xx、配了 Key 时验签通过、有 `api`），传 `resp.get("routing")` | 没配 Key（01 块的 `sign::server_pk()` 不是 `Ok(Some(_))`）时直接返回，不采用 `routing`、不测速；否则刷新 `confirmed_at`，带了 `routing` 就解析（失败忽略）、`probe_interval_secs` 限在 60~3600、`relays` 截到 32 台；rev 变了就换列表、清旧结果、唤醒测速线程（第一次拿到非空列表时启动它） |
| `pub fn reset()` | API 根地址变了，或能力判为"不支持" | 清空状态，测速线程回到等待 |

"没配 Key 不采用"是为了不让明文 HTTP 上的中间人往 `relays` 里塞任意 `host:port`，把设备变成它在局域网里的端口扫描器（下一次心跳的 `probes` 还会把结果报回去）。这条不加状态：配了 Key 时 01 块只在验签通过后调本函数。

01 块先于本块合并（第 1 批）。为了让 01 块按上表写好调用点就能编译，01 块先放一个只有这四个函数空实现的 `route/mod.rs`（`routing_rev` 返回 0、`probes` 返回 `None`、另两个什么都不做），本块替换成真实实现，并加上下面的 `self_id()`。

给上游挂钩调的函数：

- `pub fn relay_preference(provided: &str) -> Option<String>`：`provided` 非空且 `crate::report::server_is_leapgate()` 为真时返回 `Some(provided.to_owned())`，否则 `None`。`server_is_leapgate()` 由 01 块提供：每次按上游 `get_api_server` 的规则（01 块的 `api_root()`）算出当前 API 根地址，和 Config options 里持久化的 `leapgate-api-caps` 比较，不依赖进程内状态或心跳先跑过，所以进程重启后、心跳被限速（429）时都不会掉，笔记 01 风险 5 随之消失；构建时注入的默认 API 地址视为已支持。手动填的地址在第一次 Leapgate 心跳成功前返回假，这几秒里被控端照上游用本地 `relay-server`。
- `pub fn self_id() -> String`：`Config::get_id_or(String::new())`。**不能用 `Config::get_id()`**：本进程 id 为空时它会就地生成新 id 并落盘（`hbb_common/src/config.rs` `Config::get_id` L1212~1221）【读码】，界面进程在服务进程没起来时调它会造出和服务进程不一致的 id。拿不到就发空串，服务端按估计值算。

### 4.2 `libs/leapgate/src/route/probe.rs`（新）：测速线程

**跑在哪**：一个专用 `std::thread`（进程内只起一个，`std::sync::Once`），用阻塞的 `std::net`，不用 tokio。理由：01 块的 tick 跑在 `sync.rs` 的单线程 tokio 运行时上，那里每个 tick 会同步调用阻塞函数（笔记 01 §7 核对记录 B3），放在同一个运行时上计时会被拉长。

**循环**：

1. 在 `Condvar` 上等，直到有非空列表、`confirmed_at` 在 15 分钟以内、并且配了 Key（同 §4.1 的判断）。`stop-service`、服务端不可达、能力丢失都会让心跳不成功，测速随之停。
2. 拿到新列表后先等 10~30 秒的随机时间（`hbb_common::rand`）再测第一轮，之后每轮间隔 `interval × (0.9~1.1)`；用 `wait_timeout` 等，rev 变了被唤醒，照样先随机等 10~30 秒再测（实现后改定：服务端换配置后所有设备同一刻拿到新列表，随机等一下避免同时测）。
3. 每轮开头：`Config::is_proxy()` 或 `hbb_common::config::use_ws()` 为真时这一轮不测并清掉旧结果（实际中继走代理或 WebSocket，直连测的数字没有代表性，笔记 01 §3.2）。
4. 各中继并发（`std::thread::scope`，每台一个线程，最多 32 个，测完即退）。2026-10-25 起测速和真实中继连接走同一条路（真实连接是 `connect_tcp_local(target, None, …)`：不绑本地地址、系统解析、系统路由【读码：控制端 `client.rs` `create_relay`、被控端 `server.rs` `create_relay_connection_`】），不计握手，计中继关连接：
   - 地址：`check_port(host, RELAY_PORT)` 后用 `std::net::ToSocketAddrs` 解析（每轮每台一次，时间不计入；fake-ip 下得到 `198.18.x` 照用，连进 TUN 后由代理映射回域名，正是真实路径），按返回顺序逐个尝试、取第一个连上的，和上游 `FramedStream::new` 连中继的顺序一致（`hbb_common/src/tcp.rs` L124~144）【读码】。
   - 每台测 3 次，间隔 200 毫秒。每次（`try_relay`）：`TcpStream::connect_timeout(addr, 3s)`；连上后等 `SETTLE`（1.5 秒），让在本机或路由器上先完成握手的代理把上游连好；等完非阻塞地 `peek` 一次，连接已关、出错或已收到数据就判这次失败（原版 hbbr 收到首帧前既不发数据也不关，等 30 秒；代理连不上中继、规则拒绝时会在这段时间里关掉）；然后发 1 字节 `0x00`（长度为 0 的帧）并开始计时，读到干净的 EOF（`read` 返回 0）停表，3 秒内没读到、读到数据或出错都判失败。记下（发出到关连接的耗时、对端地址）。
   - 依据【读码】：hbbr `relay_server.rs` 的 `make_pair_`（上游 `rustdesk-server@873230e`、leapgate-server、官方 1.1.15/1.1.16 逐字相同）收到能解析但不是 `RequestRelay` 的首帧（或解析不了的）就直接返回，连接随之关闭，不打日志、不查 key、不进 `PEERS`；长度为 0 的帧解析成空的 `RendezvousMessage`。不用 `RequestRelay` 当探测帧（key 不对会打 warn，key 对会在 `PEERS` 挂 30 秒）。
   - 一条作废规则（命中 → **整轮作废、不上报，并清掉 `State.result` 里的旧结果**（和第 3 步开了代理时一致，服务端最多再过一个心跳就退回估计值），打一条 `hbb_common::throttled_log!` 限频 info，60 秒一条，文字固定，§6.3 引用）：**公网中继 2 毫秒内关**：任一台对端地址是公网地址的中继，3 次里有一次从发出到关连接 < 2 ms。真实路径至少一个往返，比这还快说明关连接的不是中继（代理规则拒绝、安全软件见数据就断）。"公网"指对端地址不是私网（10/8、172.16/12、192.168/16）、回环、链路本地、`100.64.0.0/10`、IPv6 的 ULA（`fc00::/7`）和链路本地；fake-ip 段 `198.18.0.0/15` 和 `fdfe:dcba:9876::/48`（mihomo 的 IPv6 TUN 和 fake-ip 段，否则会被当成 ULA 豁免）算公网。日志 `leapgate route: probe round dropped, {} closed in {}us (not the relay?)`。误杀只发生在设备和中继同机房、或 fake-ip 下用域名配的局域网中继，后果是退回估计值。
   - 不作废时：成功的取最小值，毫秒向上取整、至少 1；3 次都失败进 `down`。
   - 原来的"本地地址不在物理网卡上""对端在 `198.18.0.0/15` 不看耗时"两条作废规则 2026-10-25 删掉（02a §4.3）。
5. 结果写进 `State.result`（带这一轮的 rev 和结束时刻）。

**纯函数拆分**（为了单测，不加测试专用的生产挂钩）：`summarize(rev, attempts: &[(host, Vec<Option<Attempt>>)]) -> Option<ProbeResult>`，`Attempt { elapsed: Duration, remote: IpAddr }`；作废规则在 `summarize` 里。网络部分 `try_relay(addrs, settle)` 的等待时长作为参数传入（生产传 `SETTLE`），回环测试用几百毫秒。

## 5. 兼容矩阵

服务端是 leapgate-server 时：

| 控制端 A | 被控端 B | 结果 |
|---|---|---|
| Leapgate | Leapgate | 两端都有实测时 `reason = rtt`；B 照用服务端选的中继，本地 `relay-server` 不再生效 |
| Leapgate | 原版 | A 段实测（`rtt_a`）；B 仍按上游优先用本地 `relay-server`，第一期心跳下发 `relay-server: ''` 照旧兜底 |
| 原版 | Leapgate | 没有 `leapgate_from_id`，A 段估计；B 段实测（`rtt_b`）；B 照用服务端选的中继 |
| 原版 | 原版 | 和第一期完全一样 |

其他组合：

| 情况 | 结果 |
|---|---|
| 任意客户端，服务端是原版 hbbs（有或没有 rustdesk-api） | Leapgate 心跳 404 → 能力"不支持"：不测速、`relay_preference` 返回 `None`，被控端和上游一样；`leapgate_from_id` 被 hbbs 忽略 |
| Leapgate 客户端，leapgate-server 只有 01 块、没有本块 | 响应不带 `routing`，不测速；`relay_preference` 照常生效（第一级选的中继优先） |
| Leapgate 客户端，API 地址没配、不可达、还没确认 | `server_is_leapgate()` 为假：同原版 hbbs 一行，照上游 |
| Leapgate 客户端没配 Key（本地 `key` 和构建注入的都为空） | 不采用 `routing`、不测速，服务端按估计值；`relay_preference` 照常生效 |
| Leapgate 客户端开了代理或 WebSocket | 不测、不报，服务端按估计值；`relay_preference` 照常生效 |
| 本机开 TUN、路由器透明代理或全隧道 VPN，不配任何规则 | 测速走真实中继路径，照常上报（2026-10-25 起；此前整轮作废） |
| 原版客户端走旧路径心跳 | 响应里没有任何 Leapgate 键，和第一期一样 |

## 6. 测试

### 6.1 服务端单元测试

- `cost::score`：两端实测（`rtt`）、只有一端（`rtt_a`/`rtt_b`）、两端估计（`geo*` 不变）；一端测量没覆盖全部可达候选 → 整端估计；`down` 去掉候选；全部 `down` → 忽略 `down`；两端都没位置但一端有实测 → 仍有代价；`a_ms`/`b_ms` 是选中那台的两段。
- `Measurements`：`routing_rev` 不符、`age_s > 900`、不认识的主机名、毫秒越界、形状不对（不 panic、不影响别的条目）；15 分钟后读不到；满 1 万条时先删过期、再删最老。
- `routing_rev`：同一列表同一值、`rs` 换列表后变化、空列表非 0。
- Leapgate 心跳 handler：`routing_rev` 相同不带 `routing`、不同带；`probes` 是字符串之类的坏值时心跳照常 200；测量记在验签得到的 ID 下；之后一次不带 `probes` 的心跳把这台的记录当场删掉。
- `handle_punch_hole_request`（用现有测试夹具）：带 `leapgate_from_id` 且双方有测量时 `conn_attempt.route_reason = 'rtt'`、`route_a_ms`/`route_b_ms` 非空；`leapgate_from_id` 超长按空串处理。
- 迁移 0005 能在第一期的库上执行；`route test` 带和不带 ID 的输出。

不测：中继真实建连耗时、GeoIP 估计常数（第一期已有）。

### 6.2 客户端单元测试（`libs/leapgate`）

- `summarize`：3 次取最小、毫秒至少 1、3 次失败进 `down`；公网对端（含 `198.18.x`、`fdfe:dcba:9876::/48`）1.5 ms → `None`；私网、`100.64`、ULA 对端 1 ms → 照常采信；`198.18.x` 对端 5 ms → 照常采信（2026-10-25 改）。
- `try_relay`（回环，2026-10-25 加）：模拟 hbbr（读一帧就关）→ 有耗时；发帧前就半关（代理连不上中继，仍在读，只有发帧前的检查能分辨）→ 失败；先发数据、收到帧后回数据 → 都失败。审查时的变异（去掉发帧前的检查、把 `Ok(0)` 放宽成 `Ok(_)`、去掉 IPv6 fake-ip 段、`<` 改 `<=`）都会让测试变红。
- `on_heartbeat_ok`：rev 变化换列表并清结果、`probe_interval_secs` 越界被限、`relays` 超过 32 台截断、坏 JSON 忽略；没配 Key 时不采用 `routing`。
- `probes()`：结果的 rev 和当前列表不符、超过 900 秒 → `None`。
- `relay_preference`：`server_is_leapgate()` 为真且 `provided` 非空 → `Some`；任一不满足 → `None`（用 01 块现成的设置入口构造能力缓存，不另加测试挂钩）。
- `self_id`：id 为空时返回空串、不生成新 id。

不测：真实网络、线程调度。

### 6.3 端到端验收（维护者）

准备：leapgate-server 配 2 台以上中继（手头只有一台时，在同一台机器的另一个端口再起一个 hbbr，主机串不同即可）；两台装 Leapgate 的 Windows，都配了 Key。2026-10-25 起不需要任何代理规则：A 保持日常的 fake-ip TUN，中继用域名配置。

1. 两台都在线 6 分钟后，服务端跑 `leapgate-server route test <A 公网 IP> <B 公网 IP> --a <A 的 ID> --b <B 的 ID>`：每台中继两段都显示 `rtt …ms` 或 `down`，**开着 TUN 也有数**，数字和到中继的真实往返同一量级（不是一律 1~2 ms）。`relay status` 的 `measurements` 行是 2 台、2 台新鲜。
2. A 连 B，连接结束后查 `conn_attempt` 最新一行：`route_reason = 'rtt'`，`route_a_ms`、`route_b_ms` 有值，和第 1 步对得上。
3. 被控端本地填一个和服务端选择不同的 `relay-server`，再连一次：`b_relay = relay_offered`。
4. 在 A 上用 Windows 防火墙临时阻断到其中一台中继的出站，等一轮（≤ 6 分钟）：`route test` 里 A 段这台显示 `down`，接下来的连接不选它；解除后恢复。
5. 测速跟着真实路径走（2026-10-25 改，原来这一步测作废规则）：
   - (a) 在 A 的代理里把一台中继设成走节点，等一轮（≤ 6 分钟）：`route test` 里 A 段这台的数字变成经节点的往返（明显变大）；改回直连后回到原来的量级。
   - (b) 在 A 的代理里把一台中继设成拒绝（REJECT），等一轮：A 段这台显示 `down`，接下来的连接不选它。
   - (c) 测速期间 hbbr 日志没有新增行。
6. 原版客户端连同一个 leapgate-server：照常连接，`route_reason` 是 `geo*` 或 `rtt_b`（被控端是 Leapgate 时）。

判定通过：1~6 全部符合。

## 7. 明确不做

- 测带宽、丢包、会话中的实际延迟；连接建立后换中继（方案 §3.7）。
- 让发起方或被控端自己选中继；被控端拿到服务端的中继后按自己的测量改选。
- 界面进程单独测速、把测量值放进打洞请求（笔记 01 §3.3 备选，已被已定决策否掉）。
- `RequestRelay` 加字段；用 `token` 反查发起方当兜底。

## 8. 需要维护者定的问题

本块没有 README.md 里 P-1~P-4 的决策点。下面两项属于"不回复即按推荐"。

**D2-1：`conn_attempt.a_device_id` 要不要用 `leapgate_from_id` 填。**
现在这一列只来自登录令牌（`auth::token_owner`），是认证过的值；`device list --legacy` 也拿它配"仅见于会合"的设备。`leapgate_from_id` 是控制端自报的、不认证。
- **推荐：不填、不存。** `leapgate_from_id` 只在内存里用于选路；用没用上 A 的测量看 `route_reason`（`rtt`/`rtt_a`）。代价：未登录的 Leapgate 控制端在 `conn_attempt` 里仍看不出是哪台设备。
- 备选 A：迁移 0005 另加一列 `a_from_id text`（截到 253 字节），只记自报值。代价：每行最多多约 260 字节（`server/LEAPGATE.md` §8 行大小估算要改），任何人都能往里写任意 ID，排障时要记得它不可信。
- 备选 B：令牌为空时用 `leapgate_from_id` 填 `a_device_id`。代价：同一列混着认证值和自报值，`device list --legacy` 会被伪造的 ID 污染。不推荐。

**D2-2：测速结果的采信口径。**（2026-10-25 被 D2-3~D2-5 取代：测速改成和真实中继连接同路、量到中继关连接，只留 2 毫秒下限，见 02a §8 和本文 §4.2。下面是原来的推荐和备选，留作记录。）
目标环境里机器都开 TUN 代理、路由器透明代理只代理 TCP，这一条决定第二级在这些机器上有没有数据、数据真不真。
- **推荐：只采信本地地址在物理网卡上的测量，并且任一公网中继原始耗时 < 2 ms 就整轮作废（§4.2 第 4 步）。** 两条都不加状态。代价：开代理的机器不把中继排除在代理之外就没有第二级（退回估计值）；经全隧道 VPN（WireGuard 全局、Tailscale 出口节点）上网的设备测量其实是真的，也被作废；设备和中继同机房时被 2 ms 规则误杀。另外，上游 `client.rs` L653~657 的注释说透明代理代答握手约 3 ms【读码】，维护者的路由器如果实测落在 2~3 ms（例如经 Wi-Fi），2 ms 拦不住，验收第 1 步会看到一律 2~3 ms 的数字；那时把阈值提到 5 ms 即可，代价是同城中继误杀更多。
- 备选 A：TUN 那条只排除 `198.18.0.0/15`（mihomo、sing-box fake-ip 的常见段），不看物理网卡。代价：TUN 地址改过（例如 sing-box 默认的 `172.19.0.1`）就混进假值；好处是全隧道 VPN 的设备有数据。
- 备选 B：透明代理那条改在服务端判：`Measurements::record` 用 GeoIP 算设备到中继的物理下限（大圆距离 × 2 / 200 km/ms，减几毫秒余量），低于下限整轮无效。代价：每条测量多查 GeoIP；经代理的设备服务端看到的是代理出口的位置，下限同样失真；位置库误差大时会误杀同城中继。
- 备选 C：不检查，照报。代价：开代理的设备每台中继都报约 1 毫秒，这一端没有区分度，`route_*_ms` 的校准数据失真。不推荐。

**D2-3~D2-5（维护者 2026-10-25 定，详见 02a §8）**：D2-3 测速和真实中继连接同路、量到中继关连接（方案甲；不采用"绑物理网卡 + 物理网卡 DNS"的方案乙）；D2-4 等待 `SETTLE` 取 1.5 秒；D2-5 保留 2 毫秒下限，按"发出到关连接"算，语义仍是整轮作废。

## 9. 已知限制和风险

1. **依赖原版 hbbr 对非 `RequestRelay` 首帧静默关闭**（2026-10-25 起；原来这一条是"开代理的机器默认没有测量"，随新做法消失）。上游哪天改成等到 30 秒超时，3 秒内没 EOF 就全判 `down`，服务端按"全 `down` 时忽略"退回估计，不会报假数；改成打日志就是每台设备每 5 分钟 3 × N 行噪音。合并上游 hbbr 时要复查 `make_pair_`。
   - 代理连上游超过 1.5 秒时，超出的部分算进往返（偏大，方向保守）；代理等收到数据才让节点去连中继（懒连接）时，多算一次节点到中继的握手【推测】。
   - 经代理时中继主机在而 hbbr 没起：代理多半在 1.5 秒的等待内就关连接、判这次失败；晚于 1.5 秒才关的会被当成 hbbr 关连接，量出偏小的数。服务端健康检查（从服务端直接 TCP 建连，`router/mod.rs` `health_round`）会先把这台判不可达、从候选里去掉。
   - 代理收到上游的关连接后不及时关本地连接时，3 秒内没 EOF，判失败；全部这样时服务端退回估计。mihomo 是及时的【实测，02a §4.2】，其他代理软件【推测】。
   - 代理在多个节点间负载均衡、每条连接选不同节点时，3 次取最小，数字偏向最快的节点。
2. **`leapgate_from_id` 不认证**：A 冒用别人的 ID，只会让 A 自己这次连接按别人的测量选路，不影响别人的选路；测量表的键来自设备签名，伪造不了别人的测量。服务端不回测量，但冒用者能从选路结果侧面推断被冒用设备到各中继的相对延迟、以及它最近一次心跳是否带了完整测量（2026-10-24 审查指出：用自己控制的 B 反复调上报值、看选中哪台中继，二分出来；同日补上"不带 `probes` 当场删除"后，粒度变成一个心跳周期，能看出它此刻是否在代理或 TUN 后面、是否刚重启），被冒用设备察觉不到。信息量不超过直接向它打洞拿到的公网 IP，接受。不把 A 的测量绑定到心跳来源 IP：心跳的 HTTP 和会合的 TCP 本来就可能从不同出口出去（例如路由器只代理 TCP 的环境）。
3. **测的是 SYSTEM 服务进程的网络路径**：用户会话走分用户 VPN、按应用分流的代理时，和界面进程实际发起连接的路径可能不同（笔记 01 风险 4）。
4. **实测和估计混用的偏差**：一端实测、一端估计、权重又不全是 1 时，实测端的"最后一公里"会让代价略偏（笔记 01 §3.5、风险 3）。`route_a_ms`/`route_b_ms` 就是给以后校准第一级常数用的。
5. **最多 32 台中继参加第二级**：第 33 台起永远是 `Unknown`，它可达时两端都退回估计，等于第二级失效。启动时 warn。
6. **DNS 解析没有超时**：`ToSocketAddrs` 是阻塞的系统解析，某台中继解析卡住时这一轮推迟（只在测速线程里，不影响心跳和连接）。
7. **IPv4 字面量中继 + 只有 IPv6 的网络**：真实连接会把 IPv4 字面量改写成 `<ip>.nip.io` 走 NAT64（`ipv4_to_ipv6`），测速不做这一步，那台中继会进 `down`、被这一对排除。中继一般配域名，第一阶段不处理。
8. **开销**（估算，没实测）：每台设备每 5 分钟 N × 3 次建连，N = 4 时一天约 3500 次、约 2 MB；hbbr 对"连上就关"的连接不打日志、不计数、不封禁（笔记 01 §2.7、§3.6）。2026-10-25 起每条测速连接在 hbbr 那边多挂约 1.5 秒（一个等首帧的任务）、多收 1 个字节，同样不打日志、不计数；每台中继一轮约 5~6 秒，各中继并发。
9. **2 ms 下限的误杀**：设备和中继同机房、或 fake-ip 下用域名配的局域网中继，往返不到 2 毫秒，整轮退回估计。（原来这一条是"路由器代答落在 2 ms 以上时拦不住"，2026-10-25 起不再靠这条规则识别代答，问题随之消失。）
10. **没有实测**：整端替换是否比第一级选得更好，要上线后从 `conn_attempt` 的 `route_reason` 和两段延迟里看。
11. **API 和会合服务器不是同一台时**：`relay_preference` 只看 API 根地址是不是 leapgate-server，不看被控端当前连的会合服务器。`api-server` 手动指向 leapgate-server、`custom-rendezvous-server` 却指向原版 hbbs 时，被控端会拿 hbbs 的轮询结果盖掉本地 `relay-server`。这种配置不常见，后果只是选错中继，不加比较。
12. ~~整代代答时数据无害、部分代答时有害~~：2026-10-25 起不计握手、量到中继关连接，按目的地分流时每台中继量到的都是它自己那条真实路径，这一条不再成立。
