## 1. 目标与范围

**做什么**：控制端（发起连接、使用出口的一方）在 TCP 隧道窗口里加一条"出口映射"。这条映射不像普通映射那样把一个本地端口转到对面固定的 host:port，而是在本机 `127.0.0.1:<端口>` 开一个最小的 SOCKS5 / HTTP CONNECT 代理：每个本地代理连接变成多路复用隧道里的一个通道，目标由连接自己指定，由被控端代为连接。另外在连接页菜单里加"出口节点"目录，列出服务端说你此刻能用的出口。

**术语**（第一次出现时解释，后文直接用）：
- **多路复用隧道 / 通道**：上游 1.5.0 起的端口转发模式（`src/port_forward_mux.rs`），一条远程会话里开多个通道，每个通道一个目标；控制端发 open 帧开通道，被控端回 opened 帧（带成败和一句文案）。
- **出口映射**：存在 PeerConfig `port_forwards` 里的一行 `(本地端口, "leapgate-exit.invalid", 65536)`，用哨兵目标标记"这一行是出口"（§2.1）。
- **哨兵登录目标**：控制端登录时报的 `PortForward{host="leapgate-exit.invalid", port=65536, multiplex=true}`，被控端看到它就按出口处理（C1）。
- **乐观应答**：隧道已建好时，本地代理先回"连接成功"再开通道，被控端后来拒绝或连不上目标，本地程序只看到连接被关（C5 (A)）。
- **终止性 / 临时性失败**：建隧道失败的两类（C9）。终止性的关掉这条映射的监听，临时性的冷却 10 秒后由下一个本地连接再试。
- **socks5h**：curl 等程序的写法，表示域名交给代理解析；写成 `socks5://` 时程序会在本机解析域名。
- **CM**：被控端的连接管理小窗；**能力缓存**：契约 01（第三期）定义的"这个 API 地址支持哪些特性"（Config 选项 `leapgate-api-caps`）。
- **frb**：flutter_rust_bridge，Dart 界面调用 Rust 函数的绑定生成器，`bind.xxx` 都是它生成的。
- **TestDelay**：被控端每秒发一次的测延迟报文（`connection.rs:501` `TEST_DELAY_TIMEOUT`），控制端回应；会话因此一直有流量，不会因为静默被中继断开。
- **裸管道**：1.5.0 以前的端口转发方式，登录后整条连接直接透传到登录时报的那一个固定目标，不分通道（`listen` 里的 `Claim::Legacy` 一支）。

### 2.1 哨兵和 65536 的核实

主会话裁定：线上登录和本地映射统一用 `host="leapgate-exit.invalid"`、`port=65536`、`multiplex=true`，整串精确比较（大小写、结尾的点都不认）。理由：65536 在普通添加行里输不出来；万一被 1.5.0 以前的原版被控端拿去走裸管道，解析端口当场失败、不查 DNS（和 P-2 一致，不依赖解析失败）。逐条核实 65536 在控制端各路径上不会被截成 u16、也不会被拒【读码】：

| 路径 | 类型和处理 | 结论 |
|---|---|---|
| Dart 普通添加行 | 端口输入框只放行 0~65535（`port_forward_page.dart:187-190`） | 用户手输不出哨兵；出口按钮直接传 65536，不经这个输入框 |
| `bind.sessionAddPortForward` → `session_add_port_forward` | `remote_port: i32`（`flutter_ffi.rs:1716-1725`） | 原样 |
| `Session::add_port_forward` → PeerConfig | `port_forwards: Vec<(i32, String, i32)>`（`hbb_common/src/config.rs:329`），反序列化只用默认值宏、不查范围（`:2742`） | 原样落盘、读回 |
| 映射启动时的过滤 | `if port <= 0 \|\| remote_port <= 0 { continue; }`（`ui_session_interface.rs:2013`） | 通过 |
| 命令行 `--port-forward` | `parse::<i32>()`（`ui_session_interface.rs:2051-2059`） | 通过（顺带能从命令行起出口，无害） |
| 登录 | `LoginConfigHandler.port_forward: (String, i32)`（`client.rs:2857`），组进 `PortForward.port`（int32，`message.proto:52`；`client.rs:3890-3893`） | 原样上线 |
| Dart 显示 | `_PortForward.fromJson` 读 `int`（`port_forward_page.dart:21-24`） | 原样；出口行另画（§3.8） |

被控端各路径（02 块写法为准，这里只记核实结果）【读码】：登录分支规范化 `format!("{}:{}", host, port)` 得 `"leapgate-exit.invalid:65536"`（`connection.rs:1789-1799`）；`login_scope_digest` 按 i32 取 `to_le_bytes`（`connection.rs:2793-2803`）；CM 收到的是字符串（`try_start_cm`，笔记 01 §4）；原版 1.5.0 以前走裸管道的 `TcpStream::connect(&addr)`（`connection.rs:1821`）在 std 的 `str` 解析里按最后一个冒号切开、把 `65536` 解析成 u16 失败，回 `InvalidInput`、不发 DNS 查询【推测，按 std 实现推断，本机没有 rust-src；§5 T8 用单测钉住】。所以 65536 全线可行，不改回端口 1。

哨兵常量 `SENTINEL_HOST`、`SENTINEL_PORT: i32 = 65536` 和 `is_exit_target(host, port)` 由 S0 放在 `libs/leapgate/src/exit/mod.rs`（README §2.6），本块直接用；Dart 一侧的同名常量也在 S0 的 `exit_tunnel.dart` 里（§3.8）。

### 3.2 `exit/mod.rs`（本块往里加的部分）

四个子模块的声明、哨兵常量、`is_exit_target`、`allowed`、`login_refusal` 和 §2.4 的五条文案都在 S0（README §2.6），这里不再定义。下面的 `CONTROLLER_MUX_ONLY`、`PEER_TOO_OLD` 照 README §4 第 2 步放进本块第一个（C11）提交，其余放后面的出口提交。

```rust
/// C11. A constant rather than a bare `return true` so upstream's lines after the hook stay
/// reachable to the compiler (no unreachable_code warning, nothing modified).
pub const CONTROLLER_MUX_ONLY: bool = true;
/// C9: after a temporary failure, local connections are refused for this long.
pub const RETRY_COOLDOWN: Duration = Duration::from_secs(10);
pub const NOT_SUPPORTED: &str = "The remote device does not support acting as an exit node";
pub const PEER_TOO_OLD: &str = "The remote device is too old for port forwarding";

/// How `connect_and_login_mux` ended, as the hook maps it.
pub enum LoginEnd { Peer { mux: bool, exit: bool, secured: bool }, Refused, Failed }
pub enum Next { Use, Stop(Option<&'static str>), Cooldown }
pub fn after_login(end: LoginEnd) -> Next;
```

`after_login` 的规则（C3、C9、C10）：`Peer` 三项全真 → `Use`；`mux`、`exit`、`secured` 任一为假 → `Stop(Some(NOT_SUPPORTED))`（C3 定三项共用一句"对方不支持作为出口"；第四期被控端在登录关口已经先查了开关、多路复用、加密并回了各自的登录错误，A11，所以这里实际只会碰到没有出口位的旧对端）；`Refused` → `Stop(None)`（被拒、用户在不安全确认框里点了关闭；上游已经弹过框，不再弹）；`Failed` → `Cooldown`（对端离线、超时、中继失败、连接中途断开）。

### 3.3 `exit/proxy.rs`：本地代理握手（C4）

```rust
pub const HANDSHAKE_TIMEOUT: Duration = Duration::from_secs(10);
pub const MAX_HEAD: usize = 8 * 1024;
#[derive(Clone, Copy)] pub enum Kind { Socks5, Http }
pub struct Request { pub kind: Kind, pub host: String, pub port: u16, pub leftover: Vec<u8> }
#[derive(Debug)] pub enum Refused { Socks4, NoMethod, Command, AddressType, BadTarget, NotConnect, BadRequest, Timeout, Io }
/// Reads one request within HANDSHAKE_TIMEOUT. On refusal the refusal reply is already written.
pub async fn accept<S: AsyncRead + AsyncWrite + Unpin>(s: &mut S) -> Result<Request, Refused>;
pub async fn reply<S: AsyncWrite + Unpin>(s: &mut S, kind: Kind, ok: bool) -> io::Result<()>;
fn parse_connect(head: &[u8]) -> Result<(String, u16), Refused>;   // pure, HTTP
```

整段握手一个 10 秒上限，超时直接关、不回任何字节。读第一个字节分流：

- **`0x05`，SOCKS5**（RFC 1928）：读 `NMETHODS` 和方法表，含 `0x00`（无认证）回 `05 00`，否则回 `05 FF` 后关（`NoMethod`）。请求按精确长度 `read_exact`，不多读，所以 SOCKS5 没有 `leftover`。`VER` 不是 5 直接关；`CMD` 不是 `0x01`（CONNECT）回 REP `0x07`（`Command`，BIND、UDP ASSOCIATE 都在这里）；`ATYP`：`0x01` IPv4、`0x04` IPv6，主机写成 `IpAddr::to_string()`（IPv6 不带方括号）；`0x03` 域名，长度 1~255、必须是 UTF-8，**原样**交给被控端（不转小写、不做 IDNA、不在本机解析，也不认出"其实是 IP 字面量"的域名串，交给被控端判）；其他 `ATYP` 回 REP `0x08`（`AddressType`）。端口 0、域名长度 0 或不是 UTF-8 回 REP `0x01`（`BadTarget`）。
- **`0x04`，SOCKS4/4a**：回 `00 5B 00 00 00 00 00 00` 后关（`Socks4`）。
- **其他，按 HTTP**：读到 `\r\n\r\n` 为止，请求行加请求头最多 8 KiB，到上限还没读到结尾回 400（`BadRequest`）。请求行按单个空格切成恰好三段，方法区分大小写：不是 `CONNECT`（包括 origin-form 的 `GET /path` 和 absolute-form 的 `GET http://host/path`）回 501 后关（`NotConnect`）；版本不以 `HTTP/1.` 开头、authority 不是 `host:port` 或 `[v6]:port`、不带方括号的 IPv6、主机为空、端口不是 1~65535 的十进制回 400（`BadRequest`）。方括号里的内容去掉括号后作为主机。**所有请求头一律忽略**（不看 `Host`、不看 `Proxy-Authorization`）。读到的 `\r\n\r\n` 之后的字节放进 `leftover`，开通道时先发出去。

应答字节写死：

| 情况 | 字节 |
|---|---|
| SOCKS5 成功 / 失败 | `05 00 00 01 00 00 00 00 00 00` / `05 01 00 01 00 00 00 00 00 00` |
| SOCKS5 拒绝（握手阶段） | 同上格式，REP 为 `07`、`08`、`01` |
| HTTP 成功 | `HTTP/1.1 200 Connection established\r\n\r\n` |
| HTTP 失败 / 501 / 400 | `HTTP/1.1 502 Bad Gateway\r\nContent-Length: 0\r\nConnection: close\r\n\r\n`，501 `Not Implemented`、400 `Bad Request` 同样格式 |

不引入 fast-socks5、httparse（C4）。网页里的 fetch 和 WebSocket 发不出 `CONNECT` 请求行，也发不出 `0x05` 开头的字节，DNS 重绑定到 `127.0.0.1` 的网页借不到出口（C4）。控制端不预先过滤 `198.18/15` 字面量（C12），原样交给被控端按 B3 硬拒。

### 3.4 `exit/directory.rs` 和 `api.rs`（F3、D2）

### 3.6 `src/leapgate_hooks/exit.rs`：出口监听循环

```rust
#[cfg(not(any(target_os = "android", target_os = "ios")))]
pub(crate) async fn run<T: InvokeUiSession>(handler: Session<T>, port: i32,
    receiver: mpsc::UnboundedReceiver<Data>, key: &str, token: &str);
pub(crate) fn get_common(key: &str) -> Option<String>;   // KEY → directory_json()
#[tokio::main(flavor = "current_thread")]
async fn directory_json() -> String;                      // leapgate::exit::directory::fetch().await
```

`get_common` 走 `main_get_common` 的异步 FFI 路径，frb 在自己的工作线程上调它、不在 tokio 运行时里，所以照上游 `ui_interface.rs:1484`、`:1495` 的写法用 `#[tokio::main(flavor = "current_thread")]`，不会嵌套运行时；Dart 只能用 `mainGetCommon`，不能用 `mainGetCommonSync`（会卡住界面线程，和 `flutter_ffi.rs:2776-2780` 不让下载地址走同步路径同理）。

`run` 的流程：
1. **监听**：`tcp::new_listener(format!("127.0.0.1:{}", port), false)`，第二个参数 `false` 就是普通 `TcpListener::bind`，不设 SO_REUSEADDR（`hbb_common/src/tcp.rs:257-269`；上游端口转发传的是 `true`，`port_forward.rs:84`）。只绑 127.0.0.1、不加认证、被占用直接报错、不换端口（A10）：`handler.on_error(&format!("Failed to listen on {}: {}", port, err))` 后返回，文字和上游 `start_one_port_forward` 一致。成功打 `leapgate exit: listening on 127.0.0.1:{port}`。
2. **主循环**（`tokio::select!` 三支）：
   - `listener.accept()`：每个本地连接 `tokio::spawn` 一个握手任务，`proxy::accept` 成功就把 `(socket, Request)` 送进一个容量 `port_forward_mux::MAX_CHANNELS`（256）的 `mpsc`；失败打限频日志 `leapgate exit: local handshake refused ({Refused:?})`（60 秒，不带地址）。握手不在主循环里做，慢客户端拖不住别人。
   - `ready.recv()`：处理一个已握手的请求（下一条）。
   - `receiver.recv()`：`Data::Close` 或通道关闭就退出循环，其他消息忽略（照上游 `listen`）。退出时丢掉 `Tunnel`，隧道随之结束（上游 `lifetime` 机制，`port_forward_mux.rs:455-460`、`:741`）。窗口关掉时 `io_loop` 的运行时整个结束，监听一起停（F1）。
3. **处理请求**：`tunnel.claim()`：
   - `Claim::Muxed(h)`：先 `proxy::reply(ok=true)`，再 `h.open(&req.host, i32::from(req.port), socket, req.leftover)`（C5 (A)：先写成功应答再开通道）。`open` 报错（隧道刚断、通道满 256）时连接被丢弃，打限频日志 `leapgate exit: local connection dropped, tunnel unavailable`。
   - 其他（`Claim::Claimed`，内部状态是 Unset 或 Failed 时返回这个；`Claim::Legacy` 走不到，因为出口从不 `set_legacy`，可以和 `Claimed` 合进同一个 `_` 分支）：冷却期内（`cooldown` 是循环里的一个 `Option<Instant>`）回失败、打限频日志 `leapgate exit: local connection refused, retrying after cooldown`，结束。否则**在主循环里就地建隧道**，和上游 `establish_tunnel` 一样 await 它：把这个请求的 socket 包成 `Framed` 交给 `connect_and_login_mux(&id, &handler.password, &mut receiver, handler.clone(), &mut forward, key, token, false, &mut cancelled, SENTINEL_HOST, SENTINEL_PORT)`。这期间新到的本地连接留在内核的 accept 队列里，已握手的留在 `ready` 里，等结果出来一起处理，这就是 A6、C9 的"排队"。密码框、2FA 框、不安全确认框都由 `connect_and_login_mux` 照上游处理（A6：复用本窗口内存里上次验证通过的密码，`handle_hash` 的 "last password" 一支，`client.rs:4703-4704`）。
4. **按 `after_login` 走**（结果映射：`Ok(Some(o))` → `Peer{mux: o.mux, exit: 读 lc.peer_info 的 leapgate_exit, secured: o.stream.is_secured()}`；`Ok(None)` → `Refused`；`Err` → `Failed`）：
   - `Use`：`handler.set_connection_type(true, lc.direct == Some(true), "")`（F4：复用 `connection_ready` 事件，`flutter.rs:742-751`；`stream_type` 传空串，因为 `connect_and_login_mux` 丢掉了上游的类型标签，`port_forward.rs:418`；H-6 给返回值加的只是 KCP 守卫，不为一个括号里的标签再加字段），打 `leapgate exit: tunnel up ({direct|relayed})`；`let h = tunnel.set_muxed(o.stream, handler.clone())`；`o.local_eof` 为假时，`prebuf = req.leftover` 接上 `o.prebuf`，`take_socket(forward, prebuf)` 取回 socket（它会再接上编解码器里读了没交出的字节，`port_forward.rs:545-550`），回成功、`h.open`。之后 `ready` 里排着的请求在下几轮循环里走 `Claim::Muxed`。`o.kcp` 存进 `run` 里的局部变量 `kcp_guard`（`Option<KcpStream>`），和 `Tunnel` 同生命周期；`tunnel.claim()` 返回 `Claimed` 时，先把 `kcp_guard` 置为 `None` 再建隧道；退出循环时它随 `Tunnel` 一起丢掉。
   - `Stop(msg)`：给这个请求和 `ready` 里排着的（`try_recv` 取空）都回失败；`msg` 为 `Some` 时 `handler.on_error(msg)`（这条监听只弹这一次）；打 `leapgate exit: tunnel refused, listener closed`；**退出循环**，关掉监听，要重开映射或重开窗口才再试（C9）。
   - `Cooldown`：同样给这个和排着的都回失败；`cooldown = Some(now + RETRY_COOLDOWN)`；`handler.on_establish_connection_error(err.to_string())`（和上游端口转发同一种提示，Flutter 的 `msgBox` 先 `dismissAll` 再显示，`flutter/lib/common.dart:1178-1208`，重复失败只替换不叠加）；打限频日志 `leapgate exit: tunnel failed, retrying after cooldown: {err}`（60 秒）。
5. **隧道之后断了**：上游 `tunnel_loop` 把状态复位成 `Unset`（`port_forward_mux.rs:746`），下一个本地连接重新建（C14 懒建立；空闲不拆，TestDelay 保活，`:722`）。通道被拒时上游 `tunnel_loop` 已经按文案去重弹框（`:718-720`）。C5 (A)、F8 的"策略拒绝和 198.18 字面量各弹一次、其余不弹"靠被控端回的文案实现（其余失败回空文案，`first_report_at` 对空文案不弹，`:660`）。另外，会话中途关了出口开关时，出口隧道上新开的通道回 `MSG_NOT_ENABLED`（README §2.4 第 4 行、§3.1 M-2），同样按文案去重弹一次（也就是 F8 隧道层的"没开出口"），随后整条会话由 B8 的每秒定时器断开。这几种情况控制端都不改。

跨 await 不持有 `lc` 的读写锁：`start_one_port_forward` 被 `tokio::spawn`（`ui_session_interface.rs:2021`），整个 future 必须是 `Send`。

### 3.11 吞吐相关的说明（E2、E4、E7、E8，本块不改代码）

- E2：`CHANNEL_WINDOW`（256 KiB）第一版不改。常量只在 `src/port_forward_mux.rs:23` 定义一处，被控端导入同一个；以后调大时 `UPDATE_THRESHOLD`（`:30`，现为 `CHANNEL_WINDOW / 2`）必须钉成字面量 128 KiB 并用单测钉住，否则和 256 KiB 的旧对端互连时通道会静默卡死【推测，读码推出】；ICE 路径另受 KCP 约 1.15 MiB 的在途上限约束，调过 1 MiB 没有收益。

## 5. 测试

### 5.1 单元测试（`cargo test -p leapgate`，用 `tokio::io::duplex` 当连接）

- T1 SOCKS5 域名：`05 01 00` 得 `05 00`；`05 01 00 03 0b "example.com" 01 bb` 得 `Request{Socks5, "example.com", 443, []}`；`reply(ok)` 写出 `05 00 00 01 00…00`。
- T2 SOCKS5 拒绝：方法表没有 `00` 得 `05 FF`；CMD `02`、`03` 得 REP `07`；ATYP `05` 得 REP `08`；端口 0、域名长度 0 得 REP `01`。
- T3 SOCKS5 IP 目标：IPv4 `192.0.2.1`、IPv6 `2001:db8::1`（不带方括号）原样成主机串。
- T4 SOCKS4：`04 01 …` 得 `00 5B 00 00 00 00 00 00`。
- T5 HTTP CONNECT：`CONNECT example.com:443 HTTP/1.1\r\nHost: other.test:80\r\n\r\nXYZ` 得主机 `example.com`、端口 443、`leftover = "XYZ"`（`Host` 头不影响目标）；`[2001:db8::1]:443` 得 `2001:db8::1`。

- T7 `after_login`：三项全真 `Use`；任一为假 `Stop(Some(NOT_SUPPORTED))`；`Refused` 得 `Stop(None)`；`Failed` 得 `Cooldown`。

## 7. 已知限制

1. 本地端口不认证：本机任何程序、同机其他 Windows 账户都能用这个端口走出口（A10）。程序里请写 `127.0.0.1`，监听不含 `::1`。
2. 乐观应答（C5 (A)）：目标被拒、连不上、超时时，本地程序只看到"连接成功后马上被关"，curl 报的是空回复一类错误而不是准确原因；只有策略拒绝（`MSG_BLOCKED`）、198.18 字面量（`MSG_FAKE_IP_LITERAL`）、会话中途关了出口开关（`MSG_NOT_ENABLED`，随后整条会话由 B8 断开）这三种各弹一次框（10 秒去重，最多 8 种文案），其余失败回空文案、不弹。
3. 非直接 IP 访问且流没加密时，`connect_and_login_mux` 会先弹上游的"不安全连接"确认框，点继续后才被两端的加密检查拒掉（C10）；直接按 IP 连接的方式不能当出口用。
4. 状态显示是最近一次建立隧道时的（F4），隧道断开不更新；终止性失败后监听已关，但出口行仍在，要删掉重加或关窗重开才再试（C9）。
5. 临时性失败后 10 秒冷却期内，本地连接一律立即失败（C9）。
6. 隧道窗口开着就一直占着，经中继时占一对 hbbr 连接，每月约耗 1~2 GB 中继额度【推测】；想重试直连或解除 hbbr 降速，关掉窗口再开（C14）。
7. 隧道重建照上游认证（A6）：内存里没有可用密码（只有临时密码且已过期）时会再弹密码框；被控端是点击确认模式时每次重建都要有人点。无人值守的出口请被控端设固定密码。
8. 队头阻塞和拥塞（E4）：隧道里所有通道共用一条有序连接，丢一个包所有通道一起停，整条隧道在链路上只算一条流的拥塞窗口；ICE 走的 KCP 不做拥塞控制，长时间大流量可能挤满被控端上行，逃生口是现成的 `allow-kcp-congestion-control`；隧道选定路径后不再换。
9. 被控端发送队列共用（E7），下载跑满时新连接首包变慢。
10. C11 之后 Leapgate 控制端不能再对 1.5.0 以前的原版被控端做端口转发和 RDP；设置页的 "Reuse one connection for port forwarding" 对 Leapgate 控制端不再起作用（勾选框照旧显示，F7 不改它）。
11. 目录只在打开时取一次，可能过时；它只是建议，不在目录里的设备手填 ID 照样能用，在目录里的也可能连不上（撤销授权不断已有会话，A2）。
12. Chrome、Edge 要装代理扩展或带启动参数才能用（C7）；控制端开着 fake-ip 时，在本机解析域名的程序（写成 `socks5://`）发出的是 198.18 字面量，会被被控端拒绝并提示改用 socks5h（C12）。
13. 上游逐通道的 `debug` 行（通道号、固定文案）照旧进日志文件（§3.9）。
14. 建隧道期间删除这条映射发来的 `Data::Close` 会被 `connect_and_login_mux` 吞掉（上游同样，`port_forward.rs:481-492` 的 `_ => {}`），要等登录结束才停。关窗口不受影响：`io_loop` 收到 `Data::Close` 直接退出（`ui_session_interface.rs:2039-2041`），`#[tokio::main(flavor = "current_thread")]` 的运行时随之丢弃，正在登录的映射任务当场结束【读码】。
15. 普通映射和 RDP 经 KCP（ICE 或上游 UDP/IPv6 打洞胜出）时，登录一完成连接就失效：上游 `connect_and_login`（`port_forward.rs:177`）和 `establish_tunnel` 都丢掉了 KCP 守卫，第三期起 ICE 让这种情况变得常见。H-6 只让出口留住守卫；普通映射要改上游建隧道的路径，超出 C8，本期不做，由维护者另定。
