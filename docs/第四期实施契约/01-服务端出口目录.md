# 服务端出口目录与授权（leapgate-server）

> 标注：【读码】读过现版源码；【推测】推断，没有实测。服务端代码锚点对照 leapgate-server main `1241ca7`（A3 合入后的 HEAD），客户端对照 leapgate-client main `a57605c2f`。"清单"指 `docs/research/第四期/03-设计决策清单.md`，条目编号（A1、D2、E3…）沿用清单；"笔记 02"指同目录的 `02-服务端读码.md`，清单"核对时更正的事实"一节优先于笔记原文。

## 1. 目标与范围

**做什么**：
- 被控端在 Leapgate 签名心跳里多报一个布尔值 `exit`（此刻接受出口登录），服务端只放内存。
- 新接口 `GET /api/leapgate/user/v1/exits`，凭用户令牌列出这个用户此刻能用的出口：自己名下的设备，加上命令行授权给他本人或他所在组的设备。
- 新表 `exit_grant`（迁移 0007）和命令行 `exit grant|revoke|list` 管授权。
- 设备主人加固（A1）：已锁定公钥的设备，登录不再覆盖已有主人；延迟补绑只认锁定之前签发的令牌；新命令 `device owner` 由运维指定主人。
- hbbr 的部署参数（E3），只写部署说明，hbbr 代码不动。

**边界**：服务端只负责"发现"出口，不是关口（清单 A2 选了 (a)）。出口能不能用，由被控端的出口开关加上游认证决定（02 块），目录和授权表都不参与连接。

**术语**：
- **出口目录**：服务端回给控制端的"你此刻能用的出口"列表，只是建议。不在目录里的设备，知道 ID 和密码的人照样能手填 ID 使用。
- **授权表**：`exit_grant`，一行是"一个设备 ID 授权给一个用户或一个组"，只用命令行维护。
- **设备主人**：`device.user_id`（`server/LEAPGATE.md` §11），主人总能在目录里看到自己开着出口的设备。
- **锁定**：第三期契约 01 的公钥锁定，`peer.pk_pinned_at` 非空表示已锁定。
- **延迟补绑**：设备行没有主人时，拿这台设备上登录留下的令牌补上主人（`OWNER_FROM_TOKEN`，§11）。
- **淘汰**：`device` 表满 1 万行时，新建行会删掉最老的可淘汰行（§9.3）。

## 2. 本块定下的接口

本节是 README §2.5 的服务端细节（README §2.5 写明细节以本节为准），下面四项是服务端一侧的线上格式。

### 2.1 心跳加字段 `exit`

`POST /api/leapgate/v1/heartbeat` 的请求体（第三期契约 01 §2.3）加一个键：

| 字段 | 类型 | 含义 |
|---|---|---|
| `exit` | bool | 被控端此刻接受出口登录。02 块用 `leapgate::exit::allowed()` 算它（README §2.3；登录关口经 `login_refusal()`、每个 open、B8 定时器调的也是它，D6）。客户端为真时带 `"exit": true`，为假时不带 |

- 服务端按 `#[serde(default)]` 收，不出现等于 false，两种写法都接受。出现了但不是布尔值时，整条心跳回 400 `bad_request`，和 `routing_rev` 类型不对一样处理，这次不写内存记录。
- 不落库，不上报放行网段（D1：放行网段会暴露被控端的内网拓扑）。
- 响应只有 `features` 变了（§2.2）。

### 2.2 能力宣告 `"exit"`

心跳响应的 `features` 从 `["ice"]` 改成 `["ice", "exit"]`。`"exit"` 只表示"这台服务端有目录接口"，不表示有可用的出口，也不随私钥或配置变（常量）。控制端靠它决定要不要请求目录（F3，`leapgate::report::has_feature("exit")`，03 块）。客户端把 `features` 当任意字符串列表存，第三期客户端不认识 `"exit"` 也不受影响（客户端 `libs/leapgate/src/report/mod.rs:176-195`，`parse_caps`、`feature_in`）【读码】。

### 2.3 目录接口 `GET /api/leapgate/user/v1/exits`

```
GET /api/leapgate/user/v1/exits
Authorization: Bearer <用户令牌>
```

没有请求体、没有查询参数、不分页。成功回 200：

```json
{"exits": [
  {"id": "<设备ID>", "hostname": "study-pc", "owner": "alice", "own": true},
  {"id": "<设备ID>", "hostname": "", "owner": "bob", "own": false}
]}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | string | 设备 ID |
| `hostname` | string | `device.hostname`（从 sysinfo 拆出来的）；没有设备行或还没收到 sysinfo 时为 `""` |
| `owner` | string | 主人的用户名（`user.name`）；没有主人为 `""` |
| `own` | bool | 主人就是请求者 |

- **列谁**：主人是我的设备；授权表里授权给我本人的设备；授权给我所在任一组的设备（查询时按 `group_member` 展开，成员变了当场生效）。同一台设备满足几条也只列一次。管理员和普通用户一样，没有全局视图（D7），要看全部授权用命令行 `exit list`。
- **只列此刻可用的**（判据见 §2.4），先列 `own` 为真的，再按 `id` 排序；一个都没有时回 `{"exits": []}`。不给 IP、系统用户名、系统版本、离线设备（A13、D2）。
- **错误**按 `server/LEAPGATE.md` §9.1 的通则，因为这个前缀不是 §9.5 的设备上报路径（§3.8 的新 §9.6）：
  - 没带令牌、令牌无效、账号禁用：401 `{"error":"Unauthorized"}`。
  - 认证那一步查库失败：200 `{"error":"Server error"}`，这是提取器 `CurrentUser` 的现有行为（`src/api/mod.rs:292`）；之后的查库失败：400 `{"error":"Server error"}`。
  - 用错方法 405 `{"error":"Method Not Allowed"}`；整请求 20 秒没答完回 400 `{"error":"Request timeout"}`。
  - 所以控制端（03 块）这样判：200 且带 `exits` 数组才算成功；401 当"没登录或登录已失效"；其余一律当"网络错误"。
- 不签名（D8：目录不是关口，现有的响应签名要绑定设备的请求签名，套不到用户接口上）。控制端只在打开目录时取一次，不轮询（D2）。

### 2.4 可用出口的判据（D6）

查询那一刻三条同时成立才列出：
1. UDP 注册在 30 秒内：`last_reg_time.elapsed() < ONLINE_TIMEOUT`（30 秒，和组面板的在线判断、hbbs 的 `REG_TIMEOUT` 一致，`src/api/group.rs:18`）。
2. 最近一次验签通过的 Leapgate 心跳在 180 秒内：和 ICE 共用一个常量 `LEAPGATE_HB_FRESH`（由 `src/ice_signal.rs:38` 的 `ICE_HB_FRESH` 挪到 `src/peer.rs`）。
3. 那次心跳的 `exit` 为真。

不要求公钥已锁定，也不看 Leapgate 版本：带 `exit` 的心跳只有第四期客户端会发。判据只决定"列不列"：设备谎报 `exit` 只影响它出现在谁的目录里（它的主人和被授权的人），不扩大谁能连。

### 3.3 目录：`src/api/exit.rs`、`src/api/mod.rs`

新文件 `src/api/exit.rs`：

```rust
//! Exit directory (phase 4 contract 01, LEAPGATE.md §12.4): the exits a user may use right now.

use super::{group::ONLINE_TIMEOUT, ok_json, ApiResult, CurrentUser};
use crate::{peer::{Peer, LEAPGATE_HB_FRESH}, state::AppState};
use axum::extract::State;
use serde_derive::Serialize;

/// Devices the user (`?1`) may see as exits: owned by them, or granted to them or to a group they
/// are in. Owned ones first.
const CANDIDATES: &str = "
    with ids(id) as (
      select id from device where user_id = ?1
      union
      select device_id from exit_grant
       where user_id = ?1 or group_id in (select group_id from group_member where user_id = ?1))
    select ids.id, coalesce(d.hostname, ''), coalesce(u.name, ''), coalesce(d.user_id = ?1, 0)
      from ids left join device d on d.id = ids.id left join user u on u.id = d.user_id
     order by 4 desc, ids.id";

#[derive(Serialize)]
struct Exit { id: String, hostname: String, owner: String, own: bool }

#[derive(Serialize)]
struct Exits { exits: Vec<Exit> }

/// Registered over UDP within `ONLINE_TIMEOUT`, and its last signed Leapgate heartbeat is within
/// `LEAPGATE_HB_FRESH` and said `exit` (contract 01 §2.4).
pub(crate) fn available(p: &Peer) -> bool {
    p.last_reg_time.elapsed() < ONLINE_TIMEOUT
        && p.leapgate_hb.as_ref().is_some_and(|hb| hb.exit && hb.at.elapsed() < LEAPGATE_HB_FRESH)
}

/// `GET /api/leapgate/user/v1/exits`.
pub(crate) async fn exits(State(state): State<AppState>, user: CurrentUser) -> ApiResult {
    let rows: Vec<(String, String, String, bool)> =
        sqlx::query_as(CANDIDATES).bind(user.id).fetch_all(&state.db).await?;
    let mut exits = Vec::new();
    for (id, hostname, owner, own) in rows {
        let Some(peer) = state.pm.get_in_memory(&id).await else { continue };
        if available(&*peer.read().await) {
            exits.push(Exit { id, hostname, owner, own });
        }
    }
    Ok(ok_json(&Exits { exits }))
}
```

- 在线状态只查内存（`get_in_memory`），不经主池加载：不在内存里的设备 30 秒内没注册过，本来就不可用。照的是 `group::peers` 的写法（`src/api/group.rs:121-125`）。
- 授权给已删除设备、还没上报过的设备时，`left join` 得到空的主机名和主人；它们不在线，本来也列不出来。
- 不分页、不另设条数上限：候选是"自己名下的设备行"加"授权行"，前者受设备表 1 万行约束，后者由管理员手工维护；逐个取读锁、不等数据库，最坏几毫秒【推测】。
- `src/api/mod.rs`：`:7-13` 的模块声明里加 `pub(crate) mod exit;`；路由表在 `:86`（Leapgate 审计 alarm 那条）之后加：
  ```rust

          .route("/api/leapgate/user/v1/exits", get(exit::exits))
  ```
  请求体上限、超时（20 秒）、错误格式都用默认值。`is_leapgate`（`:404`）、`is_report`（`:410`）不改：它们按 `devauth::PREFIX = "/api/leapgate/v1/"` 判断，新路径不以它开头。

### 3.4 授权表：迁移 0007

```sql
-- Phase 4 (application exit): besides its owner, who sees a device in their exit directory.
-- One user or one group per row. device_id has no foreign key: device rows are evicted
-- (LEAPGATE.md §9.3) and a grant must not go with them, nor fail before the device reports.
```

### 3.5 设备主人加固（A1、D14）

**(1) 登录绑定**：`src/api/account.rs:362-378`。现在冲突分支是 `do update set user_id = excluded.user_id`（`:367`），后登录的人覆盖主人。改成已锁定的设备只在没有主人时绑定；锁定与否在写的同一条语句里读，不用前面 `uuid_matches` 的结果：

```rust
            sqlx::query(
                "insert into device(id, uuid, user_id, first_seen_at, last_seen_at) values(?1, ?2, ?3, ?4, ?4)
                 on conflict(id) do update set user_id = case
                   when exists(select 1 from peer where id = ?1 and pk_pinned_at is not null)
                   then coalesce(user_id, excluded.user_id) else excluded.user_id end",
            )
            .bind(&req.id)
            .bind(&req.uuid)
            .bind(uid)
            .bind(now)
```

`:361` 的注释"A pinned key does not matter here"改成新规则。没锁定的设备（原版客户端走兼容路径，永远不会锁定）照旧由后登录的覆盖。已锁定设备要换主人：原主人在设备上登出（`account.rs:431` 清掉本人的绑定），或者运维用 `device owner`。

**(2) 延迟补绑只认锁定之前签发的令牌**：`src/api/device.rs:163-165` 的 `OWNER_FROM_TOKEN` 加一行条件：

```rust
const OWNER_FROM_TOKEN: &str = "(select t.user_id from token t join user u on u.id = t.user_id
     where t.device_id = ?1 and t.device_uuid = ?2 and u.status = 1
       and not exists (select 1 from peer p where p.id = ?1 and p.pk_pinned_at < t.created_at)
     order by t.last_used_at desc limit 1)";
```

- 三处用到它的语句跟着变，不用分别改：`store_sysinfo` 的插入（`:312`）、`touch` 的更新（`:421`）和插入（`:441`）。没锁定的设备照旧。
- 为什么是"锁定之前"：锁定以后设备一定已在会合服务器注册，真主人在它上面登录时由 (1) 直接绑定，用不着补绑。锁定之后签发、却还要靠补绑的令牌，只可能来自"登录时设备已有主人、没绑上"的人。不加这条，攻击者知道设备 ID 和 uuid 登录一次就留下令牌，真主人一登出，下一次心跳就把设备补到攻击者名下，设备随之以 `own: true` 出现在攻击者的出口目录里。(2) 只防被动补绑：设备此刻没有主人时（新装还没有人登录过、主人登出后、`device owner <ID> none` 后、设备行被淘汰重建后），登录绑定仍是先到先得，知道 ID 和 uuid 的人主动登录一次就会成为主人（见 §7 第 12 条）。
- "先登录、后注册"的新装设备照常补绑：令牌签发时设备还没注册，早于锁定。第一次签名心跳在提取器 `SignedBody` 的第 8 步先锁定，handler 里的 `touch` 再补绑；同一秒签发的令牌算"之前"（`<` 比较的是 unix 秒）。
- 不选"已锁定设备整个关掉补绑"：那样先登录、后注册的新装设备就失去补绑（清单 A1 备选）。

**(3) 新命令 `device owner <device> <user|none>`**：放在 `src/cli/ops.rs` 的 `exec`，`("device", "pin-relay")`（`:39-60`）之后。`none` 表示清掉主人，否则用 `manage::user_id`（改成 `pub(super)`）查用户。在一个 `begin immediate` 事务（`api::device::BEGIN_WRITE`）里：

```sql
update device set user_id = ?2 where id = ?1;   -- 影响 0 行就报错退出，什么都不写
insert into device_policy(device_id) values(?1) on conflict(device_id) do nothing;   -- 只在指定了用户时
```

影响 0 行时的报错：`"{device} has no device row (it has not reported to this server, or its row was evicted)"`。

- 只写 `device.user_id`，不另存"命令行指定"的标记，也不加列（D14）。组面板（`src/api/group.rs:99-113`）、`device list`（`src/cli/ops.rs:315-318`）、登出清主人（`account.rs:431`）、延迟补绑和出口目录读的都是这一列，同一台设备不会在不同地方挂在不同人名下。
- 插 `device_policy` 行只为借用现成的淘汰保护：`EVICTABLE` 只看有没有这一行（`device.rs:184`、`:191`）。新行的 `relay_pin` 默认 `''`、`strategy_epoch` 默认 0，和没有这一行等价（`strategy.rs:31-39` 没有行时 epoch 取 0；路由只用非空的 `relay_pin`）；已有的行不动。`none` 不删这一行，它可能带着 `pin-relay` 的设置。
- 要求设备行已存在：在线的出口设备一定有行（签名心跳会建）。命令不替设备建行，免得绕过设备表上限。
- 输出：设了主人时 `"{device} is now owned by {user}\n"`；设备没锁定时追加一行 `"{device} has no pinned key yet: the next login on it replaces the owner\n"`（多查一次 `peer.pk_pinned_at`）。`none` 时 `"{device} has no owner now; a login on it, or a login token left on it (late binding), may bind it again\n"`。
- 名叫 `none` 的用户不能用这个命令指定，和 `pin-relay` 的 `none` 是同一种写法。

### 3.6 命令行 `exit grant|revoke|list`

- `src/main.rs:10-12` 的 `CLI_COMMANDS` 加 `"exit"`。
- `src/cli/mod.rs`：`exec` 的分发（`:153`）改成 `"user" | "group" | "ab" | "exit" => manage::exec(…)`；`changes_database`（`:120`）的元组加 `"exit"`，让 `exit list` 算只读（输出末尾不打数据库路径）；`USAGE`（`:33-49`）加两行：
  ```
    device owner <device> <user|none>
    exit grant|revoke <device> --user <u>|--group <g> | exit list
  ```
  `--user`、`--group` 已在 `VALUE_FLAGS`（`:180-183`）里。
- `src/cli/manage.rs` 的 `exec` 加 `("exit", "grant" | "revoke")` 和 `("exit", "list")`，照 `("ab", "grant" | "revoke")`（`:269-326`）写：位置参数是设备 ID，`Target::take`（`:338`）取 `--user` 或 `--group`，`user_id`、`group_id` 查名字（查不到报错），`who` 用 `Target` 的 `Display`（`user:bob`、`group:ops`）。
  - grant：先 `select exists(select 1 from peer where id = ?)`，为假时报错 `"{device} is not registered with this server"`：挡手误，也挡"先授权、后被人抢注这个 ID"（D4）；不查在线和出口开关。再 `insert into exit_grant(device_id, {column}) values(?, ?) on conflict(device_id, {column}) where {column} is not null do nothing`，输出 `"{who} may use exit {device}: it shows in their exit directory while it is online with the exit on\n"`。给主人本人授权不拒绝：无害，目录里去重。
  - revoke：`delete from exit_grant where device_id = ? and {column} = ?`，不查 `peer` 表（已删除设备的授权也能撤）。影响 0 行输出 `"{who} had no grant on exit {device}\n"`，否则输出 `"Revoked {who} on exit {device}. This only changes the exit directory: sessions already open stay, and anyone who knows the device's password can still use it\n"`（D4）。
- `exit_list`：一台设备一行，列 `DEVICE`、`OWNER`、`GRANTED TO`（`user:bob, group:ops`，用户在前），用现成的 `table`（`src/cli/mod.rs:329`）；没有授权时输出 `(no exit grants)`。末尾固定一行 `"Owners always see their own devices. Whether an exit is online and on is known only to the running server.\n"`。查询：
  ```sql
  select g.device_id, coalesce(o.name, ''), u.name, gr.name from exit_grant g
    left join device d on d.id = g.device_id left join user o on o.id = d.user_id
    left join user u on u.id = g.user_id left join user_group gr on gr.id = g.group_id
   order by g.device_id, g.group_id is not null, coalesce(u.name, gr.name)
  ```
- 授权每次查目录时都现查库，写完立即生效，不需要控制台通知运行中的服务（同 `pin-relay`）。

### 3.7 hbbr 部署参数（E3，只改部署，不改代码）

- 只加一个环境变量 `SINGLE_BANDWIDTH=256`：每对中继连接的限速，单位 Mb/s（这里 1 Mb = 2^20 bit），两个方向合计，默认 128。其余参数用默认值：`TOTAL_BANDWIDTH` 1024（整个进程所有会话合计）、`LIMIT_SPEED` 32、`DOWNGRADE_THRESHOLD` 0.66、`DOWNGRADE_START_CHECK` 1800 秒。
- 降速规则保留：会话从配对起算的平均速率超过 0.66 × 256 ≈ 169 Mb/s、且会话已超过 30 分钟时，降到 32 Mb/s，到会话结束不恢复（笔记 02 §6，清单"核对时更正的事实"）。
- 变量名一律写全大写加下划线：本仓库 `873230e` 的 `get_arg` 不分大小写、横线下划线通用，但已发布的官方镜像 1.1.15、1.1.16 只认这一种写法。值必须大于 0，设 0 不能关掉限速，会回到默认值（`check_params`，`src/relay_server.rs:108-159`）。
- 生效时机：随第一期部署那次 hbbr 重启生效。重启后在 hbbr 启动日志里核对 `SINGLE_BANDWIDTH: 256Mb/s` 这一行（`relay_server.rs:155-158` 打的）；同时把 hbbr 镜像钉到具体版本标签，不用 `latest`。
- 不做：只给出口会话放宽（hbbr 配对只认 uuid，看不到连接类型）、月流量机制。想少用贵的中继，用现成的 `[[relay]] weight`（`server/LEAPGATE.md` §5、§7）。

## 7. 已知限制

1. **目录不是关口**（A2 (a)）：撤销授权只影响目录，不断开已有会话，也挡不住知道设备密码的人。要切断某人，关掉出口开关（B8：已有的出口会话下一秒断开，之后的出口登录也被拒）；改设备密码只挡住之后的登录，已经认证的出口会话不会断（C14：窗口开着，隧道就一直在；02 §7）。设备谎报 `exit` 只影响它出现在谁的目录里。
2. **状态有延迟**：开关切换后最多一个心跳周期（空闲时 15 秒，失败退避时更久）才反映到目录；心跳停了 180 秒内仍可能列出一台刚关机的设备，但它的 UDP 注册 30 秒后就过期，实际最多晚 30 秒消失。服务端重启后，要等设备的下一次注册和心跳才回到目录。
3. **只列 UDP 注册在线的设备**：走 WebSocket 或代理、在会合服务器注册不了的被控端（`server/LEAPGATE.md` §1：TCP 注册不做）不会出现在目录里，和组面板的在线状态一致；手填 ID 照样能用。
4. **目录响应不签名**：靠部署的 HTTPS 防篡改。链路上的人改了目录，后果只是让用户选错设备、去那台设备上试密码。
5. **没锁定的设备**：登录照旧覆盖主人，`device owner` 设的主人也会被下一次登录换掉（命令输出会提示）。出口设备都是第四期客户端，正常都已锁定。
6. **已锁定设备换主人要先登出**：共用机器上多个账号轮流登录时，上一个账号不登出，主人不变；登出请求没送到时，要运维用 `device owner` 改。
7. **表满时的登录**：已锁定的设备在设备表满、没能建行时登录不绑定；之后有了空位，延迟补绑也不会补（令牌签发晚于锁定），要在设备上重新登录。
8. **`device owner <ID> none` 不一定持久**：没锁定的设备，下一次写设备行时会被延迟补绑补回这台设备上最近用过令牌的人；已锁定的设备只会被锁定之前签发的令牌补回。
9. **ID 被继承**（D9）：`device key reset --forget` 删掉 `peer` 行后，这个 ID 的设备主人、`device_policy` 和出口授权按 ID 留着，会被下一个注册这个 ID 的设备继承。
10. **设备行被淘汰**：授权还在，但设备再上报之前目录里看不到它（它也不在线）；重建行后没有主人，要靠延迟补绑或重新登录恢复（`server/LEAPGATE.md` §9.3 原有的代价）。
11. **hbbr 放宽后**：单会话最多 256 Mb/s，所有会话合计仍受 `TOTAL_BANDWIDTH` 1024 Mb/s 约束；会话平均速率超过约 169 Mb/s 且满 30 分钟后降到 32 Mb/s，关掉窗口重开才恢复。
12. **没有主人的已锁定设备，登录先到先得**：已锁定、此刻没有主人的设备，第一个用匹配的 ID 和 uuid 登录的账号成为主人，(2) 挡不住这种主动登录。后果只在归属：设备以 `own: true` 出现在他的出口目录里、挂在他的组面板下；能不能用出口仍要过被控端的认证（第 1 条）。要固定主人，用 `device owner`。
