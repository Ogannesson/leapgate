## 要点

1. 要做的是 02 已经定下的三件事，外加"查看详情"：
   - **暂停**：停下并保留断点，"继续"接着传（R2-Q25）；
   - **失败保留和重试**：失败的任务留着，"重试"从失败的那个文件接着传，已传完的不再传、也不再问替换（R2-Q34）；
   - **个别文件跳过**：文件夹里个别文件出错时跳过它、其余照传，结束时写"已完成，‹k› 个文件未传输"，"查看详情"逐个写路径和原因，带"重试未传输的文件"（R2-Q24）。
2. 读码推翻了 03 的三处估计：
   - **没有"结束时的汇总错误"**：多文件任务最后总是发"完成"，只有单文件任务整个被跳过时发一条 `skipped`。所以两种错误在协议上分得开，03 §6.3 担心的"长得一样"不存在。
   - **下载时对端出错后接不接着读，控制端判断不了**：对端是 Windows 安装版、1.4.5 及以上时，读文件由它的 CM 做，读错一个就结束整个任务；其他对端接着读下一个。控制端从版本号看不出对端装没装，所以跳过一个文件后要由控制端从下一个文件**重新发起**，不能等对端自己往下读。
   - **挂钩不止三处**：`src/client/io_loop.rs` 要五处（约 10~14 行，其中改 1 行），加 `src/client.rs` 一个变体；03 担心要碰的取消路径反而不用动，`libs/base`、CM、proto 都不动。
3. 做法的核心：**"停下但保留、从某个文件接着传"**。下载暂停、出错后重试、对端读失败后接着传，Rust 都做成同一件事：停掉任务、留着临时文件、告诉界面从第几个文件接着传；界面用现成的"添加任务 + 继续"（关窗后恢复未完成任务用的就是这一套）重新发起。上传暂停另用"软暂停"：本机不再读，对端什么都不知道，连接和对端的临时文件原样留着。
4. 代码量：Rust 约 350~450 行（不含测试），Dart 约 600~1100 行（不含测试），和 03 原估接近。要定的九条在 §8，最要紧的是 M7b-1（上传方向的单文件跳过做不做）、M7b-3（下载时对端读失败怎么接着传）、M7b-4（上传暂停的做法）。

## 1. 范围

### 1.1 做什么

| 区域 | 内容 | 出处 |
|---|---|---|
| 暂停 | 进行中的传输任务带"暂停"；已暂停的行"继续"从断点接着传；远程设备低于 1.4.2 时不显示（02 已定；上传其实不需要这个门槛，为少一种分支照 02 统一） | R2-Q25，M7b-4 |
| 失败保留和重试 | 失败的传输任务留着，行上"重试"从失败的那个文件接着传；原因不能重试的（例如远程设备拒绝）不画"重试"；"移除"同时丢掉 Rust 保留的记录 | R2-Q34 |
| 个别文件跳过 | 文件夹任务里个别文件读不了、写不了、文件名在 Windows 上无效时跳过，其余照传；连接中断、磁盘空间不足、远程设备拒绝仍整任务停下 | R2-Q24，M7b-1、M7b-3 |
| 结束时汇总 | "已完成，‹k› 个文件未传输"或"已完成，‹k› 个文件已跳过"，"查看详情"在行下展开，每个文件一行"相对路径 · 原因"，带"重试未传输的文件" | 02 区块 H，M7b-7、M7b-8 |
| 删除的部分失败和重试 | 删除时个别项目删不掉写"已完成，‹k› 个项目未删除"，"重试"重新统计、只删还在的。只改 Dart，可以先做 | 02 §2.4.7 |
| 关窗后保留 | 用户暂停的任务关闭视图后照常保存，下次打开列成"已暂停"；重连时不自动开始 | 02 §3.1，M7b-6 |
| 队列显示 | 恢复的任务在对端排到队尾，界面按"恢复后的排队序号"判断谁在跑，显示顺序不变（02"行按加入的顺序排"） | §4.4 |

- **事件**（全局 JSON 流，带会话 ID）：
  - `paused`：下载暂停后换上的新任务 ID、续传起点；
  - `kept`：任务出错停下但保留，带新任务 ID、续传起点、原文；
  - `continue_from`：单个文件出错后从下一个文件接着传，带新任务 ID、起点；
  - `file_failed`：任务 ID、文件序号、任务内相对路径、原文、本机还是远程。
- **下载暂停**：给对端发取消（对端只删自己的读任务，不碰文件），本机不删 `.download`，删掉任务，再放一个同参数、新 ID 的等待任务，事件告诉界面。必须换 ID：还在路上的旧数据块会落进新任务，报"文件序号不对"、整任务被取消。续传起点要避开"上一个文件刚改名、下一个文件还没开始"的空档，不然会对已传完的文件弹替换确认。
- **上传软暂停**：把读任务标成"等待"（读循环本来就跳过这种任务），不发任何消息；"继续"把标记改回来。不能用现有的"继续"：它会重新发起，对端多出一个同 ID 的写任务。
- **失败保留**：下载写失败（包括磁盘满）不删 `.download`；上传时对端写失败本来就不取消，对端的临时文件还在。都按"停下但保留"报给界面，用户点"重试"再用新 ID 发起。失败的任务不跨关闭视图保存（M7b-6）。
- **跳过**：
  - 下载，digest 阶段的单文件错误（文件名在 Windows 上无效、目标路径带链接）：回"跳过"给对端，对端这时正停在这个文件等确认，各版本都认。
  - 下载，写数据阶段的单文件错误、对端读失败：不回"跳过"（对端可能已经读到下一个），停下、从下一个文件重新发起（M7b-3）。
  - 上传，本机读失败：不把错误发给对端（发了对端 CM 会结束任务），读到一半的补发"跳过"，让对端丢掉写了一半的文件（M7b-1）。
  - 上传，对端写失败：读方还停在这个文件时本机标成跳过，并回"跳过"。
- **整任务停下**：连接中断（照旧，重连后自动续传）、磁盘空间不足（FT2 的 `DiskFull`）、对端在建任务时就拒绝（单向传输、文件数上限，序号为 0）、上传第一个文件还没收到任何确认就出错。
- **单个文件超过 4 GiB**（M7b-5）：下载接着传之前，本机临时文件已超过 4 GiB 的，先删掉、这个文件从头传，`paused`、`kept` 事件里带"这个文件从头传"的标志，行上加一条附注。上传两边截成同一个值，只是多传一段，不用处理。

## 4. 几处要先说清的

### 4.1 行不变，Rust 任务 ID 会变

同一次会话里，一个任务停下以后不能原样再续（它已经有文件列表，对端再回列表会让任务被取消），只能用新 ID 新建任务接着传。所以暂停、重试、跳过后接着传，Rust 任务 ID 都会换。界面上**行不变**：`FileTransferJobs` 维护"行 → 当前任务 ID"，进度、速度、已传字节在同一行上接着走。

**断线重连时不自动继续用户暂停的任务**（M7b-6）也放在这一层：保存的任务记录里没有"用户暂停"的标志，断线重连时 Rust 把所有保存的任务带着"自动开始"推回来。不往上游的任务记录加字段，由 `FileTransferJobs` 在本次会话的内存里记住用户暂停过的任务 ID（包括下载暂停后换上的那个），收到带"自动开始"的恢复事件时，这些 ID 照不自动开始处理。关闭视图再打开时恢复事件本来就不带"自动开始"，不受影响。

### 4.2 下载时对端读失败

对端会不会接着读取决于对端（要点 2），控制端一律按"不会"处理：停下，本机写了一半的文件留着临时文件、上一个已完成的文件照常收尾，记下这个文件的失败，从下一个文件重新发起。代价是每跳过一个文件，对端要重新列一遍文件夹。几千个都打不开时会一直重列，所以同一个任务连续自动接着传 20 次就停下、整行显示失败（M7b-3）。Rust 只报 `continue_from`，重新发起的是界面，所以这个计数在 Dart 里。

### 4.3 "重试未传输的文件"

没传的文件不连续，没法用"从第几个接着传"一次发起。界面为每个没传的文件各建一个单文件任务，有临时文件的自动从断点接着传。这些任务挂在**原来那一行**下面：行回到进行中，进度按它们合计，全部结束后行重新判定成"已完成"或"已完成，部分未传输"。不另起几行。

### 4.4 恢复的任务排在哪

恢复一个暂停的下载时，对端把它排到自己队尾，先把当前在传的传完；上传由本机读循环按顺序取第一个没暂停的。M7a 按"同一方向上排在最前、还没结束的就是进行中"判断，恢复以后会把排队的标成进行中、把真在传的标成排队中。M7b 给每行记一个"恢复后的排队序号"，按它判断谁在跑；行在列表里的位置不变。

### 4.5 跳过了几个文件怎么数

现在勾了"对此次传输中的其他冲突执行相同操作"以后，Rust 记住选择、自己处理后面的冲突，界面不知道跳过了几个。M7b 改成界面发给 Rust 的"记住选择"一律传否，由界面自己按勾选逐个回答。每个冲突多一次 Rust 和界面之间的往返，用户看不出区别，Rust 不用改。

### 4.6 详情很长时

详情最多列 50 个文件，后面写一行"另有 ‹k› 个文件"。现有组件一次建出全部详情行，几百行会卡。

### 4.7 关闭视图后恢复的行没有字节数

保存的任务记录里没有已传字节和总大小，恢复后的"已暂停"行只写"已暂停"，不写"已传 ‹x› / ‹总›"。维持 M7a 的已知限制（`client/LEAPGATE.md` §10.15），同一次会话里暂停的行有字节数。

### 4.8 上游已有的缺陷

读码看到几处上游的缺陷，M7b 只在自己的路径上绕开，不修上游代码：

- 上传时本机读失败、下载时对端读失败，上一个已完成的文件会留成临时文件，没改名；
- 远程建文件失败时，还在路上的数据块被追加到上一个文件末尾；
- 在两个文件之间取消，会删掉刚传完、还没改名的文件（上传方向空档大得多）；
- 上传断线正好落在两个文件之间，重连续传会跳过上一个文件；
- 续传偏移是 32 位，单个文件超过 4 GiB 时续传失败（M7b-5）；
- Windows 的 CM 处理"跳过"时不核对文件序号。

这些按"上游报告放到开发完成后"的做法，起草存进 `internal/upstream/`，开发全部完成后再发。

## 8. 要维护者定的

| 编号 | 问题 | 推荐 | 备选 | 理由和代价 |
|---|---|---|---|---|
| M7b-1 | 上传方向的单文件跳过做不做 | 做：上传时本机某个文件读不了（例如正被其他程序独占），跳过它、其余照传 | 只做下载方向的跳过和两个方向的暂停、重试；上传时本机读失败照上游整任务停，失败行可以"重试"（从这个文件接着传，文件还被占着就再失败一次） | 上传一个文件夹时遇到正被占用的文件很常见（打开着的 Office 文件、邮件数据文件）。代价是一个 Leapgate 版的上传读循环（Rust 新代码的约三分之一），`io_loop.rs` 多一处带开关的分支 |
| M7b-2 | 动手前测哪几条 | §5.1 的 1、4、9 用现有代码先测（基线），2、3 在暂停做完后测、成立再做跳过，其余放验收 | 十条全部放到验收 | 2、3 决定两种暂停的做法成不成立，必须有暂停的代码才测得了；先做暂停再做跳过，做法不成立时只返工暂停那一小块。全部放验收省一轮，但做法不成立时跳过那部分也要返工 |
| M7b-3 | 下载时对端读失败（或本机写数据阶段失败） | 停下、从下一个文件重新发起，界面上看是跳过这个文件、接着传；同一任务连续自动接着传 20 次就停下、整行显示失败 | 停下、整行显示失败，等用户点"重试" | 推荐不管对端是什么版本、装没装，表现都一样，符合 R2-Q24 的"跳过继续"。代价是每跳过一个文件，对端重列一遍文件夹；上限防的是几千个都打不开时反复重列。备选省事，但 Windows 安装版对端和其他对端表现不同（前者停、后者对端其实还在读），用户看到的是一个文件就让整批停下 |
| M7b-4 | 上传暂停的做法 | 软暂停：本机不再读，不通知对端，对端的写任务和临时文件原样留着；"继续"从停下的位置接着读 | 用取消实现：对端删掉当前文件的临时文件，"继续"时当前文件从头传 | 推荐不改协议、不删任何文件、对版本没有要求。备选在两个文件之间暂停时会删掉刚传完的文件（上游缺陷，§4.8），文件多而小的时候这段空档占了大部分传输时间。软暂停要实测上游对端长时间没有数据会不会断开（§5.1 第 3 条） |
| M7b-5 | 单个文件超过 4 GiB 时 | 写成已知限制：下载接着传（暂停后继续、重试）时，已超过 4 GiB 的临时文件由 Rust 先删掉，这个文件从头传，行上加附注说明；"暂停"照常显示 | 甲：当前文件超过 4 GiB 时不显示"暂停"、失败后不给重试（界面要 Rust 另发当前文件大小）；乙：两端都是 Leapgate 时扩展协议 | 续传偏移是 32 位（上游缺陷），接着传必然失败。推荐一条规则管暂停和重试两种情况，界面不用知道文件多大，只多几行 Rust。甲在磁盘满腾出空间以后也重试不了。乙和 R2-Q35"不扩展协议"冲突，对上游对端也没用 |
| M7b-6 | 用户暂停的任务关闭视图后保不保存 | 保存，下次打开列成"已暂停"；断线重连时不自动开始。出错停下保留的任务不保存，关闭视图后就没了 | 暂停的也不保存 | 推荐和 02 §3.1 一致："‹N› 个传输尚未完成"不计已暂停的，因为它们下次还在。备选关掉视图后暂停的行悄悄消失，N 要计入已暂停，02 那句要改 |
| M7b-7 | "已完成，部分未传输"的行算不算已完成 | 不算：汇总行的"清除已完成"不清它，和失败行一样留到重试或移除；汇总里也不计入失败数（和样稿一致） | 和已完成一样一起清掉 | 没传的文件还有一个"重试"可以做，一键清掉就丢了这个入口 |
| M7b-8 | 跳过和失败混在一起时怎么写 | 全是用户在替换确认里选"跳过"的，写"已完成，‹k› 个文件已跳过"，不画重试；有任何一个是出错没传的，统一写"已完成，‹k› 个文件未传输"，详情里分别写原因；至少一个原因能重试才画"重试未传输的文件" | 两种分开计数（"已跳过 ‹a› 个，‹b› 个未传输"）；按钮总是画 | 一行一句，用户先看到的是"有没有没传的"。备选的计数句太长，队列在窄窗口里会折行；总是画按钮会让"重试"重试用户自己跳过的文件 |
| M7b-9 | 失败的行要不要"查看详情" | 不要：和样稿一致，失败行写原因短句，归不了类时原文放在悬停提示里 | 失败行也给"查看详情"，展开写完整句和原文 | `待调.md` 记过"只看错误码分不出两种情况"的误导（M7a 验收），备选能把原文摆出来。代价是组件放宽一处限制、约 10 行，样稿要补画 |
