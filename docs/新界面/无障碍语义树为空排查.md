# 新界面无障碍语义树为空：排查

2026-10-31 排查。版本：Flutter 3.44.9（标签提交 `6b182d2c`），对照 3.47.9（`c197ca5199e`）。

- 文中标"读码"的是读源码得出、没有实际跑过；标"没实测""疑似"的同样没有验证。实测和单测的证据在 §5。
- 新界面的文件路径相对 `client/leapgate_ui/`；上游代码写成 `flutter@提交:路径` 加函数名，上游 issue 和 PR 写成 flutter/flutter#编号。
- 第 7 节的修法由维护者定，推荐是排查者的意见。

## 要点

1. 新界面在讲述人和 UI Automation 里只有窗口和 `FLUTTERVIEW` 两个元素，控件一个都读不到。根因是 Flutter 3.44.9 框架的一个 bug：被合并进父节点的浮层锚点仍会发给引擎，成了孤儿节点；引擎按规则整份拒收带孤儿的语义树更新。新界面连接框里的"帮助"按钮正好触发它，而主页一直存在，所以每一份完整的语义树都被拒收。
2. 不是补丁 0001 的问题，也不是引擎的问题。官方引擎遇到同样的更新一样拒收（读码），补丁 0001 只是把"永久失效"变成"每秒最多重试一次"。
3. 同一机制有三类触发（§6）：A 类 3.46 起上游已修，B1 类只在 master 上修了，B2 类在 3.47.9 上还在、master 上疑似也在。
4. 修法有四种（§7）。推荐 ①：在引擎的无障碍桥里丢掉孤儿节点，只改 C++，覆盖三类触发和以后同类的问题，新旧界面都受益；② 里的守卫测试很便宜，可以一起加。维护者 2026-10-31 选了 ①，已实施为引擎补丁 0003，实施和真机验证见 §9。

几个概念，后文直接用：

- 语义树：Flutter 框架描述界面控件（名字、角色、动作、层级）的一棵树，引擎把它转交给 Windows 的 UI Automation，讲述人和自动化脚本都读它。
- 合并（`MergeSemantics`，或节点设了 `mergeAllDescendantsIntoThisNode`）：父节点把整棵子树的标签和动作并成自己一个节点，子树里的节点不再单独发给引擎。
- OverlayPortal 锚点、遍历父节点：OverlayPortal 把浮层（菜单、提示、弹层）画在别处，语义上再挂回原位。它给自己的子组件包一层 `Semantics(traversalParentIdentifier: this)`，这个节点就是锚点；浮层内容的节点带 `traversalChildIdentifier`，按遍历顺序嫁接到锚点下面，所以锚点也叫遍历父节点。
- 孤儿节点：框架发给引擎了、却没有任何节点在子节点列表里列出它，从根节点走不到。
- AXTree：引擎桌面端借用的 Chromium 无障碍树（`ui::AXTree`），它维护真正交给系统的那棵树。
- 补丁 0001：自编引擎上给无障碍桥打的补丁，更新失败后丢掉整棵树并请框架重发完整的树（`scripts/windows/` 里，路线 C 的两份补丁之一）。

---

## 1. 现象

M2a 验收（2026-10-31）时：

- UI Automation 每秒查一次，持续 7 分钟以上，每次只看到窗口和 `FLUTTERVIEW` 两个元素。
- 每次运行 stderr 出现 6~7 行 `Accessibility bridge rebuilt after failed update: <id> will not be in the tree and is not the new root`，id 有 0、64、45、74、117、107。不是每帧都报。

旧界面 2026-10-30 在另一台机器上查文件传输窗口，第一次拿到 116 个元素，之后只剩空的 `FLUTTERVIEW`。它和本文的机制吻合，但没有实测（§8.3）。

## 2. 根因

### 2.1 框架：被合并的锚点照样发出

位置是 `flutter@6b182d2c:packages/flutter/lib/src/semantics/semantics.dart` 的 `SemanticsOwner.sendSemanticsUpdate`，分两轮循环：

1. 第一轮把合并进父节点的节点置 `_dirty = false`，本意是不把它们发给引擎。
2. 第二轮的发送条件是 `(node._dirty || needUpdateTraversalParent) && node.attached`，其中 `needUpdateTraversalParent = !kIsWeb && node._isTraversalParent`。

锚点是遍历父节点，`_isTraversalParent` 为真。锚点被合并进父节点时，第一轮虽然清了 `_dirty`，第二轮的旁路条件照样把它发出去；而合并后的父节点发给引擎的子节点列表是空的。于是这个锚点谁也不认领，成了孤儿节点。

MenuAnchor、RawTooltip / Tooltip、Slider 都用 OverlayPortal，都带这样的锚点。

### 2.2 引擎：整份拒收

桌面端无障碍桥（`shell/platform/common/accessibility_bridge.cc` 的 `CommitUpdates`）把框架给的子节点列表原样交给 `ui::AXTree::Unserialize`。AXTree 要求一份更新里的每个节点要么是根、要么能从根走到。有孤儿时，它在预检阶段（`ax_tree.cc` 的 `ComputePendingChangesToNode`，报错文字就是 `%d will not be in the tree and is not the new root`）把整份更新作废，什么都不应用。

AXTree 这样拒收是对的，错在框架发出了不该发的节点。

### 2.3 新界面里的触发点

连接框末尾的"帮助"按钮 `LgHelpButton`（`app/lib/widgets/lg_connect_box.dart`）用的是 `LgMenuAnchor`，也就是 MenuAnchor。它放在 `LgTextField` 里，而 `LgTextField`（`app/lib/widgets/lg_text_field.dart`）整个包在 `MergeSemantics` 里，用意是"一个语义节点：标签和错误提示属于输入框"。帮助按钮的锚点因此被合并，又被发出，成了孤儿。

主页放在 IndexedStack 里，切到会话标签也一直存在，所以每一份完整的语义树都带着这个孤儿。

## 3. 为什么补丁 0001 重建后仍是空树

1. 第一次有 UIA 客户端或讲述人查询时，引擎打开语义，框架发第一份完整的树。树里带孤儿，更新失败。
2. 补丁 0001 的 `ResetAfterFailedUpdate` 丢掉整棵树，请框架重发完整的树（在框架里把语义关掉再打开，最多每秒一次），之后只接受含根节点 0 的更新。
3. 框架新建的语义树里所有节点都是脏的，被合并的锚点照样发出，又失败。桥继续等完整的树，期间不含根节点的增量更新都被丢掉，所以树永远是空的。
4. 副作用：只要辅助技术一直开着语义，等待期间每次有语义更新，框架都可能重建一次完整的语义树，限速每秒一次。开销没有测过。

报错里的 id 时而是 0、时而是别的数，原因是（读码）：树为空时，`CommitUpdates` 取"最后一个子树列表的第一个节点"当根，哪个列表排在最后取决于 `std::unordered_map` 的遍历顺序。孤儿所在的列表排在最后时，孤儿被当成根，节点 0 就成了走不到的那个，报错写 0；根所在的列表排在最后时，报错写孤儿的 id。M2a 记录里的 64、45、74、117、107 是其他状态下的这类节点，没有逐个对上。

## 4. 不是补丁 0001 的问题，也不是引擎的问题

- 官方 3.44.9 引擎遇到同样的孤儿，同一个 `Unserialize` 一样失败。没有补丁 0001 时，AXTree 的 `error_` 一旦设上就不再清（`ax_tree.cc` 里没有清它的地方），窗口存活期间一直是坏的。这是读码结论，没有在官方引擎上实测：官方引擎有已知的 use-after-free，没必要冒这个险。
- 补丁 0001 只是把"永久失效"变成"每秒至多重试一次"，既不是起因，也修不了它。

### 5.3 引擎单测

在打了补丁的引擎上（debug 构建，用完已删、检出已复原）：把一份带一个孤儿的完整树连发 4 次，根一直无效，桥请求了 4 次完整的树；同一棵树去掉孤儿再发，根 0 正常建立。

### 5.4 上游

- flutter/flutter#186118（2026-05-20 合入，3.46 起的版本有，3.44.9 没有）去掉了 `needUpdateTraversalParent` 旁路，只发脏节点，顺带修好了 A 类。
- flutter/flutter#193372（2026-10-19 合入 master，3.47.9 没有）修 flutter/flutter#190357（推入路由里的 Slider 发出孤儿节点、Windows 无障碍树永久冻结）：遍历父节点缺失时不再发遍历子节点。它覆盖 B1 类。
- 读 master 的 `_shouldSkipInHitTest`：只有遍历父节点"不在登记表里"才跳过；已登记、但被合并进父节点的锚点不算缺失。所以 B2 类在 master 上疑似仍有孤儿。这只是读码，向上游发报告前要再核。
- 相关、还没关的 issue：flutter/flutter#182444（Windows 上 ListView 里的 Tooltip 触发同样的报错）。

| 类 | 机制 | 新界面的例子 | 后果 | 上游状态 |

| 修法 | 修好哪几类 | 代价 | 主要问题 |

| ① 引擎侧丢掉孤儿 | A、B1、B2 和以后的同类 | 约 30~50 行 C++ 加 2~3 个单测，重编一次引擎 | B2 的弹层内容读不到 |

| ④ 回移 #186118 进 3.44.9 SDK | A | 每台机器的 SDK 都要打 | 违反"Dart、框架不动"的决定 |

① 新旧界面都受益，② 只管新界面，③ 只管新界面（旧界面在 M9 之前留在 3.44.9），④ 影响两个界面，各节细说。推荐 ①，② 的守卫测试便宜，可以一起加。这是排查者的意见，由维护者定。

### 7.1 ① 引擎侧加固

（2026-10-31 已按这一节实施为补丁 0003，见 §9。）

作为补丁 0001 的后续，或者另起新补丁 0003，只改公共桥的 C++：

- `CommitUpdates` 里树为空、且待提交的更新含节点 0 时，固定用 0 当根。
- 从根出发（经待提交节点和现有树的子节点列表）走不到的待提交节点丢掉，限频记一行日志。

覆盖 A、B1、B2 和以后框架再出的任何孤儿。整棵树照常可用，缺的只是孤儿那部分：A、B1 的孤儿本来就是不该出现的节点；B2 的孤儿是弹层内容，弹层开着时讲述人读不到它。

它符合路线 C"只改 C++"的做法，新旧界面都受益。代价是约 30~50 行代码加 2~3 个桥的单测，再跑一次 `build-engine.ps1`（release 一两个小时）加 test、install，SDK 缓存里的引擎换成新哈希。风险低：它只改变那些 AXTree 本来就会整份拒收的更新的处理方式。

### 7.2 ② 应用侧绕开

只管新界面：

- 把帮助按钮挪出 `LgTextField` 的 MergeSemantics。
- 让 ExcludeSemantics 里的提示不产生浮层语义，例如把提示放到 ExcludeSemantics 外面，或者让浮层内容也排除语义。
- 把探针做成一个组件测试，走几个关键状态、断言没有孤儿，当回归守卫。

代价小，但只管自家代码、只管守卫走到的状态；旧界面和上游组件（Slider、合并的 ListTile 里的 Tooltip 等）管不到，以后新写的组件也可能再引入。

### 7.3 ③ 升级 Flutter 到 3.47.x

只修 A。B1、B2 还在：提示或弹层显示时树为空，配合补丁 0001 在关掉后恢复。这是根据最小复现和 #186118 的改动推出来的，新界面整体没有在 3.47.x 上跑过探针。补丁 0001 要在新引擎上重新适配（按 `03-实施方案.md` M10，新界面不带 0002）。旧界面在 M9 之前仍用 3.44.9 编（03 §2.2），③ 管不到它。升级本来排在切换之后（`03-实施方案.md` IQ1），单靠它不是近期的修法。

### 7.4 ④ 回移框架改动

把 #186118 的框架改动回移进 3.44.9 SDK。只修 A；违反 2026-10-26"Dart、框架不动"的决定，每台机器的 SDK 都要打，影响两个界面。不推荐。

## 8. 影响

### 8.1 端到端脚本

现在按名字找不到任何控件，端到端脚本只能按坐标投递窗口消息（`scripts/e2e/leapgate-post-input.ps1`）。

- 做了 ①，或者 ② 覆盖到的状态，可以改回按语义名操作；做 ① 时 B2 的弹层内容例外。但 ① 落地后实测发现另一层限制：托管的 System.Windows.Automation 看不到 Flutter 的树，只有原生 COM 的 IUIAutomation 能看到（§9.3）。`scripts/e2e/leapgate-uia.ps1` 原来用的是托管 API，2026-10-31 已改成 COM（§9.4）。
- 只做 ③：主页空闲时可用，但一出提示或弹层树就清空、关掉后恢复，脚本会时好时坏。

### 8.2 讲述人

现在窗口里什么都读不到。做了 ① 以后可用，只有合并输入框里弹出的弹层内容读不到。

### 8.3 旧界面

旧界面文件传输窗口先有 116 个元素、之后变空，和本机制吻合（另见 §9.3 的托管 API 问题）：上游的 Tooltip、Slider、MenuAnchor 都是 OverlayPortal，常放在合并的容器里。"先有后空、重开也空"可以这样解释（推断）：第一次查询时界面里还没有 A 类节点，之后出现了一个（例如文件列表载入后的某一行），从此每份完整的树都带着它；重开的窗口一开始就有，所以一直为空。B1、B2 类只会在浮层显示时清空、关掉后恢复，解释不了"一直为空"。没有实测，没对上是哪个控件。① 同样覆盖它。

## 9. 实施与验证（2026-10-31）

### 9.1 补丁 0003

`scripts/windows/engine-patches/0003-accessibility-bridge-drop-unreachable-nodes.patch`，只改 `shell/platform/common/accessibility_bridge.cc/.h` 和桥的单测。`CommitUpdates` 在补丁 0001 的"等完整树"闸门之后、处理挪动节点之前调用新函数 `DropUnreachableNodes`：

- 根：树非空时用现有的根；树为空时，待提交节点里有 0 才用 0，没有就什么都不做。现有树的根不是 0（0001 在请求不到完整树时会这样建树）时也什么都不做，让这份更新照旧失败、由 0001 重建。
- 先做一遍只看待提交节点的快速检查：有"新的、没被任何待提交节点列为子节点、又不是根"的节点，才从根出发遍历一次（待提交节点用新的子节点列表，其余节点用树里现有的），把走不到的待提交节点删掉，记一行 `Accessibility bridge dropped semantics nodes unreachable from root 0: …`。没有可疑节点时直接返回，行为和打补丁前完全一样。
- 不处理"子节点列表里引用了不存在的 id"（仍由 0001 重建），也不改根的选取逻辑。
- 已知没覆盖的两种：节点已在树里、这次它的父节点（或某个祖先）不再列它、它自己又被发出来；一组新节点互相认领成环。这两种都和补丁前一样整份失败，由 0001 重建；重建后完整树里的节点都是新的，会被快速检查查出来，所以最多多一次重建。框架实际产生不了环。

单测加了 5 个（完整树带孤儿、增量更新带孤儿子树、等完整树期间收到带孤儿的完整树、慢路径里同时有正常的挪动和新增、剪完以后待提交为空）。把遍历改成"树里有就用旧子节点"的变异能被第 4 个测出来。引擎的两套单测完整跑过：`common_cpp_unittests` 245 个、`flutter_windows_unittests` 353 个，全过。导出表、Dart 快照哈希和官方一致。独立审查没有必须改的问题，建议的两个测试和"根不是 0 时直接返回"已采纳，日志去重没做（GUI 程序的 stderr 平时没人看）。

### 9.2 真机验证（一台 4K 屏的 Windows 11 笔记本，新界面 M2a 构建，只换 `flutter_windows.dll`）

| 引擎 | stderr | MSAA（FLUTTERVIEW 下的 IAccessible 树） | COM IUIAutomation |
|---|---|---|---|
| 0001+0002（原来的） | `rebuilt after failed update: 0 will not be in the tree…` | 空 | 0 个元素 |
| 0001+0002+0003 | `dropped semantics nodes unreachable from root 0: 28`，没有重建 | 完整：标题栏按钮、本机 ID 和密码区、连接框、最近列表都在 | 35 个元素 |

- 旧界面换上 0003 的 dll 以后，MSAA 树也完整。
- 没能在真机上验证弹层（B2）：投递到帮助按钮的点击之后没有新的丢节点日志，弹层多半没打开。这一类靠单测覆盖。

### 9.3 UI Automation 客户端的另一层限制

- 托管的 System.Windows.Automation（Windows PowerShell 5.1 和 PowerShell 7 都试了）在 0003 下仍然看不到 FLUTTERVIEW 的任何子节点，原样的、控制视图、内容视图都是 0；FLUTTERVIEW 在它那里只是一个 Win32 窗格。旧界面同样如此。
- 原生 COM 的 IUIAutomation（Inspect、讲述人走的是这条路）能看到：新起的实例上，第一次查询就拿到 35 个元素，再查也一样，先用 MSAA 查再用 COM 也一样。
- 前几次 COM 也是 0：那几次第一个查询这个窗口的都是托管 API，而且是在程序启动后十几秒内。之后在一个 COM 已经能看到树的实例上再跑托管 API，COM 没受影响。所以只能推断：窗口刚起来时被托管 API 先查了一次，会让 UIA 在这个窗口的整个生命期里都看不到树。这个推断只来自两次对照，没有查到 UIA 内部的依据。
- 引擎这一侧：`FLUTTER_ENGINE_USE_UIA` 没有定义，`WM_GETOBJECT` 的 UIA 请求一律返回 0，UIA 只能经由 MSAA 代理拿到树（`flutter_window.cc` 的 `OnGetObject`），IAccessibleEx 默认也关着。
- 对端到端脚本的要求：用 COM IUIAutomation，不要用 System.Windows.Automation 碰新界面的窗口。

### 9.4 `leapgate-uia.ps1` 改用 COM

- 命令行参数和各操作的输出格式都没变。内部改成用 C# 声明 COM 的 IUIAutomation：
  - 只声明用到的几个接口槽位，属性一律经 `GetCurrentPropertyValue` 取；
  - 动作走 Invoke、Toggle、Value 三个模式接口；
  - FLUTTERVIEW 用 `EnumChildWindows` 找，整个脚本不加载 System.Windows.Automation。
  
  C# 代码按 C# 5 写，Windows PowerShell 5.1 也能编。
- 名字里有换行的元素（例如"主页 / 主页"），`-Name` 现在既接受原文，也接受 Dump 打印出来的写法。
- 实测（同一台笔记本，新引擎）：
  - PowerShell 7 和 Windows PowerShell 5.1 下，Dump 都列出主页的 35 个元素，按钮带 `[Invoke]`。
  - Wait、Gone 两个方向都试了，找不到、超时时报错清楚。
  - Invoke"复制 ID"后，剪贴板里是本机 ID。
  - Focus 能把焦点放进连接框；Type 键入一个示例 ID 后，出现"连接到 …"；Keys、Click 都正常。
  - Toggle、SetValue 在主页上没有对应的控件，只验了报错的那一路（"has no TogglePattern / ValuePattern"）。

## 附录：探针代码和用法

探针记录框架发出的每份语义更新，再按 AXTree 的规则重放，找出每份更新里的孤儿。核心代码：

```dart
class _ProbeBinding extends AutomatedTestWidgetsFlutterBinding {
  @override
  ui.SemanticsUpdateBuilder createSemanticsUpdateBuilder() => _Spy();
}

/// Records what the framework sends; forwards everything to a real builder.
class _Spy extends Fake implements ui.SemanticsUpdateBuilder {
  _Spy() { updates.add(<int, List<int>>{}); }
  final ui.SemanticsUpdateBuilder _builder = ui.SemanticsUpdateBuilder();

  @override
  dynamic noSuchMethod(Invocation invocation) {
    if (invocation.memberName == #updateNode) {
      final a = invocation.namedArguments;
      updates.last[a[#id] as int] =
          (a[#childrenInTraversalOrder] as Int32List).toList();
      return Function.apply(_builder.updateNode, const [], a);
    }
    return super.noSuchMethod(invocation);
  }

  @override
  void updateCustomAction(
          {required int id, String? label, String? hint, int overrideId = -1}) =>
      _builder.updateCustomAction(id: id, label: label, hint: hint, overrideId: overrideId);

  @override
  ui.SemanticsUpdate build() => _builder.build();
}

final updates = <Map<int, List<int>>>[];
final tree = <int, List<int>>{};

/// Replays the updates the way ui::AXTree accepts them; returns the orphans
/// of each update (an update with any orphan is rejected as a whole).
List<List<int>> replay() {
  final out = <List<int>>[];
  for (final u in updates.where((u) => u.isNotEmpty)) {
    final next = {...tree, ...u};
    final seen = <int>{};
    void walk(int id) {
      if (seen.add(id)) next[id]?.forEach(walk);
    }
    if (next.containsKey(0)) walk(0);
    out.add([for (final id in u.keys) if (!seen.contains(id)) id]);
    tree..clear()..addAll({for (final id in seen) id: next[id]!});
  }
  updates.clear();
  return out;
}
```

用法：

1. `main()` 第一行写 `_ProbeBinding();`。
2. 测试里调 `tester.ensureSemantics()`。
3. 每进一个状态调一次 `replay()`，返回值里每份更新一个列表，列表非空就是这份更新会被整份拒收，里面是孤儿的 id。

`updateNode` 走 `noSuchMethod` 转发，探针因此不依赖它的参数表，3.44.9 和 3.47.9 都能编。

重放只用来找孤儿：被拒收的那份更新里能走到的部分照样记进 `tree`，不模拟 AXTree 整份作废，也不模拟补丁 0001 的重建。
